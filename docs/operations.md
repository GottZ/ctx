# Operations

## First run: ctx init

```bash
ctx init
```

The wizard is the documented first-run path and is idempotent — it reports every item and only changes what is missing:

1. **Config** — asks for base URL and API key, writes `~/.config/ctx/config` (mode 0600). The key is checked before it is written: a value that is not 64 lowercase hex characters is named by its counted deviation (`63 characters, expected 64`, `2 non-hex characters at positions 5, 17`) and asked again (a model key — `ctxm_…`, the credential of the `/v1` model API — is named as such: the server refuses it on every knowledge path), and a well-formed key is probed against `GET /api/whoami` — a `401` is asked again too, up to three attempts, and never written. Only when the server cannot be reached at all is the config written anyway, marked `key not verified`; the next step then names the unreachable host.
2. **Server** — reads `/health`. A `degraded` or `unhealthy` server is shown but accepted: an install whose [backend pool](#backends) is still empty answers `unhealthy` with HTTP 503 by design, and that is precisely the state the backend-pool step fixes.
3. **Key** — the authenticated probe again, on every run: a re-run over a hand-edited, rotated or revoked key reports `rejected (401 unauthorized)` and says whether to fix the config file or an exported `CTX_KEY`, instead of ending `ready`. The backend-pool step needs an accepted key and is skipped otherwise.
4. **Backend pool** — lists the pool and, when no enabled `_global` row serves the `synthesis` or `embed` role, asks for host, protocol, chat model, embedding model and an optional API key (for the `anthropic` protocol: the chat model's context window, a separate embedding host and protocol, and the key), then runs the same seed `ctx backends seed` runs (same server-admin gate, same full-trust posture, same sealed-secret handling — the key is read without echo and never lands in the row). Afterwards, and whenever it finds a pool already populated, it **probes** each serving row and names the dead ones. A key below server-admin is not an error here: the step says so, points at `ctx backends seed`, and init carries on — hooks and statusline do not need an admin key.
5. **Version** — compares the local build against the latest GitHub release. This is the only request init sends to a host other than your ctx server (`api.github.com`, without your key); `ctx init --no-update-check` or `CTX_NO_UPDATE_CHECK=1` (any non-empty value) skips it entirely — no request is made, the line shows the local version marked as skipped. Meant for offline and air-gapped installs.
6. **Hooks** — `SubagentStart` / `SubagentStop` in Claude Code's `settings.json` (`$CLAUDE_CONFIG_DIR/settings.json` when that variable is set).
7. **Statusline** — `ctx statusline` in the same file. Claude Code has one statusline, so installing ctx's replaces whatever is there: a statusline that is not ctx's is shown with its command and replaced only on an explicit `y` — the default keeps it.

Both steps rewrite `settings.json` as a whole (re-sorted, re-indented). Before a rewrite that changes an existing file, the wizard copies it to `settings.json.bak-<UTC timestamp>` in the same directory, with the original's permissions, and names the copy — `diff` against it shows exactly what init changed. Two rewrites in one run keep two copies (`…Z` and `…Z-2`); the first one is the file as it was before init. An unchanged file is not touched.

**Uninstall:** `ctx init --remove` reverses steps 6 and 7 without asking — it takes the `ctx brief` / `ctx persist` hook commands out of `SubagentStart` / `SubagentStop` (a matcher group that also holds foreign commands keeps them) and removes the statusline only when it is ctx's; a foreign one is named and kept. The rewrite leaves a `settings.json.bak-<UTC timestamp>` like any other, and a file without ctx entries is not touched. The client config from step 1 stays where it is: it holds your API key, so the command names the file and leaves deleting it to you.

## Claude Code integration (optional)

`ctx init` (steps 6 and 7 above) writes the hooks and the statusline for you; below is the same thing by hand.

**Statusline** — live block count, health, and rate limits:

```json
{ "statusLine": { "type": "command", "command": "ctx statusline" } }
```

**Slash commands** — add to `~/.claude/settings.json`:

```json
{
  "customSlashCommands": [
    { "name": "ctx",        "command": "ctx query \"$PROMPT\"" },
    { "name": "ctx-save",   "command": "ctx save $PROMPT" },
    { "name": "ctx-browse", "command": "ctx search $PROMPT" },
    { "name": "ctx-stats",  "command": "ctx stats" }
  ]
}
```

**Agent hooks** — automatic project briefing for subagents:

```json
{
  "hooks": {
    "SubagentStart": [{ "hooks": [{ "type": "command", "command": "ctx brief --hook" }] }],
    "SubagentStop":  [{ "hooks": [{ "type": "command", "command": "ctx persist --hook" }] }]
  }
}
```

## Environment variables

Every var below can also carry a runtime override in `context_settings` (precedence: **DB override > env > default**; sealed `context_secrets` + trigger-fed audit trail in `context_settings_audit`, migration 051). The boot loads the overrides right after the migrations and builds the effective snapshot; sensitive keys take a `secret_ref` (the *name* of a sealed secret), resolved in-memory only. The override layer is never fatal: unknown keys, restart-only/coupled keys (incl. the `CONTEXT_DB_*` group), corrupt values and a missing or wrong master key each degrade to a WARN while the env/default value stays active; `CTX_SETTINGS_DISABLE=1` switches the whole layer off. Live editing goes through the admin-gated [Settings API](api.md#settings-api); direct SQL edits (and break-glass resets) take effect immediately (the 051 triggers NOTIFY a listener that rebuilds the snapshot).

The **`mut` column** is the mutability class per key: **hot** keys take effect without a restart (snapshot consumers pick them up on the next request/cycle); **restart** keys are process wiring (DB connection, listener, worker-goroutine count — runtime writes rejected with 409). The two **coupled** classes — a write that flushes `context_embed_cache`, and an embed-model write that would move the vector space and is therefore refused — have no members left since the tuple retirement: no settings key addresses an embedding endpoint any more, so no settings write can move the vector space. That obligation lives entirely on the pool now: a `base_url`/`protocol` edit on a serving-eligible embed-role row — or a disable-profile change that hands embed serving to a different host — flushes `context_embed_cache` via the NOTIFY listener (model-only edits do not flush; the cache keys on the model already). Edits made while ctx is stopped emit no notification and are caught at the next boot instead, against a persisted fingerprint ([migration 132](#migration-132-the-embed-cache-coupled-fingerprint--and-the-one-time-cleanup-it-does-not-do-for-you)).

**Retired: the backend tuple env vars.** The `CTX_{CHAT,CHAT_FALLBACK,EMBED,DREAM,DREAM_EMBED,RERANK}_*` connection tuples are gone as of **v5.0.0**. Nothing reads them: the config registry no longer knows their 29 settings keys, so a value in `.env` reaches no field, feeds no seed and appears in no boot dump; the keys themselves answer `404` like any unknown key — no tombstone status, no hint in the response, so the upgrade path is this document and nothing on the wire. The living configuration is the **backend pool** (`ctx backends`, web `/settings/backends`), and [migration 133](#migration-133-the-backend-tuple-rows-are-deleted--and-the-upgrade-hop-that-has-to-come-first) deletes leftover `context_settings` rows on the 29 keys in every scope. The status channel-probe, their last runtime reader, has taken its model from the serving chain (the highest-priority enabled, not profile-disabled `embed` backend) since v4.38 and reports `channel_probe.state = "no embed backend"` when no such backend exists.

The 29 names, to grep an inherited `.env` against — `CTX_CHAT_{HOST,API_KEY,PROTOCOL,MODEL,NUM_CTX,THINK}`, `CTX_CHAT_FALLBACK_{HOST,API_KEY,PROTOCOL,TIMEOUT}`, `CTX_EMBED_{HOST,API_KEY,PROTOCOL,MODEL,NUM_CTX}`, `CTX_DREAM_{HOST,API_KEY,PROTOCOL,MODEL,NUM_CTX,THINK}`, `CTX_DREAM_EMBED_{HOST,API_KEY,PROTOCOL,MODEL,NUM_CTX}`, `CTX_RERANK_{HOST,API_KEY,MODEL}`. Note what is *not* on it: `CTX_DREAM_ENABLED`, `CTX_DREAM_PARALLELISM`, `CTX_RERANK_ENABLED` / `_MAX_DOCS` / `_BLEND_WEIGHT` and every other `CTX_DREAM_*` knob are live keys and stay in the table below. The retirement is the connection tuples only, not the prefixes they share.

**The boot names what is left of them.** A tuple env var that is still set to a non-empty value produces one WARN naming the variable (`deprecation=retired_env`); a leftover settings row produces one WARN naming the key and scope (`deprecation=retired_settings_row`). Neither is fatal, and neither ever prints a value — six of the names are `_API_KEY` vars and a boot log travels into aggregators and support bundles. Both are the built-in progress signal of the cleanup order below: expected while the old configuration is still in place, silent once it is gone. The second retirement vintage ([Migration 152](#migration-152-the-rows-of-the-keys-that-had-no-successor-are-deleted): `distill.local_only`, `root_map.label_budget`) runs the identical two-part signal under its own labels, `deprecation=retired_env_v2` and `deprecation=retired_settings_row_v2` — same never-fatal, name-only shape, minus the v5.0.0-release and backend-pool references that would be false for a key retired without a successor. The third ([Migration 153](#migration-153-the-rows-of-the-keys-whose-subject-is-gone-are-deleted): the distiller's three foreign-source keys) does the same again under `deprecation=retired_env_v3` and `deprecation=retired_settings_row_v3` — every vintage keeps its own marker pair rather than reusing an older one, so counting lines answers for one upgrade instead of summing two windows.

**What the env tripwire does and does not reach.** It warns about *values*, not declarations: a variable declared but empty — `${CTX_CHAT_HOST:-}`, which is what an unmodified v4 compose file produces for all 29 — counts as unset, exactly as the loader has always counted it. It sweeps only the seventeen **value-bearing** names (the six `_HOST`, six `_API_KEY` and five `_MODEL` vars); the twelve remaining ones carry no topology and their compose scaffold defaults are hard-wired non-empty, so warning about them would fire on every untouched v4 install without naming a single lost setting. Two of those seventeen did ship a non-empty compose default and would therefore have slipped through the value filter on every untouched install, so their scaffold *values* are exempt by name: `CTX_RERANK_HOST=http://ctx-rerank:8082` and `CTX_RERANK_MODEL=bge-reranker-v2-m3` stay silent, any other value on those two vars warns. And the reach is split in two by your compose file: this release's `docker-compose.yml` declares none of the 29, so on a deployment that took the new compose file with the release the `.env` lines never reach the container at all — inert, and nothing to warn about. On a deployment still running its own older compose file (a foreign copy does not travel with a release), and on every non-compose form — bare binary, systemd unit, k8s manifest — the variables do arrive and the WARN fires. **Silence from the tripwire on an un-updated compose file means "clean"; silence on an updated one means "unreachable".** The authority in both cases is `ctx backends list`.

**Order of operations.** Topology into the pool FIRST ([`ctx backends seed`](#backends) / [`ctx init`](#first-run-ctx-init), verify with `ctx backends list`), and drop the env vars — together with their compose `environment:` declarations — only AFTER the upgrade is verified, because until then they are what a rollback to v4.x reads. Coming from a v4 release, do not skip straight to v5: the [upgrade hop](#migration-133-the-backend-tuple-rows-are-deleted--and-the-upgrade-hop-that-has-to-come-first) is mandatory. The template ships pre-retired: `.env.example` carries no tuple assignments at all, so a fresh `cp .env.example .env` starts on the pool path.

**Retired: the three env vars of the distiller's foreign source.** `CTX_DISTILL_SOURCE_PATH`, `CTX_DISTILL_SOURCE_LABEL` and `CTX_DISTILL_SESSION_QUIET_FOR` are gone as of **v5.17.0** — the third retirement vintage. What ended here is not a value but its **subject**: all three configured the distiller's reader over a foreign agent runtime's read-only state database — which file to open, what to call it in the run journal, how long its sessions had to be quiet — and that reader fell whole with the release, so there is no source left for a successor key to point at. The arm itself keeps running, on the compaction checkpoints of this store's own corpus. An env var still set to a non-empty value produces one WARN naming the variable (`deprecation=retired_env_v3`); a leftover settings row produces one WARN naming the key and scope (`deprecation=retired_settings_row_v3`). Neither is fatal, and neither prints a value. Unlike the tuple vars above, these three carry **no scaffold exemption**: no release ever shipped them with a non-empty compose default, so a value that reaches the sweep is one somebody wrote. [Migration 153](#migration-153-the-rows-of-the-keys-whose-subject-is-gone-are-deleted) deletes the leftover `context_settings` rows on the three keys in every scope, and that section is also where the reason stands why `distill.ctx_source_label` and `distill.ctx_quiet_for` are **not** the place to move an old value to.

An answer cut before its *first* complete object stays an ordinary decode failure and does feed the breaker, as does a call whose insights the evidence gate all rejected. `_BLOCK_TYPE` names the block type the insights are written under; it is trimmed and lower-cased and then has to name a **compiled** block type that neither takes part in the dedup guard nor is `full-pass` retrieval, and it may be retrieval-`excluded` only if it is one of the derived layer's own types (`insight`, `catalog`) — every other value, an unknown name and the empty string included, is a **422**: an unknown type falls through to the default type (`full-pass` knowledge) at write time, a guarding type would archive the very originals it quotes, and an excluded foreign type would write blocks no query can ever return. Finally, `_BLOCK_SENSITIVITY` may **not** be lowered while `_CTX_ENABLED` is on — lowering it below `credentials` is an act before switching the source on, never a knob during operation. **What the write actually produces (A02-9):** one block per run, upserted again after **every** batch so the insights are durable before the watermark that claims their range — identity `(_CATEGORY, "Destillat aus Compaction <root> ab <watermark_from>[ — Teil <n>]", scope)`, so two batches of a run grow one block and two runs over different ranges write two. The `— Teil <n>` half appears from the **second** block of one range onward; a range with one block carries the same title as before the shard layout, so no existing block is renamed. The arm opens the first block of the range that still has room — the highest existing one, or its successor when that one is already full — and **hands over** to the next shard as soon as the one it is writing fills up, so a full block is no longer a standing state. `_MAX_BLOCK_RUNES` caps ONE block on insight boundaries, drops the **youngest** insights (so the published prefix stays stable) and the block states in its own text how many it left out and in which direction — and those insights open the next shard instead of being discarded with the run. What stays irreducible is the **first-call boundary**: an insight whose very first call already exceeds the cap has no shard it fits into, so a cap far below the yield of one call still loses material (measured: cap 2400 keeps 12 of 15 claims; the default of 6000 keeps all). It is therefore a **retrieval size**, not a ceiling on the layer; the cost ceiling is the spend guard, which counts GPU seconds. What bounds the CHAIN is `_MAX_BLOCKS_PER_ROOT`, and its default `0` means **no cap**, never "no blocks" — the same reading `_SPEND_MAX_CALLS` gives its own zero. It is a not-aus for the operator rather than a steering knob: at the 6-9 shards a materially rich range is expected to need, a cap is meant never to bind, so a value far above that (64 rather than 10) is the honest setting. What it bounds is **one range** — one `watermark_from` — and that is deliberate: a cap over all ranges of a root would silence that root for good once its watermark had moved often enough, while a per-range cap ends the current chain and lets the next range start its own. **No material is lost either way, and the two shapes of that are worth telling apart.** Where the batch that filled the last allowed shard was itself fully covered, the watermark moves on and the remainder starts a new range (measured on a 12-chunk fixture at three cuts: cap 2, 3 and 4 each write two ranges and hold all 12 insights for the same four calls the uncapped run needs). Where the cap binds **inside** a batch, there is no next range: the chunks whose insights found no shard are left out of the dedup ledger, the watermark does not advance over them, and the range **waits** — every further tick then re-reads it, makes no call and answers `partial` with `budget` until the cap is raised, at which point the range picks the held-back material up again. A held range is stopped, and it is cheap **as long as `_MAX_BLOCK_RUNES` carries at least one insight**: the rune meter then refuses the next call before it is paid for, so a holding tick spends no GPU second and writes no block. Below that threshold — a cap under the yield of a single first call — the arm re-reads and re-buys the same batch on every tick (measured: 20 ticks, 20 calls, no claim, at 1 800 runes), which is the irreducible first-call boundary named above and not a property of the shard cap: the uncapped run pays the same rate on that material. The backstop there is the spend guard, which counts GPU seconds. A not-aus that binds is meant to be noticed either way. **Chain length has a second, unconditional bound of 256** that applies to reading a range, walking its title chain and WRITING it — the arm never grows a chain it would then refuse to open — and `_MAX_BLOCKS_PER_ROOT` is its key: a cap above 256 raises all three at once, so a range that legitimately needs a longer chain is a settings change rather than a deletion. Above that stands a form limit of 9 999, the largest ordinal a shard title can carry at all. A cap strike hands over instead of ending the run, and only a shard that filled up **without a single call**, one the cap forbids a successor to, or one whose successor could not place a single insight, ends it with `skipped/budget` — that state means the cap is below the demand of one insight, and no further shard would change it. **That threshold is two numbers, not one:** a shard above the first carries the title suffix and the chain line naming its predecessor (~133 runes together), so its floor sits that much above shard 1's, and in the band between the two floors shard 1 still takes an insight while none of its successors can. The arm **rests** in that band — it refuses the hand-over, holds the material back and repeats `partial/budget` on every tick (measured at `_MAX_BLOCK_RUNES` 1 900: one hand-over, then no further block; raising the key releases the range and it covers its material) — rather than writing one empty shard per tick up to the chain bound of 256, which is what it did before that refusal existed and which no later run removes. A braked run keeps its yield: the block is seeded from itself at run start, so a follow-up run over the same `watermark_from` **adds** to the block instead of replacing it, and a body the arm cannot read back is refused (`failed/block_write_failed`) rather than overwritten. The per-batch rewrite costs **no** embedding work today because `insight` is retrieval-`excluded` and the embed backfill skips such blocks entirely; flipping that type to visible turns the same cadence into up to one re-embed per batch, which is a figure to budget before the flip, not after. Operationally visible: `blocks_written` on the run row counts durable writes (one per batch, not one per insight), and a refused write ends the run `failed/block_write_failed` **without** marking the batch seen — the material stays readable, the calls already paid for are still booked, and the next tick re-reads it. **Compose surface.** An env var only reaches the container if the `docker-compose.yml` `environment:` block declares it — setting an undeclared one in `.env` alone does nothing. The gap that sentence used to describe (95 of 218 registry names declared, 123 unreachable) is closed by construction: the `ctx` service block declares **every** env-fed registry name — 216 today (`config.EnvVars()`) — plus all seventeen env-only names that live outside the registry (`config.EnvOnlyServerNames()`, read raw): both `CTX_SECRETS_KEY*`, both `CTX_BOOTSTRAP_*`, the three `CTX_CAMO_*`, `CTX_SETTINGS_DISABLE`, and the nine OAuth/proxy names — `CTX_CANONICAL_ISSUER`, `CTX_OAUTH_REDIRECT_EXTRA`, `CTX_OAUTH_ACCESS_TTL`, `CTX_OAUTH_REFRESH_TTL`, `CTX_OAUTH_FAMILY_CAP`, `CTX_OAUTH_DCR_MODE`, `CTX_OAUTH_MAX_CLIENTS`, `CTX_OAUTH_REGISTER_RATE`, `CTX_TRUSTED_PROXY` — for 233 declarations in total. The declared form is `NAME: ${NAME:-}`, which sets the variable **empty**, and empty is "not set" to every reader in the tree: `config.FromEnv` maps an empty value to absent, and so do the only two direct readers of a registry name, `overview.WorkerMemLimitBytes` and `schemacontract.ResolveMode`. The default therefore still comes from the registry and never from this file. Three tests hold both halves — `TestComposeDeclaresEveryRegistryKey` and its env-only sibling `TestComposeDeclaresEveryEnvOnlyServerName` (every name of both classes is declared) and `TestComposeCopiesNoRegistryDefault` (no declared line repeats a registry default) — and a fourth, `TestComposeDeclaresNoRetiredVar`, keeps retired names out. The block is generated, so a new registry key reaches the container by regenerating it; the first two tests are what say the regeneration was not skipped for either class.

**Behind a reverse proxy.** The per-IP rate limits of `/auth/login`, the SSO routes and `/register` key on the direct peer; `X-Forwarded-For` counts only when that peer equals `CTX_TRUSTED_PROXY` (the proxy's IP as ctxd sees it, e.g. `CTX_TRUSTED_PROXY=172.18.0.2`). Left empty behind a proxy, every client shares the proxy's bucket and 30 login attempts a minute lock everyone out; ctxd logs one value-free warning per process the first time such a request arrives with `X-Forwarded-For`, and never trusts the header without the variable. **For the model API (`/v1`, `/v2`) the variable is a release prerequisite, not a recommendation:** the model-key door refuses every request that arrives with `X-Forwarded-For` while `CTX_TRUSTED_PROXY` is empty — `503 proxy_misconfigured`, `x-should-retry: false`, one ERROR line per process — because without it the client address is unknowable: network allowlists of model consumers would check the proxy's address, and the failure lock would merge all clients. Set it before `gateway.enabled` goes on. The value is the proxy's plain address; a port (`172.18.0.2:443`) or IPv6 brackets (`[2001:db8::10]`) are accepted and stripped, a host name, a CIDR or a URL is not an address — such a value is logged as an ERROR when the door is built and treated as unset, so requests through the proxy answer `503 proxy_misconfigured` instead of silently taking the proxy for the client. With it set, the door also reads the proxy's `X-Forwarded-Proto` (rightmost entry, only from that peer) as the TLS evidence for model consumers without `allow_plaintext`.

**Pinning a value.** Two levers, and a literal in the compose block is neither: set the var in `.env` (it flows through the declaration and shows as `env` in the boot dump), or set a `context_settings` override under the key's **settings key** (`recall_check.interval`, `graph_cache.enabled`, `retrieval.selector.enabled`, … — the registry's key names, which are what the [Settings API](api.md#settings-api) and the boot dump speak). A value written into the compose block instead would be a second source of truth for that default: it survives a registry change silently and then feeds the container a number the code no longer believes in — which is why the second gate refuses it. The authority for what actually arrived stays the boot dump, where a var that never arrived shows `"default"` as its source. Being declared changes reachability, not posture: the groups that were unreachable until now — the 35 `CTX_DISTILL_*` above all — are settings-first by design and are still meant to be driven through the Settings API rather than a redeploy.

**The lines that do carry a value.** Four of them, and each is a deployment decision rather than a default: `CTX_RERANK_BLEND_WEIGHT` `0.5` (registry `1.0`), `CTX_GRAPH_EXPAND_ENABLED` `true` (registry `false`), `CTX_GRAPH_OVERVIEW_ENGINE` `ctx` (registry `gonum`) and `CTX_READ_SCOPES` `private,shared` (registry `private,shared,work`). The first two are a **pair**: V3 warns when `rerank.blend_weight` is `1.0` while `graph.enabled` is true, so a deployment that turns graph expansion on has to pull the blend weight off `1.0` — changing one without the other re-arms that warning. The five `CONTEXT_DB*` and `LISTEN_ADDR` lines carry container wiring (credentials from `.env`, the `db` service name, the fixed port, the listener) and not a registry default; neither gate judges them. Both sets are listed by name in the test, so a fifth decision cannot appear undocumented and an existing one cannot quietly be aligned with the default — both go red.

**First deploy after this change.** The block grew from 105 to 227 declarations, so the compose config hash changed and `docker compose up -d --no-build` **recreates** the `ctx` container rather than leaving it running. Pick a window outside a running `distill_run` or dream tick: an in-flight cycle is cut, which is non-fatal (the block's cooldown and score for that cycle are simply not written and it is re-picked) but costs the cycle. Nothing else moves — `ctx settings list` renders the same effective value for every key before and after, because an empty variable and an absent one are the same input to the loader.

**First run on a fresh DB.** The bootstrap pair above is the ops answer to the henhouse-egg gap (no key exists yet to create the first key). Order: set `CTX_BOOTSTRAP_ADMIN_KEY` in `.env` (`openssl rand -hex 32`; the compose `environment:` block declares it — the compose-surface rule above applies) → boot → create the real keys with it (`ctx keys create <label> --home <scope>`, see [cli](cli.md)) → remove the bootstrap key from `.env`. On any later boot with a populated `context_api_keys` it is a no-op anyway (fail-closed), but a plaintext admin credential has no business staying in `.env`. With the first real key in hand, point the CLI at the server and finish the first run there: `ctx init` (or `ctx backends seed`) gives the fresh install its [backend pool](#backends) — until it serves a `synthesis` and an `embed` backend, `/health` answers `unhealthy` with HTTP 503 and queries fail on the embedding step. The **container** healthcheck (`/ctx -health`) stays green through that window: it judges serving, not greenness — see below.

**Container healthcheck semantics (`/ctx -health`).** The compose healthcheck runs the image's own probe; it fails on exactly three states — the local server does not answer, its answer is not a health document, or `services.database` in that document is not `ok`. Everything else counts as serving, the fresh install's `unhealthy`/503 on an unseeded pool included. That is deliberate: a fresh install is un-seeded until an operator seeds it, and a container that reported `unhealthy` for a state only an operator can leave would make every `depends_on: condition: service_healthy` and every load-balancer readiness gate block the very window in which the seed has to happen — where the LB gates API access, it would block the seed itself. The health *endpoint* keeps its full verdict (`ok` / `degraded` / `unhealthy`); use `/health` or `ctx status`, not the container's health flag, to see whether the backends serve. The semantics live in the binary, so pulling the image is enough — no compose file needs editing.

**Three default-off gates.** `retrieval.selector.enabled`, `graph_cache.serve_ego` and `graph_cache.serve_expand` ship **false** on purpose, and so does `graph_cache.enabled`. Each guards a built, tested engine that is deliberately dark until its evidence lands — the selector until the `recall_check` measurements exist to justify a dispatch threshold, the two serve flags until the graph-cache bench (E-05-1). Flipping them is an operational settings change, not a deploy, and every one of them is `hot` and **global-only**: they dimension process-shared resources (one CSR snapshot, one HNSW index, one buffer pool), so a per-tenant override would touch nothing tenant-private and could only mis-tune the shared thing. None of the three groups carries strict parsing — a malformed value logs a WARN and keeps the protective default instead of aborting the boot, the right degradation for an operational knob (unlike the security-ceiling caps, which do abort).

## Boot-time validation & config dump

`ctxd` parses all `CTX_*`/`CONTEXT_*` env vars through a typed registry (`internal/config`) and logs one `config: effective` record at startup: every setting with its origin (`settings` for a DB override, `env`, or `default`), secrets masked per class — presence-only for the DB password, and a short sha256 fingerprint for the fingerprint class, so key rotation stays provable from logs without leaking the value. Since the tuple retirement no registered key is in that fingerprint class any more: the `api_key`s it was built for are `api_key_ref` columns on backend pool rows now, and nothing about them reaches this dump.

Invalid configurations abort the boot **after logging every finding** with field + reason. Beyond the long-standing fatal parses (malformed ints, unknown timezone, missing DB password), these previously-booting-but-broken-at-runtime states are startup errors: `CTX_SCORE_THRESHOLD` above `CTX_CONFIDENT_THRESHOLD`, and out-of-range knobs (`_BLEND_WEIGHT` outside [0,1], negative rate limits, negative timeouts and window sizes). The checks that guarded backend *topology* in env — unknown protocol values, malformed host URLs, embedded `user:pass@` credentials, cross-host credential inheritance in the dream-embed fallback chain — went with the tuple keys they read; their protection did not. It moved to the pool write path, where a `base_url` carrying userinfo is rejected with `422` before the row is stored (see [api](api.md#backend-pool)), which is the surface that actually configures a backend now. A malformed `CTX_DREAM_LANGUAGE` is fatal (V14) rather than tolerant — the value is interpolated into an LLM system prompt, so an unconstrained string would be a prompt-injection surface on an unattended background pipeline. An unknown `CTX_DREAM_JSON_MODE` is fatal for the mirror-image reason (V20): the tolerant reading would be the default, `strict`, so a typo would silently keep the very wire setting the operator was trying to turn off. Malformed values on tolerant knobs keep their defaults but now log a WARN instead of failing silently.

**Duration keys are range-checked as a class (V17).** "Negative timeouts" above is not a hand-wave at a few checked knobs: **every** seconds-typed key — all 37 of them, i.e. everything the settings API types as `seconds` — is walked generically and a negative value is a **boot abort / `422` on the settings write**. The reason is diagnosability, not tidiness: every consumer of a duration reads a non-positive value as *unset* and substitutes its own default, so a `-30` would run the default while `GET /api/settings` renders `-30s` — a key that looks configured, is not, and says nothing about it. What `0` means is deliberately **not** part of this check and stays per key (`dream.temporal_timeout` / `dream.cycle_timeout`: the package default; `status.channel_probe_interval`: off; the embed back-off bases: retry immediately). The class is **typed**, not universal: a key that is not a duration is not walked. Counts have their own walk now (V35, below); the float multiplier `CTX_DREAM_EVAL_CAP_RETRY_FACTOR` still carries its own sign check (V19), because the remaining float keys are thresholds in `[0,1]` with range checks of their own. The two keys that had their own sign check before, `CTX_DREAM_TEMPORAL_TIMEOUT` (V16) and `CTX_DREAM_CYCLE_TIMEOUT` (V16c), were folded into V17 and report exactly once; their key-specific budget and floor WARNs (V16b, V16c) are untouched. One class more sits a layer earlier, in the parser: a seconds value beyond **±9223372036** (`math.MaxInt64` nanoseconds) cannot be represented as a duration at all and is rejected on parse — it must be, because the wrap lands on a plausible small value (`9223372036855` would render as `224.192ms`) that no range check downstream could distinguish from a real setting. That rejection follows the key's `parse` tag like any other malformed value: fatal for the four strict `CTX_DISPATCH_*` keys, WARN + registry default for the rest, and never applied when it arrives as a settings row.

**Count keys are range-checked as a class too (V35), and this one is an upgrade note.** The same statement now covers **every** `int`-typed key — all 90 of them, i.e. everything the settings API types as a count — walked generically after every other pass: **negative values on `int` keys abort the boot**, and an existing negative `context_settings` row is **dropped with a WARN while the registry default is served**. Before this, 62 of the 90 counts had no sign check at all (`CTX_RECALL_CHECK_LEG_TIMEOUT_MS`, `CTX_RECALL_CHECK_PARK_MAX_MS`, `CTX_LLMLOG_RETENTION_DAYS` among them): `-1` parsed, was stored, and rendered as a configured number in `GET /api/settings` while the consumer read it as unset and served its own default. A `PUT /api/settings/<count key>` with a negative value now answers `422` where it used to answer `200`. **Before upgrading**, grep `.env` and the compose `environment:` block for `CTX_*: -<n>` and check `context_settings` for negative rows on count keys — a negative env value stops the boot, a negative row changes the *effective* value silently (the WARN in the boot log is the only signal). What `0` means stays per key and is deliberately not part of the walk, exactly as with V17: `distill.spend_max_calls` `0` is the documented kill switch, `dream.num_predict` `0` the package-default sentinel, `pool.blob_stage_max_bytes` `0` "no staging". Three keys keep a **WARN** instead of the abort, because a normalizing pass repairs the value before the walk sees it and surface and consumer therefore agree again: `CTX_DREAM_BACKOFF_GRACE`, `CTX_DREAM_BACKOFF_INERT_OFFSET` (reset to their defaults, V6) and `CTX_DREAM_PARALLELISM` (clamped to 1, V10). Sixteen hand-written sign checks were folded into the walk rather than exempted from it — the V17 argument, one type over: an allowlist of "keys with their own sign check" has to be maintained in lockstep with every future per-key check, and forgetting it double-reports the same field. The three checks that guard a **floor** rather than a sign kept theirs and gave up only the negative half (`graph.hop_depth` ≥ 1, the seven `distill.*` sizing keys ≥ 1, `distill.concurrency` in `[1, 16]`), so `0` still fails with its own key-specific reason.

**Settings-only keys are validated by the same pass** even though no env var reaches them (`env:"-"`, DB override or registry default only). The newest of them is `pool.blob_stage_max_bytes` (tenant-overridable, default `1048576`): the largest decoded payload a `confirm_writes` key may have **staged** on the MCP `blob_store` tool, held server-side in `context_pending_writes` until the write is confirmed or its `writes.confirm_ttl` runs out. A payload above it is refused by name — never written direct, which would hand exactly that key the bypass its flag exists to close. `0` here does **not** mean unlimited: it disables blob staging entirely, so such a key cannot store blobs at all. That is why a negative value is a boot abort / `422` on the settings write rather than a WARN — `0` is already the switch, so anything below it would render as a configured byte count while the runtime read it as one. (The key carried its own check, V9d, until the count walk V35 absorbed it; the refusal and its reason are unchanged, only the message is now the generic one.) Its sibling `pool.blob_rate_limit_write` keeps its own reading of `0` (fall back to the *value* of `query.rate_limit_write`); the two are deliberately not unified, because one bounds a counter and the other a buffer. Both are documented with the surfaces they gate in [api](api.md#endpoints).

Its younger sibling `pool.blob_scan_max_bytes` (tenant-overridable, default `16777216`) bounds a different cost on the same write path: how much of a **decoded** payload the credentials detector reads before the upsert. The block path needs no such key — a block is capped at 50 KB and its scan is free — while a blob is capped at 50 MB and the scan is regex work over every byte of it, synchronously, before the write returns. A payload above the cap, or one that is not valid UTF-8, is **stored anyway**, carrying `metadata.sensitivity = "unscanned"`. That is deliberately not fail-closed: the live corpus is binary uploads and blobs that predate any Go write path, and a scanner that refused them — or called them credentials — would be an outage rather than a net. The unscanned state is written into the row rather than left implicit, so the limit is visible where the data is instead of inferred from an absent field. `0` here means the scan is OFF (everything stored `unscanned`) — unlike `pool.blob_stage_max_bytes`, where `0` is the fail-closed reading, there is no payload size at which "scan nothing" protects anything. A negative value is a boot abort / `422` on the settings write for the same reason its sibling gives: `0` is already the switch, so anything below it would render as a configured byte count while the runtime read it as off. (Its own check, V9e, was folded into V35 with the other fifteen; the refusal stands, the message is the generic one.) Raising the cap costs write latency on large payloads; lowering it moves payloads into the `unscanned` state, where `blob_fetch` will deliver them.

## `tenant.devmode`: developer transparency in one tenant

`tenant.devmode` is the umbrella flag a tenant working **on** ctx turns on to see its own machinery instead of the production-hardened summary of it. It is a `bool`, `hot`, **tenant-overridable**, defaults to **false**, and carries **no env var** on purpose: it lowers a privacy default, so the only way to raise it is a settings write, which leaves an audit row in `context_settings_audit`. An env would let the same change ride in on a compose edit that no audit can reconstruct.

**Every consumer of devmode is listed here.** The list is the point of the flag being an umbrella rather than one switch per surface; a wave that adds a consumer adds it to this list, to the `TenantConfig.Devmode` comment, and to nothing else.

| Consumer | `false` (default) | `true` |
| --- | --- | --- |
| llmlog body sealing (E4/8b) | A `credentials`-class LLM call keeps its telemetry and `block_ids` — the egress trace stays ID-exact — but its prompt/reply bodies are dropped at **write** time (`llmlog.Entry.Slimmed`): no plaintext shadow corpus of the hottest tier in `context_llm_log`. `GET /api/llmlog/{id}` renders `body_state: "sealed"`. | This tenant's `credentials`-class calls are stored **with** bodies; the detail endpoint renders `body_state: "present"` and the status page marks the card `credentials-class · unsealed by tenant devmode`, so the class is never mistaken for a harmless one. |

**Turning it on for exactly one tenant.** There is one settings API and it derives its target scope from the caller, never from the body ([api](api.md#settings-api)): a **server-admin** key writes `_global`, a **tenant-admin** key writes only its own tenant scope. So the per-tenant override is a PUT with that tenant's admin key:

```bash
curl -sS -X PUT https://<host>/api/settings/tenant.devmode \
  -H 'Authorization: Bearer <TENANT-ADMIN-KEY>' \
  -H 'Content-Type: application/json' \
  -d '{"value": true}'
```

The response echoes `previous` and the new effective value; the write is hot (a NOTIFY rebuilds that tenant's generation — no restart, no deploy). `DELETE` on the same path removes the override **in the caller's own scope** and restores sealing there — a `_global` row, if one exists, survives a tenant-admin DELETE and keeps applying. The same PUT with a **server-admin** key lands at `_global` instead and means something much larger: the operator has decided against E4 for **every** tenant on this server, present and future — a tenant created later inherits it until that tenant's admin sets its own override. Both are legitimate; only one of them is per-tenant.

**What a tenant-scoped override actually reaches.** The interactive query path resolves the caller's tenant and follows the override. The dream stages resolve the scope they run under — and for the **default tenant** that background scope is `_global`, which the settings overlay skips by design. On the default tenant, therefore, only a `_global` write reaches the dream write sites; a tenant-scoped `true` unseals its interactive calls but not its background ones. A **named** tenant's dream stages run under that tenant's scope and follow its override. Separately, dream rows carry no `api_key_id` and are visible to the **server-admin only** whatever devmode says — the flag decides what is stored for them, not who may read them. On a single-tenant server whose operator is the server-admin, the `_global` write is consequently the one that delivers full transparency, not the accidental one.

**The switch is not retroactive in either direction.** Turning it on creates no bodies for calls that already happened — their columns hold empty strings and stay that way, which is why an old row keeps reading `sealed`. Turning it off removes nothing already written: those bodies live out their `scheduler.llmlog_retention_days` like every other body and are then NULLed by the retention janitor. **Retention is untouched by this key** — an unsealed `credentials` body is evicted on exactly the same horizon as an `internal` one.

**It does not widen the tenant boundary.** The llmlog read gate is attribution-based (`api_key_id = ANY(<the tenant's keys>)`, uniform `404` otherwise) and `tenant.devmode` appears nowhere in that query. A tenant that switches it on gains its own bodies and cannot reach a neighbour's row; background rows carry no `api_key_id` and stay server-admin-only either way. That is also why this key is tenant-overridable while its two `tenant.allow_*` siblings are not: those **grant reach outside** the tenant and must stay operator-set, whereas devmode only decides how much of its own machinery a tenant sees.

`GET /api/llmlog/{id}` reports `body_state` from the **row**, not from the sensitivity class, so an unsealed row renders as what it is. `required_sensitivity` stays on the card in every state.

## `federation.max_depth` and the model-API ingress assert

**`federation.max_depth`** (settings-only, `int`, default **3**, `hot`, global-only, parse-strict): the longest incoming `Ctx-Hop` chain this instance serves. A request whose chain already holds that many entries is refused with `508 federation_depth` (`Ctx-Reason: depth`) on every authenticated group with model egress (`/api`, `/mcp`, and `/v1`, `/v2` once mounted) — this instance would be hop *n + 1*. The value is read per request, so a write applies to the next one:

```bash
curl -sS -X PUT https://<host>/api/settings/federation.max_depth \
  -H "Authorization: Bearer $CTX_KEY" -H 'Content-Type: application/json' -d '{"value":4}'
```

Boot and write validation (V45): `1 ≤ max_depth ≤ 16` — `0` would refuse every request, and a value above the `Ctx-Hop` parse limit of 16 entries could never be reached (a longer chain is a `400` first). A settings write outside the range is a `422`; a row written by `psql` replaces the key's one row and is then dropped with a WARN, so the registry default `3` applies (not the value the row replaced). The boot record shows it as `federation: max_depth=3`. Raise it only for a deliberate chain of instances (B → A → C → …): every hop adds its latency and holds a request slot on each instance it passes.

**The ingress assert.** `gateway.enabled` turns the model API on, and the model API only exists with its federation loop guard in front of it ([security](security.md#federation-loop-guard-ingress)). A build whose router mounts no model group — every build up to the one that mounts `/v1` — therefore refuses the flag:

- `PUT /api/settings/gateway.enabled {"value":true}`, and a `DELETE` of a `false` override that would fall back to `CTX_GATEWAY_ENABLED=true`, answer `409` "the model API cannot be enabled before its federation ingress is mounted", and no row is written. Turning it off is always allowed.
- The boot refuses an effective `true` from either layer: `gateway: refusing to start` with `gateway.enabled is true (source: env|settings) but no model group with its federation LoopGuard is mounted …`, exit code 1. **Remedy** — the settings API is not reachable while the boot refuses, and an env value does not beat a settings row, so it depends on the source the message names: `env` ⇒ unset `CTX_GATEWAY_ENABLED` or set it to `false`; `settings` ⇒ remove the row with `psql` (`DELETE FROM context_settings WHERE key = 'gateway.enabled';`), or start once with `CTX_SETTINGS_DISABLE=1` (override layer off), `DELETE /api/settings/gateway.enabled`, and restart without the switch. Either way a build that mounts `/v1` boots with the flag on. A `psql` write of `true` is not refused at write time; this assert catches it at the next start.
- **Upgrade note.** Up to 5.31 `PUT /api/settings/gateway.enabled {"value":true}` was accepted (nothing was mounted, so it changed nothing). An install that stored that row does not boot after this release until the row is removed as above. Check before the upgrade: `SELECT scope, value FROM context_settings WHERE key = 'gateway.enabled';`.
- The same flag gates the model-consumer self-service (`gateway.tenant_self_service` takes effect only while `gateway.enabled` is on), so that stays closed too until a build mounts `/v1`.

## Write rejections in the server log

A write `POST /api/store` refuses after its body parsed leaves a `WARN` record `store: write rejected` — at most one per key, code and minute (see *Throttled* below); the request logger's `http request` line names method, path, status and `request_id`, but not the key, and `ctx persist --hook` is silent on the client by design. The record carries:

| Field | Value |
| --- | --- |
| `api_key_id` | the UUID of the key (`context_api_keys.id`) — never its hash or plaintext |
| `code`, `status` | the machine code and HTTP status the client was answered with (`rate_limit` 429, `reserved_category` / `provenance_protected` / `scope_denied` 403, `size_cap` 413, `missing_fields` 400, …; `internal` 500 too — its cause is on the `ERROR` line with the same `request_id`) |
| `request_id` | joins the record to the request logger's line |
| `category`, `scope` | the write's category and its scope **as requested** (`""` = the key's home scope), each capped at 100 runes |
| `suppressed` | refusals of the same key and code the throttle swallowed since that pair's previous line |

It never carries the title, the content, the metadata, the tags or the rejection's prose. An unauthenticated request (no key to name) and an unparsable body (no write to name; it keeps its own `store: invalid request body` line) get none.

**Throttled per key and code.** A key over its write budget is refused on every write of the window, and a refused write books no write row, so the write budget bounds no refusal — a looping client is refused as often as it asks. The first refusal of a `(api_key_id, code)` pair in a 60-second window — the window of the write rate limit — gets its line; the rest are counted. The count reaches the log on the pair's next line (`suppressed`), or, for a pair that stays quiet, on a `store: write rejections suppressed` record (`api_key_id`, `code`, `suppressed`) written by a sweep that runs at most once per window on the next refusal of any key. The counts live in the process: a restart drops what is pending. The window is a constant, not a setting: it bounds the server's own log volume.

```bash
docker compose logs ctx | grep '"store: write reject' | grep '"api_key_id":"<key-uuid>"'
```

## Backups & disaster recovery

`backup.sh` archives only the pg_dumps — the sealed-secret ciphertexts are in every dump, the master key (`CTX_SECRETS_KEY`) is in **none**, by design. Disaster recovery needs both the dump and the separately-stored master key. See [security](security.md#sealed-secrets--break-glass) for master-key setup, rotation and break-glass extraction.

### Site-local backup hooks: backup.d/

`backup.sh` dumps `context_store` and `n8n`, verifies every dump with `pg_restore --list`
and rotates by explicit file patterns (`context_store-*.dump`, `n8n-*.dump`, 7 days). Everything
deployment-specific — extra databases in the same Postgres instance, table-data exclusions,
a shorter retention — lives outside the tracked script: every `backup.d/*.sh` (gitignored,
sourced in name order after the core dumps) sees three helpers:

| Helper | Effect |
|---|---|
| `backup_dump LABEL USER PASSWORD DB [pg_dump-args…]` | dumps `DB` as `LABEL-<date>.dump`, registers it for the integrity check, counts a failure |
| `backup_rotate GLOB DAYS` | adds a rotation rule for the hook's own files (evaluated in the rotation step) |
| `backup_require_var NAME…` | `[FATAL]` exit when a variable is unset or empty |

A hook that fails counts as one error in the summary (exit 1) but does not abort the run.
`BACKUP_HOOKS_DIR` overrides the directory. Example hook:

```bash
# backup.d/10-graph.sh — extra database, embeddings excluded, 3-day retention
backup_dump graph "$POSTGRES_USER" "$POSTGRES_PASSWORD" graph --exclude-table-data=node_embedding
backup_rotate "graph-*.dump" 3
```

### LLM-log body export: ctx-llmlog-export

`ctx-llmlog-export` is a SELECT-only bulk export of `context_llm_log` as JSONL — one line per
row, 1:1 with the live schema (`to_jsonb`), meant to secure the prompt/response **bodies**
before a retention window (`CTX_LLMLOG_RETENTION_DAYS`, hot-mutable) ever NULLs them, and as
the raw source of a replay corpus. Because each line is `to_jsonb` of the row, a new column shows up
without a code change: since migration 158 every line additionally carries `"consumer_id"` (`null`
on every row until the OpenAI-compatible API writes it) — additive, existing keys are unchanged.

```bash
cd go && go build ./cmd/ctx-llmlog-export
set -a; . .env; set +a
CONTEXT_DB_HOST=<db> ./ctx-llmlog-export -out /secure/dir/llmlog-$(date +%F).jsonl \
  [-since <RFC3339> [-since-id <uuid>]] [-until <RFC3339>] [-pipeline a,b] \
  [-batch 5000] [-strict] [-summary <path>]
```

The config is validated in full before the first database contact: an error-severity issue from
`internal/config` — the cross-field rules included — is printed and ends the run with exit ≠ 0
before any pool is opened.

It reads the DSN from the same config source as `ctxd` (`CONTEXT_DB*`). The `-until` pin, every
page and the final `count(*)` gate run in their own short `READ ONLY` transaction (no write path
by construction; no hours-long snapshot pinning the database's xmin horizon on large tables). The
window is stable regardless: `-until` defaults to the database `now()` **minus one minute**
(commit margin — `created_at` is the insert's transaction start, the commit may land up to the
insert timeout later) and an explicit `-until` later than that is **clamped to the same margin**
(the summary's `until` is the effective bound — an open window would lose not-yet-committed rows
from every later delta), the table is append-only inside a closed window, and retention NULLs
bodies without deleting rows. Keyset pagination is `ORDER BY t.created_at, t.id` (input columns —
a bare `id` would bind to the `id::text` output column and sort by text collation); the cursor
carries a redundant `created_at >=` so the planner uses the hypertable's `created_at` index and
chunk exclusion.

The JSON summary on stderr (always printed, also on failure) carries `rows_total`, `rows_body`,
`rows_bodyless_slim` (credentials-class rows whose bodies were slimmed to `''`),
`rows_bodyless_null` (bodies NULLed by retention), `count_gate`, `bytes` (what was actually
flushed — valid even after a cancel), `watermark` + `watermark_id` (the last row). A delta run
continues **exactly** behind the previous run with `-since <watermark> -since-id <watermark_id>`;
`-since` alone is inclusive and re-exports every row sharing the watermark's `created_at`.

Containment is fail-closed and checked before any DB connection: the target directory (and the
`-summary` directory) must have no group/other bits (`0700` or stricter) and must not resolve
under `/tmp`, `/var/tmp` or `/dev/shm`; the file is created `O_EXCL` with mode `0600` only after
the connection is up (a config/DB failure leaves no empty file behind) and is never overwritten.
Exit codes: `0` clean · `1` perimeter, config, DB or I/O error (including a failed `fsync` of
the output or `-summary` write — this takes precedence over 2/3, because "file complete, keep it"
is only true once it is durably on disk) · `2` NULL bodies found — the
export still ran to completion first (rescue-first; `-strict` aborts at the first NULL instead)
· `3` count gate violated. The export contains unanonymized prompt bodies — keep it inside the
same trust boundary as the database itself.

### GPU-second cost report: ctx-armcost

`ctx-armcost` is a SELECT-only cost report over `context_llm_log`, grouped by `pipeline` and by
`dispatch_class`. **The currency is the GPU second, not the dollar.** `cost_usd` is set in a
handful of rows on an on-prem serving stack and is deliberately *not* carried as a metric — the
report prints one provenance line (`cost_usd: in k von n Zeilen gesetzt — nicht verwendet`) with
live-counted numbers and nothing else.

```bash
cd go && go build ./cmd/ctx-armcost
set -a; . .env; set +a
CONTEXT_DB_HOST=<db> ./ctx-armcost -out /secure/dir/armcost-$(date +%F).json \
  [-since <RFC3339>] [-until <RFC3339>] [-days 7] [-by-class=false] \
  [-arm cluster-label -per-topic]
```

The config is validated in full before the first database contact: an error-severity issue from
`internal/config` — the cross-field rules included — is printed and ends the run with exit ≠ 0
before any pool is opened.

Per group it reports `n`, the occupancy sum in seconds, `wire_s` (Σ `duration_ms`), p50/p95
duration, prompt/completion token sums with the count of rows where they are NULL, the error
count and rate, `dispatch_abort` rows, and the rows without a duration or without a queue wait.
Two numbers, not one, carry the cost: `belegung_s` follows the design formula
`(duration_ms - COALESCE(queue_wait_ms, 0)) / 1000`, while `wire_s` omits the subtraction.
They differ by exactly Σ `queue_wait_ms`, and the report says which of the two bounds the truth —
see the mandatory footnotes below.

The **non-disruption metric** is the gate every measurement campaign runs against: p95 of the
`interactive` class inside the window versus p95 of the equally long window immediately before it.
A factor above **1.5** means the campaign disturbed live traffic and its dump is discarded rather
than partially scored. The rule text is printed in every report, green or red.

Three footnotes are part of the output, not decoration — without them no number here is
interpretable: `llmlog.Record` writes asynchronously in its own goroutine, so a count from the same
table never sees in-flight calls and is systematically low; `nullInt` turns 0 into NULL on insert,
so token sums are patchy (the `(null)` columns count the affected rows); and, since MW10,
`duration_ms` on every path that sets `queue_wait_ms` already measures the wire call alone, so the
design formula subtracts the lease wait a second time — `belegung_s` is a lower bound, `wire_s` an
upper one.

**Per-topic view of one arm** (`-arm cluster-label -per-topic`, both flags or neither). It answers
the question the label arm's dead end raises: how many model calls does a single cluster topic cost
over its life, and which living topics are stuck at `label_attempts >= 3` with a stale core. The
section carries its OWN window — from the birth of the oldest *living* topic to the pinned `until`,
i.e. "since the first run" — while the cost tables keep the rolling `-days` window; both windows are
printed. Every living topic is listed, including the ones that never saw a call (they show `0`, they
are not missing), plus the exhausted ones again as their own section with the age of their label.

`context_llm_log` carries no `topic_id`, so the attribution is reconstructed from the arm's code:
`block_ids` of a `cluster-label` row IS one topic's core array at tick time (`topiclabel.go:481`
hands `core_blocks` to the chain call, `llm/chain.go:688` writes it onto the row), and
`graph_cluster_topic.core_blocks` is the copy of that core which survives the node teardown
(`overview/topic.go:944-949`). The rule is therefore an **overlap plus a time bound** —
`block_ids && core_blocks AND log.created_at >= topic.created_at` — never set equality, because the
stored core is only the youngest generation. Equality is reported separately as the `exakt` column.
A row that touches two living topics is counted at **both** and additionally counted as ambiguous;
wherever `mehrd. > 0`, that row's numbers are upper bounds. The report prints the full assignment
balance sheet (assigned / ambiguous / unassigned / retired-only / rows without `block_ids` — the K9
rejection lines / rows before the window) so the per-topic numbers have a denominator. The view is a
measurement only: it changes nothing about the arm.

Same containment and transaction discipline as `ctx-llmlog-export`: every query runs in its own
short `READ ONLY` transaction (SQLSTATE `25006` on any write, by construction), the window is
pinned to the database `now()` **minus one minute**, a `count(*)` gate over the same window must
match the summed group counts, and the `-out` JSON is created `O_EXCL` with mode `0600` in a
directory with no group/other bits that does not resolve under `/tmp`. Exit codes: `0` clean · `1`
perimeter, config, DB or I/O error · `2` misuse of the `-arm`/`-per-topic` pair (only together, and
only for an arm whose attribution rule is implemented — nothing is written and the database is never
touched) · `3` count gate violated · `4` the non-disruption metric broke its threshold. The table and
the JSON file are written on `3` and `4` as well — they are the evidence.

The rule behind all three: DB-direct tools open `READ ONLY` (`pgxdb.Read`, or a connection that sets
`default_transaction_read_only`), and the only writing exception is `ctx-distillreset` — a list
`cmd/dbaccess_test.go` pins site by site, so a new direct write is a line with a reason or a red test.
The fence judges packages no server binary reaches, which is why the JSONL export reader lives in
`internal/llmlogexport` rather than in `internal/llmlog` (the package `ctxd` writes its log rows
through): the reader is a tool, the writer is the server, and only the tool answers to this rule.

### Shadow-retype reset: ctx-distillreset

The shadow measurement programme builds its corpus by re-typing the distiller's insight blocks to a
shadow type on a **measure copy** (a registry row carrying `retrieval.shadow_measurable`; the
re-type itself is one `UPDATE`, content and metadata untouched). The arm finds its block identity
over `(category, title, scope)` **without** the type, so afterwards it refuses every run that covers
the same watermark range again — `outcome=failed`, `error=block_write_failed`, on every tick. That
is correct behaviour (Festlegung 4b: a foreign type on the arm's identity is never overwritten), but
it left the measurement with no documented way back. `ctx-distillreset` is that way back.

```bash
cd go && go build ./cmd/ctx-distillreset
set -a; . .env; set +a
CONTEXT_DB_HOST=<copy> ./ctx-distillreset -from-type session-insight-shadow          # shows
CONTEXT_DB_HOST=<copy> ./ctx-distillreset -from-type session-insight-shadow -apply   # writes
```

The config is validated in full before the first database contact: an error-severity issue from
`internal/config` — the cross-field rules included — is printed and ends the run with exit ≠ 0
before any pool is opened.

It sets `type_name` back to the arm's configured block type and touches **no other column** — not
`updated_at` (the anchor a campaign's drift stamp reads: a reset that moves it turns the restoration
of a state into corpus movement, which is exactly what the stamp hunts as contamination), not
`type_source`, not content, metadata, sensitivity or the archive flag. It is the exact inverse of
the documented forward `UPDATE`, and nothing else. Without `-apply` it lists what it would write;
run twice with `-apply`, the second run finds nothing.

Three gates, all of them before any write: the instance must label itself `measure-copy` over
`server.instance_kind` (**no override** — unlike the dump driver's `-allow-live-instance`, because a
live corpus never gets into this state in the first place); the source type must be in the registry
**and** carry `retrieval.shadow_measurable`, so the tool is not a general re-type hammer and a
genuinely foreign type on the arm's identity stays refused by the tool as well as by the guard; and
the target type is the arm's configured `distill.block_type`, not a free parameter, and must be
registered too. Derived blocks (`metadata.provenance`) in the same space are listed as skipped and
never touched. Every affected row is printed with id and title.

Exit codes: `0` clean · `2` misuse (missing `-from-type`, before any DB contact) · `3` a gate
refused · `5` the instance is not a measure copy · `1` everything else.

The refusal itself is diagnosable from the server log since the same wave: the type conflict leaves
`have_type`, `want_type`, `category`, `scope` and a `remedy` hint as fields on one ERROR line. The
run journal is unchanged and still carries the class `block_write_failed` and nothing else.

## Backends

The backend pool (`context_backends`) is the living LLM configuration — `ctx backends` lists and manages it, the web UI at `/settings/backends` does the same visually.

Two ways in on a fresh installation. Interactively, [`ctx init`](#first-run-ctx-init) asks for host, protocol and the two models (for the `anthropic` protocol also the chat model's context window and a separate embedding host, since the Messages API serves no embeddings), seeds the pool and probes what it wrote — the same code path, wrapped in prompts. Non-interactively (scripts, CI, cloud-init), `ctx backends seed` writes the first two rows without any interaction:

```bash
ctx backends seed --host http://gpu-host:11434 --model qwen3 --embed-model qwen3-embedding
# or, for anything beyond one host and two models:
ctx backends seed --file seed.json
```

The SeedSpec file has one object per role; everything except `host` and `model` is optional (`protocol` defaults to `ollama`, `trust` to `full-trust`, `name` to `chat-primary` / `embed-primary`):

```json
{
  "chat":  {"host": "http://gpu-host:11434", "model": "qwen3", "num_ctx": 32768, "think": false},
  "embed": {"host": "http://gpu-host:11434", "model": "qwen3-embedding"}
```

Hosted Claude through the native Messages API (`protocol: "anthropic"`, see [api — Anthropic](api.md#backend-pool)) is a two-host spec: the chat leg needs the key (sealed into a secret, as below) and `num_ctx` (the wire has no window discovery), the embed leg stays on a local `ollama`/`openai` backend because the Messages API serves no embeddings. `base_url` is the API root without `/v1`:

```json
{
  "chat":  {"host": "https://api.anthropic.com", "protocol": "anthropic", "model": "claude-opus-5-5", "num_ctx": 100000, "api_key": "sk-ant-…"},
  "embed": {"host": "http://gpu-host:11434", "model": "qwen3-embedding"}
}
```

What to know before running it:

- **A server-admin key is required.** A tenant-admin's writes would be pinned to its own tenant scope — the seed refuses instead of reporting success over a shared pool that stays empty.
- **The rows are seeded `full-trust`**, which is what lets them serve your own blocks (the pool's default block sensitivity is `credentials`, and a `public` backend is filtered out of that chain). Set `"trust"` per role in the spec to deviate deliberately.
- **`api_key` never lands in the table.** It is sealed into an F2 secret first and the row carries only the reference, so the server needs a configured `CTX_SECRETS_KEY` (`openssl rand -hex 32`) before a spec with `api_key` can be seeded. Without one the run aborts and writes nothing — there is no plaintext fallback.
- **It is idempotent per row.** A run interrupted between the two creates is completed by simply running it again. Rows *outside* the pair it manages abort the run instead (`--force` overrides only that check), so an already-configured pool is never touched by accident.
- **The anthropic leg is validated on the spec.** `protocol: "anthropic"` on the embed leg, without a key, or without `num_ctx` aborts before anything is sealed or written — the same rules the server enforces with a 422 on `backend-create`.
- **A seed file is transient, not config.** It carries the api_key in the clear: `chmod 0600`, delete it after the seed, never commit it.
- **A pool that exists is not a pool that serves.** `ctx init` probes each serving row and names the dead ones; `ctx backends test <id>` does it for a single row. Rows named `herbert-chat` / `llama-embed` on `http://localhost:11434` are the residue of an env bootstrap that ran with nothing configured — inside the ctx container that URL is the container itself. They have to *leave* the pool, and `--force` does not do that for you: it only skips the foreign-row guard and then creates the seed's own rows, leaving the legacy pair enabled at priority 100 next to them (dead members of every failover chain, one health-probe timeout each). Delete them first — `ctx backends delete <id>` — then run `ctx backends seed`. Parking them instead (`ctx backends update <id> '{"enabled":false}'`) keeps them out of the chains but leaves the seed needing `--force`.

**A backend behind a redirect to another host.** The wires follow a redirect only on the same origin or as an `http`→`https` upgrade on the same host ([security — backend redirects](security.md#web-login-oauth--ssrf-hardening)); a `base_url` that answers with a redirect to another host, a subdomain or another port has to be entered with the redirect's target URL — until then every call on that row fails with the redirect status and ctxd logs `WARN redirect refused` with both origins.

### External offer per target

Whether a target admits the external class of `/v1` consumers is data on its backend rows (`limits`, server-admin rows on a shared origin as for `slots`), checked per target kind. Nothing about authentication or priority has to be configured on the engine itself — ctx is the admission authority in front of it.

| `limits` key | Type | Merge over the origin's rows | Rule |
|---|---|---|---|
| `internal_reserved_slots` (R) | integer 1 … 2147483647 | maximum | Slot-managed target (llama.cpp, SGLang on the LAN): offered only with `slots` S > 0 and 1 ≤ R ≤ S − 1, checked **after** the merge (R on one row and `slots` on another count together); a declared `background_reserved_slots` must stay ≤ R − 1. The external leases together hold at most E = S − R slot units — the sum of their weights (engine sequences, `Request.Weight`), not their count. |
| `external_offer` | bool | every row must offer | Self-admitting target only — every row of the origin a peer ctx (`provider_class` `ctx`) or an external locality. On a slot-managed target it is ignored with a WARN; a self-admitting row that also carries `slots` needs R as well. |
| `external_max_inflight` | integer 1 … 2147483647 | minimum | Caps the sum of the external weights (engine sequences, `Request.Weight`) on an offered self-admitting target — an external acquire heavier than the cap is refused at once; without it the remote admission alone acts. Ignored with a WARN without a valid `external_offer`. |

A `/v1` request that splits its work into sub-blocks (embedding inputs, rerank documents) acquires the first sub-block like any external request; every further sub-block is a **continuation**: it waits at the head of the external class — before every external request that is still waiting for its first sub-block, of any consumer — and is never refused by the external cap ladder or the wait budget, because the request was already admitted once. It still respects the partition (at most E units) and the rank order (a waiting interactive request goes first, background goes first under `o2`), counts in the queue depth others see, and ends with `ErrExternalNotOffered` like every external waiter when the offer is withdrawn or the kill switch flips. Only the `/v1` sub-block walk asks for continuations. Because continuations go first, a steady stream of them — several split requests at once — can keep a heavy ordinary request (one whose weight does not fit between them) waiting until its wait budget ends with a busy refusal; the dispatcher sets no limit on continuations.

**Chain filter of `/v1`.** Before the first acquire, the `/v1` admission drops every chain row whose target does not offer the external class (the rules above, read per row's origin); with none left the request is a `503 model_unavailable` without any acquire. A target that stops offering between the filter and the acquire refuses the acquire the same way. Each lease of a request carries at most `min(sub_batch, E)` units — the alias's sub-batch, clamped to the target's external capacity E — so a split request never asks for more than the partition holds.

A malformed value (wrong type, below 1 or above 2147483647, not an integer) is a 422 on `backend-create`/`backend-update`. A violation the write path cannot see — it needs the other rows — logs a WARN at the next policy derivation and leaves the target without an offer (fail-closed), as does a malformed value on a row that predates the check; a target without slots and without `external_offer` (a LAN llama.cpp without `slots`, say) never offers. `api_key_ref` is no condition. The server-admin `/api/status` dispatch section shows per target `internal_reserved`, `external_offered`, `external_capacity`, the external wait view and its refusals (`external_rejects.cap` / `.not_offered`).

```
POST /api/manage {"action":"backend-update","id":"<row id>","data":{"limits":{"slots":4,"internal_reserved_slots":2}}}
```

**Fairness inside the external class.** Who of the waiting `/v1` consumers gets a freed slot unit is a fixed mechanism of the dispatcher, not a setting (the interactive `dispatch.fairness` is unrelated and stays `fifo`). Per target:

- **Shares, tenant first, then consumer.** `T_act` is the number of tenants with at least one external lease or waiter on the target. Each active tenant's share is `max(1, ⌈E / T_act⌉)` units (E = the target's external capacity: S − R, or `external_max_inflight`). Inside a tenant, each active consumer's share is `max(1, ⌈tenant share · fair_weight / Σ fair_weight of the tenant's active consumers⌉)` — `fair_weight` is the consumer's value (1 … 100, default 1). Because the tenant share comes first, a tenant that mints more consumers (self-service) splits its own share among them instead of growing it. A self-admitting target without `external_max_inflight` has no shares, only the order below.
- **Order.** When units free up, the dispatcher orders the heads (oldest waiters) of all consumers' queues. Heads whose consumer and tenant stay within their shares after the admission go first — a consumer or tenant that holds no unit counts as within its share whatever the request's weight (one request in flight); among them the tenant with the least slot time, inside it the consumer with the least slot time per `fair_weight`; equal slot times keep arrival order. Only when no head is within its share is the same order applied to all heads — a consumer above its share gets a unit only when nobody below their share waits, and a single consumer may use all of E (no unit idles). The first head in this order is admitted when it fits with its weight. A consumer's own requests stay strictly first-in-first-out; a running lease is never aborted for fairness (a monopolist's hold shrinks as its leases end).
- **Slot time** is lease duration × weight, summed per consumer and per tenant over a fixed one-hour window (in memory; a restart resets it), plus the time the currently held leases have run. Long streams therefore count for what they occupy, not as one pick each. The order is re-read at every wake of the target and at the start and end of every external lease — that is at an external arrival, a release, the expiry or cancel of an external request, a policy change, and an interactive admission (a background admission too while bulk requests wait — under `o2` while any external request waits) while external requests wait. Between these events it does not move with the clock: a request that would rank first by the time elapsed since then waits for the next such event.
- **A heavy head keeps its place.** When the first head in the order does not fit now (its weight exceeds the free units), no other request of the external class — waiting or new — takes a unit while it waits, so the units it needs accumulate as leases end; only a newcomer that ranks before it in the order passes it. Exception: while interactive (and, under `o2`, background) alone holds so many units that the head could not fit even if every other lease ended, nothing is held back for it and lighter requests use the free units. **Aging.** The shares alone would starve a heavy request next to a busy consumer of the **same** tenant: with that consumer's share s, a request of weight w stays above its tenant share as long as w + (s − 1) exceeds the tenant share — the busy consumer keeps s − 1 units and stays first in the order (one active tenant, E = 5, two consumers of equal `fair_weight`, s = 3: weight 4 or 5). The condition describes the shape, it is necessary, not sufficient: the request starves only if it also does not fit beside those units and the units of other tenants. So the waiting request of a consumer that holds no unit ages — counted from the later of its arrival and the moment its consumer last dropped to zero held units, once it has waited one median lease duration of its class (when the class's lease window is warm, 32 samples or more) or once its class has admitted E units to other consumers, whichever comes first. A consumer with a backlog therefore does not age by releasing its own leases: its next request starts counting when the consumer holds nothing. An aged request counts towards its tenant's share as one unit (it is within the share while its tenant has room for one more unit) and goes first among its own tenant's requests, whatever its consumer's slot time; between tenants the slot-time order stays, so it takes its tenant's turn and never another tenant's. As the first head it keeps its place as described above and is admitted when the leases it needs units from have ended. Aging changes the order only at the events listed under slot time — an aged request that fits waits for the next such event (on an idle target with long leases until the next lease ends); a request of weight 1 only gains its place inside its tenant. The thresholds are fixed mechanism values, not settings; each external class counts its own, and an aged bulk request never passes an `urgent` one. What remains: such a request still ends at its wait budget (`dispatch.external_max_wait`) when the aging threshold plus the end of those leases exceeds it — the wait estimate at its arrival does not include the aging wait. A request of the full external capacity is served only once the capacity has drained; when its leases are short against those of the other consumers, the utilisation during that time is lower than without it. A consumer that keeps asking for the full capacity gets about the same slot time whatever its `fair_weight` (measured: 45 % of the used slot time at `fair_weight` 1 against 3, where its weight would give 25 %) — aging serves it after a fixed wait, not after one relative to its weight. While a head keeps its place, the units it needs stay free even when it cannot get them within its budget, and no lighter request of the class runs in them meanwhile (no partial backfill); and a heavy request of a tenant with more slot time than a busy tenant that keeps cycling at its own share waits until the slot times cross (no aging across tenants) — these are named limits.
- **A heavy head is not starved by background (order `o1` only).** While the external head the freed units serve first (the first head in the order — or a waiting continuation) fits the external partition but not the slots — ctx's own background work holds units of the partition, as the work-conservation rule allows — background takes no further unit the head needs; background keeps its floor of R minus the interactive units, and every unit beyond the head's need. Nothing is held back for a head that interactive alone keeps out (it would not fit even if only the interactive units were held): background keeps using the free units. Under `dispatch.external_order=o2` (background before external) nothing of this applies: background keeps every free unit, and an external head waits until background lets go or its wait budget ends.

**Lanes: two external classes.** A `/v1` consumer's `admission_lane` is its ceiling, and each request runs in one of two external classes: `urgent` in the external class, `bulk` in the external bulk class. The lane is the minimum of the ceiling, a peer's `Ctx-Class` hint and `service_tier` — `flex` lowers to `bulk`; a `ctx-peer` consumer's hint counts only with a `Ctx-Path` (`interactive`/`external` keep `urgent`, `background`/`external_bulk` lower), a peer without a hint is `bulk`, an app's hint is ignored; nothing raises a request above its ceiling. A peer instance therefore gets **two consumers** when it is paired — one with ceiling `urgent` for its humans, one with ceiling `bulk` for its background work — so the peer's dream or backfill never queues in front of its users on this instance. Both external classes share the external partition E (the sum of their weights stays ≤ E), the wait budget `dispatch.external_max_wait` and the cap values `dispatch.external_queue_per_consumer`/`_per_tenant`/`_max`, but each class counts its own queue against those caps, has its own lease window and its own counters. The bulk class ranks last in both orders: a waiting `urgent` request goes first, and a bulk request never takes a unit that the `urgent` request the freed units serve first still needs — while that request waits for its units (it does not fit yet, and the classes above it do not keep it out on their own), bulk work waits too, under `o1` and `o2`; an `urgent` request that interactive (and, under `o2`, background) work alone keeps out does not hold bulk back. Background that may run now goes before bulk in both orders; background held back by interactive demand (the herald) does not hold bulk back — bulk then uses the free units of the external partition. With `dispatch.background_aging_after` set, an aged background request that the aging escape would admit also goes before a newly arriving bulk request (and, under `o2`, before a newly arriving `urgent` one), and any refusal without an enqueue wake — a non-blocking acquire that would block, a spent or predicted wait budget, a queue cap, of any class (a blocking acquire the target does not offer ends before it; a non-blocking one yields like every other non-admission) — hands a free unit to such an aged background request at once instead of leaving it idle until the next release. **Known limit:** bulk is not served under sustained `urgent` load above the external capacity — while an `urgent` request waits at every release, a bulk request never gets a unit: it ends at its wait budget (`dispatch.external_max_wait`) with `expired` and a Retry-After, or — once the bulk lease window is warm and the estimate exceeds its budget — is refused at once with `predicted` and a Retry-After; it never waits past the budget. An aging rule for bulk across the class order (`dispatch.external_bulk_aging_after`) is named, not built — design/03 §4.8: an escape over background only, never over interactive or `urgent` work; the aging above orders bulk requests only among themselves. The fairness shares, `heldBy` and slot time count both classes together (one consumer's `urgent` and `bulk` leases are one consumer's), the order is applied inside each class. The prediction of a bulk request uses the bulk lease window and adds the weight of the `urgent` requests waiting ahead of it. The time until the first unit frees reads the held leases of both classes, each with the median lease duration of its own class (a class whose window is still cold — fewer than 32 samples — counts with the requesting class's): long bulk generations next to short `urgent` chats neither shed every bulk request nor queue `urgent` requests the long leases cannot serve within their budget. The server-admin `/api/status` dispatch section shows the bulk class next to the external one: `external_bulk` (waiting, wait aggregates) and `external_bulk_rejects`; `held_external` counts the leases of both classes. The lease windows of interactive and background are kept but not published (nothing reads them).

**Prediction, relational cap and Retry-After.** The dispatcher measures, per target and class, how long a lease lasts from admission to release (the last 512 lease ends; the median `L50` and the 90th percentile `L90`). For the external class it uses them in three places once at least 32 lease ends are recorded — before that, none of this applies, and an external request waits up to its budget as before:

- **The serve-by deadline counts the lease.** A request that needs its answer by a deadline may wait at most until that deadline minus `L90` minus 500 ms: a lease admitted later would most likely not end in time.
- **A wait that cannot pay off is refused at once.** A request that would have to wait first joins the queue; if that makes it the request the freed units go to and it fits, it is admitted at once. Any other request gets an estimate of its wait from its own place: the weight its consumer already has waiting plus its own, at the consumer's share of the target's external capacity E — split like the fairness order, first equally among the tenants with waiting requests, then inside the tenant by `fair_weight` among its consumers with waiting requests — in rounds: the first round lasts until the first running external lease reaches the `L50` of its own class (per running external lease `max(0, L50 − age)` with the `L50` of the lease's class, the smallest of these — with one external class that is the oldest lease's; 0 when no external lease runs, and 0 as soon as one runs past the `L50` of its class), every further round a full `L50`. A request that is first in the fairness order now waits only its first round. A tenant that adds consumers splits its own share; it does not shrink the share of another tenant. If the estimate exceeds what is left of the request's wait budget (the budget counts from the arrival, so time the request already spent waiting for the dispatcher counts against it), the request leaves the queue again at once, before its arrival re-reads the order for anyone else (a busy refusal, counted as `predicted`), instead of holding a connection until the budget runs out. Continuations are never refused this way.
- **The queue length follows the capacity.** The queue a whole wait budget can serve is R = `⌈1.5 × E × dispatch.external_max_wait / L50⌉` requests; each tenant with waiting requests may hold its equal part of it (a tenant alone may use all of R), so a target whose leases run long keeps a short queue and one tenant never fills it for the others. Tenants that arrive one after another keep the places they took — the k-th gets up to `⌈R / k⌉` — so the whole queue can grow beyond R, up to `dispatch.external_queue_max`, which stays the absolute ceiling. A request beyond its tenant's part is a busy refusal counted as `cap`.
- **Limits of the estimate.** It models the shares, not the slot-time order beyond the first request: a fresh or lightly used tenant that is second in the order can be overestimated and refused although it would be served soon, a tenant whose running leases hold much of E can be underestimated (it then waits up to its budget, as before). With every external lease just started and `L50` above the wait budget, even the first request in the order is refused: the first round assumes that every running lease lasts `L50` — it sees neither how widely lease durations spread nor which of the E running leases ends first — so with widely spread durations a unit often frees well before `L50` and the request is refused all the same. The first round is read off one running lease only — the one closest to the `L50` of its class: one lease running past `L50` (a long stream) makes the first round free however fresh the others are, and a heavy request first in the order counts only its first freed unit although it needs several — both at most one round optimistic, bounded by the wait budget.

Every busy refusal of an external request carries a Retry-After from that same estimate of the refused request's own place, in all its rounds (also for a request first in the order) — how many requests or consumers another tenant has waiting does not change it; how many tenants are waiting and how long the running external leases have run do — rounded up to the next of `dispatch.external_retry_after_steps` (default `1,2,5,10,20,30` seconds; the largest step caps it). A request whose wait budget ran out gets at least the time it waited, rounded up the same way. Before 32 lease ends are recorded, and on a self-admitting target without `external_max_inflight` (no E: no prediction and no capacity-based queue length there), it is the external queue depth times the recent 95th-percentile wait, rounded up the same way. The lease-duration view is in the dispatcher snapshot; `/api/status` does not show it yet.

## GPU-host maintenance (eject)

To take a GPU host (e.g. `herbert`) down for maintenance without dropping in-flight work, use the eject toggle as a quiesce gate. The disable profile takes the host's backends out of every NEW chain; requests already on the wire finish normally (a 27B synthesis ≤60s, an in-flight dream cycle ≤700s). The runbook: **activate the profile → watch the DispatchTile until `inflight=0` for that origin → then service the host.** `ctx eject on` (or the disable-profiles card on the backends settings page) activates it; the status page's DispatchTile shows `inflight`/`waitQ` per origin live, so `inflight=0` is the safe-to-stop signal. `ctx eject off` restores the host to the pool. There is no active drain — a waiting lease already holds its chain, and failover + cooldown heal the dead-host case on their own; the DispatchTile is the quiesce monitor, not an automated barrier. See [security](security.md#trust--sensitivity-gating) for the toggle's admin gating and persistence semantics.

## Foreign load detector

**Topology doctrine.** ctx orders the work on a GPU — interactive before background, the reserved internal partition, fairness, wait budgets — in its dispatcher, without any help from the engine: no backend has to support authentication or priorities, an OpenAI-compatible wire is enough. That ordering only holds while ctx is the **one admission authority of each GPU**, and that is a deployment convention, not something the engine enforces: one ctx instance fronts each GPU engine, and everything else — LAN clients, scripts, other ctx instances — reaches the engine through that instance (other instances register it as a `ctx` backend row, never the engine port itself). A client that talks to the engine port directly lands in the engine's own FCFS queue ahead of ctx's whole ordering, while every ctx-internal counter still looks fine. The detector is the evidence that the convention holds: it reads the engine's own metrics and compares them with what ctx itself put on the engine. Port authentication on the engine (`--api-key` plus the row's `api_key_ref`) is an optional extra layer where an engine supports it, never a precondition.

**Activation is per backend row**, as data: a server-admin sets `metadata.foreign_load_probe` to the engine's probe kind on a `_global` row.

```
POST /api/manage {"action":"backend-update","id":"<row id>","data":{"metadata":{"foreign_load_probe":"sglang"}}}
```

`metadata` is replaced as a whole on update, so carry the row's existing keys along (`backend-list` shows them). `sglang` is the only kind today. Any other value is a `422` on `metadata.foreign_load_probe`, and so is the key on a tenant row, whatever its value: the probe observes the GPU host, which is the server operator's, and its readings expose every tenant's load. Removing the key stops the probe. Rows sharing one origin (`scheme://host:port`, the dispatcher's key) are probed once. A row that is disabled, or parked by an active disable profile (the eject case above), is not probed — the GPU is lent out on purpose.

**What it reads.** On its own cadence — every `status.foreign_load_interval` (default 5 s), plus once right at each UTC hour boundary — the detector sends `GET <origin>/metrics` to each marked origin. That cadence does not depend on anyone reading the status: a headless instance, with no dashboard open and nobody polling `/api/status`, probes exactly like an observed one, and a status read never starts a round. Rounds are single-flight: a hung engine holds at most one probe for at most `status.foreign_load_timeout`, a tick that finds a round still in flight starts none, and `/api/status` answers from the last round that landed. The ticker starts and stops with the server; a round in flight at shutdown is cancelled and leaves no reading. The probe uses the same HTTP transport as the backend's inference calls, and sends `Authorization: Bearer <secret>` only when the row has an `api_key_ref` (a ref whose secret did not resolve is reported as `api_key_ref unresolved`, without sending). From the Prometheus text it reads three families and ignores every other line:

| Family (sglang) | Use |
|---|---|
| `sglang:num_running_reqs` (gauge) | requests the engine's scheduler runs now, summed over all label sets (one per TP/PP/EP rank) |
| `sglang:http_requests_active` (gauge, optional) | HTTP requests in flight on the model endpoints, queued ones included — one per HTTP request, the unit of a dispatcher lease |
| `sglang:http_responses_total` (counter) | HTTP responses finished on the model endpoints, any status code |

The model endpoints are `/v1/chat/completions`, `/v1/completions`, `/v1/embeddings`, `/v1/rerank`, `/generate`, `/encode` and `/classify`. `/health`, `/metrics` (the probe's own GET) and the info routes never reach the model, and unknown endpoints are ignored. The arrival counter `sglang:http_requests_total` is deliberately not read: it counts a request when it arrives, so requests in flight across an hour boundary would land in the wrong hour.

**Two checks.**

- **Per round — engine vs. held, each gauge in its own unit.** `running` counts the sequences the engine's scheduler runs and is compared with `held_weight`, the sum of the weights of the dispatcher's held leases on the origin (a `/v1` lease of weight w — chat `n`, embedding inputs, rerank documents of the lease — is w sequences; every in-house lease weighs 1); `active` counts HTTP requests and is compared with `held`, the number of held leases (one HTTP request per lease). A lease is taken before a request is sent and released after it ends, so the lag between dispatcher and engine only ever reads as engine ≤ held. When `running > held_weight` or `active > held` holds for `status.foreign_load_hysteresis_ticks` consecutive rounds, the target is `suspected` (with `since`); without the `active` gauge, `running > held_weight` alone decides. It clears after the same number of consecutive rounds without either excess. So a weighted lease is not foreign load (one external lease of weight 3: `running` 3, `active` 1, `held` 1, `held_weight` 3 — clean), while a foreign request is (`active` 2 against `held` 1) and so is a foreign sequence (`running` 4 against `held_weight` 3). `active` is what still sees foreign requests waiting in a saturated engine's queue: there, `running` is pinned at the engine's limit and reads `running = held_weight`. `held` and `held_weight` are read from the dispatcher before and after the GET, and the larger of the two counts, each on its own. It applies only to a target the dispatcher holds slots for. A pass-through origin (no `limits.slots`, or `dispatch.enabled=false`) does not count its leases in `held`, so `held` is `null` there and only the hourly check runs.
- **Per hour — engine responses vs. ctx's own calls.** Both sides count a call when it ends: the engine its response, ctx the `context_llm_log` row it inserts after the call. The ticker wakes on every hour boundary, so the response counter read right at the boundary stands for it. If that round cannot start because the previous one is still in flight, the first round of the hour stands in, provided it starts within one interval plus one probe timeout of the boundary. With two consecutive boundaries, the engine's request delta for that hour is compared with `sum(duration_n)` of that hour bucket in the LLM-usage rollup (migration 159), taken over every backend row on the origin — every scope, matched by row name, and by `base_url` for calls logged without a backend name. The hour is `suspected_hourly` when the engine **exceeds** ctx's count by more than `max(status.foreign_load_hourly_min_abs, status.foreign_load_hourly_min_ratio × ctx requests)`. A deficit — ctx logged calls the engine never counted — is not foreign load. An hour whose boundary round came too late, or across which the counter went backwards (engine restart), is not compared.

**Status section** (server-admin only, see [api](api.md)): `foreign_load` is an array with one row per probed origin. It is present while at least one row is probed — marked, enabled, and not parked by a disable profile — and absent otherwise, so under eject the section disappears. An empty array would read as "probed, nothing foreign" for an engine nobody observes, so it is never sent.

| Field | Meaning |
|---|---|
| `target`, `probe`, `backends` | normalized origin, probe kind, names of every backend row on the origin |
| `running`, `active`, `held`, `held_weight`, `delta` | last reading (`delta = max(running − held_weight, active − held)`, `running − held_weight` without the `active` gauge); `null` when the round failed, `active` also `null` when the engine does not expose the gauge, `held`/`held_weight`/`delta` also `null` for a pass-through target |
| `suspected`, `since` | the per-round verdict and when it was entered |
| `suspected_hourly`, `hourly` | the verdict of the last compared hour, with `{hour, engine_requests, ctx_requests}` |
| `probe_error` | `null`, or the failure class of the last round: `timeout`, `unreachable`, `http status <code>`, `metric family absent: <name>`, `api_key_ref unresolved`, `metrics body over <n> bytes` — never request material or a secret |
| `probed_at` | when the last round landed |

**Log lines.** Each state change logs one WARN, never one per tick: `status: foreign load suspected` / `… cleared`, `status: foreign load hourly mismatch` / `… cleared`, `status: foreign load probe failed` and `status: foreign load hourly rollup read failed` (both WARN on entering the failure; their counterparts `… probe recovered` and `… read recovered` log at INFO). The detector exports nothing — ctx still has no metrics endpoint of its own; it only reads the engine's.

**Settings** (all `global-only`, hot):

| Key | Default | Meaning |
|---|---|---|
| `status.foreign_load_interval` | `5` (s) | cadence of the probe rounds (the ticker also wakes on every UTC hour boundary); a change applies from the next wait on; `>= 1`, and interval + timeout below 1 hour (otherwise no hour would ever be read) |
| `status.foreign_load_timeout` | `2` (s) | bound of one `/metrics` GET and of the hourly rollup read; `>= 1` |
| `status.foreign_load_hysteresis_ticks` | `2` | consecutive rounds to enter and to leave `suspected`; `>= 1` |
| `status.foreign_load_hourly_min_abs` | `5` | absolute floor of the hourly tolerance |
| `status.foreign_load_hourly_min_ratio` | `0.01` | relative term of the hourly tolerance, in `[0,1]` |

**Limits of the reading.**

- **Detection takes rounds, not seconds.** `suspected` needs `status.foreign_load_hysteresis_ticks` consecutive rounds, so with the defaults a foreign client is flagged 5–10 s after it starts, and the window grows with the interval. A changed interval applies from the next wait on: the wait in progress at the change still runs on the old value, at most until the next hour boundary. Keep the interval short for the hourly check too: when the boundary round cannot start (a slow round still in flight), the next regular round stands in up to one interval plus one timeout late, and at high request rates a long interval can push that hour past the ratio tolerance — the defaults shift a boundary by at most 7 s, about 0.2 % of an hour.
- **`running` counts scheduler requests, not HTTP requests.** A request that fans out inside the engine — `n > 1`, or several inputs in one call — runs as several scheduler requests. ctx's own calls carry their fan-out as the lease weight, which is why `running` is compared with `held_weight`. Two gaps remain: ctx's internal rerank sends up to `rerank.max_docs` documents in one call on a lease of weight 1, and whether SGLang splits a rerank call into one scheduler request per document is not verified — mark a rerank engine only after checking that.
- **Another ctx instance on the same engine counts as foreign load.** That is the doctrine above, applied: it should reach the engine through the owning instance.
- **The hourly check credits a call to the backend that answered.** ctx logs one `context_llm_log` row per call, under that backend. An attempt that reached this engine, failed, and was then served by a fallback backend is counted by the engine but not credited to this origin. Hours with many failed attempts can therefore drift toward `suspected_hourly`, and the tolerance settings are the knob.
- **Row names are unique per scope only.** Two rows with one name on different origins share their rollup rows, which favours ctx's side of the comparison.

## Models & hardware

ctx is **engine-agnostic**: every LLM role speaks the OpenAI-compatible or the Ollama wire protocol (per-backend `protocol`), and the chat-class roles (synthesis, translate, dream, digest, chat) can also run on the native Anthropic Messages API (`anthropic`, hosted Claude — no embeddings or rerank there), so any provider serving one of those works — local llama.cpp / Ollama or a remote API. Models are configuration, not code: each `context_backends` row carries a per-role `model_map` (see [architecture — backend pool](architecture.md#backend-pool-f3-migrations-053055)). The models below are the **tested production reference**, not hard requirements. Beyond the LLM backends, ctx itself is a single Go daemon plus PostgreSQL 18 + pgvector — no GPU needs of its own.

| Role(s) | Reference model | Host type | Purpose |
|---|---|---|---|
| `synthesis` / `chat` / `translate` / `digest` — `dream` inherits chat unless split | qwen3.6:27b (Q4_K_M MTP GGUF, non-thinking — `model_map` params `think: false` on the serving row) | GPU llama.cpp; CPU fallback via the `llama-cpu` compose sidecar | Query answer synthesis, web chat, query translation, digest, Dream evaluation |
| `embed` / `dream-embed` | Qwen3-Embedding-8B (Q4_K_M GGUF), 1024-dim vectors | CPU llama.cpp sidecar (`llama-embed`) — deliberately CPU-sized | Block + query embeddings for the semantic RRF channel |
| `rerank` | bge-reranker-v2-m3 (Q8_0 GGUF, multilingual de+en cross-encoder) | CPU llama.cpp sidecar (`ctx-rerank`, 4 GB mem limit) | Post-RRF cross-encoder rerank; with no rerank host set, LLM-as-judge on the chat model |

**Minimal setup — CPU-only works.** Nothing requires a GPU; the trade is latency. Embeddings are CPU by design (~23 tok/s prefill on a Xeon E-2176G with the tuning below, ~8 GB projected memory for the sidecar). The rerank sidecar is CPU by design too (~0.85 s/doc — the query body-heartbeat keeps proxies alive on the long path). Chat/synthesis is where a GPU pays off: the same 27B GGUF answers in ≤60 s on GPU vs ≈4.5–5.5 min per answer on CPU (`llama-cpu` fallback). Fallback chains are first-class: the backend pool walks priority-ordered rows per role, so a CPU backend can back a GPU one.

**Bring your own model.** Backends are configured in the pool and nowhere else: `context_backends` is the source of truth, and hosts, roles, model maps, timeouts and priorities are managed through `ctx backends` (or web `/settings/backends`), never through env edits. On a fresh installation seed it directly — [`ctx backends seed`](#backends) or [`ctx init`](#first-run-ctx-init). The `CTX_{CHAT,CHAT_FALLBACK,EMBED,DREAM,DREAM_EMBED,RERANK}_*` connection vars that used to bootstrap those rows are [retired](#environment-variables) and read by nothing.

**Changing the embed model changes the vector space.** Every stored vector must be regenerated before the new model can serve queries — that is a supervised re-embed migration (`ctx admin embed-migration`, state machine below), not a config flip. A runtime write to the embed model is rejected (409, env-/migration-only); the chat/dream/rerank models carry no such coupling.

## Embedding backend tuning (CPU llama.cpp)

The `llama-embed` sidecar (`docker-compose.override.yml`, Qwen3-Embedding-8B, `--n-gpu-layers 0`) serves the `embed` + `dream-embed` roles on CPU. The intuitive GPU tuning is **wrong on CPU** — measured on a Xeon E-2176G (AVX2 + F16C, no AVX512):

- **Keep the KV cache at f16 — do NOT quantize it.** With F16C the CPU reads f16 KV in hardware (nearly free); q4_0/q8_0 need real dequant arithmetic *and* llama.cpp forces Flash Attention for a quantized V cache, and CPU-FA is poorly optimized. Result: f16 ran ~23 tok/s with flat degradation, while q4_0 *and* q8_0 both dropped to ~17 tok/s with a length-growing penalty (−11 % → −25 % across 512→2560 tokens). KV quant on CPU buys memory at a real speed cost; on a **GPU** the trade flips (bandwidth-bound → quant is a win) — which is the long-term reason to move embeddings to a dedicated GPU.
- **`--flash-attn off` on CPU.** FA was the actual slowdown above (both quant configs used it); f16 without FA is the fast path.
- **`--ctx-size` is split across `--parallel` slots** unless unified KV is on: per-slot window = `ctx-size / parallel` (e.g. `32768 / 2 = 16384`). An embed exceeding its slot window fails hard with HTTP 400 `exceed_context_size` — the request is rejected, not truncated.
- **`--kv-unified` (needs `--cache-ram > 0`) gives one shared pool.** Every slot then sees the full `ctx-size`; a single long embed can grow up to the whole pool while other slots are idle (verified: an 17.7k-token input runs under a 32768 pool that would 400 against a rigid 16384 slice). Cost: the slots share the pool (contention only if two large embeds run at once — rare on CPU, which serializes anyway) and ~+1 GB projected for a small `--cache-ram 2048` (default is 8192 MiB — an unnecessary prompt-cache for an embedding server; set it small or `0`). Without cache-ram the pool falls back to the rigid per-slot partition.
- **Current recommended config:** f16 KV, `--flash-attn off`, `--ctx-size 32768`, `--parallel 2`, `--kv-unified`, `--cache-ram 2048` → 32768 usable tokens per embed (covers every existing block incl. the ~65k-char veterans), ~23 tok/s, ~8 GB projected host memory. On a 64 GB box shared with many other DBs/services, treat that as budgeted headroom — not free RAM.

**Re-embed migration scaffolding (migration 114).** `context_embed_models` registers every embedding model's identity (family, native/stored dims, matryoshka, quantization — serving variants that change the vector space MUST be distinguishable in the model string); `context_embed_migrations` carries the dual-column re-embed state machine (pending→running→verifying→done, abort/rollback with mandatory reasons, a partial unique index enforcing at most ONE active migration), and `context_blocks` gains the `embedding_next`/`embed_model_next` cutover pair. `ClearEmbedding` now nulls BOTH vector pairs and deletes the block's backfill failure memo in one transaction — a content edit un-parks an oversize-parked block and can never leave a stale migrated vector behind fresh content. The verify gate and cutover arrive in later waves (the worker itself: next paragraph but one); creating a migration validates models, dims equality, target backend (local, global-scoped, `embed_next` model-map key), leftover `_next` data and a fail-closed disk pre-flight.

**Embedding provenance (migration 109).** `context_blocks.embed_model` is writer-attributed since 109: it names the model that actually produced the *current* vector (taken from the serving backend at store time, not from config), and `NULL` means "no vector". The historic DDL default is gone; rows embedded before 2026-06-10 carry the canonical live label under the documented Ollama→llama.cpp same-space assumption (see the migration's comment). Storing a vector without a model string is rejected fail-closed. The partial index `idx_embedding_pending (created_at) WHERE embedding IS NULL AND NOT is_archived` serves both backfill paths and the future re-embed migration scan; the dead `embed_status` column and its index are dropped.

**Backfill failure memo (migration 113, Achse 04 W04-2).** Both backfill paths — the scheduler arm (`backfillOneEmbedding`) and the query-path pre-search loop (`backfillPending`) — used to retry a NULL-embedding block **indefinitely** if it exceeded the embed window: no truncate, no skip, nothing written to the DB on failure, so the next pick landed on the exact same block (observed 2026-07-10: a 13k-char block at 4704 tokens against a 4096 window looped every ~20 s and blocked ~265 pending blocks behind it). This is closed structurally, not operationally: every failed embed attempt now upserts a row into `context_embed_failures` (`block_id`, `attempts`, `last_error` — normalized, ≤500 chars, never raw wire/embed-text content —, `last_class`, `next_attempt_at`), and both pick queries exclude a block whose `next_attempt_at` is still in the future. A non-oversize failure (backend down, transient wire error) gets an exponential backoff (`embed_backfill.backoff_base` × 2^(attempts-1), capped at `embed_backfill.backoff_cap`; defaults 1min/24h; the base must be > 0 — V21 rejects 0, which would mean "retry immediately" and a tight loop against a failing backend, issue #38) — the next PEEK reaches the next-oldest block instead of re-picking the same one. An oversize block — classified either by a conservative pre-wire token estimate (`len(text)/4` against `embed_backfill.max_tokens`, default 24000, chosen to sit under the live kv-unified pool's 32k minus interactive headroom — see the tuning section above) or by an HTTP 400 whose body names `exceed_context_size` — gets `next_attempt_at = 'infinity'` instead: permanently parked, never a blind 24h-in-slow-motion retry, but never silently dropped either (the memo row stays visible in `context_embed_failures`). A content change releases the park: `ClearEmbeddingTx` (behind `ClearEmbedding` for manage-update and MCP update, and behind `UpsertBlock`'s real-content-change path) deletes the block's backfill memo (`migration_id IS NULL`) in the same transaction that nulls its vectors (W04-3), so an edit that shrinks a previously oversize-parked block below the token threshold makes it pickable on the next cycle. Migration-scoped memos stay as that migration's bookkeeping. The query-path loop additionally carries a synchronous cap (`embed_backfill.sync_cap`, default 4): before this wave a large rest-transient (e.g. after a bulk ingest that outran the scheduler arm) made the *first* interactive query pay the entire nachzug inline; now it embeds at most `sync_cap` blocks per request and leaves the rest to the scheduler arm. Keeping blocks compact (~1–1.5k chars per the store guidance) or sizing the embed window above your largest block is still the actual fix for an oversize block's content — the memo mechanism only stops it from starving everything behind it.

**The dedicated backfill arm and the query-path time budget (tracking issue: force-push.me/damienmoon/ctx/issues/1).** Two gaps in the above showed up on a CPU embed backend (Qwen3-Embedding-8B at the documented ~23 tok/s) with a ~10k-token block. First, the scheduler arm ran only at the top of the dream loop, so with `dream.enabled=false` — the default — nothing backfilled pending embeddings in the background at all; the query path was the only path. `runEmbedBackfillLoop` is now its own goroutine, started regardless of Dream, round-robin over the background tenants like the dream loop and inside each tenant's owned scopes (the chain resolves with the iterated tenant's backend visibility, so a block of another tenant is never sent to this tenant's private backend). A pick that embedded a block, or parked one as `oversize`, loops at once; an empty pick, and a `wire`-class memo (backend suspect — probed once per interval instead of walking the backlog into memos against it), wait `embed_backfill.interval` (default 15 s). The wait runs in 15 s slices and re-reads the key, so a hot change applies within one slice; `0` turns the arm off (polled every 15 s for a hot re-enable). The dream loop keeps its inline call and its own pacing; the tx-wrapped `FOR UPDATE SKIP LOCKED` pick makes two pickers safe. When the oldest pending block has no eligible embed chain (its floor-adjusted sensitivity is above every backend the tenant may use — e.g. the `credentials` default against a `no-credentials`-only pool), the pick narrows to the sensitivities and scopes the chain can serve and takes the next such block in the same call, instead of stalling on the oldest one. That skip writes no memo by design: eligibility is recomputed from the live chain on every pick, so a trust change, or the audit lowering a block's sensitivity, makes it pickable at once; a pool-wide outage (not even `public` resolves) stays a memo-free no-op with its WARN. Second, `sync_cap` bounds how *many* blocks a query embeds inline, not how *long*: one block that needs 7 minutes consumed the caller's whole 120 s deadline, the question's own embed was never admitted, and the query answered 500 instead of degrading. `embed_backfill.sync_budget` (seconds, default 30, `0` = unbounded) now bounds the whole pre-search loop per request; each wire call runs under what is left of it. A block that overruns the budget — or dies with the request context while a budget is active — is memoized with the class `caller_timeout`: while the arm runs (`interval > 0`) the query path never picks it again (`EmbedFailureQueryPathExcludedPredicate`), the background arm picks it at once (`next_attempt_at = now()`), and a later wire failure there reclassifies it as `wire` with the ordinary backoff. The block stays FTS-visible meanwhile. Previously such a failure was memoized as `wire` and re-burned the deadline of every query that landed after the backoff lapsed. The two keys opt out independently: with `sync_budget=0` a request cancel keeps the pre-budget class `wire`, and with `interval=0` (arm off) the query path keeps the plain predicate and retries a `caller_timeout` block inside its budget, so the hand-off never leaves a block to nobody — both at `0` is the pre-arm behavior. In the mixed case `sync_budget > 0, interval = 0` with Dream off, a block that never fits the budget is retried, and cut, by every query (each spends up to `sync_budget` on it) and stays unembedded until the arm or Dream is switched on. Remaining cost of the arm: one embed of a large block can take minutes on a CPU backend, and an interactive embed (e.g. a query's question embed) that lands on the same backend waits behind it — the dispatch layer lets a younger interactive acquire overtake a *waiting* background one, not a running prefill (unless the target row opted into `preempt_background`, which cancels the background embed instead). Where that matters, give the backfill its own backend with the `dream-embed` role: the scheduler's embed chain switches to that role as soon as any backend row carries it (no fallback to `embed`), while the query path stays on `embed`.

**Backfill skips retrieval-excluded types (2026-07-25).** Both backfill paths now also skip a block whose *type* carries retrieval policy `excluded` in the block-type registry (shipped builtins: `checkpoint`, `system-meta`). Such a vector has no consumer at all — every ranked path filters against the registry's visible-type allowlist, so the embedding was written once and then read by nobody. The trigger was a live incident on 2026-07-25 with two independent arms: 33 Hermes "Compaction source" parts (`type=checkpoint`, ~36.5 kB each) saturated the CPU embed backend for hours, and the digest rebuild rewrites `topic-map-private` (`type=system-meta`, 73.7 kB ≈ ~32k real tokens) on **every** boot, which clears its embedding and bought ~60 min of CPU embed for a dead vector — recurring, forever. The filter is policy-driven, not a hardcoded type list (same mechanic as `test.sh` T19), and deliberately conservative in the fail-safe direction: only `_global`-`excluded` skips; `damped` and `aggregate-to-parent` stay embeddable, a block whose type has no registry row at all stays embeddable, and a tenant scope that overrides an excluded type to a visible policy re-opens that type for the backfill (the pick has no reader identity, so the reader-aware overlay rule is mirrored as the union over all possible readers). Two operational consequences: blocks of an excluded type keep `embedding IS NULL` forever — that is the intended end state, not a stuck queue — and the `/status` `embed_backlog` metric still counts them, so a corpus with such blocks shows a permanent backlog floor (live at the time of writing: 24 `checkpoint` + 1 `system-meta`). Existing `infinity` failure memos for such blocks become moot: the predicate no longer even sees the rows. Flipping a type's policy from `excluded` to a visible one makes its blocks embeddable again on the next cycle without any manual step.

**Re-embed migration worker (Achse 04 W04-4).** With an active migration in `running` or `verifying`, a dedicated scheduler arm (`migrateOneEmbedding`, BACKGROUND class, defers to interactive demand) walks all blocks that carry an old-space vector (`embedding IS NOT NULL AND embedding_next IS NULL AND NOT is_archived`) oldest-first from a persistent cursor, embeds them via the model-map key `embed_next` on the regular embed chain, and writes `embedding_next`/`embed_model_next` — the serving pair stays byte-identical until the cutover. Operator knobs: `embed_migration.batch_per_cycle` (default 8, `<=0` disables the arm), `embed_migration.max_tokens` (default 24000, pre-wire oversize gate; `0` disables the estimate — the wire classification of HTTP 400 `exceed_context_size` stays), `embed_migration.backoff_base`/`backoff_cap` (defaults 1min/24h; the base must be > 0 — V21, same tight-loop reasoning as the backfill sibling) — all hot, global-only. Failure memos are migration-scoped rows in `context_embed_failures` (independent from the regular backfill's memos): transient wire errors back off exponentially, `oversize` and `sensitivity_ineligible` (no backend trusted for the block's sensitivity) park at `infinity` — visible in the memo table, surfaced in status/state.sh with W04-7. **If a migration sits in `paused` with `last_error = "model guard: resolved <X>, expected <Y>"`**: the target backend's model_map lost (or never had) the `embed_next` key resolving to the migration's `to_model` — fix the backend row, then resume; the guard re-checks every cycle and exists because a missing key silently falls back to the OLD model (relabeling old vectors as migrated). The arm maintains a runtime partial index `idx_embedding_next_pending` (created `CONCURRENTLY` when a migration is active, INVALID leftovers from a crashed build are dropped and rebuilt automatically, dropped again once the migration is terminal) — seeing it in the catalog is normal only while a migration exists. Measured backend behavior (2026-07-24, CPU llama.cpp, kv-unified): a parallel embed that overflows the shared pool WAITS (no error path), and even below the pool limit a small interactive embed queues behind a large prefill — at ~20 tok/s CPU prefill a 24k-token block holds a slot for ~19 min, which is what `max_tokens` actually bounds.

**Re-embed migration verify gate (Achse 04 W04-5).** Once the current pending set hits zero (declared `infinity` skips excepted; blocks under a finite backoff still hold), the arm auto-transitions `running → verifying`, stamping the watermark (`verify_started_at`) and clearing any previous `verify_report` — the arm keeps draining post-watermark writes the whole time. In `verifying` a one-shot background runner executes the five-stage gate and stores the verdict as JSONB in `verify_report`: (1) *completeness* — the watermark-scoped pending count must be 0 (skips with an `infinity` memo of this migration are excepted in the SQL predicate itself) and no finite failure memos may remain; the report names the skip list and the `visibility_loss` numbers (skips + archived rows that lose their serving vector at the swap — shown before the operator confirms); (2) *integrity* — dims=1024, L2 norm within ±1 % and `embed_model_next = to_model` on every migrated row, folded into the single quality-scan pass (one sequential table read total — the fp32 TOAST is ~41 GB at 10M); (3) *index build* — `idx_embedding_next_hnsw` (`CONCURRENTLY`, halfvec, m=16/ef_construction=128 = the canonical live parameters) plus the three `_next` sister partial indexes (`idx_embedding_pending_next`, `idx_dream_pending_next`, `idx_guard_pending_next`) that the cutover renames canonically; INVALID leftovers are dropped and rebuilt, a valid index is REUSED (re-runs never rebuild a finished HNSW). At 1M+ set a session-level `maintenance_work_mem` for the build window (~2.8 kB/vector graph; above host RAM the fast path is structurally out — declared Achse-06 limit; (4) *quality* — currently the DEGRADED Overlap@k report (old vs. new neighborhoods, informative only) until the Achse-01 `recall_check` replaces it; (5) *guard sample* — cosine distribution of coexisting live blocks in the new space vs. the strictest live guard thresholds, report-only (a pile-up near `p_threshold_duplicate` means recalibrate thresholds BEFORE confirming the cutover). Verdicts: green → the row STAYS `verifying` awaiting the operator confirm (W04-6/7); red → `paused` with the defect classes in `last_error` and the full finding in `verify_report` — never auto-abort. To re-run after fixing a red finding: `resume` (paused→running); the drained arm re-enters `verifying` with a fresh watermark and the gate runs again. Knobs (hot, global-only): `embed_migration.verify_sample_n` (guard-sample reservoir + report list caps, default 1000), `verify_overlap_k` (default 10), `verify_overlap_samples` (default 16, `0` skips the quality stage).

**Re-embed migration cutover, rollback, cleanup (Achse 04 W04-6).** All three are explicit operator actions (E-04-2; the HTTP/CLI surface lands with W04-7). **Confirm** (`verifying → done`) runs ONE transaction: embed-cache flush first (row deletes, MVCC-safe), completeness re-check under the lock with the identical watermark+memo predicate as the verify gate, then the catalog swap — column renames (`embedding`↔`_old`, `embedding_next`→`embedding`), HNSW rename, and the three partial-index pairs (without which backfill/dream/guard scans would silently seq-scan post-swap) — plus the model_map flip (`embed`→to_model, `embed_next` removed) as a data write in the same tx, and the status CAS. The tx also re-adds a fresh empty `embedding_next` pair so content updates (`ClearEmbedding`) never hit a missing column. After commit: synchronous pool reload, a provenance sweep (serving vectors labeled ≠ to_model are cleared and re-embed via regular backfill), and the migration's `infinity` memos are copied to backfill memos (parked blocks never enter a wire-retry loop). Confirm refuses fail-closed on: non-green/missing verify report, unfindable/non-updatable `embed` model_map row, foreign `embed_next` arming, missing or INVALID `_next` index. It returns visibility_loss + post-watermark transient + sweep count for the operator. On `lock_timeout` (5s) the whole tx aborts and a retry is a new confirm. **Rollback** (`done → rolled_back`, requires a non-empty reason) is the mirror tx — it refuses if any `_old` anchor resource is missing, if a follow-up migration exists, or if the fresh `_next` pair carries data. **Cleanup** (only from `done`) drops the four `_old` indexes by name plus both `_old` columns — after cleanup rollback is impossible (the way back is a new migration in the opposite direction); the permanent `_next` pair stays. **Re-create after rollback**: leftover `_next` data blocks `create` (use `purge`); `ReuseExisting` is only valid on top of an ABORTED migration's leftovers — rollback data is on record as suspicious and is never silently reused.

**Re-embed migration operator surface (Achse 04 W04-7).** The whole state machine is driven through `ctx admin embed-migration <action>` (thin transport over the server-admin-only `/api/manage embed-migration-*` family; every action needs an ADMIN key — a tenant-admin gets 403, the vector space is global and scope-free). The normal run:

1. **Register the target model** in `context_embed_models` (family, native/stored dims, quantization) and arm the target backend's `model_map` with `"embed_next": {"model": "<to_model>"}` (the backend must be local, global-scoped, and carry `RoleEmbed`).
2. **`create --from <model> --to <model> --backend <name>`** — validates both models are registered, dims are equal (v1 refuses dimension changes), the backend is arm-correct, no leftover `_next` data exists, and runs a real statfs disk pre-flight. A refusal (unknown model, dims mismatch, disk insufficient with the actual byte numbers, `another migration is already active`) is surfaced verbatim. Only ONE migration is active system-wide.
3. Start it with **`resume`** (pending→running) and **watch `status`**: `pending` (arithmetic: `total − migrated − failed − skipped`, never a corpus `count(*)`), the two parked-`∞` counts (migration-scoped oversize/ineligible + the independent backfill-scoped set), and `has_verify_report`. `status --exact` adds a true index count (a scan — use sparingly). `--json` (or a non-TTY pipe) emits the raw envelope; `failures` lists the `context_embed_failures` memos (admin-only; `last_error` is already normalized, never raw wire/embed text).
4. **`pause`**/**`resume`** are the CAS transitions (running↔paused). A migration that pauses itself with `last_error = "model guard: …"` needs the backend `model_map` fixed, then `resume`.
5. The arm auto-transitions to `verifying` and runs the gate (W04-5). On green the row STAYS `verifying` — inspect `status` (the rich manage view carries the full `verify_report` WITH block-IDs over all scopes; this is why the endpoint is admin-only and why `/api/status`'s `embed_migration` field is deliberately block-ID- and report-content-free). On red the arm parks in `paused` — fix the finding and `resume` to re-verify.
6. **`confirm`** runs the cutover and prints `visibility_loss` (blocks that permanently lose their serving vector at the swap — skips + archived-with-vector; an informed decision, not fail-silent), `post_watermark_pending`, `sweep_cleared`, `memos_copied`, and the flipped backends. It refuses fail-closed on a non-green/missing report, an unfindable `embed` model_map row, a foreign `embed_next` arming, or a missing/INVALID `_next` index — each verbatim.
7. **`cleanup`** drops the `_old` rollback anchor once you trust the new space. After cleanup the only way back is a new migration in the opposite direction.

**`abort --reason <text>`** (before cutover) and **`rollback --reason <text>`** (after cutover, while `_old` still exists) both require a non-empty reason (refused verbatim otherwise). **`purge`** nulls leftover `embedding_next` data and is refused while any migration is active — it is the follow-up to an abort, and what `create` points you to when `_next` data blocks a fresh run. `create --reuse-existing` adopts an ABORTED migration's leftover `_next` (model must match); rollback leftovers are never silently reused.

The `create` disk pre-flight statfs's the ctx container's own root filesystem (`/`). On the single-host RAID-0 deployment that is the same physical array the DB writes to, so it is a real same-order lower-bound guard; ctxd does not bind-mount the DB data volume, so it is a safety floor, not exact PGDATA accounting — size the headroom generously at 1M+ (design §6.1: ~6.9 kB/vector fp32+HNSW, ×1.2 margin). `state.sh` shows the active migration line plus both parked-`∞` sets (`n/a` on a pre-114 schema).

## Deploy & migrations

`docker compose build ctx` builds the multi-stage Go binary (incl. the embedded Svelte SPA — see [development](development.md)); `docker compose up -d ctx` starts ctx + PostgreSQL.

**Container memory limit.** The `ctx` service ships with a 512 MiB cgroup limit (`deploy.resources.limits.memory`). That is stage 1 of a declared ladder tied to corpus scale: the overview rebuild's in-process compute path measures ~254 MB at the current 200k-node cap, so the previous 256M limit sat directly on the OOM edge — `graph_overview.max_nodes` guards the CPU wall, not memory. Later stages (≥1G at 1M nodes, ≥2–4G toward the 10M target, plus the worker child budget) are design decisions of the Skalen-Pfad axis, not tuning suggestions; raise the limit with the corpus, not preemptively. Migrations run at boot in order. Since migration 108 every applied migration is pinned by a sha256 checksum in `_migrations.checksum`; rows from before 108 (and M031+-style self-record rows) are stamped by an idempotent boot backfill. The backfill attests the embedded file *as shipped in the running binary*, not the historic apply — editing an already-applied migration file surfaces as a `migration_integrity` drift once the schema-contract check (Achse 03) lands. Since v5 the first 113 versions have no file of their own any more (see [the migration baseline](#the-migration-baseline-001113-ship-as-one-file) below); their checksums come from the folded chain instead, and the drift check compares against those with the same severity it always had. Rolling the multi-tenant line out to a running deployment (migrating the production DB from 057 across the 058–068 chain) is a separate operational step; the single-tenant default tenant keeps every path byte-identical until tenants are provisioned — see [multi-tenancy](multi-tenancy.md#self-service-onboarding-v411).

### Dependency graph and Dependabot alerts

GitHub's dependency graph for `go/go.mod` is filled by the CI job `dependency-graph` (`actions/go-dependency-submission`, build target `all`), which submits the module list `go list` resolves on every push to `root` — only from the current tip of `root`, so a re-run of an older run never submits that commit's graph again — for runs whose `ci.yml` carries that guard; a run created before it still submits on a full re-run, so re-run only its `Web Live Tier` job (see `GOVERNANCE.md`, Releases). Dependabot alerts therefore refer to the real module graph, not to a parsed and possibly stale `go.mod` snapshot (until 2026-10-31 GitHub's own parser held a pre-July state and raised an alert on a chi version the module no longer required).

### Shutdown and the LLM-log write path

Every LLM call ctx makes writes one row to `context_llm_log` (the telemetry behind `/api/llmlog`, the 24 h rollup on `/api/status` and the tenant cost budgets). The write is asynchronous so it never delays the call, and it is bounded so it never crowds out the requests that share ctxd's 20-connection database pool:

- **Throttle.** At most **4** inserts run at once; further rows wait in a queue of at most **4 096** rows. Both numbers are fixed in the code (`internal/llmlog`): they bound ctx's own bookkeeping, not a policy anyone tunes. Before this, every row got its own goroutine and connection, so a slow database let a burst take all 20 connections.
- **Losses are counted, not silent.** A row the full queue cannot take is dropped; an insert the database refuses (or that runs past its 5 s deadline) is lost. Both are counted since process start and shown to a server-admin on `GET /api/status` as `"llmlog": {"insert_failures": N, "insert_dropped": M}` — present at `0/0` too, so a zero means "nothing lost", not "not measured". The section is absent on a tenant-admin's view: the counters cover every tenant and the background. In the log, the first loss raises one `WARN` (`llmlog: insert failed, row lost` or `llmlog: insert queue full, row dropped`, with `insert_failures_total`/`insert_dropped_total`), and at most one more per minute after that however many rows are lost; every failure still has its `DEBUG` line. A rising `insert_failures` usually means the database is unreachable or `context_llm_log` is broken (missing table, failing trigger); a rising `insert_dropped` means the queue stayed full — the database has been slow or unreachable for long enough to back up 4 096 rows.
- **Shutdown settles the queue, twice.** On `SIGTERM` ctxd stops HTTP (up to 15 s), ends the model gateway's loops with their final flush (up to 5 s, alongside the next step) and waits up to **5 s** for every queued and running llmlog insert; then it waits for the scheduler to finish its running work, and settles the queue once more (up to 5 s) before it closes the pool. The first settle exists because the scheduler wait has no limit: a dream cycle that is running when the signal arrives is not cancelled, it runs to its end or to `dream.cycle_timeout` (700 s by default). If that outlasts the stop grace period, Docker kills ctxd during the wait — the HTTP side's rows have had their settle by then, and only the rows still queued from the scheduler are lost. The log says which way each settle went: `llmlog: settled at shutdown` (with `after=http` or `after=scheduler`, the elapsed time and the loss totals) or `WARN llmlog: settle at shutdown incomplete, pending rows are lost`.
- **`stop_grace_period`.** Docker waits 10 s between `SIGTERM` and `SIGKILL` unless told otherwise — too short for the 15 s HTTP drain alone. The shipped `docker-compose.yml` sets `stop_grace_period: 30s` on the `ctx` service: 15 s HTTP drain + 2 × 5 s llmlog settle + margin for the scheduler wait; the model gateway's final flush (the batched `last_used_at` stamps of model keys and the last `gateway rejections` lines, at most 5 s, measured in milliseconds; `gateway: usage stamps and rejection counts flushed at shutdown` in the log) runs alongside the first settle and adds nothing. A test pins it at 25 s or more. Keep it at least that long in your own compose file, and raise it if you raise the shutdown budget or want a running dream cycle to finish rather than be killed.

### Upgrading to the next release (after 5.29.6)

- **Backends no longer follow a redirect to another origin.** A row whose `base_url` redirects to another host, port or from `https` to `http` now fails with the redirect status instead of sending the request to the target; `WARN redirect refused` in the log names both origins. Enter the target URL as `base_url` ([Backends](#backends)).
- **Own compose file: set `stop_grace_period` yourself.** If you run ctx from your own compose file rather than the shipped one, add `stop_grace_period: 30s` to the `ctx` service. Without it Docker kills ctxd 10 s after `SIGTERM`, before the HTTP shutdown and the LLM-log settle have finished, and the rows still queued at that moment are lost ([Shutdown and the LLM-log write path](#shutdown-and-the-llm-log-write-path)).
- **New `llmlog` section on `/api/status` (nothing to do).** A server-admin's status frame carries `"llmlog": {"insert_failures", "insert_dropped"}`; scripts that pin the exact key set of the frame must accept it.

### Upgrading to 5.29.5

5.29.5 bundles the fixes from a second, private review of the 5.29.1 fixes and ships migration 157. A single-tenant install (every scope in the default tenant, no tenant-scoped backend rows, no enabled tenant quota, `CTX_OAUTH_DCR_MODE` not `open`) needs no action: migration 157 changes no row there, and the one change its users see is that images in issues and comments load on click. The points below are what an operator should check on a multi-tenant deployment, with tenant quotas, with open OAuth client registration or on an IPv6-only host.

- **Migration 157 runs at boot (nothing to do).** Migration 156 repaired the blocks the pre-156 guard had *archived* against another tenant's block; every other block it had decided kept its decision keys — a review flag, a clean verdict, a block a person kept through `guard-resolve` — with `guard_similarity` and a `guard_matched_id` naming the foreign block. 157 takes every live block whose `guard_matched_id` names an existing block the tenant-bounded guard could not have matched — a block of another tenant, a block in a scope registered to no tenant, or any block outside the own scope when that scope is registered to no tenant — whatever its `guard_status` or lifecycle. Without a person's verdict the guard's decision is handed back: `guard_status = active` and the seven guard decision keys removed (`guard_checked_at` included, so the next guard batch re-checks a block it still checks inside its own tenant and restores a review flag where a real near twin exists there). A verdict a person gave through `guard-resolve` (`keep` or `archive`) stays: such a row loses only the keys that point at the foreign block (`guard_matched_id`, `guard_similarity`, `guard_is_cross_scope`), keeps its `guard_status` and trace and is not put up for a verdict again. Every touched row is marked `metadata.guard_repair = 'M157'`. Empty, malformed and dangling matches are left alone, no row is un-archived, the statement is idempotent, and an install whose blocks all sit in scopes registered to the default tenant changes no row. To list what it touched: `SELECT id, scope, category, title, guard_status, metadata->>'guard_resolution' AS resolution FROM context_blocks WHERE metadata->>'guard_repair' = 'M157'` ([Migration 157](#migration-157-live-guard-decisions-that-name-a-match-outside-the-tenant)).
- **`guard_matched_id` is redacted on two more paths.** The block that `manage update` returns and the issue reads (`issue-get` with its thread, `issue-update`, `/api/project/{id}/issues…`, MCP `issue_*`) drop `metadata.guard_matched_id` when the matched block lies outside the caller's scopes, as `get` and `search` already did. The update responses judge against the key's write scopes, so a key that may read but not write the matched scope sees the field on `get` and not in the update response. Stored metadata is unchanged.
- **The shared-secret opt-in is bound to the operator's provider host.** A tenant row reaches an operator (`_global`) secret behind `tenant.allow_shared_secrets` only when a `_global` row with the same `api_key_ref` has the same origin (scheme, host and port of `base_url`; case, an explicit default port and the path do not count). The write gate and the resolver apply the rule on every pool reload: a row that leaned on the fallback from any other host goes **keyless** at the first reload after the upgrade, `backend-create`/`-update` answer it `422`, and an operator who later moves or deletes its row leaves the tenant rows that relied on it keyless the same way. Revoking the opt-in now takes effect at once — a tenant-scope settings write reloads the backend pool. List the rows that depend on the fallback (no tenant-scope secret of that name) next to the operator rows that carry the same ref, and compare the origins:

  ```sql
  SELECT t.name, t.scope, t.base_url AS tenant_url, g.name AS operator_row, g.base_url AS operator_url
    FROM context_backends t
    LEFT JOIN context_backends g ON g.scope = '_global' AND g.api_key_ref = t.api_key_ref
   WHERE t.scope <> '_global' AND coalesce(t.api_key_ref, '') <> ''
     AND NOT EXISTS (SELECT 1 FROM context_secrets s WHERE s.name = t.api_key_ref AND s.scope = t.scope)
   ORDER BY t.scope, t.name;
  ```

  If its tenant had the opt-in, a listed row whose `tenant_url` matches none of its `operator_url` origins (or that has no `operator_row`) sent the operator key named by its `api_key_ref` to a host the tenant chose: rotate that key ([multi-tenancy — scope-bound `api_key_ref`](multi-tenancy.md#backend-pool-isolation-egress)).
- **`backend-list` withholds `api_key_ref` on rows the caller cannot write.** A tenant-admin sees the `_global` rows without the operator's secret names (the field is absent, not empty); its own rows, and every row for a server-admin, are unchanged, and the backend settings table shows a withheld ref as managed at server scope. Scripts that read `api_key_ref` from a tenant-admin listing must treat the field as optional.
- **Embed cache: one manual flush if tenant embed rows ran before 5.29.1.** If tenant-scoped embed rows were in use before 5.29.1, empty `context_embed_cache` once (`DELETE FROM context_embed_cache`; the cache refills on demand). Entries such a row wrote under the operator's model name cannot be told apart from the operator's own; every `_global` hit refreshes their `last_access`, so the 30-day TTL never reaches them, and the automatic coupled-set flush at the first boot fires only when the tenant row's host/protocol pair differed from every `_global` embed row's. Installs that never had a tenant embed row have nothing to do.
- **Embed-equivalence flag and role decisions.** A tenant-admin keeping `metadata.embed_equivalence_verified` on a row can no longer change which of `embed`/`dream-embed` the row carries or the model either of them resolves to (`422` on `metadata`); for such a change a server-admin re-runs the equivalence probe. Everything else on a flagged row (chat roles, priority, limits) stays the tenant-admin's to change. Decisions that depend on whether a role exists — the dream-embed bootstrap split, the rerank cross-encoder vs. LLM-judge choice, the topic labeller's no-backend state — are now made in the caller's tenant view: a tenant row carrying `dream-embed`, `rerank` or `digest` no longer switches those modes for other tenants.
- **`{"enabled":false}` brakes every row.** `backend-update` with exactly that payload skips the validation guards, so a tenant row that every other write answers with `422` — an operator `api_key_ref` without the opt-in or off the operator's host, a private `base_url` — can be disabled by its tenant-admin or a server-admin. Any other key next to it, and `enabled:true`, take the fully gated path: re-enabling or editing such a row needs the row fixed first (or deleted).
- **Tenant cost budgets count provider-reported cost; web chat now books it.** This and the next two points only matter with an enabled `context_tenant_quota` row; without one every gate stays a no-op. `daily_cost_usd`/`monthly_cost_usd` add up `context_llm_log.cost_usd`, which ctx fills only from the `usage.cost` that **openrouter-class** backends report; ctx keeps no price list. A backend that reports no cost (`protocol: anthropic` on either path, a generic `/v1` server) books `NULL`, so on such a backend only `daily_calls` bounds a tenant. Before you rely on a cost cap, list the enabled external backends whose `provider_class` is not `openrouter` and that serve chat, synthesis or translate roles a quota'd tenant can reach. A streamed web-chat turn on an openrouter-class backend now writes `cost_usd`, the served model and `metadata.provider_request_id` on its `web-chat` row, like the non-streaming pipelines; tenants that chat on OpenRouter reach their cost budget sooner than before. Rows written before the upgrade stay `NULL`; nothing is backfilled.
- **More of the query path is gated.** The web chat's `ctx_query` tool runs under the session owner's scope: its embed and rerank chains, the quota gate and the tenant config overlay use that scope, so a tenant over its budget gets a failed tool call (`query failed`) instead of free retrieval, and a tenant-private embed or rerank backend now serves the tool (before: `embedding failed`); block grants still do not apply to chat tools. Query translation and the temporal LLM fallback are gated too: a tenant over its call budget makes neither call (the request still ends in the embed step's `429`), and `external_off` drops an external translate backend (the query keeps its original text). `POST /api/project` refreshes the quota accountant like `scope-create`, so a new project scope is gated at once instead of after up to 30 s. Cross-encoder rerank rows now carry `api_key_id` and count towards `daily_calls`: with `rerank.enabled=true` and a cross-encoder backend every reranked query is one more attributed call, so a `daily_calls` value tuned before the upgrade may be reached sooner.
- **The MCP `query` tool reports refusals as errors.** A refused query (`quota_exceeded`; also `no_eligible_backend`, including a refusal inside the synthesis path's already committed `200`) is an `isError` tool result naming the code (`query refused: quota_exceeded`), where it used to be an empty answer that read as "nothing found"; another HTTP error status without an error text becomes `query failed (HTTP <status>)`. MCP clients that took empty answers for "no results" will see errors instead ([multi-tenancy — cost/call quotas](multi-tenancy.md#costcall-quotas)).
- **SSE frame cap (nothing to do).** Both stream parsers (openai and anthropic wire) measure a frame as its data lines arrive: each line weighs its length plus the newline that joins it, so the 4 MiB frame cap bounds the dispatched payload exactly and a frame of empty `data:` lines reaches it too, at a constant cost per line instead of one that grew with the frame. A read error mid-stream — a line over the frame cap, the 64 MiB stream cap, a broken connection — now ends the turn with that error instead of first dispatching a frame buffered without its blank line. One visible difference: a connection that breaks after `data: [DONE]` but before its blank line used to count as a finished turn and is now a read error; at EOF in the same place the turn is still accepted. No setting changes.
- **Images in issues and comments are click-to-load.** Issue bodies and comments — issues mirrored by forge sync included — no longer load remote images on render; as in chat answers, each image shows a placeholder with its host and path and loads only when the viewer clicks **Load image**, one click per image. `POST /api/img/sign` accepts one URL per request and only `origin:"assistant"` (also the default when the field is absent); a request with several URLs is `400`, and so is any other origin, `issue` included. Clients that call the endpoint directly must send a valid origin (or none) and one URL per request. Browser tabs opened before the upgrade keep the old bundle until reloaded and fail closed: their issue and comment images stay placeholders ([security — image proxy and LLM output](security.md#image-proxy-and-llm-output-camo)).
- **The OAuth consent warning follows the requested callback.** Only deployments with `CTX_OAUTH_DCR_MODE=open` see a difference. The `/authorize` consent screen no longer warns about a self-registered client when the `redirect_uri` of that request is an exact member of the static allowlist (`https://claude.ai/api/mcp/auth_callback`, `https://claude.com/api/mcp/auth_callback`, `https://chatgpt.com/connector_platform_oauth_redirect`) or of `CTX_OAUTH_REDIRECT_EXTRA`. Every other callback keeps the warning — loopback included, and the foreign entry of a client that registered a vetted and a foreign callback together. Admin-mode and `ctx mcp add` clients never showed it. Because an entry in `CTX_OAUTH_REDIRECT_EXTRA` now also suppresses the warning, list only callbacks you vet ([security — web login, OAuth & SSRF hardening](security.md#web-login-oauth--ssrf-hardening)).
- **Boot warning in open registration mode.** With `CTX_OAUTH_DCR_MODE=open` ctxd logs one `WARN` at startup (`oauth: dynamic client registration is open …`, attribute `env=CTX_OAUTH_DCR_MODE`); `off` (the default) and `admin` stay silent. If the line appears and open registration is not intended, unset the variable.
- **OAuth client names lose invisible characters.** `client_name` at `/register` drops Unicode format characters (bidi controls, zero-width characters, BOM, tag characters) and control characters before it is stored, and the consent page applies the same filter to every stored label when it renders. Existing rows are not rewritten (the render filter covers them); to list labels carrying the common ones: `SELECT client_id, label FROM context_oauth_clients WHERE label ~ '[[:cntrl:]\u200B-\u200F\u202A-\u202E\u2060-\u206F\uFEFF]'`.
- **NAT64 egress.** The SSRF guard no longer refuses the whole NAT64 well-known prefix `64:ff9b::/96`: such an address is judged by the IPv4 address it embeds, so an IPv6-only host behind DNS64 reaches public IPv4-only IdP, forge, image and tenant-backend hosts again, while every embedding of a refused IPv4 range (loopback, RFC 1918, link-local, CGNAT …) stays refused. `64:ff9b:1::/48` (local use) stays refused whole. A tenant row whose `base_url` is a literal `64:ff9b::` address of a public IPv4 is accepted on write. This supersedes the NAT64 part of the 5.29.1 note on the egress deny-list.
- **Chunk ingest reports failures in the body.** `POST /api/ingest` in chunk mode answers `200` even when chunks fail: `success: false`, `failed > 0`, and `results[i].status = "failed"` with an `error` (for example `source not found` for a source outside the key's home scope, the rule since 5.29.1). Scripts must read the body, not only the status. ctxd has no endpoint that creates `context_sources` rows; create them out of band in the ingesting key's home scope.

### Upgrading to 5.29.1

5.29.1 bundles the fixes for the privately reported 2026-10-31 advisories. A single-tenant install (every scope in the default tenant, no tenant-scoped backend rows, OAuth clients created with `ctx mcp`) needs no action; the points below are what an operator of a multi-tenant or OAuth-exposed deployment should check before or right after the upgrade.

- **Tenant backend rows and operator secrets.** A tenant row's `api_key_ref` now resolves in the row's own scope; a row that named an operator (`_global`) secret goes **keyless** unless its tenant has `tenant.allow_shared_secrets`. Audit with `SELECT name, scope, api_key_ref FROM context_backends WHERE scope <> '_global' AND coalesce(api_key_ref,'') <> ''` and rotate every operator key such a row referenced ([multi-tenancy — scope-bound `api_key_ref`](multi-tenancy.md#backend-pool-isolation-egress)).
- **Tenant backend hosts.** A tenant row whose `base_url` names a loopback, private, link-local or docker-internal host (or a literal IP in any range the SSRF deny-list refuses) fails on its next call and is rejected on its next write; a `?` or `#` in `base_url` is rejected on the next write for rows of every scope. LAN backends are a `_global`-only choice now; the audit query is in [multi-tenancy — backend pool isolation](multi-tenancy.md#backend-pool-isolation-egress).
- **OAuth `grant_types` are enforced.** `/token` honours the client's registered grants: a DCR client registered with the old default `grant_types={authorization_code}` receives no refresh token any more (new registrations default to both grants; operator clients created with `ctx mcp` keep both). If those clients should keep refreshing: `UPDATE context_oauth_clients SET grant_types='{authorization_code,refresh_token}' WHERE registration_source='dcr' AND grant_types='{authorization_code}'`. Deleting a client now also revokes its tokens ([security — web login, OAuth & SSRF hardening](security.md#web-login-oauth--ssrf-hardening)).
- **Browser login checks the origin.** `POST /auth/login` requires `Content-Type: application/json` and an `Origin`/`Referer` of this server's own host (the canonical issuer or the request `Host`). Behind a reverse proxy that rewrites `Host`, set `CTX_CANONICAL_ISSUER`, or the web UI login answers `403`; CLI clients that send none of these headers are unaffected.
- **Wider egress deny-list.** IdP, forge, camo and tenant-backend egress now refuse every IANA special-purpose range, among them CGNAT `100.64.0.0/10` (Tailscale addresses), `198.18.0.0/15`, NAT64 and 6to4; an IdP or image host reachable only on such an address stops working. For NAT64 that held up to 5.29.4: since 5.29.5 an address in the well-known prefix `64:ff9b::/96` is judged by the IPv4 address it embeds (a public IPv4 passes, an embedded refused range stays refused), and only NAT64 local-use `64:ff9b:1::/48` stays refused whole ([Upgrading to 5.29.5](#upgrading-to-5295)). The SSO client ignores `HTTP(S)_PROXY` and dials direct.
- **Data repair and maps.** [Migration 156](#migration-156-the-duplicate-guard-never-looks-across-tenants) un-archives blocks the duplicate guard had archived against a block of another tenant (nothing to do; an install whose scopes are all registered to the default tenant repairs zero rows). The repair as first shipped could abort the migration, and with it the boot, on a database with an archived row beside a live twin of the same title; it was amended after 5.29.2 ([Migration 156](#migration-156-the-duplicate-guard-never-looks-across-tenants)). Topic and root maps written by `POST /api/digest` before the fix can still hold entries from scopes another tenant granted; they are clean only after a rebuild ([multi-tenancy — background pipeline isolation](multi-tenancy.md#background-pipeline-isolation)).
- **Quotas bind the tenant.** A tenant quota now applies to every scope of the tenant and also gates web chat, the query embed and the rerank leg, so an over-budget tenant gets `429 quota_exceeded` on retrieval-only queries too ([multi-tenancy — cost/call quotas](multi-tenancy.md#costcall-quotas)). `/api/ingest` has its own write rate-limit bucket (`query.rate_limit_write`, counted per request, not per chunk).
- **Images in assistant answers are click-to-load.** The web chat no longer fetches remote images in model output on render; each one shows a placeholder and loads on click, and the image proxy refuses URLs with a query string, userinfo or a path over 512 bytes ([security — image proxy and LLM output](security.md#image-proxy-and-llm-output-camo)).

### CLI rollout: the envelope exit-code contract (v5.15.0)

**Release note.** v5.15.0 changes what the `ctx` CLI does with a failed call. Two dozen command paths used to print the server's `{"success":false,…}` answer to stdout and exit **0**; they now exit **1** with the reason on stderr. The response is still printed to stdout first, so `ctx stats | jq` and every other pipe keeps its bytes — only the exit code and stderr are new. Success paths are byte-identical. The affected commands are `stats`, `categories`, `get`, `delete`, `list-meta`, `digest`, `save`, `search`, `query --json`, `manage`, `dream` / `dream stats` / `dream review` / `dream enable` / `dream disable` / `dream throttle`, `mcp` / `mcp list`, `mcp delete`, `keys` / `keys list`, `keys delete` and all three `block-grant` verbs. Two of them also change their output, and only those two: `ctx keys list` and `ctx mcp list` answered a `403` with *"No API keys provisioned."* / *"No MCP clients registered."*, which is now the server's reason on stderr instead. `ctx health` (no envelope on `GET /health`) and the silently degrading hook surfaces (`brief`, `persist`, `statusline`, `ingest`) are unchanged, as is `ctx contract` with its own 0/1/2/3 scale. `ctx api` keeps its exit codes and now prints the failed response body its documentation always promised. The full table is in [the CLI reference](cli.md#exit-codes-one-contract-for-every-command).

**This is a server-independent change.** The wire contract did not move: an old CLI against a new server and a new CLI against an old server both behave exactly as before the upgrade, apart from the exit code the new CLI produces locally. There is no ordering requirement between updating the daemon and updating a host.

**Rollout, per host.** The CLI is a release asset, not part of the container, so each host that has `ctx` installed updates on its own schedule:

```bash
ASSET="ctx-$(uname -s | tr A-Z a-z)-$(uname -m | sed 's/x86_64/amd64/;s/aarch64/arm64/')"
ctx version                       # what this host runs today
curl -fsSL "https://github.com/GottZ/ctx/releases/latest/download/$ASSET" -o /usr/local/bin/ctx
chmod +x /usr/local/bin/ctx
ctx version                       # confirm the hop
```

Run `ctx version` on **every** host before and after, and note which hosts are on which side — a mixed fleet is fine, but a script that was written against exit 0 fails only on the hosts that already hopped.

**What to check before you update a host.** Anything that calls `ctx` and does not want to stop on a failure: `set -e` shell scripts, cron jobs, git hooks, CI steps, `backup.d` hooks. The commands above now propagate a failure where they used to swallow it — that is the point of the change, but a script that ran daily *through* a `403` will now stop. Grep for them:

```bash
grep -rn 'ctx \(stats\|save\|search\|get\|delete\|digest\|manage\|list-meta\|query\)' /etc/cron.d /etc/crontab ~/bin /usr/local/bin
```

Sonde of 2026-09-05 on the maintainer's own fleet: no consumer of the old exit-0 behaviour found locally, on `spark` or on `home`; `herbert` was not checked.

**Rollback** is a re-download of the previous asset — the binary carries no state and writes no schema:

```bash
ASSET="ctx-$(uname -s | tr A-Z a-z)-$(uname -m | sed 's/x86_64/amd64/;s/aarch64/arm64/')"
curl -fsSL "https://github.com/GottZ/ctx/releases/download/v5.14.0/$ASSET" -o /usr/local/bin/ctx
chmod +x /usr/local/bin/ctx
```

### The migration baseline: 001–113 ship as one file

v5 requires the v4.x hop (see [migration 133](#migration-133-the-backend-tuple-rows-are-deleted--and-the-upgrade-hop-that-has-to-come-first) below), so every database that reaches it through the supported path has already applied migrations 001–132. That made the first 112 files dead weight on the upgrade path and pure setup cost on the fresh-install path, and v5 replaces them with a single `113_baseline.sql`. The chain is 21 files instead of 132; nothing about what a database ends up containing changed.

**Which path your database takes is decided the same way it always was** — by version number in `_migrations`, not by inspecting the schema:

- **Fresh install.** `_migrations` is empty, version 113 is missing, the baseline runs, then 114–133 run on top of it. The baseline records all 112 folded versions under their original filenames and checksums, so a fresh v5 database and one upgraded through v4.38.0 carry identical `_migrations` content — including for the sake of a later downgrade, which skips by version and therefore still finds every version it knows.
- **Upgrade from v4.38.0.** Version 113 is present, so the baseline is skipped exactly the way any applied migration is skipped, and only 133 runs.
- **A database that stopped somewhere below 113.** The runner refuses it by name — `database predates the migration baseline: highest applied migration is N` — instead of rebuilding over a live schema. The fix is the hop: bring it to v4.38.0 first, then come back. This is the one case where skipping the hop stopped being merely manual and became a hard stop.

**The deleted files are still readable.** They are embedded verbatim inside the baseline, between `-- @@ ctx-fold` markers, and `migrations.Section("051_settings_store.sql")` hands any of them back byte for byte. That is what makes the checksums the baseline writes into `_migrations` verifiable rather than copied: a unit test hashes every section against the value recorded before the fold. Two files (043, 044) carried their own `BEGIN;`/`COMMIT;` block; those four lines are gone, because the runner supplies the transaction and an inner `COMMIT` would have ended the baseline's atomicity halfway through.

**The comments inside the baseline are a record of a state, not a description of the current one.** Three `TODO(multi-tenant)` markers survived the fold — on `context_settings.scope` (`113_baseline.sql:5063`), on `context_secrets.scope` (`:5094`) and on `context_backends` (`:5317`) — and all three name work that has since landed: per-tenant settings resolve through `internal/settings/overlay.go` and `loadTenantOverrideRows` (`internal/settings/reload.go`), per-tenant secrets through `BuildFromRowsScoped` in the same file, and `context_backends` got its scope dimension from the folded ex-062 section of the very same baseline (`:6144 ff.`, `uq_backends_scope_name`). They are not corrected in place, and that is deliberate: the running binary hashes the embedded file (`internal/schemacontract/check.go:140`) against `_migrations.checksum`, so editing an applied migration — a comment included — surfaces as `migration_integrity` drift. **Read a migration as the protocol of the state it was written in; the current truth about tenancy is in the Go tree.**

**One operational consequence worth knowing:** the baseline is one file, so it is one transaction. A fresh install that fails partway through leaves nothing behind and is recovered by booting again — where the old chain could leave a database stranded between two applied migrations.

### Migration 116 (link-write NOTIFY): prefer a write-quiet window

Migration 116 installs the graph-cache dirty signal — five triggers plus one function across `context_dream_links`, `context_structural_links` and `context_blocks`. `CREATE`/`DROP TRIGGER` is a **metadata-only** change (milliseconds of actual work once the lock is held), but it takes `ACCESS EXCLUSIVE` on all three tables. Behind a long-running reader or writer — an Ego-graph hop, a dream batch, a bulk import — the migration queues on that lock and every subsequent reader and writer queues behind *it*. At 1M+ blocks that is the difference between an unnoticed boot step and a stalled instance.

Two consequences for the deploy:

- **The file carries `SET LOCAL lock_timeout = '2s'`.** If the lock is not granted within two seconds the migration aborts with SQLSTATE `55P03` (`lock_not_available`) instead of holding the queue open. The migration runner (`internal/store/migrations.go`) has **no** `55P03` retry: the failure propagates and boot fails. That is deliberate — the recovery is the next boot attempt, not a retry loop that keeps re-queuing for the same lock.
- **The re-run is safe.** Each migration file runs inside its own transaction; on any error the runner rolls that transaction back and does not record the version, so a `55P03` abort leaves the schema exactly as it was — no half-installed trigger set. Simply restarting ctx re-runs 116 from a clean state. Doing that in a write-quiet window (no dream cycle, no forge sync, no bulk import in flight) is what makes the first attempt succeed.

The migration is idempotent beyond that (`CREATE OR REPLACE FUNCTION` + `DROP TRIGGER IF EXISTS`), adds no table and no column, and needs no backfill: the graph cache is derived in-process state whose baseline is the boot rebuild.

### Migration 123: the overview meta table records every rebuild *attempt*

`graph_overview_meta` used to describe successful rebuilds only — the row is written by the persist transaction, so a run skipped by `graph_overview.max_nodes`, killed by `graph_overview.rebuild_timeout`, or returned early because the rebuild is disabled or the block-type registry is unwired left nothing behind but a log line. `computed_at` then stands still in all of those cases exactly as it does after a successful rebuild, and a consumer of the aggregates cannot tell "fresh" from "frozen for weeks".

Migration 123 adds three columns and drops one default:

| Column | Meaning |
|---|---|
| `last_attempt_at` | when a rebuild was last **attempted** for this partition — every outcome, including the skipped ones. `computed_at` keeps meaning the last **success**. |
| `skip_reason` | `NULL` = the last attempt succeeded. Otherwise `node-cap`, `timeout`, `error`, `disabled`, `registry-unwired` (partition frozen, `computed_at` is stale) or `advisory-lock`. |
| `candidate_n` | node candidates **of this scope** at the last attempt (`visible ∩ overview.include`) — the coverage denominator and the distance to `max_nodes`. Never a cross-scope total. |

`advisory-lock` is **contention, not a freeze**: it means another instance was rebuilding that partition successfully at that moment. Treat it as an attempt timestamp, never as a cap.

### Migration 130: the rebuild run journal

Migration 123 gave `graph_overview_meta` a per-scope *attempt* stamp. That answers "is this partition frozen?", and it is deliberately overwritten by the next attempt — it is **state**, not history. Migration 130 adds the missing half: `graph_overview_run`, one row **per rebuild attempt**, kept for `graph_overview.run_retention`.

The reason it is a separate table rather than more columns on `_meta` is not tidiness. A scale path needs phase durations, peak RSS, the partition hash and the effective node cap *per run*; folding them into a row that is replaced every cycle would delete the history at every rebuild.

**The row is written in two phases, by the parent process, outside the persist transaction.** The rebuild itself runs in a worker *child*, and `graph_overview.rebuild_timeout` kills it with SIGKILL and no grace period — a killed child writes no result. A journal that only recorded finished runs would therefore be blind to exactly the runs that die at the time or memory budget. So the parent inserts a row with `outcome = 'running'` *before* it spawns the child and updates it afterwards:

- **an open row with no `finished_at` is the SIGKILL/OOM evidence**, not a bookkeeping glitch;
- child-side columns stay `NULL` on that path — `NULL` means "not measured", where `0` would be a claim nobody made;
- at boot, `running` rows older than twice the rebuild budget are closed as `failed` / `killed` (a live daemon would long since have finished them).

This matters operationally right now: the current in-process compute path peaks at ~423 MB at the 200k-node cap against a 512 MiB container limit, and the parent's graph cache is not included in that figure. An OOM kill is a realistic outcome, and this table is where it becomes visible.

| Column group | What it answers |
|---|---|
| `outcome`, `skip_reason`, `started_at`, `finished_at` | did the run finish, and why not |
| `load_ms`, `cluster_ms`, `persist_ms`, `lock_held_ms` | where the wall clock went. `lock_held_ms` is measured from **lock grant** to commit — waiting for the lock is not holding it |
| `peak_rss_kb`, `parent_rss_kb` | the cgroup budget is shared by parent and child, so a child peak without the parent load has no denominator |
| `node_n`, `edge_n`, `dangling_n`, `selfloop_n` | the input cut. `dangling_n` counts edges whose other endpoint is outside the node cut — previously discarded in silence (~7.5 % live) |
| `max_nodes_eff` | the cap value **this** run used, so an inherited default is distinguishable from a chosen one |
| `partition_hash` | SHA-256 over the canonical partition — the anchor that turns "the clustering changed" from a suspicion into a diff |

`graph_overview.run_retention` (`CTX_GRAPH_OVERVIEW_RUN_RETENTION`, seconds, default 90 d, hot) trims the journal in batches after the rebuild tick, never inside the persist transaction. `0` keeps every row — a deliberate forensic window, not an accident.

### Migration 131: `dream_last_inert` — the inert standing survives its stamp

A dream cycle that writes no links stamps its block *further up* the same back-off curve (`dream.backoff_inert_offset`); until now that outcome lived only inside the resulting `dream_cooldown_until` value and was lost the moment you asked "what would this block's cooldown be under a *different* policy?". Migration 131 adds `context_blocks.dream_last_inert` (boolean, default `false`, metadata-only ADD COLUMN — no table rewrite at any corpus size): `SetDreamCooldown` records the cycle outcome alongside the stamp, and the `dream-backoff-restamp` manage action reads it to re-evaluate the whole corpus under a freshly saved policy **without** collapsing inert blocks onto the active base (at the default offset 7 / exp 1.6 that collapse would re-open mature inert blocks a factor ~29 too early and flood the dream queue after every save).

No backfill, deliberately: historic stamps do not carry their policy generation, so the inert outcome is not reconstructible. Existing blocks read `false` on their *first* restamp (back-off only delays, never loses links) and converge to the true value with their next completed cycle.

### Migration 132: the embed-cache coupled fingerprint — and the one-time cleanup it does *not* do for you

A base_url or protocol change on a serving-eligible embed row moves the vector space while the model name — the cache key — stays put. The NOTIFY listener flushes `context_embed_cache` when that happens (see [Environment variables](#environment-variables), the `mut` column). That covers every edit made while ctx is *running*, and structurally nothing else: an edit applied by `psql` in a maintenance window with the container stopped emits no notification, and the next boot takes its in-memory comparison baseline from exactly that already-edited pool. The diff is then empty by construction and old vectors keep answering.

Migration 132 adds `context_embed_cache_meta`, a single row holding `coupled_fingerprint` — a sha256 over the sorted `(host, protocol)` pairs of all serving-eligible `embed` / `dream-embed` backends. It is the only witness of that topology that survives a restart. On boot, right after the backend pool loads, ctx compares the pool against the stamp on record: **differ → flush the embed cache and re-stamp; equal → do nothing.** The stamp advances only after a *successful* flush, so a failed one is retried by the next boot (and by the next coupled write) instead of being silently marked done. Model-only changes still do not flush — the cache keys on the model and addresses different rows by itself.

**The one operator step, once per installation.** The migration deliberately seeds no fingerprint, and the first boot after the upgrade **stamps without flushing**. That is a chosen trade-off: flushing there would force a complete embed warmup on *every* installation of this upgrade in order to heal the minority that ever moved its embed host. If yours is in that minority — if this deployment has at any point in its history changed `CTX_EMBED_HOST`/`_PROTOCOL` or edited the `base_url`/`protocol` of an embed-role pool row — clear the historic residue once, at a moment of your choosing:

```bash
docker compose exec db psql -U "$CONTEXT_DB_USER" -d "$CONTEXT_DB" \
  -c 'DELETE FROM context_embed_cache;'
```

The cache refills from normal traffic; there is no state to restore. If the embed host was never moved, do nothing — from the seeded stamp on, the offline window is closed for good. The stamp is diagnostic, too: `SELECT coupled_pair_n, updated_at FROM context_embed_cache_meta;` reads as "this many embed connection identities were on record as of then".

### Migration 133: the backend tuple rows are deleted — and the upgrade hop that has to come first

The 29 `chat.*` / `chat_fallback.*` / `embed.*` / `dream.*` / `dream_embed.*` / `rerank.*` connection keys left the settings registry in v5.0.0 (see [Retired: the backend tuple env vars](#environment-variables)). Migration 133 removes what is left of them in the database: every `context_settings` row on one of those keys, **in every scope** — the global ones and the tenant-scoped `*.api_key` overrides alike. It touches no schema and no other key.

Deleting rather than leaving them inert is the point. An unregistered key's row is ignored, but only for as long as nobody registers that name again; the day a future release ships something called `rerank.model`, a years-old row would quietly become live configuration on every installation that still carried it — with no warning, nothing in the settings list, and no reference visible from the secrets API. After this migration the rows do not exist, so they cannot come back.

**What it tells you.** When it actually deletes something, the migration writes three lines into the boot log (`docker compose logs ctx`): how many rows went, that their values live in the backend pool now (`ctx backends list`), that this upgrade is supported **from the 4.38 line only** — if you jumped here from anything older, roll back, migrate to last 4.x, verify the pool, then come back — and where the deleted values are. On a database that has no such rows it says nothing.

**The v4.x hop is mandatory.** Reach the last v4.x release — **v4.38.0** — before you move to v5.0.0. Not "preferably": v4.38.0 is the last binary that still reads the tuple env vars, and one boot on it is what carries a configuration that only ever existed in `.env` across into the backend pool, using code that has been running in production instead of a value you retype from memory. It is also the release that names every tuple var and every leftover settings row you still have, one WARN line each, so the cleanup list is produced for you rather than reconstructed. Skipping the hop costs you differently depending on how old the database is. From **v4.19.0** (migration 113) onwards it is not fatal but it is manual: on v5 the env bridge is gone, an unseeded pool boots empty and degraded-by-design (`/health` `unhealthy`, boot advisory `backend_pool: empty`), and you fill it by hand with `ctx backends seed` from whatever you know your topology to be. **Below v4.19.0 it is fatal by design**: v5 folds migrations 001–113 into one baseline, so a database that never applied 113 has no path forward inside the v5 binary and the runner says so instead of guessing — `database predates the migration baseline` (see [the migration baseline](#the-migration-baseline-001113-ship-as-one-file)). Such a database must go through a v4.x release first; v4.38.0 is the one to pick.

The cohort where skipping it actually costs something is the oldest one: an installation upgrading from **before migration 053** never had a backend pool at all, so its topology lives *only* in the env vars and settings rows. For it the hop is the entire migration — boot v4.38.0 once, let it populate `context_backends`, verify with `ctx backends list`, then go to v5. Jumping straight from a pre-053 release to v5 does not land anywhere at all: such a database is also below migration 113, so the v5 binary refuses to migrate it (see above) and the hop is not a recommendation for this cohort but the only way in. Once it is on v4.38.0 the usual rules apply — verify the pool before moving on, because after migration 133 has run the settings rows are gone and the audit query below is the only machine-readable record of what the values were.

**Do not roll over this upgrade.** Take the old container down before the new one comes up — no rolling deploy, no two versions serving side by side while migration 133 runs. The migration's row deletes emit NOTIFY events that drive any still-running old binary into a full settings reload, and there its registry still knows the 29 keys: the deleted overrides fall back to env → default under it. How much that costs depends on which old version overlaps. From **v4.37 onwards** it is close to cosmetic — those binaries stopped reading the tuple fields at runtime (serving has come from the pool since 053), so a lost `chat.host` override changes a status display and not a route. With a **pre-v4.37** binary in the overlap it is real: those versions still consume the config fields, so the fallback puts them on the registry default `localhost:11434` and they serve against it. In the documented single-compose deployment — `docker compose up -d` stops the old container before starting the new one — this window does not exist at all.

**Recovering a value.** Every delete is recorded by the ordinary settings audit trigger as an `unset` with the old value attached, marked with the migration's request id:

```bash
docker compose exec db psql -U "$CONTEXT_DB_USER" -d "$CONTEXT_DB" -c \
  "SELECT entity_key, scope, old_value FROM context_settings_audit
    WHERE metadata->>'request_id' = 'migration-133-retire-backend-tuples';"
```

Restore what you find **into the backend pool** (`ctx backends`), not as a settings row — writing these keys back through the settings API is not possible any more, and on v4.37 and later it was already refused. Two consequences worth planning for: keep the `CTX_*` tuple variables in your `.env` until the v5 boot is verified — after this migration they are the only remaining source a rollback to 4.x can read — and check `GET /api/secrets` afterwards for sealbox entries whose `referenced_by` is now empty, because a deleted `*.api_key` row took its reference with it while the secret itself stays.

### Migration 152: the rows of the keys that had no successor are deleted

`distill.local_only` and `root_map.label_budget` left the settings registry in v5.16.0. Migration 152 removes what is left of them in the database: every `context_settings` row on those two keys, **in every scope** — both were hot-mutable and therefore writable per tenant through `PUT /api/settings`, so a global-only delete would leave exactly the rows nobody can see. It touches no schema and no other key.

**This is not the Migration 133 situation.** Those 29 keys had a destination — their values moved into the backend pool, and the runbook section above is mostly about getting them there. These two have none. `distill.local_only` never lowered anything: the distill call sets that flag fixed in code, with or without the key. `root_map.label_budget` was a cap without a subject: nothing outside its own tests ever read it. ### Migration 153: the rows of the keys whose subject is gone are deleted

`distill.source_path`, `distill.source_label` and `distill.session_quiet_for` left the settings registry in v5.17.0. Migration 153 removes what is left of them in the database: every `context_settings` row on those three keys, **in every scope** — all three were hot-mutable and therefore writable per tenant through `PUT /api/settings`, and a global-only delete would leave behind exactly the rows the boot sweep is worst at surfacing, because the full settings reload reads `_global` alone. It touches no schema and no other key.

**Why this is its own vintage and not part of 152.** Two reasons that fall together. [Migration 152](#migration-152-the-rows-of-the-keys-that-had-no-successor-are-deleted) is landed, applied and frozen, and it is pinned to its own key list by set equality — three more names in that list would have turned the pin red with no repair path. And the reason for the retirement is a different one: the keys of that vintage had no successor because their **value** led nowhere, while these three have none because their **subject** is gone. They configured the reader over a foreign agent runtime's read-only state database — which file to open, what to call it in the run journal, how long its sessions had to be quiet — and that reader, together with its adapter, fell whole in v5.17.0. The distiller arm keeps running; its source is the compaction checkpoints of this store's own corpus.

**`distill.ctx_source_label` and `distill.ctx_quiet_for` are not renames of the deleted keys.** They are the checkpoint source's own keys, minted with that source and live ever since, and the migration says so in a boot line of its own because the spelling invites the mistake. Copying a deleted label into `distill.ctx_source_label` does not migrate a setting, it **renames a living source**: one label is one watermark series, the renamed series has no journal history, and the arm restarts every session of it at `distill.initial_backfill_rows`. Copying the old quiet value into `distill.ctx_quiet_for` replaces a default measured against checkpoint ages (30 min, against a median compaction distance of 11 minutes) with one that was measured against a foreign database's live rows. Neither key needs anything done to it by this upgrade.

**What it tells you.** When it actually deletes something, the migration writes three lines into the boot log (`docker compose logs ctx`): how many rows went, that the `distill.ctx_*` keys are not their successors, and where the deleted values can still be read. On a database that has no such rows — every fresh install, and any installation that never wrote one of the three keys — it says nothing at all and changes nothing. Running it twice is a no-op; a second application deletes zero rows and stays silent.


There is nowhere to restore such a value to — the settings API answers 404 on all three keys in every scope, and no key took any of them over. The query exists so that a rollback to a pre-v5.17.0 binary can put the rows back by hand, and so that an operator who wants to know what a tenant had configured can still find out.

**Rolling over this upgrade.** The row deletes emit the usual `ctx_settings_write` events, so an old binary still serving alongside reloads its settings and loses these overrides. For the new binary that changes nothing — no code reads the three keys any more. ### Migration 154: snapshot markings without a superseder are repaired once

A dream `supersedes` link "A supersedes B" retires its target B as `lifecycle_state='snapshot'` with `superseded_by=A`. Older binaries reverted that only when the dream replace sweep physically deleted the link, and only while the pointer still named the deleted source — a pair re-classified to topical/recurrent, a superseder that was archived and swept, or a second superseder taking over never reached the target. Such a block stays a snapshot with nothing superseding it: excluded from dream linking and from the guard, and replaced in query results by a block that no longer claims to supersede it. Since the supersedes reconcile (`store.ReconcileSupersedesTargets`) runs on every dream batch, dangling-link sweep and `dream-link-resolve`, new orphans no longer arise; the ones already on disk are only healed when something touches them again. Migration 154 applies the same rules once to every non-archived snapshot with a pointer:

- **move** — the pointer's source no longer supersedes the block (no `supersedes` link, source archived, or source in another scope), another source does: `superseded_by` moves to the first of those with weighted confidence ≥ 0.7, else to the first remaining one; the block stays a snapshot.
- **restore** — no superseder at all: `lifecycle_state` → `knowledge`, `superseded_by` → `NULL`. As at runtime, the state the block had before it became a snapshot (`canonical`, `synthesis`) is not recorded anywhere and does not come back.

It creates no snapshot (a knowledge block with a valid superseder is marked by the runtime on its next touch), leaves archived blocks alone and does not bump `updated_at`.

**What it tells you.** When it changes something, two boot-log lines (`docker compose logs ctx`) give the restored and moved counts and the recovery query. On a database without such rows it says nothing. A second application changes nothing.

**Recovering a pointer.** Every touched row carries the previous pointer in its metadata:

```bash
docker compose exec db psql -U "$CONTEXT_DB_USER" -d "$CONTEXT_DB" -c \
  "SELECT id, lifecycle_state, metadata->'supersedes_repair' FROM context_blocks
    WHERE metadata ? 'supersedes_repair';"
```

### Migration 155: `anthropic` joins the backend wire protocols

`context_backends.protocol` was pinned by a `CHECK` to `openai`, `ollama` and `rerank`. Migration 155 widens it to include `anthropic` (the native Messages API wire, [api — Anthropic](api.md#backend-pool)). It resolves the baseline's unnamed constraint from `pg_constraint` by table and definition, drops it and re-adds it as `context_backends_protocol_check`; no row changes, the column keeps its `DEFAULT 'openai'`. Nothing to do at upgrade time. **Downgrading** a daemon below this migration with an `anthropic` row still in the pool makes that row dispatch onto the wrong wire — the Ollama `/api/chat` path on the pipelines (the old fallthrough for unknown protocols), the OpenAI SSE path on web chat (the old stream path never read the protocol); the pool loads the row either way, validation runs only on create and update — so disable or delete such rows before rolling the binary back; the widened `CHECK` itself is harmless to an older binary.

### Migration 156: the duplicate guard never looks across tenants

`ctx_guard_check` (the SQL half of the duplicate guard) gets one more candidate predicate: the nearest neighbour is searched only among the scopes owned by the checked block's tenant (`context_tenant_scopes`); a scope registered to no tenant gets same-scope candidates only. Signature, thresholds, the same-scope axis and the result shape are unchanged; the HNSW iterative scan (`hnsw.iterative_scan = relaxed_order`, transaction-local) is now set on every call instead of the same-scope axis only, because every call is a filtered ANN now. The migration also **repairs data**: blocks archived as duplicates (`guard_status = archived_dup`) of a block in another tenant are un-archived, their `guard_*` metadata cleared, marked `metadata.guard_repair = 'M156'` and handed back to the next guard batch — idempotent, a second run changes nothing; the rows the repair holds back (below) stay archived. To list what it returned, filter on `metadata->>'guard_repair' = 'M156'`: migration 121 writes the same key with `'M121'`, so `metadata ? 'guard_repair'` finds its rows too. Single-tenant installs (every scope in the default tenant) see no behavioural change. Background: [multi-tenancy — background pipeline isolation](multi-tenancy.md#background-pipeline-isolation) (GHSA 2026-10-31 §2). Nothing to do at upgrade time; the first guard batch after the upgrade may re-check the repaired blocks.

**Amended after 5.29.2.** The repair as shipped in 5.29.1/5.29.2 un-archived rows without looking at the partial unique indexes over live rows (`category, title, scope` and, for chunks, `source_id, chunk_index`). Saving a title again after the guard archived it creates a new live row, so an archived row next to a live twin is ordinary data — and un-archiving it is a `23505` that rolls the migration back and stops `ctxd` from booting (`migrations failed`, exit 1, the same on every restart). The amended statement holds back three kinds of rows, which stay archived exactly as they were: a row whose slot a live row holds, all but the newest of several archived rows for one slot, and a row a person archived through `guard-resolve` (`metadata.guard_resolution = 'archive'`). The statement repeats until a pass returns nothing, so a newer row that is itself blocked never keeps an older one of the same slot archived: when it is done, every row it held back sits in a slot a live row holds or carries a person's verdict. A database that already applied the 5.29.1/5.29.2 file skips 156 and keeps that file's checksum in `_migrations`; the schema contract accepts it (`migrations.IsAmendedChecksum`), every other mismatch is still `migration_integrity/breaking`. The shipped file is kept byte for byte as `go/migrations/testdata/156_guard_tenant_candidates.c095c391.sql.txt`: `go test ./migrations/` ties the accepted checksum to it, and the M156 integration suite runs it against its corpus and requires the `23505` before it applies the amended file. To see what the repair held back:

```sql
SELECT b.id, b.scope, b.category, b.title, b.metadata->>'guard_resolution' AS resolution
  FROM context_blocks b
  JOIN context_blocks m ON m.id::text = b.metadata->>'guard_matched_id'
  JOIN context_tenant_scopes mts ON mts.scope = m.scope
  LEFT JOIN context_tenant_scopes bts ON bts.scope = b.scope
 WHERE b.is_archived AND b.guard_status = 'archived_dup'
   AND (bts.tenant_id IS NULL OR bts.tenant_id <> mts.tenant_id);
```

Each row it lists was archived against another tenant's block and is still archived; un-archive the ones you want back by hand after renaming or retiring the live twin.

**Databases that applied the 5.29.1/5.29.2 file** (`SELECT checksum FROM _migrations WHERE version = 156` returns `c095c3918345c0fa…ca121`) never run the amended statement. That file also un-archived blocks a person had archived through `guard-resolve` whenever their `guard_matched_id` pointed into another tenant; it left `metadata.guard_resolution = 'archive'` on them and set no `guard_repair` marker. Apart from the one-time repairs in migrations (121, the checkpoint repair folded into the baseline, and 156), nothing in ctx un-archives a block, so every row this lists was archived by a person and is live again:

```sql
SELECT id, category, title, scope
  FROM context_blocks
 WHERE NOT is_archived
   AND metadata->>'guard_resolution' = 'archive';
```

Archive each one again with `ctx guard resolve <id> archive`, one id per call, with a key that may write the block's scope: the single-id form takes any live block, while the batch form (several ids) only touches flagged blocks and skips these as `not_flagged`.

### Migration 157: live guard decisions that name a match outside the tenant

Migration 156 repaired the blocks the pre-156 guard had **archived** against another tenant's block. Every other block the old guard had decided kept its decision keys, whatever happened to it since — a review flag, a clean verdict, a block a person kept through `guard-resolve`, a block that has become `canonical` — and with them `guard_similarity`, `guard_is_cross_scope` and a `guard_matched_id` naming the foreign block. The read paths drop `guard_matched_id` when the caller cannot read the matched block, but the similarity, the cross-scope flag and a review flag raised against the foreign block stayed, and they are a decision the tenant-bounded guard never makes.

Migration 157 selects live rows (`NOT is_archived`; it does not filter on `guard_status` or the lifecycle) whose `guard_matched_id` names an existing block that the 156 candidate predicate excludes: a block of another tenant, a block outside the row's own scope when that scope is registered to no tenant, or a block in a scope registered to no tenant. The last case goes beyond the 156 repair predicate, which only looked at matches in registered scopes. Empty, malformed and dangling matches (the matched block is gone) are left alone. What it does depends on whether a person has decided on the row:

- **No `guard-resolve` trace** (no `metadata.guard_resolution`): the guard's decision is handed back. `guard_status` returns to `active` and every guard decision key leaves `metadata` (`guard_status`, `guard_checked_at`, `guard_similarity`, `guard_matched_id`, `guard_is_cross_scope`, `guard_threshold_duplicate`, `guard_threshold_review`). Without `guard_checked_at` a row the guard still checks (lifecycle `knowledge`, a type with `guard.check`) is pending again, and the next guard batch re-checks it against its own tenant only; a block that really has a near twin in its own tenant gets its review flag back from that check. A row the guard no longer checks — decided while it was `knowledge`, `canonical` or a snapshot now — simply carries no decision afterwards.
- **A `guard-resolve` trace** (`keep` or `archive`, any decision of a person): the decision stands. Only the keys that point at the foreign block go — `guard_matched_id`, `guard_similarity`, `guard_is_cross_scope`; `guard_status`, `guard_checked_at`, the thresholds and the trace (`guard_resolution`, `guard_resolved_at`) stay. The row is not pending, so the guard does not put it up for a verdict again — a re-check could otherwise archive a kept block as the near duplicate of a block in its own tenant.

Both kinds of row get `metadata.guard_repair = 'M157'`. No row is un-archived, so the partial unique indexes over live rows cannot be hit; the statement is idempotent (no touched row carries `guard_matched_id` any more) and an install whose blocks all sit in scopes registered to the default tenant changes no row. Nothing to do at upgrade time. To list what it touched, with the rows that kept a person's verdict told apart:

```sql
SELECT id, scope, category, title, guard_status, metadata->>'guard_resolution' AS resolution
  FROM context_blocks
 WHERE metadata->>'guard_repair' = 'M157';
```

Until the guard has run, the rows without a resolution show `guard_status = active` without `guard_checked_at`; afterwards they carry the guard's new decision next to the marker.

### Migration 158: `consumer_id` on `context_llm_log`

`context_llm_log` gets a nullable `consumer_id UUID`: the external consumer of the OpenAI-compatible API (`/v1`) a row is attributed to. Consumers are a credential class of their own (`ctxm_` model keys); they never authenticate as a knowledge key and so never fill `api_key_id`. Like `api_key_id` the column has no foreign key — the log references a credential, it does not depend on it, so deleting a consumer never anonymises or deletes its history. A `CHECK` (`ck_llm_log_one_identity`, `num_nonnulls(api_key_id, consumer_id) <= 1`) holds on the hypertable and on every chunk, existing and future: a row names a knowledge key, a consumer or nobody (background work), never both. An insert with both fails with `23514`; through the daemon's write path such a row is lost and counted (`llmlog.insert_failures` on `/api/status`). A partial index `idx_llm_log_consumer` on `(consumer_id, created_at DESC) WHERE consumer_id IS NOT NULL` serves per-consumer windows and stays empty until the first `/v1` row. No existing row changes and there is no backfill: every row so far is internal, so `consumer_id` is NULL everywhere, and nothing in this release writes it yet.

**Boot time.** Adding the column is a catalog change. Adding the `CHECK` validates every existing row, and the index is built chunk by chunk — two reads of every chunk's heap, the prompt and response bodies stored inline in the row included (only bodies above the TOAST threshold lie outside the heap and are not read), while `context_llm_log` stays locked until the migration's transaction commits. Measured on a synthetic copy of production shape — 1 000 000 rows over 29 chunks, 976 MB of heap (about 1 kB per row; the live table has 945 bytes), TimescaleDB 2.31.0 in the test container: `CHECK` validation **0.45 s**, index build **0.43 s**, the whole migration through the boot runner **0.75 s**. For comparison, a serial read-only scan of the same predicate over the live table (352 565 rows, 29 chunks, 318 MB of heap, 2026-11-03) took 0.15 s from shared buffers. Those runs read a warm cache. Cold, as measured in review (nothing cached), the whole migration through the runner took about 0.9–1.25 s for 1 000 000 rows / 976 MB of heap and about 2.85 s for 3 000 000 rows / 2.9 GB — roughly 0.7–1 s per GB of heap and cold read. Take that as the upper bound to plan with: extrapolated (not measured), a 30 GB heap read cold twice would hold `context_llm_log` locked for roughly 40–60 s at boot. Above roughly 10 GB of `context_llm_log` heap — about 15–20 s of exclusive lock at boot, two scans at those 0.7–1 s per GB each — a follow-up migration with `ADD CONSTRAINT … NOT VALID` plus a separate `VALIDATE CONSTRAINT` would be the way; its precondition, not measured here, is to check how TimescaleDB carries both onto existing and future chunks. Reproduce the measurement with `CTX_M158_PROBE_ROWS=1000000 go test -tags=integration -p 1 -run TestMigration158CostProbe -v ./internal/llmlog/`. Nothing to do at upgrade time, with one caveat: the migration sets `lock_timeout = '3s'`, so a session that holds a lock on `context_llm_log` while ctxd boots — a long query in `psql`, a dashboard — makes the migration fail and the boot with it (`migrations failed`); the next start retries it.

**Downgrading** below 158 needs no schema change: an older binary never names `consumer_id`, its rows keep it NULL, and the `CHECK` accepts them. Drop the objects only together with a revert of the code that writes the column (a current binary names it in every insert, so without it every LLM-log row is lost): `DROP INDEX idx_llm_log_consumer; ALTER TABLE context_llm_log DROP CONSTRAINT ck_llm_log_one_identity; ALTER TABLE context_llm_log DROP COLUMN consumer_id;`.

### Migration 159: the hourly LLM-usage rollup

`context_llm_usage_hourly` keeps one row per hour (UTC) and dimension — the knowledge key (`api_key_id`) or the `/v1` consumer (`consumer_id`; never both, `source` reads `internal` or `gateway`), `pipeline`, `backend_name` (falling back to `host`, as the status page does), `model`, `model_alias` and `hop` (from `metadata.gw`; empty and 0 until `/v1` writes rows), `dispatch_class`, `backend_locality` — with the counts the status and quota paths compute from the raw log today: `calls` (every row, failed ones included), `errors`, `unattributed_ok`, `estimated_calls`, token sums, `duration_ms_sum`/`duration_n`, `queue_wait_ms_sum`/`queue_wait_n`, `cost_usd`, and three 16-bucket log2 histograms, `latency_hist`, `queue_wait_hist` and `ttft_hist` (bucket *i* counts values up to 60·2^i ms, the last one everything above 983 040 ms). An `AFTER INSERT` trigger on `context_llm_log`, `trg_llm_usage_rollup`, adds every new row in the row's own transaction; the migration backfills every existing row once. Its first reader is the tenant quota accountant (since W06-4): `daily_calls` and the cost budgets are summed from the rollup plus the raw rows of each window's first, partial hour ([multi-tenancy — Cost/call quotas](multi-tenancy.md#costcall-quotas)). Since W06-5 the status page's `llm_24h` rows are read the same way, the server view and the per-tenant view alike, with the same figures as the raw-row aggregate they replace (`llm_24h_complete` from `unattributed_ok`); rows with as many calls are ordered by backend, then pipeline. A backend or pipeline name longer than 100 characters is shown cut to 100, and two names that differ only after the 100th character share one row, as they share one rollup row. The same cut applies to `model_alias`, with one difference: a model alias may be up to 128 characters long (the alias registry, migration 162) and a gateway row keeps all of it in `metadata.gw.alias`, but the rollup keeps the first 100 — two aliases that differ only after the 100th character are counted in one rollup cell, so per-alias usage of such aliases is exact only in the raw rows (`metadata->'gw'->>'alias'`). Keep alias names that must be told apart in usage within 100 characters.

**Boot time.** The backfill is one `GROUP BY` over the whole log. Measured on a synthetic copy of production shape (1 000 000 rows over 29 chunks, 976 MB of heap, TimescaleDB 2.31.0 in the test container, warm cache): backfill 8.0 s, the whole migration through the boot runner 7.5 s, 77 238 rollup rows, 109 MB with indexes — about 8 s per million log rows. For the live table on 2026-11-03 (352 720 rows) that is about 3 s, extrapolated, not measured. While it runs, inserts into `context_llm_log` wait (creating the trigger locks the table against writers until the migration commits); reads are not blocked, and at boot nothing writes yet. The `lock_timeout` caveat of 158 applies unchanged. Reproduce with `CTX_M159_PROBE_ROWS=1000000 go test -tags=integration -p 1 -run TestMigration159BackfillProbe -v -timeout 40m ./internal/llmlog/`.

**Cost per insert.** Every LLM-log insert also upserts its hour's rollup row. The expensive case is many writers on the same row: with eight concurrent writers on one dimension (the daemon itself writes at most four log rows at a time) p99 insert latency rose by 0.9–1.5 ms over a baseline without the trigger, p50 by about 0.4 ms; with the same load spread over 64 dimensions of one hour, p99 rose by 0.45–0.85 ms. About 92 % of the row updates were HOT (the new row version stays on its page) in the one-row case and more than 99 % with 64 rows; the table is created with `fillfactor = 50` and autovacuumed every 5 000 dead row versions. Reproduce with `CTX_M159_LOAD_INSERTS=50000 go test -tags=integration -p 1 -run TestUsageRollupLoad -v ./internal/llmlog/`.

**The trigger does not fail an insert over its content.** It reads `metadata.gw` only where the JSON types fit, clamps `hop` to 0–16 and `ttft_ms` to non-negative values, sums `cost_usd` without a precision limit, and cuts every text dimension — pipeline, backend, model, alias, dispatch class, locality — to its first 100 characters, so that no entry of the rollup's unique index outgrows the B-tree limit of 2 704 bytes (at most 6 × 400 bytes of text plus a fixed rest; a model name of 3 000 bytes, which an upstream can return, would otherwise fail the log insert with `54000`). A malformed stamp is counted as "no alias, hop 0, no time to first token"; two names that differ only after the 100th character share a rollup row (today's longest has 25 characters). One setting it depends on: the upsert assumes the default isolation level `read committed`, which ctx never changes — under `default_transaction_isolation = 'repeatable read'` concurrent writers on one rollup row fail with `40001` and their log rows are lost, so do not change that setting for the ctx database.

**Deletes are not subtracted.** The rollup counts calls as they are written. Deleting or truncating `context_llm_log` rows leaves it unchanged (ctx itself deletes no log rows; the body janitor behind `CTX_LLMLOG_RETENTION_DAYS` only NULLs bodies, an `UPDATE` the trigger does not see). Since the quota accountant and the status page read the rollup, rows deleted by hand keep counting against `daily_calls` and the cost budgets, and in `llm_24h`, until they leave the window. To bring it back in line after a manual delete, stop ctxd and run `TRUNCATE context_llm_usage_hourly` followed by the final `INSERT … SELECT` of `159_llm_usage_rollup.sql` in one transaction. Nothing to do at upgrade time.

**Downgrading** below 159 needs no schema change: an older binary never names the table, and the trigger keeps counting its rows. Remove the objects only together with a revert of the rollup readers (W06-4 quota, W06-5 status), whose binary reads the table: without the table every quota refresh fails — the accountant keeps its last generation and after a restart serves none, so the quota fails open — and the status page shows `llm_24h` empty with `llm_24h_complete` false (the tenant view keeps its last generation); with the trigger dropped but the table kept the rollup goes stale, and both see only the raw rows of each window's first, partial hour plus whatever the stale rollup still holds. To remove them: `DROP TRIGGER trg_llm_usage_rollup ON context_llm_log; DROP TABLE context_llm_usage_hourly; DROP FUNCTION llm_usage_rollup_ins(), hist_add(bigint[], bigint[]), llm_usage_hist_one(int), llm_usage_hist_idx(bigint);`.

### Migration 160: audit trail for api keys and tenant quotas

Two trigger sets write every change of `context_api_keys` and `context_tenant_quota` into `context_settings_audit` (`entity_type` `api_key` and `tenant_quota`) — what is recorded, what never is, and the `via` channels are in [security — Audit trail](security.md#audit-trail). The key trigger fires on `INSERT`/`DELETE` and on an `UPDATE` of one of the ten audited columns that changes it; the `last_used_at` write of each authentication does not reach it. New are five functions (`audit_state_api_key`, `audit_state_tenant_quota`, `audit_actor_meta`, `audit_api_keys_write`, `audit_tenant_quota_write`), three triggers (`trg_api_keys_audit_ins_del`, `trg_api_keys_audit_upd`, `trg_tenant_quota_audit`) and the index `idx_settings_audit_entity` (`entity_type, created_at DESC`); no table. It also redefines the 051 settings/secrets audit function `audit_settings_write` with one change: its `via` honours a stamped channel (`offboarding` on the settings and secrets the keys deleted by `tenant-delete` last wrote); an unstamped write — an older binary's included — records what it recorded before.

**Backfill.** One `snapshot` row per existing key and per existing quota row, with the current whitelist state and `metadata = {via: migration, tenant_id}` (no `tenant_id` for a quota whose scope no tenant owns). A key or quota that already has an audit row gets none, so a second run writes nothing. An install with 12 keys and no quota row gets 12 rows. Find them with `SELECT entity_type, count(*) FROM context_settings_audit WHERE action = 'snapshot' GROUP BY 1;`.

**Boot time.** No table is rewritten; the backfill reads both tables once. Creating the triggers locks `context_api_keys` and `context_tenant_quota` against writes until the migration commits (reads are not blocked) — at boot nothing writes yet, but another ctx process authenticating against the same database waits until the backfill is done: milliseconds for a dozen keys; the review of this change measured 0.7 s for the whole migration with 1 000 000 audit rows and 2 000 keys. The `lock_timeout` caveat of 158 applies unchanged. The audit rows are readable only with SQL for now; the read surface for admins, which hides server-admin actors from tenant-admins, follows in a later release. Nothing to do at upgrade time.

**Downgrading** below 160 needs no schema change, but the triggers keep running and an older binary stamps nothing: its key writes are recorded as `via = 'sql'` without an actor, its quota writes as `sql` too (naming the row's `updated_by` as actor on a create or when the write changed it) — indistinguishable from a `psql` edit until you upgrade again. To remove the triggers: `DROP TRIGGER trg_api_keys_audit_ins_del ON context_api_keys; DROP TRIGGER trg_api_keys_audit_upd ON context_api_keys; DROP TRIGGER trg_tenant_quota_audit ON context_tenant_quota;` and then the five functions and the index. The rows written so far stay.

### Migration 161: model consumers and model keys

Two new tables, `context_model_consumers` and `context_model_keys`, hold the external callers of the OpenAI-compatible model API and their keys (`ctxm_…`, stored only as SHA-256 and a short hint, never in plain text). Nothing in this release writes them — the admin actions and the `/v1` endpoints ship later — so the migration changes no behaviour outside the database. Also new: the column `context_tenants.max_model_consumers` (`INTEGER`, `64` for every tenant including the default tenant; `NULL` = unlimited, set only by hand), the read-only check function `ctx_model_auth(key_hash, client_ip, secure)` with `model_cidrs_private(cidr[])`, two triggers that make deactivating a consumer revoke its live keys and refuse new ones (`psql` included: a key insert into an inactive consumer fails with SQLSTATE `23514`, and an insert and a deactivation running at the same time wait for each other on the consumer row, so under READ COMMITTED — what ctx uses — the key is either revoked or refused; reactivating revives no key; known limit: a deactivation run by hand under `REPEATABLE READ` does not revoke a key committed after its snapshot), two identity triggers (a consumer's `tenant_id` and a key's `consumer_id` never change — SQLSTATE `23514`), the audit triggers of both tables ([security — Audit trail](security.md#audit-trail)), and the index `idx_settings_audit_entity_tenant` (`entity_type, metadata->>'tenant_id', created_at DESC`) on `context_settings_audit`. The index lets a tenant-admin's `GET /api/audit` read its own rows directly; before, a tenant without rows of an entity walked every row of that entity (measured 1.1–3.0 s per request at 1 000 000 rows depending on host load, 0.3 ms with the index).

**Boot time.** No table is rewritten and nothing is backfilled. The index build is the only step that grows with data: until the migration commits, it lets reads of `context_settings_audit` through but makes every audited write — settings, secrets, backends, keys, quotas — wait. A few hundred audit rows take milliseconds; measured for this change: 4.4–9.1 s at 1 100 000 audit rows (82 MB index) on a loaded host. After the build the migration briefly locks `context_tenants` and, against writes, `context_api_keys` and `context_principals`, so knowledge-key authentication of another ctx process on the same database waits those milliseconds. The `lock_timeout` caveat of 158 applies unchanged. Check: `SELECT count(*) FROM context_model_consumers;` returns `0`, `SELECT DISTINCT max_model_consumers FROM context_tenants;` returns `64`.

**Tenant deletion.** `tenant-delete` removes a tenant's model keys and then its model consumers (step 7b of the prune), in the transaction that deletes its knowledge keys and before them, so the `RESTRICT` foreign keys of both tables no longer stop the last step (a consumer created while the prune runs still can, as a knowledge key minted meanwhile always could — repeat `tenant-delete` then); the step locks the tenant's consumers before it deletes their keys, the order every consumer write takes, so a rotation or deactivation running at the same time waits instead of deadlocking it; each removed row gets one `prune` audit row with `via = offboarding`, the deleting admin and the tenant. No other path deletes rows of either table — a consumer is deactivated, a key revoked.

**Downgrading** below 161 needs no schema change: an older binary never touches the new objects. To remove them, in this order: `DROP FUNCTION ctx_model_auth(TEXT, INET, BOOLEAN); DROP FUNCTION audit_state_model_key(context_model_keys); DROP FUNCTION audit_state_model_consumer(context_model_consumers); DROP TABLE context_model_keys, context_model_consumers;` then `DROP FUNCTION audit_model_keys_write(), audit_model_consumers_write(), model_keys_identity_immutable(), model_consumers_identity_immutable(), model_keys_consumer_active(), model_consumer_deactivate_revokes(), model_cidrs_private(CIDR[]); ALTER TABLE context_tenants DROP COLUMN max_model_consumers; DROP INDEX idx_settings_audit_entity_tenant; DELETE FROM _migrations WHERE version = 161;` (the last statement lets a later upgrade apply 161 again). The audit rows written so far stay.

### Migration 162: model aliases

A new table, `context_model_aliases`, holds the public model names of the OpenAI-compatible model API: each row maps a name — the `model` an external program sends — to a pool role (`chat`, `embed`, … — a role, never a backend row, so trust, disable profiles, cooldown and tenant visibility of the pool apply unchanged), a kind (`chat`, `embedding`, `rerank`), a sensitivity floor (default `credentials`, the strictest), a `policy` object of request caps, a description and `enabled`. `scope` is `_global` for the operator's catalog or a tenant scope; a tenant alias takes the place of the `_global` alias of the same name for that tenant's consumers — by its mere existence, disabled or invalid included: a tenant that wants the operator's alias of that name back deletes its own alias, disabling it keeps the name hidden for that tenant. Nothing seeds the table and nothing in this release writes it — the admin actions and the `/v1` endpoints ship later — so the migration changes no behaviour outside the database: ctxd loads an empty alias registry at boot and offers no model. Also new: an identity trigger (`id`, `name`, `kind` and `scope` of an alias never change — SQLSTATE `23514`, `psql` included; renaming is delete + create), a notify trigger on the existing `ctx_settings_write` channel (`notify_settings_write()`, unchanged; the listener reloads the registry and nothing else, in the background and coalesced: a burst of alias writes costs at most the running reload plus one, and the listener keeps serving its other notifications meanwhile), and the audit triggers of the table ([security — Audit trail](security.md#audit-trail)). `policy` keys are flat, dotted names (`{"max_n": 2, "tools.max_count": 64}`), not nested objects. A row whose `policy` the server cannot parse — an unknown key, a wrong type, a value over its code ceiling — is loaded but never offered, with one `WARN` line per reload naming the alias and the key. Remove rows with `DELETE`, not `TRUNCATE`: a `TRUNCATE` fires neither the audit nor the notify trigger, so it leaves no history and the running registry keeps offering the old rows until the next alias write, listener reconnect or restart.

**Boot time.** One new, empty table; no existing table is touched or locked, nothing is backfilled — milliseconds. The `lock_timeout` caveat of 158 applies unchanged. Check: `SELECT count(*) FROM context_model_aliases;` returns `0`; the boot log carries `modelalias: snapshot reloaded` with `generation=1 aliases=0`.

**Downgrading** below 162 needs no schema change: an older binary never touches the table (its listener would route an alias write to the full settings reload, harmless while nothing writes). No foreign key points to the table yet; the grant table that will reference alias ids ships with a later migration. To remove the objects, in this order: `DROP FUNCTION audit_state_model_alias(context_model_aliases); DROP TABLE context_model_aliases;` (its triggers go with it) `DROP FUNCTION audit_model_aliases_write(), model_aliases_identity_immutable(); DELETE FROM _migrations WHERE version = 162;` (the last statement lets a later upgrade apply 162 again). `notify_settings_write()` and `audit_actor_meta()` stay — they belong to earlier migrations. The audit rows written so far stay.

### Migration 163: instance identity, and indexes on the model-key foreign keys

A new one-row table, `context_instance`, holds the identity of this ctx instance: `instance_id` (a random UUIDv4) and `instance_secret` (32 random bytes, the HMAC key of the hop tokens of the federation layer; it never leaves the table — [security](security.md#instance-identity)). The migration draws both on its first apply; a later apply leaves them as they are. The identity belongs to the **database, not the process**: every ctxd on one database is the same instance. Nothing reads it yet beyond the boot — the hop tokens and the loop guard ship later — so the migration changes no behaviour outside the database, except that ctxd now **refuses to start without an identity**.

**Boot abort.** ctxd reads the identity right after the migrations, before any other boot step writes to the database; no row, a secret that is not 32 bytes long, or a database error ends the boot with exit code 1 and the log line `{"level":"ERROR","msg":"federation: instance identity missing — run migrations","error":"…"}` (the `error` field says which: `store: instance identity missing`, `store: instance identity invalid: secret is 16 bytes, want 32`, or the database error, e.g. `42P01` on a database below 163). A normal boot logs `{"level":"INFO","msg":"federation: instance identity loaded","instance":"<id>"}` — the id, never the secret. The row is never removed by ctx; if it was deleted by hand, `INSERT INTO context_instance DEFAULT VALUES;` creates a new identity (recorded as an audit `create` row). That is a different instance for every peer bound to the old id. `TRUNCATE context_instance` is refused (SQLSTATE `23001`): it would remove the identity without an audit row. A failing write by hand — a `NULL` id, a secret of another length — reports the violated constraint or column and nothing else: a guard trigger raises before PostgreSQL's own constraint error, which would print the whole failing row, the live secret included, to the client and into the server log.

**Cloned databases.** A database restored from another instance's backup — a measurement copy, a migrated host — carries that instance's identity and secret. Once instances call each other, the two then take each other's requests for loops and refuse them: fail-closed, but both look broken. Give the copy its own identity before it joins the network, then restart it (the identity is read at boot only; there is no hot reload):

```sql
UPDATE context_instance SET instance_id = gen_random_uuid(),
       instance_secret = gen_random_bytes(32), rotated_at = now();
```

The audit trail records it as a `rotate` row with the old and the new `instance_id`. A managed `instance-rotate` action follows in a later release.

**Indexes on the 161 foreign keys.** The same migration adds seven partial indexes — `context_model_keys` (`rotated_from`, `created_by_key`, `revoked_by_key`, `created_by_principal`, `revoked_by_principal`) and `context_model_consumers` (`created_by_key`, `created_by_principal`), each `WHERE … IS NOT NULL`. Migration 161 declared these columns as foreign keys (`ON DELETE SET NULL`) without an index, so every deleted key, knowledge key or principal made the foreign-key triggers scan the whole table. Measured at 128 000 model keys (1 000 tenants × 64 consumers × 2 keys): the tenant prune's model-key delete 1.9 s → 13 ms, a whole `tenant-delete` prune 2.2 s → 33 ms, with no sequential scan of either table left in the delete path. On an upgrade from 160 both tables are empty, so the indexes build instantly.

**Boot time.** One new table of one row, seven indexes on tables that are empty on an upgrade from 160 — milliseconds. The `lock_timeout` caveat of 158 applies unchanged. Check: `SELECT count(*), max(uuid_extract_version(instance_id)) FROM context_instance;` returns `1 | 4`, and the boot log carries `federation: instance identity loaded`.

**Downgrading** below 163 needs no schema change: an older binary ignores the table and the indexes. To remove the objects, in this order: `DROP FUNCTION audit_state_instance(context_instance); DROP TABLE context_instance;` (its triggers go with it) `DROP FUNCTION audit_instance_write(), instance_row_guard(); DROP INDEX idx_model_keys_rotated_from, idx_model_keys_created_by_key, idx_model_keys_revoked_by_key, idx_model_keys_created_by_principal, idx_model_keys_revoked_by_principal, idx_model_consumers_created_by_key, idx_model_consumers_created_by_principal; DELETE FROM _migrations WHERE version = 163;` — but a later upgrade then applies 163 again and draws a **new** identity, which every peer bound to the old one refuses. Prefer downgrading the binary alone. `audit_actor_meta()` stays (160); the audit rows written so far stay.

### Migration 164: model grants

A new table, `context_model_consumer_grants`, holds the single model releases of a model consumer: one row per consumer and model alias, bound to the alias **id**, never its name. `all_models` (161) stays the wildcard next to it — `true` releases every alias the consumer can see, the grants count while it is `false`. Both foreign keys cascade: deleting an alias removes its grants, so an alias created later under the same name — perhaps routed to an external, paid backend — is **not** granted to anyone; a consumer's grants go with the consumer (only the tenant prune deletes one, and it removes the grants first so their audit rows still name the tenant). `consumer_id` and `alias_id` of a grant never change (SQLSTATE `23514`, `psql` included): a grant is added or removed, never edited. The admin actions write the table — `models` on `model-consumer-create`/`-update` ([api](api.md#model-consumer-administration)), checked against what the consumer is offered at that moment (its `tenant_scope`; `_global` only for a `ctx-peer`) — and `model-alias-delete` answers `409 model_granted` while an active consumer holds a grant on the alias. A `psql` `DELETE` of an alias takes its grants with it. Nothing on `/v1` reads the table yet (the endpoints ship later), so the migration changes no behaviour outside the database and the admin actions. No backfill: releases existed only as `all_models`, which stays as it is. Every grant and ungrant is recorded in the audit trail ([security — Audit trail](security.md#audit-trail)). Remove rows with `DELETE`, not `TRUNCATE`: a `TRUNCATE` fires no audit trigger.

**Boot time.** One new, empty table. Its foreign keys take `SHARE ROW EXCLUSIVE` on `context_model_consumers`, `context_model_aliases`, `context_api_keys` and `context_principals` until the commit — milliseconds, during which writes to those tables wait (knowledge-key authentication of another ctx process on the same database among them); reads do not. The `lock_timeout` caveat of 158 applies unchanged. Check: `SELECT count(*) FROM context_model_consumer_grants;` returns `0`.

**Downgrading** below 164 needs no schema change: an older binary ignores the table — its `model-consumer-create`/`-update` answer `400` to a `models` field again, its `model-alias-delete` deletes a granted alias without the `409` (the cascade still removes the grants, with audit rows), and its tenant prune lets the grants go with the consumers by cascade — their `ungrant` rows then carry no `tenant_id` and read scope `_global`, so only server-admins see them. No foreign key points to the table. To remove the objects, in this order: `DROP FUNCTION audit_state_model_grant(context_model_consumer_grants); DROP TABLE context_model_consumer_grants;` (its triggers and indexes go with it) `DROP FUNCTION audit_model_grants_write(), model_grants_identity_immutable(); DELETE FROM _migrations WHERE version = 164;` (the last statement lets a later upgrade apply 164 again). `audit_actor_meta()` stays — it belongs to 160. The audit rows written so far stay; the grants themselves are gone, so a later upgrade starts with none.

### `graph_overview.csr_loader`: the rebuild's input substrate

`CTX_GRAPH_OVERVIEW_CSR_LOADER` (default `false`, hot) switches how the rebuild gets its graph into memory. It changes no result — the partition, the modularity and the intra-cluster degrees are byte-identical either way, and that identity is a gate, not a hope.

The current path materialises the graph three times before the clustering library sees it: an edge slice holding **two UUID strings per edge**, a symmetrisation map keyed by node pair, and a string→index map. Measured on a synthetic corpus at constant density, those three alone cost:

| Nodes | Pairs | edge slice + maps | CSR | Factor |
|---|---|---|---|---|
| 50 000 | 112 370 | 41 MB | 23 MB | 1.78× |
| 200 000 | 449 575 | 117 MB | 39 MB | 2.97× |
| 400 000 | 899 260 | 217 MB | 62 MB | 3.50× |

The factor grows with the corpus because the fixed Go runtime baseline stops dominating; between the 200k and 400k rows the *marginal* cost is 100 MB versus 23 MB. This matters against a 512 MiB container limit at which the full rebuild already peaks at ~423 MB at the 200k node cap.

The CSR path reads nodes and edges in **one repeatable-read transaction** and builds compressed adjacency arrays in two cursor passes. Two consequences worth knowing before flipping it:

- **It holds a read snapshot for the whole load.** That blocks vacuum on `context_blocks` and `context_dream_links` for the duration — seconds today, minutes at the 10M target. `load_ms` in the run journal is where you watch it. The snapshot is not optional: the two passes must agree, and a link written between them (dream writes in background batches) would otherwise corrupt the adjacency **silently**.
- **Both paths stay in the binary.** Rolling back is a config flip, not a redeploy — which on a system whose deploys are built from tag worktrees is the difference between a minute and an afternoon.

Leave it off until the identity gate has been green across several deploys on your own corpus.

### The clustering engine

Since v4.31.0 the rebuild runs on `internal/louvain`, the project's own Louvain/Leiden kernel (`engine=ctx` is the shipped default; gonum remains in the binary as the rollback path — a config flip, not a redeploy). The switch was cut as an announced release step: the one-time partition break it implies is absorbed by the topic layer's tombstone re-attach window.

Why the own kernel: the wall that `graph_overview.max_nodes` guards against is an implementation property, not a property of the Louvain method. gonum recomputes each community's total degree on every evaluation (its own source comments say the saving "does not appear to be compelling") and re-sweeps every node on every iteration instead of queueing the ones a move actually touched. Fixing both, measured on the same graphs at constant density:

| Nodes | Pairs | gonum | own kernel | Factor |
|---|---|---|---|---|
| 50 000 | 112 370 | 4.6 s | 25 ms | 183× |
| 200 000 | 449 575 | 31.7 s | 126 ms | 252× |
| 400 000 | 899 260 | 100.7 s | 284 ms | 355× |

Modularity is identical to four decimal places, and the factor grows with the corpus because gonum's cost is superlinear while the queue-based one is near-linear. The S12 acceptance run on a real-shaped corpus confirmed the scale target: 9.8M nodes clustered in 30.7 s (K1) / 86.5 s (K2) at σ-drift < 4e-18.

The package also carries an optional refinement pass that splits any community into its connected components before the next aggregation level, so a community can never be delivered in two pieces with no edge between them. That failure mode is documented in the Leiden literature for sweep-based Louvain; against this kernel it could not be reproduced in 2 400 runs, plausibly because re-queueing a departing node's neighbours re-evaluates them immediately instead of a full sweep later. The pass is kept as a guarantee, not as a repair — it cannot lower modularity, and on an already-connected partition it changes nothing.

### Switching the engine: `graph_overview.engine`

`CTX_GRAPH_OVERVIEW_ENGINE` (`gonum` | `ctx`, default **ctx** since v4.31.0, hot) selects the clustering core. **Switching it recomputes every `cluster_id` in one go.** The topic layer absorbs that through the tombstone re-attach window, so make sure `graph_overview.tombstone_retention` covers at least two rebuild cycles *before* any switch (the shipped 45 d default does), and treat a switch as an announced release step rather than a config tweak — that is how the v4.31.0 cut itself was done.

An unknown value is a **boot error**, not a fallback. Writing `engine=leiden` and silently getting a gonum partition would be indistinguishable from success.

The engine also decides **which cap key applies** — `graph_overview.max_nodes` (200 000) for gonum, `graph_overview.max_nodes_ctx` (5 000 000) for the own kernel. There is no engine-dependent default; there are two keys with static defaults, and the value that actually applied is recorded per run in `graph_overview_run.max_nodes_eff`. That way an inherited 200 000 is distinguishable from a chosen one.

**`graph_overview.time_budget`** (seconds, default 600) becomes the primary liveness guard at `engine=ctx`. It bounds the **compute phase only** — a budget spanning the load would report a slow disk as compute time — and the mover checks it between queue blocks, so exceeding it is a clean skip rather than a SIGKILL. What does *not* change: the result is discarded whole. `graph_cluster_member` stays untouched, `computed_at` does not advance, the map freezes exactly as it does at the node cap. The guard swaps the trigger (node count -> runtime, the quantity itself instead of a proxy), not the mode.

The freeze reports the **existing** `skip_reason = 'timeout'` rather than a new value, so no migration is needed; the run journal carries the finer distinction. And a frozen run touches no identity: no topic is retired, renamed or relabelled.

### Kicking a rebuild ahead of cadence: `overview-rebuild-start`

`POST /api/manage` with `{"action":"overview-rebuild-start"}` (server-admin) wakes the rebuild loop before its `rebuild_interval` elapses — built for release steps whose evidence lives in the next rebuild (an engine cut's tombstone re-attach, a centroid backfill), where waiting out a six-hour timer is dead time. The kick takes the SAME path as the interval arm: tenant rotation, yield-on-active-queries, timeout and journal semantics are identical, and the interval re-arms after the run. The response is asynchronous (`armed:true`, or `armed:false` when a kick is already pending — coalesced, not an error); progress is read from `graph_overview_run`, not from the response.

### The child memory budget: `graph_overview.worker_mem_limit`

`CTX_GRAPH_OVERVIEW_WORKER_MEM_LIMIT` (bytes, default **0 = off**, hot) caps the rebuild child's Go heap and adds a pre-flight estimate that turns "out of memory" into a clean skip with a journal row.

**The default is off on purpose, and it deviates from the design.** The design proposed 160 MiB; that figure predates the measurement. The current compute path peaks at ~423 MB at the 200 000-node cap, so a 160 MiB ceiling would abort every run at today's cap — a memory guard would become a memory ban and the map would freeze permanently. Pick the value against `peak_rss_kb` in `graph_overview_run`, which exists for exactly this; ~60 % of the container limit is a reasonable starting point *after* you have seen your own numbers.

Two things happen regardless of the setting, because they cost nothing and only help:

- The child raises its own `oom_score_adj` to the maximum. The memory limit belongs to the **cgroup**, not to a process, and parent and child share it — without this the kernel may pick the daemon (which holds the graph cache over the whole corpus) as the OOM victim. The rebuild is the disposable work; the server is not.
- The child renices itself and drops to the idle I/O class, as before.

The pre-flight estimate runs **before any edge is loaded** — checking after the load would be checking after the expensive part — and it deliberately assumes the denser of the two design scenarios. An estimate that reads low would let the run walk into exactly the OOM it exists to prevent.

### `graph_overview.component_split`: clustering components separately

`CTX_GRAPH_OVERVIEW_COMPONENT_SPLIT` (default **true**, hot, effective only at `engine=ctx`) clusters each connected component on its own, with the resolution rescaled per component (γ_t = γ·m_t/m).

This is **provably the same objective**, not an approximation: a community spanning two components can always be split with strictly positive ΔQ, so the global maximisation decomposes exactly. The rescaling is what makes that true — without it, a six-node component would be cut into three communities merely because the rest of the corpus is large, silently changing the resolution for small components.

The run carries the decomposition identity `Q = Σ_t (m_t/m)·Q_t(γ_t)` as a **live control computation**, not just a test assertion: it costs nothing (the per-component values already exist) and a deviation beyond 1e-9 aborts the run rather than persisting a silently mis-resolved partition.

The honest yield is small and shrinking: 6.3 % of live nodes sit outside the giant component, and a giant component is the structurally enforced normal form above the percolation threshold, so its share grows with the corpus. The durable gain is `component_n` in the run journal — a quantity that simply did not exist before.

`graph_overview.compute_parallelism` from the design is **not implemented**. Fanning out across components would buy well under one percent at today's component distribution, paid for with threads in a nice-19 child running next to local inference. If a corpus ever shows many mid-sized components, that is its own change with its own measurement.

### Where the rebuild's lock time actually goes

The rebuild holds an advisory lock for the whole persist transaction, and that hold time is what serialises rebuilds of the same partition. Since migration 130 it is measured (`lock_held_ms`, from lock **grant** to commit — waiting for a lock is not holding it).

The member write now streams through `pgx.CopyFrom` into a temporary table that is filled **before the lock is taken**, so the one non-delta-proportional part of the write no longer counts against the hold. `copy_ms` is recorded next to `lock_held_ms` rather than folded into it, which is deliberate: without the split, moving work into an unmeasured phase would look like an improvement.

The measurement immediately shows where the time really is. On a 900-member corpus: `copy = 6 ms` against `lock_held = 776 ms`. The copy is negligible; the hold is almost entirely the topic-identity phase and the two aggregations. Anyone planning to shorten the hold should start there, not at the member write — and the run journal now says so per run instead of by intuition.

`graph_overview.delta_persist` (default **true**, hot) goes one step further and writes only the member rows that actually changed. It is **not** a lock-time measure and should not be sold as one — measured A/B on the same corpus, it saves 1.5 % of the hold (1365 ms → 1345 ms at 1 200 members). What it is for is **vacuum pressure**: the full replacement rewrites every member row on every run and marks every old one dead, which at 9.8M members and four runs a day means 39.2M dead tuples per day against 9.8M live rows, plus index bloat on three indexes. With delta persist an unchanged run writes **zero** rows.

One number worth knowing before relying on it: `cluster_id` is the smallest member UUID, so a newcomer with a smaller UUID renames a whole community and every member row gets rewritten even though nobody moved. The journal therefore reports `members_changed` **and** `members_reassigned` separately, and the difference is exactly that amplification. In a constructed worst case it was 27 % of the written rows.

`computed_at` becomes nullable **and loses its `DEFAULT now()`** (from migration 057). A partition that has never built successfully but already has an attempt behind it — a fresh deploy above the node cap — needs a row without a success timestamp; with the default in place a skip upsert that does not name the column would silently claim freshness. The read path is unaffected: `max(computed_at)` ignores NULL, so "never built" stays the zero timestamp and the `stats.computed_at` wire field stays `null` exactly as before.

Deploy notes, same shape as 116: the file carries `SET LOCAL lock_timeout = '3s'`, so it aborts with `55P03` rather than queueing behind a long-running persist transaction (a 400k-node rebuild measures ~465 s); every statement is idempotent, so the next boot simply re-runs it. Existing rows are backfilled with `last_attempt_at = computed_at` and `candidate_n = node_n` — historically correct, because only a successful run could have written them. No new table, no index.

### Topic identity: what a rebuild now does to `graph_cluster_topic`

Since migration 124 the map has an identity layer that the rebuild teardown does **not** touch. `cluster_id` still turns over on every run — it is the smallest member uuid of a community and changes the moment that one block leaves — but the `topic_id` on the node row stays, and it is the value a later map edge or retrieval signal refers to.

Each rebuild decides, per partition, what happened to last generation's topics:

| Outcome | Rule | Row |
|---|---|---|
| continued | mutual plurality **and** the new cluster holds at least **half** of the old topic's members | `last_seen_at` moves |
| re-attached | the cluster covers at least **half** of the core of a topic that died inside `graph_overview.tombstone_retention`, in the same scope | `retired_at` back to `NULL` |
| split | at least half of the NEW cluster's members came out of one old topic **that is still alive** in this run | new row, `origin_kind='split'`, `origin_topic_id` set |
| born | none of the above | new row, `origin_kind='birth'` — `origin_topic_id` is still recorded when the cluster came out of a topic that did *not* survive |
| retired | no cluster continued it | `retired_at` set; `merged_into` names the topic its majority went to, or `NULL` for a plain death |

There is no threshold to tune. "Half of the substance" is the rule in all three places, and it is scale-invariant on purpose: a stable one-block topic keeps its identity (1 of 1), and a 300-block topic is never inherited off a two-block overlap.

**Which wins when a cluster could both continue and re-attach.** A topic that tears into three clusters — none of them holding half — dies and leaves three fragment topics behind. When the community later reassembles, the reassembled cluster *does* have something to continue: a fragment. Left alone it would keep the fragment's identity forever while the real predecessor, whose whole core lies inside it, stayed a tombstone. The rebuild therefore lets a tombstone take a cluster from a continuation candidate in exactly one case: the candidate descends from that tombstone (its `origin_topic_id` chain reaches it) and was born no earlier than the tombstone died. Against an **independent** living topic the continuation always wins — organic growth outranks old graves.

Two operational consequences:

- **A topic never crosses a scope.** If a group of linked blocks moves from one scope to another, the old topic dies and a new one is born in the target scope. That is deliberate: a topic carries a label, and a label built from one scope's content must not appear on another scope's map.
- **A frozen map keeps its identities.** A run skipped by `graph_overview.max_nodes` returns before the persist transaction opens, so nothing is retired, nothing is renamed, and the last good map stays readable and labelled. The same holds for the second freeze reason, `empty-node-cut`: if the node set comes out empty while the partition still has living topics — reachable by configuration, because the node set is the *intersection* of the retrieval-visible types and `overview.include`, and an empty intersection selects nothing — the rebuild refuses rather than retiring every topic it has. The trade-off is deliberate and worth knowing: a partition whose last block is legitimately archived now freezes instead of emptying itself, and `skip_reason = 'empty-node-cut'` in `graph_overview_meta` is where you see it. A partition that has no identities *yet* is unaffected and still persists its honest empty map.

`graph_overview.tombstone_retention` (`CTX_GRAPH_OVERVIEW_TOMBSTONE_RETENTION`, seconds, default 45 d, hot) is the window in which a dead topic can still be re-attached. It exists for **batch imports**: an import that tears a partition apart across several rebuilds would otherwise rename every topic it touched. `0` switches the re-attach off — the rebuild then mints fresh identities, which loses continuity but can never revive a wrong one.

**The purge reads the same key, and that is the point.** Expired tombstones are deleted after each rebuild tick, so what the purge removes the re-attach can no longer read — one key governs both ends of the window and they cannot drift apart. Three properties are worth knowing operationally:

- it runs in the **parent** process, in its own short transactions, and holds **no** advisory lock. Steady state is a few hundred rows and would be harmless anywhere; the switch-on case is not — moving `tombstone_retention` from `0` to 45 d after months of operation makes the first purge a six-figure `DELETE`, and inside the rebuild's held lock that would stall the map;
- it works in **batches of 5000** with a per-tick round cap, so one transaction is never open long enough to hold up autovacuum or a parallel rebuild, and a pathological backlog is drained over several ticks instead of in one;
- `0` means **never delete** and is a legitimate operating state. A living topic is never purged however old it is, and a tombstone a node row still points at stays until that row is gone.

Lineage shortens rather than tearing: `origin_topic_id` and `merged_into` of surviving rows fall to `NULL` through `ON DELETE SET NULL`, so a stale reference degrades to "died, destination unknown" instead of a dangling id. The log line is `scheduler: topic tombstones purged` with `purged` and `retention`; it only appears when something was actually removed.

The rebuild log line `overview: topic identity` reports the run: `carried`, `reattached`, `born`, `split`, `retired`, plus `members_changed` and `members_reassigned`. The last two are worth reading together — `members_reassigned` is the share of the churn that is nothing but a community rename (the block moved `cluster_id` while its topic stayed the same). A high share means the map is stable and only its internal keys are moving.

### Every topic has a name, always

Since migration 125 a topic carries a `label`, and the rebuild writes one for **every** living topic in the same transaction that assigns the identity. No model is involved, no backend has to exist, no pipeline has to have succeeded: the map is never a list of unnamed circles, and nothing on the display path ever waits for inference.

The name is derived deterministically, strongest source first:

1. the three most frequent **tags** of the topic's core blocks (not of all members — the core is the statement about the cluster, the rim is noise). Only blocks classified `internal` or `public` contribute: a tag is free-form user input that no pipeline ever screened, and unlike the model-written name this path has neither a credentials scan nor an echo gate behind it. Note the consequence — `sensitivity` defaults to `credentials`, so on a deployment without a sensitivity audit most topics are named by their categories rather than their tags,
2. the three most frequent **categories**,
3. the representative block's title — today's map text, as the last readable rung.

Each stage is whitespace-normalised **before** it is tested for emptiness, and the whole cascade is capped at 120 characters with a code-owned constant as the terminal rung. Both details are load-bearing rather than cosmetic, and for the same reason: an empty or overlong label breaks the label CHECK *inside* the rebuild transaction, which rolls the whole rebuild back and freezes that partition's map for good. There is no length or content constraint on tags anywhere in the system, so a tag consisting of a single tab, or one of 200 characters, is an ordinary API write — and neither may be able to kill a map.

`label_source` records where a name came from, in descending strength: `manual` (a human set it) → `llm` (the label pipeline) → `fallback` (the cascade above) → `none` (never labelled). **The rebuild only ever writes over `fallback` and `none`.** A hand-set or model-set name survives every rebuild.

What the rebuild *does* maintain for every row, whatever its source, is the drift state: `label_stale` becomes true when the topic's core has changed since the name was built (`label_core_hash` vs the freshly written `core_hash`), and `label_attempts` resets to zero at the same moment — a changed core is a new input, so a topic that failed to get a model-written name three times is eligible again rather than unnamed forever. Membership churn at the *rim* of a cluster changes neither, which is what keeps re-labelling rare.

The counter `labels_touched` on the `overview: topic identity` log line is the number of topic rows the label pass wrote in that run.

### The label pipeline: a better name, never a required one

A second arm (`scheduler: topic labeling`, own goroutine, own cadence) asks a model for a short topical name and writes it as `label_source='llm'`. It is an **improvement path**, not a dependency: every failure — no backend, no eligible chain, an unparsable answer, a rejected one — leaves the deterministic fallback in place. Nothing on the read path ever waits for it.

It runs in the **parent** process, not in the rebuild worker: the worker child builds a database pool and nothing else (no backend pool, no admitter), a model call inside the persist transaction would hold the advisory lock for minutes, and the two cadences belong apart — a partition is rebuilt every 6 h, a name only has to follow a core drift.

**What gets selected.** Living topics of the served tenant's scopes whose `label_stale` is set and whose `label_attempts` are below three, ordered by cluster size so the topics at the top of the map are named first. `label_source='manual'` is excluded **in the selection**, not only on write — filtering it on write alone would spend a full model call per interval on every pinned topic, forever, because a successful call does not raise the attempt counter.

**Why it is safe to ship on.** `CTX_GRAPH_OVERVIEW_LABEL_ENABLED` defaults to `true`, but `CTX_GRAPH_OVERVIEW_LABEL_MIN_TOPICS` (default 10) is what decides whether anything happens: a scope with fewer living topics is not labelled at all. A small or fresh corpus therefore stays quiet without an operator having to know a switch exists, and the first labelling run happens when a corpus becomes complex enough to need names — not as a boot-time backlog. `false` remains the hard opt-out.

**Three layers keep it off the interactive path**, in order of how they act: `CTX_GRAPH_OVERVIEW_LABEL_BATCH` (default 200) caps the calls **one tick** may start across all scopes of the tenant served; the interactive-demand check sits *inside* the batch loop and ends the batch (the remaining topics stay selectable for the next tick); the background lease preempt is the last resort, because it aborts running attempts and spends GPU time without a result. A batch also ends when it reaches `CTX_GRAPH_OVERVIEW_LABEL_INTERVAL`, which makes "a tick never outlasts its interval by more than one label" a property of the code rather than an assumption about model latency — the brake is checked *before* each label, so a call already running is not cut and the tick can overrun by at most one `CTX_GRAPH_OVERVIEW_LABEL_TIMEOUT` (90 s by default; configuring it above the interval is what makes that bound visible, and boot WARNs when you do).

**Label output hardening** (three stages, the first two unconditional):

1. the finished label runs through the same credentials scan the block write path uses — a secret that survived from content into a title and from there into a name is discarded;
2. a deterministic **echo gate**: if the label repeats a substantial word pair (order-independent), a distinctive single word of seven characters or more, or — for scripts without word separators such as Han, Kana and Hangul — a contained run of three characters or more from the title of a `credentials`/`personal` core block, it is discarded. Both sides are Unicode-normalised (NFKC) and case-folded first, so a different normalisation form, a full-width rendering or a reordered pair is not an escape. Deterministic on purpose — guarding a model's output with another model would only move the failure one level up;
3. `CTX_GRAPH_OVERVIEW_LABEL_CREDENTIALS_FALLBACK_ONLY` (opt-in, default off) keeps a core containing credentials out of the model path entirely.

Turning that third stage ON is **sticky**: the affected topics are parked (their drift anchor is written, so they stop being selected) and turning the knob back off does not un-park them — the arm reads a fresh config snapshot each tick and cannot observe that the value just changed. They re-arm by themselves on their next core drift, or immediately with

```sql
UPDATE graph_cluster_topic SET label_stale = true
 WHERE label_source = 'fallback' AND label_core_hash IS NOT NULL
   AND retired_at IS NULL;
```

Re-arming automatically was rejected on purpose: it would widen the label selection from one narrow index range to two, permanently, to serve a rare and deliberate transition.

A discarded label costs one attempt and leaves the fallback standing. A **preempted** call does not: the background lease preempt and a dead context mean the system took the slot back, not that the model failed, and counting them would let three busy ticks lock a topic out until its core happens to drift. Rejections are **counted, never silent**: `rejected_shape`, `rejected_scan` and `rejected_echo` appear both in the arm log and in `/api/status` under `cluster_map.labeling`. Neither the rejected name nor the matched fragment is ever published — the echo gate logs a fingerprint (length plus a short hash), because the fragment it matched is by definition the string suspected of carrying substance out of a credentials-classified title.

The prompt carries **titles only, never content** (12–24 of them, capped by `CTX_GRAPH_OVERVIEW_LABEL_PROMPT_MAX_TITLES`), plus the topic's top tags and categories, all inside one nonce-guarded block with a fresh nonce per prompt. The answer contract is a single JSON object with exactly the key `label`; validation is purely structural (non-empty, at most 120 characters, no control markers) — **no confidence is read and none is asked for**, because the project's own measurement says a model's self-assessment is unusable as a gate. The label language follows `CTX_DREAM_LANGUAGE`: one language knob per corpus, not two. The **root map's own scaffolding** — its headings, coverage wording, freeze clauses, footer and number formatting — reads the same key, so the labels and the sentences around them can no longer disagree; empty or a `de*` tag keeps the frozen German map, every other tag renders it in English.

`/api/status` renders the arm under `cluster_map.labeling` with a `state` of `active`, `below-threshold (n/N)`, `no-backend` or `off`, plus the tick's counters and `latency_p50_ms`/`latency_p95_ms`. A pipeline that is doing nothing produces no log lines, so the state is the signal.

### `topic` and `label` on `GET /api/graph/overview`

Each map node gained two **optional** fields. `topic` is the stable identity across rebuilds, `label` its name. Both `omitempty`: a database that has not yet run a rebuild with the identity layer answers byte-identically to before, which is what makes the change deployable ahead of any rebuild.

`label` **accompanies** `repr_title`, it does not replace it — the only interaction path of the map is the drill-down on `repr_id`, and `repr_title` is its caption. Clients render `label ?? repr_title`. The wire grows by roughly 82–102 bytes per node; the node cap stays at 2000 (default 500), because lowering an explicitly requested parameter would be a behaviour break for existing clients.

**Why `topic` may be emitted while `cluster_id` may not.** `cluster_id` *is* a block UUID — the smallest member id of the community — so emitting it would disclose the existence and identity of a possibly invisible block. `topic_id` is a v4 UUID: no block reference, and no timestamp component either (a v7 would leak when a rebuild first saw the community). It is also scope-partitioned, so two tenants can never observe a common handle. Everything else the identity knows — `retired_at`, `merged_into`, `origin_topic_id`, `created_at`, `label_attempts` — stays server-side: those are events whose timing allows inferences about rebuild runs and corpus activity.

**The legacy switch decides per request, and it errs towards a complete map.** As soon as *one* readable node row lacks a `topic_id`, the whole response falls back to the pre-identity shape — no `topic`, no `label`, node set unchanged. A map without identities is exactly the old map and lossless for a client; a map with missing *nodes* would be silent data loss. The mixed state is real and lasts: the rebuild serves one tenant per tick at a 6 h cadence, so with N tenants full coverage takes N × 6 h, and a caller whose read scopes span both partitions (the `shared` case) would otherwise get a silently halved map.

**A frozen partition stays on the legacy path.** The two freeze reasons — `node-cap` and `empty-node-cut` — both return *before* the persist transaction opens, so a partition that was frozen while its node rows still carried `topic_id = NULL` keeps exactly those rows: no rebuild ever assigns them an identity, and the probe therefore keeps answering "legacy" for every request that reads that scope. Two consequences worth knowing: the scope serves no `topic`/`label` at all, and — because the decision is per request, not per scope — it drags every scope read alongside it onto the legacy path too. The fix is not a read-path setting but the freeze itself: clear the cause (`skip_reason` in `graph_overview_meta` names it), let one rebuild succeed, and the identity appears with it.

One visible consequence of the scope-bound identity: a cluster whose members live in two scopes now renders as **two** nodes with disjoint `scope_mix` and disjoint `top_categories`, instead of one node with merged counts. Live that case is zero and `/api/status` counts it under `cluster_map.cross_scope_clusters`. Meta-edges keep working across the split because the identity path aggregates them per (cluster pair, **scope pair**) and resolves each endpoint to the half it actually touches — a cluster-pair-only aggregate could not say which half an edge belongs to, and the edge would have to be dropped. The scope pair is stored **oriented like the cluster pair**: `cluster_a`/`cluster_b` are normalised so the smaller UUID comes first, and `scope_s`/`scope_t` are swapped along with them. Reading the two positionally is the whole point of keeping them.

### Retiring the two dead linear topic maps (ops step, not a migration)

`topic-map-work` and `topic-map-hth` have not been rebuilt since 2026-03 and still show up in every `ctx search index` result; the second one additionally advertises a **wrong** bootstrap path (its title says `hth`, its scope says `work` — a pre-scope-clamp leftover). `scripts/archive-legacy-topic-maps.sh` retires them.

It is deliberately **not** a migration: it touches data, and a human should see the pinned before-state before anything commits.

```bash
bash scripts/archive-legacy-topic-maps.sh          # dry run — rolls back, changes nothing
bash scripts/archive-legacy-topic-maps.sh --apply  # commits
```

Both modes print the same pin — id, scope, content length, content SHA-256 — and a ready-to-paste rollback one-liner per row. The step sets `is_archived = true` and **never deletes**: an archived block is gone from the hit list but still readable via `ctx get <id>`, and that readability *is* the rollback path.

Two belts keep it off the wrong block: an explicit title allowlist (exactly those two), and a **producer guard** — a scope is skipped as long as an *active* API key calls it home, because then something still writes that map and archiving would be fighting a live producer. The active tenant's `topic-map-private` is in neither list. Re-running the script is a no-op (it only picks up blocks that are not yet archived).

Order matters: run this **after** `digest.mode=stub`, so the in-band pointer to the root map is already in place for the map that stays.
