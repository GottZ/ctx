# HTTP API

All endpoints under `/api/*`. Auth via `X-Context-Key` header or `Authorization: Bearer` token.

## Endpoints

| Endpoint | Description |
|----------|-------------|
| `POST /api/query` | 4-Way RRF + LLM synthesis (auto-backfills pending embeddings). Optional `categories_exclude` / `types_exclude` arrays filter slot-stealers (`block_roles_exclude` = documented legacy alias for `types_exclude`, both ⇒ union). Optional `sensitivity` classifies the query text for trust gating (default settings key `pool.default_query_sensitivity`). Optional `include_content` attaches a ≤1500-char snippet per source on the retrieval-only path (`synthesize:false`, default off so eval/sweep responses stay byte-identical — the chat harness's ctx_query tool sets it). Whenever synthesis is on (`synthesize != false`), the response commits `200` up front and streams a whitespace keepalive every 25s so buffering proxies don't hit their read timeout; the body stays valid JSON (leading whitespace, RFC 8259) and a late synthesis failure reports `success:false` inside the 200 body. |
| `POST /api/store` | Upsert (embedding async via scheduler). Optional `sensitivity` (`credentials`\|`personal`\|`internal`\|`public`) classifies the block manually (`sensitivity_source='manual'`); absent ⇒ settings key `pool.default_block_sensitivity` (fail-closed `credentials`). On an upsert conflict an explicit value applies upgrade-only — downgrades go through `manage update` with `confirm_sensitivity_downgrade`. A credentials pattern in the content forces `credentials` upgrade-only regardless of the requested level (G40 detector, `sensitivity_source='pattern'`). Optional `type` validates against the registry and sets `type_source='manual'`. |
| `POST /api/search` | Lightweight search (no LLM). Results carry the type axes (`type`/`lifecycle_state`/`type_source`). Optional `types` / `types_exclude` arrays are server-side opt-in type filters (bind parameters; `block_roles_exclude` = legacy alias, both ⇒ union). Optional `cluster` is the topic facet — see [Cluster facet](#cluster-facet-clusterhandle). |
| `GET /api/graph/ego` | Scope-filtered k-hop ego subgraph over dream links (read-only, no LLM — see [Graph API](#graph-api)). |
| `GET /api/graph/all` | Flat load-all seed: every visible block up to the budget ceilings (newest-first, deterministic), induced edges of both data classes, degrees. Same envelope as ego with `focus:""`; no traversal params (see [Load-all](#load-all-flat-corpus-seed)). |
| `GET /api/graph/overview` | Scope-pure Louvain cluster supergraph ("landkarte"); reads precomputed scope-partitioned aggregates, gated on `graph_overview.enabled` (off → 404). Read-only, no LLM. |
| `GET /api/graph/cluster` | Cluster ego: the members + neighbour topics of ONE topic handle (see [Cluster ego](#cluster-ego-get-apigraphcluster)). Double-gated on `graph_overview.enabled` **and** `cluster.route_enabled` (both default off → 404, indistinguishable from an absent route). |
| `POST /api/synthesize/daily` | Manual trigger of the daily synthesis (Tagesbericht) for the caller's `home_scope` — the same `GenerateDailyReport` path the 03:00 scheduler iteration runs (digest role, constant internal). Concurrency cap 1 per principal (429 fail-fast), dispatch-interactive (429 + `Retry-After` on capacity rejection). Optional `?date=YYYY-MM-DD` (M103) re-synthesizes the report titled that day over its historical window `[date-1 03:00 UTC, date 03:00 UTC)` — the backfill path; the `(category, title, scope)` upsert replaces the old report in place (same block id, embedding regenerates). A malformed date or a window that has not closed yet ⇒ 400. `{ok, block_id, scope[, date][, reason:"no_activity"]}`. The report language follows the hot `dream.language` setting, read per request: empty (default) keeps the German surface this row describes, any other tag localizes **title and tag together** (`Daily Report <date>` / `daily-report`) — so a change **starts a new series** instead of continuing the old one, and a backfill after the switch writes a second block for a day that already has a `Tagesbericht`. Deliberate and operator-triggered; see [`CTX_DREAM_LANGUAGE`](operations.md#environment-variables). |
| `GET /api/whoami` | Calling key's identity: `label`, `home_scope`, `read_scopes`, the server-global `admin` tier flag, plus the Model-C tenant identity `tenant_id` + per-tenant `role` (`owner`/`admin`/`member`), and the feature-flag bag `capabilities` (`{workflow: true}` since v4.3.0 — switches the SPA's issues/board surface visible; the field is data, so a later per-tenant gate only changes the value, not the SPA). The SPA login gate probes it, derives its read-only degradation from `admin`, and tells server-admin from tenant-admin. |

A server-admin additionally sees `advisories` (`[{subject, state}]`, omitted when empty): named reasons for states the frame can only show as an absence — today exactly `backend_pool: empty` (fresh install, nobody seeded yet; deliberately NOT in the public `/health` body). Served from a cache (N pollers cost one collection). Carries hostnames, so it is admin-gated where `/health` stays anonymous. Opens to a tenant-admin with a reduced own-tenant view (see [multi-tenancy](multi-tenancy.md#telemetry-per-tenant-views)). |

| `POST /api/manage` (`disable-profile-list/create/update/delete/toggle`) | Disable-profile registry (tenant-admin; tenant profiles may only contain own-scope backends, `_global` profiles are operator-owned). Toggle returns `{profile, impact, as_of}`; blacking out a whole role requires `confirm_role_blackout` (else 422; `dry_run` supported); the reserved `eject` profile is not deletable. |
| `POST /api/manage` (`backend-create`/`backend-update`, field `disable_profiles`) | Profile membership as a backend property: list of profile NAMES (key absent = unchanged, `[]` = detach all); joins sync in the same transaction as the backend write. A tenant-admin may attach its OWN backend to `_global` profiles (self-disable) or its own tenant profiles; a scoped profile never contains foreign-scope backends. `backend-list` echoes `disable_profiles` including inactive membership. |
| `GET\|PUT\|DELETE /api/graph/category-hues[/{category}]` | Per-category graph HUE overrides (093, AM-2): GET (**any valid key** — the graph is a member surface) returns the resolved sparse map `{category: hue}` for the caller's `{_global, tenant}` view, tenant beating `_global` per category; PUT `{"hue":0–359}`/DELETE (**tenant-admin**) write the caller's own scope (operator → `_global`), never a client-supplied one. Only the hue is overridden — sat/lum stay theme tokens, so every choice sits inside the G1a contrast sweep. Absent override = seeded hash colour. UI: the hue wheel at `/settings/hues` (U02-W6) — markers sit at perceptual OKLCH angles for distance judgement, the stored value is always the HSL degree. |
| `GET /api/llmlog` | **Admin** LLM telemetry table (`?limit=`/`pipeline=`/`errors_only=`). NEVER returns the `request_system`/`request_user`/`response_content` body columns (the prompt shadow corpus); the `error` is normalized to a class + 256-char-capped detail. Tenant-admin sees only its own tenant's rows. |
| `GET /api/events` | **Admin-only** SSE live stream (`text/event-stream`) for the dashboard. The collector diffs its snapshot ONCE per tick and fans `status`/`backends`/`llmcalls` events to every connection; a new connection gets the full state first, then diffs. The pull path additionally carries `guard_review_by_scope` (S6): one four-tuple per scope the CALLER may read, out of the same per-tick generation (0 extra queries), per-credential and therefore never in the shared snapshot or the push frame — the /guard page polls and compares this vector (list and counter run on two different scope predicates: `ReadScopes` vs. home scope) and reloads when it moves; absent section renders '—', never '0'. The `status` frame carries the `guard_review` section (same generation as the pull paths, S2): present-with-zeros means a freshly measured empty queue, an ABSENT section means no fresh generation — and its `built_at` stamp is diff-neutral (zeroed in the diff key like `as_of`), so a walking stamp alone never fires a frame. One tick costs at most ONE frame per event kind: the telemetry rows of a tick ride a single `llmcalls` frame `{rows, count}`, and above `events.llmcall_coalesce_threshold` it degrades to the content-free `{kind:"llmcalls-bulk", count, cursor}` refetch signal (the client reloads over `GET /api/llmlog`) — the same coalescing doctrine `project.events.coalesce_threshold` runs on the domain-event hub. `hb` keepalive event (`CTX_EVENTS_PING_INTERVAL`) carrying `{last_good_at, degraded, health}` — a REAL named event, not an SSE comment, so the client can observe it: `last_good_at` is the newest tick whose DB-backed reads all answered, so a stream that keeps arriving while that stamp freezes means "transport fine, server blind" (`as_of` cannot say this — it advances on failed reads too). The SPA consumes it (S4): the `/status` SSE client arms a payload+transport watchdog (2.5 × ping interval) that flips its state to `stale` when the stamp stops advancing or frames stop entirely — `stale ≠ open` reactivates the page's poll fallback with no call-site change, and a `ConnState` live-region indicator (dot + word, `degraded>0` → `partial`) renders it in the page head. The watchdog is opt-in per stream: `/api/project/events` keeps its comment keepalive and stays unwatched. A rolling 90s write deadline that outlives the absolute server `WriteTimeout`, the `CTX_EVENTS_MAX_CONNECTIONS` cap → 429 (client degrades to polling), and an in-stream re-auth every 12th tick that ends the stream on key revocation. |
| `GET /api/project/events` | **Member** SSE domain-event stream (`text/event-stream`, workflow W9) for live board / issue-list updates. A key receives IDS-ONLY frames — `project` events `{kind, project_id, op, block_ids}` or the coalesced `{kind:"issues-bulk", project_id, count}`; NEVER title/content/body (the client refetches over the read API). Frames are **scope-filtered at the fan-out**: only the caller's readable project scopes, never another tenant's. Optional `?project_id=` pins the stream to one project (foreign/unknown ⇒ 404 uniform). Per-**tenant** connection cap (`project.events.max_connections`) → 429; `: ping` keepalive; a 10k-import burst collapses to one `issues-bulk` frame per tick (`project.events.flush_interval` / `coalesce_threshold`). In-stream re-auth recomputes the caller's scope tags from the FRESH read set every ~12 flush ticks: a revoked key or a tenant change ends the stream, and a revoked cross-tenant **scope grant** (tenant/role unchanged) drops that scope's frames — separate from the server-admin telemetry `/api/events`. |
| `POST /api/digest` | Topic map generation. Rebuilds the linear topic map and — when `root_map.enabled` is on — also renders the **root map** (`root-map-<scope>`, cluster-per-line, capped at `root_map.budget_bytes`). It never starts a Louvain rebuild: the map is rendered from the cluster state that already exists, so the route cannot become a lever on a job bounded only by `graph_overview.rebuild_timeout`. Carries its own write rate-limit bucket (`digest`) since the root-map wave. Response gains `rootMapTitle` / `rootMapLength` **additively**; `title`, `blockCount`, `categoryCount` and `contentLength` keep their meaning, and the two corpus counts behind them now run under `root_map.count_timeout` (0 = not measured this round) instead of unbounded. |
| `POST /api/ingest` | Obsidian vault ingestion. |
| `POST /api/blob/*` | Binary storage (store/fetch/search/manage). Write rejections additionally carry a machine-readable `"code"` (Gap-C6-c): the closed vocabulary is `unauthorized`, `invalid_body`, `missing_fields`, `invalid_sensitivity`, `invalid_encoding`, `scope_denied`, `size_cap`, `unknown_type`, `unknown_action`, `constraint`, `rate_limit`, `internal` — one code per rejection class across `/api/store`, `/api/blob/store` and the MCP `store` tool (there as `structuredContent.code`, the `Content[0].Text` prose is unchanged; a STAGED answer is deliberately uncoded — IsError plus code means refused, IsError without code means staged). Answers without a code keep their exact pre-existing envelope (no empty `code` key). `store` runs on its OWN write budget: `pool.blob_rate_limit_write` (tenant-overridable, default 10) per api key and 60-second window, counted over the separate `blob-write` action in `context_access_log` — a key at its `query.rate_limit_write` block-write limit may still upload, and uploads never consume the block budget. `0`/unset falls back to the VALUE of `query.rate_limit_write` (unlimited needs BOTH at 0). The budget is booked BEFORE the upsert, so a write that ends in a constraint violation still costs it; over budget ⇒ **429**. Each stored blob leaves one audit row referencing it through `context_access_log.blob_id`, which is intentionally unconstrained — the row survives the blob's deletion. **MCP transport (W02-8):** `blob_store` / `blob_fetch` run this same write path — required fields, name caps, base64 decode, the `writableBlockScopes` gate and the `blob-write` budget are ONE shared core (`handler/blob_core.go`), so both surfaces answer the identical code and the identical prose for the identical request. `blob_store` takes the payload as `file` (base64, same `invalid_encoding` verdict) **or** `text` (UTF-8) — exactly one of the two — and carries **no `scope`** (decision D4, like the `store` tool): an MCP blob write always lands in the calling key's `home_scope`, while the explicit-scope gate stays the REST route's. A `confirm_writes` key gets the call **staged** (a `payload_hash` instead of an id, `IsError=true`, executed by `confirm`), and a payload above `pool.blob_stage_max_bytes` (tenant-overridable, default 1 MiB; `0` disables blob staging for such keys entirely) is **refused by name** rather than written direct. The budget is charged at stage time, so the confirm books nothing. `blob_fetch` reads a **byte range** of the stored payload (`offset`/`length`, default 262144, max 1048576; a larger `length` is refused, never clamped, so a short answer always means the blob ended) and names its `encoding` (`text` when the window is valid UTF-8, else base64); `meta_only` returns metadata alone. The REST fetch route is unchanged and still answers the whole blob in one piece. |

## Manage actions

`POST /api/manage` covers CRUD, Guard API, stats, key/MCP-client management, the block-type registry and the issue corpus.

- **Keys/clients:** `api-key-create` requires `home_scope`; key + MCP-client management and mutating `dream-mode` require an **admin key** since migration 052 (see [security](security.md#admin-tier)). `api-key-create`/`api-key-update` accept optional `write_scopes` (078, E4b) — explicit per-key write scopes that must be ⊆ `allowed_scopes ∪ {home_scope}` (else 400); the effective block-write gate and its double enforcement are in [multi-tenancy](multi-tenancy.md#per-key-write-scopes-e4b-migration-078). Per-tenant scoping of the `api-key-*` actions and the tenant lifecycle (`tenant-*`, `tenant-grant-*`, `scope-*`, `tenant-limit-set`, `tenant-usage-get`, `tenant-quota-*`, `block-grant-*`) are in [multi-tenancy](multi-tenancy.md).
- **Block-type registry:** `type-list`/`type-get` are open reads; `type-create`/`type-update`/`type-delete` are the **operator transport** (server-admin, `_global` namespace) of the same store logic the REST `PUT/DELETE /api/types/{name}` surface uses — kept functional for MCP/CLI consumers, not superseded (see [Block-type registry](#block-type-registry)). `manage update` accepts a registry-validated `type` field; `list-meta` accepts the `types`/`types_exclude` filters.
- **Issue corpus:** `issue-create`/`issue-update`/`issue-get`/`issue-list`/`issue-comment-create`/`issue-link-create`/`issue-link-delete` are the **operator transport** (all tierOpen; isolation is store-layer scope filtering, not an admin tier) over the same store issue logic the REST `/api/project` issue surface (W6/W7) uses — kept reachable for MCP/CLI operators, not the primary UI surface (see [Issue corpus](#issue-corpus)).
- **Backend pool:** `backend-list`/`create`/`update`/`delete`/`test` — see [Backend pool](#backend-pool).
- **Guard review:** `guard-list` returns the flagged blocks of the caller's read scopes (similarity-sorted; each row carries `type_name`, `guard_status`, `similarity` and the matched partner `matched_id`/`matched_title` — cross-scope partners are `[redacted]`). Filters: `status`, `category`, `types[]` (bind parameters, WF-T10 line); `limit` clamps to 200. `guard-stats` is the aggregate pull. `guard-resolve` takes `id` + `data.resolution ∈ {archive, keep}` (unchanged single wire shape) **or** `data.ids[]` (batch, cap 500, one transaction): the batch touches only actually-flagged states (`needs_review`/`near_duplicate`/`possible_duplicate`) and accounts for every id — `resolved[]` plus `skipped[]` with a reason (`invalid_id`/`not_found`/`already_archived`/`not_flagged`; cross-scope ids collapse into `not_found`, no existence oracle). Write gate is `writableBlockScopes`. The **push side** of the same pipeline: `GET /api/status` carries a `guard_review` section (per-state counts + `oldest_updated_at` + `built_at`) on **both** paths — global for server-admin, home-scope-filtered for tenant-admin — and the daily report closes with a `Guard-Review offen` stand section while the queue is non-empty (live reports only, never backfills). Both paths read ONE generation per `events.tick_interval` (a single `GROUP BY ROLLUP (scope)` aggregate carrying the grand total and every scope's row), so N tenant polls inside a tick cost one query, not N. `built_at` is that generation's success stamp: a failed rebuild keeps the previous generation untouched, and once the stamp exceeds three tick intervals the section is **omitted** rather than served stale. A scope with no flagged blocks reads `{0,0,0,null}` (materialized from `context_tenant_scopes`); an unknown or empty scope yields **no section** — the grand total is reachable only through the server-admin path, never through a scope lookup. MCP transport: `guard_list`/`guard_resolve` mirror these actions (REST field parity, golden-pinned); `guard_resolve` refuses `archive` for `confirm_writes` keys (not stageable — fail-closed instead of bypassing the staging policy). SPA surface: `/guard` (tenant-admin-or-up nav, server-side authorization unchanged).
- **Dream review & link curation:** `dream-review` is the read surface (stats, `low_confidence` candidates — pinned links are excluded from the candidate queue, `supersedes_pairs`, `recent_checked`); each link row carries the resolve identifiers `source_id`/`target_id`/`relationship` plus `rationale` (and `pinned` on supersedes pairs). `dream-link-resolve` (tierOpen, guard-resolve pattern) is the write side — one link per call, addressed by `data.source_id` + `data.target_id` + `data.relationship` (the relationship is matched as a guard: a link re-classified since the review reads as not found instead of being blindly resolved). `data.resolution ∈ {confirm, delete}`: **confirm** sets `pinned=true` (+ optional `data.rationale`, durable; confirm without rationale keeps an earlier one) — a pinned link survives the dream replace sweep (migration 119); **delete** removes the link and, for `supersedes`, reverts the target's snapshot marking (`lifecycle_state` → `knowledge`, `superseded_by` → `NULL`, only while it still points at this source). Write gate is `writableBlockScopes` on the **source block**; foreign/invisible/absent links and malformed ids collapse into one `Link not found` (no existence oracle). Every resolve is audited in `context_write_log` (`decision='dream_link_resolve'`). Automatic dream writes leave `rationale` NULL — the benchmarked V5 eval prompt emits no reason field.
- **Back-off re-evaluation:** `dream-backoff-restamp` (tierTenantAdmin) recomputes every existing re-dream cooldown stamp under the **current** `dream.backoff_*` policy: `dream_cooldown_until = dream_checked_at + curve(dream_eval_count, dream_last_inert)` — the immediacy half of a policy save, since the hot config only governs *future* cycles while stamps written under the old curve would persist for up to the old cap. The block's inert standing is preserved (`dream_last_inert`, migration 131), transient minutes-scale claim stamps are recognized by their sub-hour span and left untouched (a live worker claim must not reopen), and the mutation binds to the caller's **own entitlement** (`home_scope` + `allowed_scopes`, never grant-widened read scopes — a granted reader must not rewrite a foreign tenant's dream scheduling). Response: `{restamped, skipped_transient}`. The settings UI triggers this automatically after a Save of back-off keys.

**Explicit type on writes.** `POST /api/store`, `manage update` and the MCP `store` tool all take an optional `type`: the name is validated against the caller's effective registry snapshot (unknown ⇒ rejected fail-closed, code `unknown_type`) and the block is written with `type_source='manual'`, which the title classifier never re-touches afterwards. Omitting `type` keeps the classifier's guess (`type_source='auto'`). On the MCP side the field is hash-bound through the stage-then-confirm dance (`CanonicalWrite.type`), so a `confirm_writes` key confirms exactly the type it staged; an absent `type` canonicalizes to the same bytes as before the field existed, leaving every already-issued `payload_hash` valid. The MCP `update` tool carries no `type` — re-typing an existing block stays on `manage update`.

**Type axes on responses.** `/api/search`, `manage get`, the MCP/chat `recent` surface and `manage list-meta` carry `type` (policy type), `lifecycle_state` and `type_source` per block; `/api/query` results carry `type`. Server-side type filters (`types` / `types_exclude` arrays) are pure opt-in bind parameters — no hard exclude (retrieval-excluded types stay browseable by design), with `block_roles_exclude` kept as the documented legacy alias everywhere including `/api/query` (both names ⇒ union).

The block-type registry has its own REST namespace, the canonical surface going forward: reads (workflow W1) are **member-gated** — any valid key reads — and writes (workflow W2) are **admin-or-tenant-admin-gated**. ## Issue corpus

Issues and comments are ordinary `context_blocks` (`type_name` `issue`/`comment`, migration 084 seeds) — they inherit scope isolation, RRF, Guard and Dream for free (Modell C, one project scope = one repo corpus). The **primary** wire surface is the REST `/api/project` issue family (workflow W6/W7); the `manage issue-*` actions below are the **operator transport** over the identical store functions (`store.InsertIssueBlock`/`UpdateIssueBlock`/`InsertCommentBlock`/`GetIssue`/`ListIssues`, plus the structural-link store) — one logic, two transports (masterplan K2). **render:'untrusted'.** Every body-bearing response (`issue-create`/`issue-update`/`issue-get`/`issue-list`/`issue-comment-create`) carries `render: "untrusted"` — issue/comment bodies are attacker-controlled markdown; the UI MUST take the sanitising render path (the field cannot be silently overlooked).

Foreign-scope MCP writes arrive only with F6-C6.

### Forge sync (`manage` actions, workflow I-F)

Under masterplan K14 there is **no** separate forge-repo registry — the project register above **is** the forge registration. So the forge family carries only the PULL sync surface, as `manage` actions (all **tenant-admin**; ownership is re-checked per project, a foreign project ⇒ uniform 404). GitHub PULL-only in I-F: conditional ETag requests (a 304 does 0 writes and does not count against the rate limit), a `since` window, strict Link-header pagination, `pull_request`-field PR filtering (PRs never become issues), and rate-limit respect (403 + Retry-After / x-ratelimit-remaining:0 ⇒ exponential `backoff_until`, cap 1h — never a conflict). Outbound dials pass a dial-time SSRF guard (`net.Dialer.Control` re-checks the resolved IP against the private/loopback/link-local deny-list, closing DNS rebinding). **The 3-way direction logic + block/mapping writes are Welle I-G** — I-F fetches, gates and records; it writes no blocks.

### Webhooks (inbound, workflow W13)

`POST /webhooks/github/{project_id}` is the **first and only unauthenticated write surface** — mounted OUTSIDE the `/api` Auth group because GitHub POSTs it with no api key. HMAC-SHA256 over the raw body against the per-project sealed secret (`X-Hub-Signature-256: sha256=<hex>`, constant-time compare) takes the place of the api key. The **verbindliche Prüf-Reihenfolge** (the order is part of the security model) is `Body-Cap → Projekt-Lookup → HMAC-Verify → Rate-Limit → INSERT → 202`:

- **Signature before any DB write:** a forged/absent signature ⇒ **401** and ZERO `context_webhook_events` rows.
- **Rate-limit after verify:** the per-project budget (`webhook.rate_limit`, default 120/min) counts ONLY signature-valid deliveries, so an unsigned flood can never push a legitimate delivery into 429 (Denial-of-Sync). Overflow ⇒ **429** + `retry_after_s`.
- **Unknown/unconfigured project ⇒ uniform 401** with structural constant-work (the lookup→resolve-secret→hmac chain runs against a process-constant random secret; no response oracle).
- **Redelivery idempotency:** `UNIQUE(project_id, delivery_id)` + `ON CONFLICT DO NOTHING` collapses GitHub's own redeliveries (identical `X-GitHub-Delivery` GUID) to exactly one row. This is NOT replay-protection — the GUID is unsigned; the real mitigation is the translator (below).
- **Events are a TRIGGER, never authority:** the scheduler inbox arm drains pending rows with `FOR UPDATE SKIP LOCKED`, **debounces** them to ONE forge sync per project, and the sync translator applies the 3-way content hash against the forge IST-state. A replay (new GUID, old payload) therefore changes NO block state — the payload is never upserted.

**Secret lifecycle** (`POST|DELETE /api/project/{id}/webhook-secret`, tenant-admin of the owning project): the secret is **server-generated** (crypto/rand, 32 bytes hex), sealed (AES-256-GCM, AAD binds name+scope) in the PROJECT scope under the server-fixed name `webhook.github.<project_id>`, and **revealed once** in the POST response (paste it into the GitHub webhook config). Rotation = another POST (old secret stops verifying). Deliberately NOT `ctx secrets set` / `/api/secrets`: that path maps a tenant-admin onto its HomeScope and could never reach the project scope. `webhook_secret_ref` is server-managed — a PATCH that names it ⇒ **422** (a free ref would turn the public endpoint into an HMAC-verification oracle over foreign secrets). A project delete AND a tenant prune drain the sealed secret (no orphaned credential).

Config keys: `webhook.rate_limit` (per-project deliveries/min, tenant-overridable) and `webhook.retention` (age past which the scheduler Janitor arm evicts PROCESSED inbox rows index-gestützt over `idx_webhook_done`, default 14d, global-only; 0 = keep forever).

## Project issues (read surface)

The project issue read surface (workflow W6, `MountProjectIssues`) is the SPA's board + list + detail source. It resolves `{id}` to the project's single scope, requires that scope in the caller's `read_scopes` (else 404 uniform — no existence oracle), and bounds every read to that ONE scope (never `read_scopes` wholesale, and NO block grants — a project's issue view is deliberately scope-pure). All GETs are **member-gated** inside the mount (a missing gate is a missing route, never fail-open). Every body-bearing response carries `render: "untrusted"` (issue/comment bodies are attacker-controlled markdown) plus the `workflow_status`/`type_name` fields (wire-consistent with the `manage issue-*` transport).

| Endpoint | Description |
|----------|-------------|
| `GET /api/project/{id}/issues` | One keyset page. Filters: `state` (one workflow status), `labels` (repeated or comma-separated; AND), `q` (full-text). `sort=updated` (default) \| `created`. `after=<opaque token>` resumes; `limit` ≤ 100. Response `{success, render, issues:[{id,scope,type_name,title,workflow_status,updated_at}], cursor}` — `cursor` is the opaque `after` token for the next page, or `null` at end of data. |
| `GET /api/project/{id}/issues/{block_id}` | Full issue + the first page of the comment thread inline: `{success, render, issue, comments, comments_cursor}`. A foreign/absent/malformed id ⇒ 404 uniform. |
| `GET /api/project/{id}/issues/{block_id}/comments` | The comment thread, ASC keyset on the immutable `(created_at, id)`: `{success, render, comments, cursor}`. `after`/`limit` as above. |
| `GET /api/project/{id}/board` | Per-config-status columns: `{success, render, columns:[{status, count, issues:[…], cursor}]}`. `count` is index-only; `cursor` is the per-column `after` token — load more of a column via `…/issues?state=<col>&after=<token>`. |

**Sort + pagination semantics.** `sort=updated` (the board view) keys on the MUTABLE `(updated_at, id)`: a row updated mid-pagination moves ahead of the consumed cursor and drops out of that traversal — accepted **list** semantics (a UI view, not an export contract), gated in `TestW6CursorAndSemantics`. For a **lossless** traversal (agents, export) use `sort=created` — keyset on the IMMUTABLE `(created_at, id)`, which no update reorders. The opaque `after` token is a base64url-encoded keyset cursor; a malformed token ⇒ 400 (never 500).

**`q` full-text search (masterplan K4 decision).** `q` binds to the **existing FTS tsvector GIN path** (`idx_context_ts_de` / `idx_context_ts_en` over `title || content`, migrations 001/044) — matching `plainto_tsquery('german', q) OR plainto_tsquery('english', q)`, scope/type/status-predicated. This is **not** a silent sequential scan (the EXPLAIN gate asserts the FTS GIN index is used, no `Seq Scan`). No new trigram index was needed: design/03 §6.1 specifies the FTS path, and `idx_trgm_title` already exists too (001). The freed W6 migration slot (086) instead carries `idx_blocks_workflow_created` for the `sort=created` traversal.

**Index story + scale (design/03 §6.1, W6 EXPLAIN gate).** At the target scale (10k+ issues/repo, proven against a 10k-issue + ≥200k-non-issue backdrop):

- `state` list rides the named `idx_blocks_workflow_board` (M077); `sort=created` rides `idx_blocks_workflow_created` (M086) status-unfiltered, and the board index when a `state` narrows it (both index-backed, no `Seq Scan`). At 215k rows the planner serves these as a Bitmap Index Scan on the named index + a bounded top-N heapsort — index-backed and keyset-correct; P95 < 100 ms (measured ~20–28 ms). The RED differential (index/bitmap scans disabled) Seq-Scans the 210k table an order of magnitude slower.
- `q` rides the FTS GIN indexes (above).
- Board `count` is an **Index Only Scan** over the board index (no heap) — degrades to a heap Filter only when a `labels` filter is present (documented edge).

**Documented deviations from design/03 §6.1.**

- **`labels` is a post-filter, not a dedicated GIN index.** §6.1 sketched `labels → Array + GIN`; the shipped I-B primitive (M077 / `store.WorkflowStatusListSQL`, design/02 §3.3) treats `labels` as an AND post-filter over `metadata->'labels'` (`?&`) inside the board-index range scan — the board index already bounds the row set, so the post-filter stays cheap. W6 keeps that I-B semantics rather than adding a labels GIN index (Achse-02 schema hoheit); the default jsonb GIN index does not cover the `metadata->'labels'` sub-path, so a labels probe rides the board index with a Filter.
- **`sort=created` first page is O(scope-issues), not O(limit).** With the `+infinity` first-page keyset sentinel the planner bitmaps the whole status-unfiltered issue set then top-N sorts (bounded by the scope) — <100 ms at the 10k target; a mid-page `after` cursor tightens the range. An ordered O(limit) range scan at 100k+ issues/repo would be a follow-up optimization.

**Unmapped status.** An issue whose `workflow_status` is not in the type config is **not** shown on the board and **not** returned by the default merge list (both are config-status-bound), but IS reachable via an explicit `?state=<unmapped>` and via the lossless `?sort=created` (which surfaces all statuses) — gated in `TestProjectIssuesW6`.

## Project issues (write surface)

The project issue write surface (workflow W7, the write half of `MountProjectIssues`) shares the ONE `RequireMember` gate group with the W6 reads (a missing gate is a missing route, never fail-open). `RequireMember` admits; each write handler then runs the per-project **write-scope gate** and calls the SAME store functions as the `manage issue-*` transport (`store.InsertIssueBlock`/`UpdateIssueBlock`/`InsertCommentBlock`) — one write logic, two transports. Every body-bearing response carries `render: "untrusted"` plus `workflow_status`/`type` (wire-consistent with W6/I-D; the `store.Block` wire name for the type is `type`).

**Write-scope gate + no-oracle (design/03 §4.6/§5.2).** `{id}` resolves to the project's single scope. A caller who can not even **read** that scope (scope ∉ `read_scopes`), an unknown project id, and a foreign block id all read as a uniform **404** (no existence oracle). A caller who **can read** the scope but whose writable set does not contain it (`writableBlockScopes(ar)` = `home_scope` ∪ `write_scopes ∩ readable` ∪ `shared-if-allowed`, the SAME formula as `/api/store` and `manage`) gets **403** — returned only to someone who already knows the scope exists, so it leaks nothing. Every store write is bounded to the project's ONE scope (`writableScopes = [scope]`, not the caller's whole writable set), so a block id belonging to another (even writable) project reads as not-found through this path — never silently mutated (scope purity, mirrors the W6 reads).

| Route | Behaviour |
|---|---|
| `POST /api/project/{id}/issues` | Create an issue. Body `{title (required), content?, tags?, metadata?, status?}` — **no `scope` field** (the scope is the project's; an unknown key ⇒ 400). `workflow_status` = the type's `initial`; a supplied `status` must be a valid ENTRY transition (`"" → status`) or **422**. Response `{success, render, issue}`. |
| `PATCH /api/project/{id}/issues/{block_id}` | Update fields and/or status. Body `{title?, content?, tags?, metadata?, status?}` (all optional; none ⇒ 400). A status change is validated against the type-config transition graph (`set.ValidateTransition`) — an out-of-policy target ⇒ **422**. The `#L<seq>` title prefix is preserved; `metadata` is JSONB-merged. A block outside this project's scope ⇒ 404 uniform. Response `{success, render, issue}`. |
| `POST /api/project/{id}/issues/{block_id}/comments` | Create a comment under the path issue. Body `{author?, content?, metadata?}` — **no `parent_id`** (the parent is `{block_id}`) and **no `scope`** (the store forces the comment into the parent's scope, the comment-scope invariant). A parent outside this project's scope ⇒ 404 uniform. Response `{success, render, comment}`. |

**State validation is policy data, not Go.** The initial status and every transition come from `set.WorkflowInitial`/`set.ValidateTransition` over the resolved type registry — swapping the registry status set changes the 422 verdict **with no rebuild** (gated in `TestProjectIssuesW7`: after dropping a status from the `_global` issue config + registry reload, a transition to it flips 200 → 422; a hardcoded list would keep returning 200).

**Rate limit (design/03 §4.4).** Issue writes ride the existing **per-`api_key_id`** write throttle — the same `query.rate_limit_write` config (tenant-overridable), 60-second window and `context_access_log` substrate as `/api/store`, so `/api/store` and the issue surface share ONE write budget. Over budget ⇒ **429**. A limits-lookup error is fail-closed (500, never silent unlimited). The project-scoped sync/webhook limits of §4.4 (which need a project dimension the `context_access_log` substrate lacks) are W11/W13, not this per-key write path; no new limiter is introduced here.

**Body cap.** 1 MB per request (the enclosing group's `MaxBodySize`); an over-cap body ⇒ 413. The store additionally caps an issue/comment body at 50 KB ⇒ 422.

| `hops` | 1 | 1–3 | BFS depth |
| `per_node_cap` | 25 | 1–100 | top-N edges per frontier node by `raw_confidence` — slots count only visible, filter-passing edges |
| `limit` | 500 | 1–1500 | total node budget (truncation: closer hop wins, then higher confidence, then id) — ceiling set by the G39 1M benchmark (p95 < 500ms) |
| `min_confidence` | 0 | 0–1 | gates dream edges only (traversal + display); structural facts are 1.0 by definition and always pass (GD4) |
| `link_class` | all classes | dream five + registry structural classes (e.g. `references`, `duplicate-of`) | ONE parameter over both vocabularies (GB5): the CSV partitions by data class — `link_class=references` shows only that fact class, `link_class=topical` only that dream class; absent = everything. `supersedes` is display-only, never traversed; unknown class → 400 naming the full vocabulary |
| `category` | all | CSV | filter on neighbor blocks (focus always included) |
| `created_after` / `created_before` | open | RFC3339 | window on neighbor `created_at` |
| `edge_limit` | 4000 | 1–20000 | budget for edges within the node set, strongest first |

Out-of-range values are a `400`, never silently clamped. Response: `nodes` (id, title capped at 120 chars, category, scope, visible `degree` — capped at 201, rendered "200+"; since GB4 the degree counts visible link ROWS of both data classes, per direction per class, so it stays consistent with the client's multigraph badge math — and `hop`), `edges` as compact index tuples `[srcIdx, dstIdx, relIdx, confidence]`, and `stats`. The payload never contains block `content` (load it lazily via `manage get`).

Since graph-structural GA8 the envelope additionally carries `struct_rels` + `origins` (response-local legends: sorted distinct sets of the DELIVERED classes/origins, built after truncation) and `structural_edges` (all-integer tuples `[srcIdx, dstIdx, classIdx, originIdx]` — no confidence slot, structural facts are 1.0 by definition and pass every `min_confidence`), plus `stats.structural_edges` (`stats.edges` stays dream-only). All three are arrays unconditionally; old clients ignore the fields. Since GB3 the traversal itself follows **both** data classes: per hop the frontier expands over dream links (strongest-first) AND structural links (newest-first, E5), merged into the shared node budget as a fair zipper (alternating classes — neither a degree-10⁴ dream hub nor a fact hub can starve the other class out of the budget). A block reachable ONLY via structural references — every forge-sync issue and daily report — now appears in its neighbors' ego graphs by default. Edges share ONE `edge_limit` under fact precedence with a dream floor of `min(|dream|, edge_limit/2)`. The visibility triple gates every structural leg exactly like the dream legs (per-leg red-proven), grant-only nodes stay leaves class-agnostically, and an invisible focus stays an indistinguishable `404` regardless of its structural edges. On the SPA side (GC1) structural edges render as **curved teal arrows** (`@sigma/edge-curve`, one color for all classes) while dream edges stay straight lines — parallel structural facts on the same pair separate by curvature; the class itself is text (panel legend + window badge), not a color axis. The panel's structural class filter (GC2) is a BLOCKLIST (default: everything visible, unknown classes never hidden) and mirrors itself through the same unified `link_class` channel — whenever either side filters, the SPA derives BOTH sides into one CSV (a one-sided CSV would empty the other side per the partition semantics above). The link-class fieldset doubles as the edge legend (GC3): token-bound swatches mirror the canvas form language, structural checkboxes carry their semantics in the accessible name, and the stats line surfaces the structural count. The block detail window lists loaded structural links as a navigable section (direction glyph, class + origin badge, cap 50) that re-derives after every merge (GC4) — report chains are traversable textually, as the a11y equivalent of the canvas arrows.

Since the graph-budget wave the envelope also carries `budget_report` — the typed refinement of the single `stats.truncated` bool, which until now collapsed every cut (node budget, both induced-edge truncations) into one flag. Shape: `{"limits":[…],"budgets":[…],"counts":{…},"source":"sql","cache_age_ms":0}`. The two arrays are the two layers: **limits** are your OWN parameters running out (`node_limit_reached` = `limit`, `edge_limit_reached` = `edge_limit`) — ask for more and you get more; **budgets** are server-side guards (OOM/time), which no amount of asking lifts. `counts` gives how often each class tripped, `source` names the answering arm. Additive and unconditional (empty arrays when nothing tripped): `stats.truncated` keeps its exact old meaning, old clients ignore the field. Budget trips are a `200` with a report — only parameter violations are a `400`. Deliberately absent: any class derived from pre-visibility-check candidate sets. Such a trip would reveal that raw edges exist beyond the cap — including foreign private ones — on a block you can see; those classes stay in server telemetry.

Since the Cluster-Topic-Map wave C2 the envelope additionally carries `clusters` + `cluster_of` + `stats.clusters` — where the delivered nodes sit in the Louvain cluster map. `cluster_of[i]` is positionally parallel to `nodes[i]` and indexes `clusters[]`, or `-1` for "no visible membership" (unclustered, visible only via a block grant, or created after the last rebuild). Each `clusters[]` entry is `{cluster, topic?, label?, topics?, size, top_categories, scope_mix, in_response}`: `cluster` is a RESPONSE-LOCAL ordinal (never a stable id — resolving one against another response is meaningless), `size` is the scope-pure size summed over the partitions of that cluster you may see, `in_response` how many of THIS response's nodes sit in it. Gated on `cluster.ego_annotate` (default **off**): off ⇒ both arrays empty and `stats.clusters` 0 — and the same empty shape answers whenever the annotation declines, so a client never branches on the reason. Above `cluster.ego_annotate_max_nodes` (default 500) the annotation declines with the `cluster_annotate_capped` budget trip rather than lowering the node ceiling of the route itself; `/api/graph/all`, whose `limit` defaults to the ceiling, therefore stays unannotated by default. The annotation costs one membership probe, reported as the `cluster_annotate_probe` budget posten — on the cache arm it is the only remaining database roundtrip, and its cost stays visible instead of hiding in the cache win. Deliberately absent: the internal `cluster_id`. It is the smallest member UUID of the community and block ids are uuidv7, so emitting it would reveal that an invisible block exists and roughly when it was created.

Since wave C5 each entry additionally carries the **stable handle**: `topic` (the v4 topic id from the identity table — the same value `GET /api/graph/overview` emits) and `label`, both optional. The ordinal stays what `cluster_of` indexes; the handle is what survives a rebuild, so it is the only value worth persisting on the client side or feeding into `cluster:<handle>` searches. A cluster the identity layer has not reached yet — pre-rebuild rows, and the mid-rollout window while the rebuild serves one tenant per tick — simply carries no `topic`/`label`, keeping the exact pre-C5 object; that is a normal state, not an error, and it never costs the entry its `size`. A handle is **scope-bound** by design ("one handle = one scope-pure topic"), while an entry is keyed by cluster: a cluster whose members live in two scopes you can both read therefore carries `topic` = the handle of the LARGER visible half plus `topics` = all of them, primary first. `topics` is omitted whenever there is only one (live: always) rather than repeating `topic` as a one-element array. Handles are never derived from a cluster or block id — that derivation is exactly the existence/time oracle the ordinal exists to avoid.

**Security semantics.** The visibility triple (not archived, block type on the registry visibility allowlist, scope readable by the key) is applied inside every hop AND inside the per-node cap legs — a node reachable only through a foreign private bridge is never delivered, and invisible edges never consume cap slots. `degree` counts only visible neighbors (scan budget 1000 raw edges/direction). "Does not exist" and "not visible" answer with an identical `404` (no existence oracle); only successful calls write an access-log row (`action='graph'`, `block_id=NULL`).

### Load-all (flat corpus seed)

`GET /api/graph/all` returns the flat "load all" seed behind the SPA button of the same name: **every visible block** (canonical visibility triple + the ego node filters), newest-first with an id tiebreak so truncation is deterministic, plus the induced edges of both data classes and the visible degrees. Nothing is traversed — the node set is predicate-defined, not reachability-defined, so blocks without any link (and disconnected components) appear too.

Params are the ego set MINUS `block`/`hops`/`per_node_cap`: `limit` (default **1500** = the ceiling — the button's whole point), `edge_limit` (default **20000** = the ceiling, matching the client's hard edge budget), `min_confidence`, `link_class` (same unified GB5 channel), `category`, `created_after`/`created_before`. Ceilings are still enforced, never clamped; the corpus growing past a ceiling reports as `stats.truncated` + `budget_report` limits (`node_limit_reached`/`edge_limit_reached`) — the endpoint stays a budgeted view at 1M+, never an unbounded dump. Response: the ego envelope verbatim with `focus:""` and `params.hops`/`params.per_node_cap` echoed as 0 (not applicable). Same auth, same `graph` rate-limit bucket; there is no focus, hence no 404 arm.

### Overview (cluster "landkarte")

`GET /api/graph/overview` returns the cluster supergraph: a few hundred meta-nodes (precomputed Louvain communities over the dream-link graph) with `size`, `top_categories`, a representative block, and aggregated inter-cluster meta-edges. The Louvain rebuild runs offline in the scheduler (`internal/overview`; clustering core selected by `graph_overview.engine`, default the own `internal/louvain` kernel since v4.31.0); the endpoint only reads precomputed tables. Since WF T6 the node set is policy-cut: a block becomes a Louvain node only if its type is on the registry visibility allowlist AND carries `overview.include=true`.

```
GET /api/graph/overview?min_cluster_size=1&min_inter_cluster_weight=0&node_limit=500&edge_limit=2000
```

| Param | Default | Range | Meaning |
|-------|---------|-------|---------|
| `min_cluster_size` | 1 | ≥1 | hide meta-nodes whose visible size is below this |
| `min_inter_cluster_weight` | 0 | ≥0 | hide meta-edges below this aggregated weight |
| `node_limit` | 500 | 1–2000 | max meta-nodes (largest first) |
| `edge_limit` | 2000 | 1–20000 | max meta-edges (strongest first) |

Response: `nodes` (`cluster` ordinal, optional `topic`/`label`, `size`, `top_categories`, `repr_id`/`repr_title`, `scope_mix`), `edges` as compact tuples `[srcOrdinal, dstOrdinal, link_count, weight]`, and `stats` (`computed_at`, `null` if never built). Gated on the hot setting `graph_overview.enabled` (default off → `404`).

`topic` is the **stable identity** of a map node across rebuilds and `label` its name; both are omitted entirely until the server has run a rebuild with the identity layer, and omitted for the whole response while any readable partition is still without one (the server errs towards a complete map, not a complete identity). Render `label ?? repr_title` — the label accompanies the representative title rather than replacing it, because `repr_id` is the drill-down target and `repr_title` its caption. `cluster` stays the per-request ordinal the edge tuples point at. The internal `cluster_id` is still never emitted: it IS a block uuid, whereas `topic` is a v4 uuid with no block reference, no timestamp component and a scope partition, so two tenants can never observe a common handle.

### Cluster ego (`GET /api/graph/cluster`)

`GET /api/graph/cluster?cluster=<handle>` opens ONE topic: its members, its neighbouring topics and its metadata. It is the drill-down the map lacks — clicking a cluster today opens the ego net of its representative, which in 41 of 59 live clusters is simply the oldest block with `quality_score = 1`, so the caller lands in an arbitrary neighbourhood instead of in the topic.

```
GET /api/graph/cluster?cluster=<handle>&limit=500&neighbor_limit=50
```

**Read caps, this route's own:** `limit` 1–1500 (default 500, member blocks) and `neighbor_limit` 1–200 (default 50, neighbour topics). Out of range is a `400`, never a silent clamp; a malformed or missing handle is a `400` before any database roundtrip. Hitting the member cap sets `stats.truncated`.

Response: `cluster` (`handle`, `label?`, **`label_source`** / **`label_model?`**, `size`, `top_categories`, `scope_mix`, `repr_id`/`repr_title`, `computed_at`), `nodes` (member blocks: `id`, `title` capped at 120 chars, `category`, `scope`, `created_at` — no `content`, load it lazily), `neighbors` (`handle`, `label?`, `size`, `link_count`, `weight`) and `stats`. `label_source` (`manual` > `llm` > `fallback` > `none`) and `label_model` are the label **provenance**: they live here, on the detail route, and deliberately not on the overview wire, where per-node provenance would be noise on a dense list.

Deliberately absent: `degree` and `hop` on the member nodes. `hop` is meaningless without a focus (every member is equally far from "the topic"), and the per-node visible-degree query is the p95 driver that forced the ego route's node ceiling from 5000 down to 1500 — shipping it here would mean an unmeasured cost on a new route.

**Partition-scharf.** A handle names one scope-pure topic, so `cluster.size` and `nodes[]` describe the same set — including for a caller who can read both halves of a cluster that spans two scopes: the other half is a different handle, with its own label. Neighbours are TOPICS, and a meta-edge counts only when **both** endpoint scopes are visible; an endpoint whose handle cannot be resolved is dropped rather than delivered as "unknown". `computed_at` rides along unconditionally — unlike the ranking stage below, a read path has a viewer who can judge freshness, so the route serves and lets you decide.

**Gates and 404 semantics.** Double-gated on `graph_overview.enabled` AND `cluster.route_enabled` (both default **off**); a closed gate answers the same generic `404` as an absent route. `404` is identical for "handle unknown", "handle exists in a scope you cannot read" and "handle retired", and **no access-log row is written on that path** — otherwise telemetry itself would be bumpable by UUID probing. Only successful calls log (`action='graph-cluster'`, `block_id=NULL`), and the route carries its own `graph-cluster` rate-limit bucket.

### Cluster facet (`cluster:<handle>`)

`POST /api/search` takes an optional `cluster` field: a hard restriction to ONE topic of the cluster map, addressed by the same stable handle the graph surfaces emit (`topic` on `GET /api/graph/overview` and on the ego annotation). The CLI spells it `ctx search cluster:<handle>`, the MCP `search` tool as an optional `cluster` argument — a field on the known tool rather than an eighth tool, because a new tool raises the selection load of every MCP client.

The facet is **partition-scharf**: a handle names one scope-pure topic, so the answer is that topic's members — never the other half of a cluster that happens to span two scopes you can both read, whose half carries its own handle and possibly its own label. Resolution runs `graph_cluster_topic → graph_cluster_node → graph_cluster_member`, all under your read scopes, and the ordinary visibility predicate applies unchanged on top: the restriction can only ever narrow what you could already see.

**No existence oracle, one rule.** A well-formed handle always answers `200` with a possibly empty list — unknown, foreign, retired and member-less are one indistinguishable outcome. Only a **malformed** handle is a `400`, decided before any database roundtrip. If unresolvable handles answered differently, the handle space would be enumerable, and because handles are stable per topic the NUMBER of foreign topics would be derivable.

Gated on `cluster.facet_enabled` (default **off**). While the gate is closed the field is ignored completely — not rejected, not echoed, not applied — so a request carrying it is byte-identical to the same request without it. When the facet applies, the response echoes it under `filters.cluster`. Cost at scale: the restriction stays a semi-join (never a materialised id list), so the planner keeps the choice between a hash semi-join and an index nested loop; measured against a worst-case fixture (a topic owning the oldest corpus decile), it drives from the membership side and touches 300 heap rows against a ceiling of 100 × the outer limit.

### Cluster boost (categorical retrieval)

`POST /api/query` carries an optional **categorical** ranking stage beside the existing Dream-graph one: results sitting in the same Louvain cluster as the query's strongest hits get reinforced. Where the graph stage argues from EDGES ("these two blocks are linked"), this one argues from CATEGORIES ("these blocks live in the same community"). It runs BEFORE the graph stage, and that order is load-bearing rather than stylistic — Louvain builds its communities from the same `context_dream_links` table the graph stage traverses, so running it afterwards would pay a graph-reinforced neighbour twice for one piece of evidence.

Gated on `cluster.enabled` (default **off**): off ⇒ the response is byte-identical, and the whole stage is fail-open — any error keeps the pre-boost ranking, never a `500`. The top `cluster.seed_count` results vote for their clusters with the RRF `1/(60+rank)` weight; at most `cluster.top_clusters` clusters clearing `cluster.min_share` win, and their members are multiplied by `1 + cluster.boost_weight * share`. Since `share ≤ 1` by construction, the ceiling is `1 + boost_weight` — 12 % at the default, below the Dream-graph boost and far below the reranker, which stays the final arbiter. `cluster.size_damping` (default **on**) normalises a cluster's vote by its share of the visible map, so "this cluster is relevant" stays distinguishable from "this cluster is large".

**Freshness fail-safe.** The stage refuses to boost from a landkarte it cannot vouch for. Past `cluster.max_staleness` (default 24 h) — or when even ONE of your read scopes has no successful rebuild on record, or when the freshness seam is unwired — it turns itself into a no-op and records the `cluster_stale` trip. Deliberately stricter than `GET /api/graph/overview`, which keeps serving a stale map with a `200` and lets you judge by `computed_at`: a ranking signal has no viewer to judge it. Aggregation over several scopes is the MINIMUM age, not the maximum — the maximum would hide a frozen partition behind a fresh one. The freshness source is `graph_overview_meta.computed_at`, never the scheduler's arm stamp: that stamp is set BEFORE a rebuild and survives every skip, so it reports "the arm ran", never "the map is fresh".

Because a correct fail-safe looks exactly like a broken rebuild from the outside, `GET /api/status` carries a server-admin `cluster_map` section: per scope `computed_at` / `last_attempt_at` / `skip_reason` / `candidate_n` / `staleness_ms` (`-1` = never successfully built, which is not the same statement as "0 ms old"), plus `consecutive_failures` (rebuild attempts since the last success — `skip_reason: "advisory-lock"` among them is CONTENTION, not a frozen map: another instance built it) and `cross_scope_clusters`. The last one is the scope-boundedness monitor: cluster topics belong to exactly one scope, so this is expected to stay `0` — a non-zero value means a handle and its aggregate have begun describing different objects.

Three invariants: the stage never ADDS or removes a result (injection is its own separate, default-0 knob), it never PUNISHES one (a block with no visible membership row — unclustered, grant-only, or newer than the last rebuild — keeps its score bit for bit), and a grant-only result casts NO vote (its scope is outside your read scopes, so its membership row is already filtered — a shared block cannot drag the grantee's own blocks up over the grant bridge). A boosted result carries `cluster_boost` (the applied share) as provenance; the internal cluster id is deliberately absent, for the same oracle reason as on the overview.

**Security semantics** (the solved scope-count-leak). Aggregates are **scope-partitioned** — each precomputed row belongs to exactly one scope (nodes) or scope-pair (edges), and a request sums only rows whose scope(s) lie entirely within the caller's `read_scopes` (edges need **both** endpoint scopes visible). No global total is ever exposed, so a private member count cannot be recovered by difference. The internal `cluster_id` (smallest member UUID) is **never** emitted — clients see a per-request ordinal, so the identifier is not an existence oracle. Only successful calls write an access-log row (`action='graph-overview'`, `block_id=NULL`).

## Settings API

Runtime config editing over the `context_settings` override layer. **Admin-gated including reads** — the effective config (hosts, models, thresholds) is operational intelligence, and a non-admin key that can read it can also enumerate what to attack. (Tenant-admins reach a two-scope view — see [multi-tenancy](multi-tenancy.md#per-tenant-settings--secrets).)

```
GET    /api/settings           # every registry key: value, source, type, mutability, default, description
GET    /api/settings/{key}     # single key + last 10 audit rows (action, actor, via)
PUT    /api/settings/{key}     # body {"value": <scalar>} — validated BEFORE persist
DELETE /api/settings/{key}     # drop the override, revert to env/default
```

- **Key descriptions.** Every registry key carries a one-line operator `description` (registry map `config.keyDescriptions`, completeness boot-enforced + test-pinned): what the value controls, its unit semantics and the practical effect of changing it. Rendered under the key in the settings UI and part of its fuzzy-search corpus.
- **Retired keys answer like typos.** The 29 backend-tuple keys (`chat/chat_fallback/embed/dream/dream_embed/rerank` × host/protocol/model/api_key/num_ctx/think/timeout) left the registry in v5.0.0; their living value is a [backend-pool](#backend-pool) row. On the wire they are simply **unknown**: `GET`, `PUT` and `DELETE` all answer `404`, with no field, status or hint distinguishing them from a misspelled key — the move is documented in [operations](operations.md#environment-variables), deliberately not announced by the API. The `superseded` response field they used to carry is gone from every settings response, and so is the read-only `legacy (superseded)` card the settings UI collected them in.
- **Validation before persist.** A PUT builds the candidate config through the same path the reload uses; a value the build would reject or ignore is a `422` and never reaches the table (no row, no audit entry). Unknown keys are `404`; `restart`/`coupled` keys are `409` with the env var to set instead. String inputs are normalized to their registry type before persist (`"0.7"` → the number `0.7`).
- **Hot effect.** After commit the handler swaps the snapshot — the next request/cycle runs with the new value, no restart. Direct `psql` edits arrive through the NOTIFY listener with the same effect (audited as `via='sql'`).
- **Masking rule.** Any response position carrying the effective value of a sensitive key renders `"(set via env)"` when the value comes from env (incl. `previous.value` on PUT and the post-revert `value` on DELETE). DB-sourced sensitive values render the secret **name** (`secret_ref`), never resolved material.
- **secret_ref gate.** A sensitive key accepts only the *name* of an existing sealed secret; a provider-key-shaped value is rejected with `422`, so material can never reach `context_settings` or its append-only audit. Since the tuple retirement the class has one member left, `server.db_password`, and it is `restart`-only — the gate is a guard for future sensitive keys, not a path anyone walks today. Provider credentials live on the pool row instead (`api_key_ref` → [sealed secret](#backend-pool)), where the same name-not-value rule holds.
- **Embed-cache coupling lives at the pool now.** No settings key addresses an embedding endpoint any more, so no settings write can move the vector space and none flushes `context_embed_cache`. The flush moved with its subject: a `base_url`/`protocol` edit on a serving-eligible `embed`-role [backend row](#backend-pool) triggers it, and a boot compares the pool against a persisted fingerprint for edits made while ctx was stopped (see [operations](operations.md#migration-132-the-embed-cache-coupled-fingerprint--and-the-one-time-cleanup-it-does-not-do-for-you)).

**Settings UI (SPA `/settings`).** The generic editor renders one collapsible card per key prefix (collapsed by default, state persisted per browser; a card with unsaved edits stays open) with a jump-chip row and expand/collapse-all. The toolbar carries a **Levenshtein fuzzy search** (`/` focuses it) over keys, descriptions, effective values, env vars and types — three tiers per token (substring, in-order subsequence, edit-distance-to-best-substring with a 1–2 typo budget by token length), multi-token queries AND across fields, hits are highlighted and ranked by score; sensitive values are excluded from the corpus. The **dream card** embeds the back-off curve editor: the six `dream.backoff_*` drafts render live as a smoothed active/inert cooldown curve (log-scale, saved policy ghosted behind, corpus maturity histogram from `dream-stats` underneath), and the curve is directly draggable — the curve body solves `factor` through the pointer, the min/cap guide lines set floor/ceiling, steppers adjust `grace`/`inert_offset`. Every interaction writes **drafts only**; the card's Save button activates them (the normal PUT flow), after which the UI automatically runs `dream-backoff-restamp` and refetches the histogram, so the saved policy governs the whole corpus immediately.

```bash
curl -s -X PUT "$CTX/api/settings/rerank.blend_weight" \
  -H "X-Context-Key: $ADMIN_KEY" -H "Content-Type: application/json" \
  -d '{"value":0.6}'
# → {"success":true,"key":"rerank.blend_weight","value":0.6,"source":"db",
#    "previous":{"value":0.5,"source":"env"},"warnings":[]}
```

## Backend pool

Manage actions (all **admin-gated, reads included** — the list discloses egress topology; tenant-admin scoping in [multi-tenancy](multi-tenancy.md#backend-pool-isolation-egress)):

```
POST /api/manage {"action":"backend-list"}                 # rows + live status (effective_state, cooldown, sanitized last_error)
POST /api/manage {"action":"backend-create","data":{…}}    # full validation, see below
POST /api/manage {"action":"backend-update","id":…,"data":{…}}   # single-field patch
POST /api/manage {"action":"backend-delete","id":…}        # hard delete (llmlog history stays readable)
POST /api/manage {"action":"backend-test","id":…,"data":{"probe":"chat"}}  # reachability dry-run
POST /api/manage {"action":"backend-test","data":{"probe":"embed-equivalence",…spec}}  # cosine proof, id optional
POST /api/manage {"action":"backend-reorder","data":{"order":[id…],"expected":{id:prio…}}}  # atomic priority ladder
```

**Atomic reorder.** `backend-reorder` rewrites the priority ladder in ONE
transaction: `order` is the complete desired top-to-bottom sequence of the
caller's *writable* backends (T37 — a tenant-admin's own rows only; visible
`_global` rows keep their numbers and interleave), `expected` the id→priority
snapshot the client based the move on. Priorities are reassigned in descending
10-steps (top = n·10), which eliminates ties structurally; unchanged rows are
skipped so the audit trail records only actual moves. A concurrent edit
answers `409 {error:"stale", current:{…}}` instead of being overwritten; a
foreign/unknown id or a partial order is a 422. This is what the admin table's
drag-reorder and ▲▼ ride on — the per-row `priority` patch stays for direct
numeric placement (the prio cell's click-to-edit).

**Embed-equivalence probe.** `probe:"embed-equivalence"` embeds a fixed canonical
sample set (both asymmetric prefixes, Umlaute, code, symbol noise) on the local
reference embed backend AND on the candidate, compares the DB-relevant vectors
(1024-truncated, L2-normalized — the exact ingest path) per sample and verdicts
`verified` against a threshold of `0.995` min-cosine (empirically anchored:
same weights across a precision/quantization boundary measure ≥ 0.997, a
different model lands far below 0.99). The candidate may be **unsaved**: send
the full spec instead of an `id` — validation blocks persisting an external
embed backend unverified, so test-before-create is the intended order (the
backend dialog's *cosine-test* button does exactly this). On `verified` the
response carries a ready-to-merge `metadata_patch` with
`embed_equivalence_verified:true` plus an `embed_equivalence_proof` object
(reference, models, `min_cosine`, `checked_at`); the dialog folds it into the
save payload. Failures answer HTTP 200 with `verified:false` and a `failure`
message — the verdict lives in the body, like every `backend-test` outcome.

**Validation guards** (create AND update, `422` with field errors): credential-carrier headers in `extra_headers` (`Authorization`, `Cookie`, `*-key`, `*-token`, …) and credential-semantic `extra_body` fields are rejected — provider keys go through `api_key_ref` (the *name* of a sealed secret, resolved in-memory only); a `base_url` carrying userinfo (`user:pass@host`) is rejected for the same reason — the URL is echoed unredacted by every list response, log line and the append-only audit (rows written before this guard load fine and are rejected on their next write); `locality` is cross-validated against `base_url` (a publicly routable host must be `external`); embed roles on external backends are blocked without `metadata.embed_equivalence_verified=true` (foreign quantization corrupts the shared vector space). `metadata.score_domain` (rerank dialect slot) must be one of `auto` | `logit` | `probability` — `auto` (the default for every row that does not set it) keeps the wire-container coupling: `results` ⇒ raw logits, `data` ⇒ calibrated [0,1] probability; explicit values override the coupling for dialect-mixing backends. Changing the *effective* score domain of a rerank-capable backend (create with a non-`auto` value included — the delete+create bypass is closed like the trust confirm's) requires `confirm_score_domain_change:true`; the 400 carries the full chain of change (effective immediately on all future rankings; the access-log score trail is only comparable up to the switch; no corpus reprocessing — no curation artifact persists rerank-derived data) and the confirmed write echoes it as a warning. Raising `trust` requires `confirm_trust_elevation:true`. Every mutation reloads the pool snapshot synchronously — `backend-update {"enabled":false}` is an instant brake, no restart; psql edits converge via the 053 NOTIFY trigger.

**OpenRouter (first external backend, G29).** `provider_class: "openrouter"` refines the openai wire: the request **always** carries `provider.zdr:true` + `provider.data_collection:"deny"`, independent of trust level — trust decides WHICH content may flow, the provider class decides whether the provider may store it. `extra_body.provider` entries merge but can only tighten (the force runs after the merge). The single escape is `metadata.allow_data_collection:true`, requiring `confirm_data_collection:true`. Responses feed telemetry: `usage.cost` → llmlog `cost_usd` (local NULL), the top-level `model` (that actually answered) overwrites the row's model, the response `id` lands in `metadata.provider_request_id`. A "no providers" rejection (zdr/deny filter leaves no provider) classifies as configuration-permanent (1h cooldown, no retry storm). `backend-test` additionally reports `credits_remaining`/`usage_usd` (`GET /v1/key`) and `zdr_endpoints` (`GET /v1/endpoints/zdr`). **`base_url` is the API root WITHOUT the version segment** — the wire paths append `/v1/...` themselves; a `base_url` ending in `/v1` double-segments to a 404, and since v4.25.4 create/update reject such a root with a 422 (all openai- and rerank-protocol backends, not just openrouter).

## Web chat sessions

(F6, migration 056) The persistence layer, server-side tool harness and streaming HTTP endpoint for web chat. `context_chat_sessions` is **scope-owned**: list and delete key on the creating tenant's home scope, so a key never sees a foreign tenant's chats. It snapshots the creating key's `read_scopes` and carries a **monotone `max_sensitivity` high-water-mark**. Reading or continuing a session requires `session.read_scopes ⊆ caller.ReadScopes` (else 404, no oracle), closing the shadow-corpus channel against future least-privilege keys. The HWM rises with **every** appended message (in the same short transaction that assigns the message `seq`), so a credentials-touched session stays full-trust-only for its whole life. `context_chat_messages` records per-message `sensitivity` (fail-closed `credentials` default), tool-call metadata, telemetry and a gapless `seq` (`UNIQUE(session_id, seq)`). A turn claims its session via a short `busy_until` CAS — a second concurrent turn gets 409 without blocking, a crashed turn self-heals on expiry. Retention is off by default (`CTX_WEBCHAT_SESSION_RETENTION`).

The **harness** (`internal/chat`) drives the model loop (model call → tool execution → next call), re-resolving the F3 chat chain each iteration on `max(request, session HWM)` sensitivity (an empty chain ends the turn — never a silent escalation). Four read-only tools run under the session's `read_scopes` snapshot: **ctx_query** (hybrid retrieval, delegated to `/api/query` with `synthesize:false`+`include_content:true`, attributed to the real key), **ctx_search**, **ctx_get** (full block, paged past the window via a resumable `offset`), **ctx_recent**. Each result is annotated with `max(sensitivity)` of the blocks it carried; tools are offered only to a full-trust backend, and the closing call after the tool-budget cap carries no tools array. Tool errors return to the model as `{"error":…}` and never abort the turn. Events flow through a narrow `Sink` interface, so a future headless agent runner can drive the same loop without HTTP.

**Endpoints** (auth required; `CTX_WEBCHAT_ENABLED=false` ⇒ 404):

| Route | What |
|---|---|
| `POST /api/chat/stream` | Run one turn, response `text/event-stream`. Body `{session_id?, message, sensitivity?, tools_enabled?, max_tokens?}` — empty `session_id` creates a session. Pre-stream failures are JSON (`404` unknown/foreign session or feature off, `409` busy, `429` scope semaphore); once the first event flows, later failures are `error` events. SSE events: `session, backend, delta, tool_call_start, tool_call, tool_result, usage, done, error` + a `: hb` keepalive every 15s. Errors are **laundered** to class code + backend NAME (the raw backend URL never reaches the client). Wrapped in the scheduler signal so dream yields the single llama.cpp slot during a turn. |
| `GET /api/chat/sessions?limit=50` | List the caller's home-scope sessions (metadata + `message_count`, newest first; no content). |
| `GET /api/chat/sessions/{id}?after_seq=0&limit=0` | One session + its messages (full tool-result contents); gated by `read_scopes ⊆ caller` → 404 on miss. Pagination additive. |
| `DELETE /api/chat/sessions/{id}` | Hard-delete (messages cascade); home-scope-owned → 404 on miss. llmlog logs `web-chat` **metadata-only** (no conversation bodies in the un-scoped `context_llm_log`). |

A per-`home_scope` semaphore (`CTX_WEBCHAT_CONCURRENT_TURNS`, default 1) bounds concurrent turns — multi-tenant fairness on the single slot (429 before stream start).

## Camo image proxy

(design 07-camo) A signing image proxy that lets the SPA render foreign remote images WITHOUT widening the Content-Security-Policy and without the viewer's browser ever contacting the foreign origin (no tracking-pixel deanonymization). Off by default — fail-closed unless `CTX_CAMO_ENABLED` is truthy AND the sealbox master key `CTX_SECRETS_KEY` is present; when off both routes 404 and the renderer keeps its `[external image blocked]` placeholder.

**Why a proxy, not an `img-src` widening.** The markdown renderer runs entirely client-side and the CSP pins `img-src 'self' data:` (byte-pinned by `TestCSPByteLiteralPin`). A proxied image is re-hosted under `/api/img/…` = `'self'`, so it is already allowed — the CSP is never touched. The server fetches the bytes; the browser only ever talks to `'self'`.

**Two surfaces, opposite auth (design §4.2, D2b).** The SPA has no signing secret, so it cannot mint proxy URLs itself; a browser `<img>` request carries no api key (at design time SPA auth lived in `sessionStorage`; since OAuth R4 a session cookie does ride same-origin subresource requests, but the HMAC signature stays the capability — the fetch route is deliberately credential-free), so the fetch endpoint cannot be api-key-authed. Hence:

| Route | Auth | What |
|---|---|---|
| `POST /api/img/sign` | api key + per-key rate limit | Batch-mints proxy paths for the foreign image URLs a rendered document wants to show. The auth-gated mint bounds the signature oracle. |
| `GET /api/img/{sig}` | none — the HMAC signature IS the capability | Verifies the signature over `url`+`exp` (labeled-HMAC subkey of `CTX_SECRETS_KEY`, constant-time, prev-key rotation slot) BEFORE any upstream request. Forged ⇒ 403, expired ⇒ 410, ZERO fetch either way (no SSRF/timing oracle without a valid sig). |

**Fetch policy (design §4.4, analog to the forge W11 guard).** Scheme allowlist (`http`/`https`); SSRF dial guard on the resolved IP of **every** hop including redirects (the classic "302 → internal IP" bypass is closed at the dial layer via the shared `internal/ssrfguard`); 3-hop redirect cap; dial/header/total timeouts 5s/5s/10s; size cap (`CTX_CAMO_MAX_BYTES`, default 10 MiB — `LimitReader` + `Content-Length` precheck, no unbounded buffering); and a two-layer content-type gate — the declared type must be in `{image/png, image/jpeg, image/gif, image/webp, image/avif}` AND the sniffed bytes must not be active content (HTML/XML/SVG/text/script). `image/svg+xml` is excluded outright (XSS vector). On success the bytes are served with the sniffed image content-type + `X-Content-Type-Options: nosniff` + `Cache-Control: public, max-age=<TTL>, immutable`; on failure a bodyless 502/415 + `no-store` (no substitute image, no retry storm).

**SPA rendering (design §4.3).** The shared markdown pipeline (`renderMarkdown`, the one sanitized sink for chat, issues and comments) leaves every foreign remote image as a visible `[external image blocked]` placeholder carrying the URL in `data-camo-src`. A post-render pass (the `camoProxy` Svelte action on each `{@html}` container) batch-signs those URLs via `POST /api/img/sign` and swaps each placeholder for the proxied same-origin `<img>`. It is additive and fail-safe: a disabled proxy, a sign failure, or a URL the server declines all leave the placeholder in place, and same-origin / `data:` images are never touched.

Env (all default-safe): `CTX_CAMO_ENABLED` (default false), `CTX_CAMO_TTL` (signature + cache lifetime, default `24h` — bounds the auth-less fetch endpoint's relay window), `CTX_CAMO_MAX_BYTES` (default `10485760`). No new secret and no DB migration — the signature is stateless and the signing key is derived from the existing `CTX_SECRETS_KEY` (rotation via `CTX_SECRETS_KEY_PREV`).
