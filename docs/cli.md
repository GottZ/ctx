# CLI Reference

The `ctx` CLI reads its config from `~/.config/ctx/config` (`CTX_BASE_URL` + `CTX_KEY`). On a TTY most commands render a table; when piped they emit JSON — the exceptions are listed under [Output on a terminal and in a pipe](#output-on-a-terminal-and-in-a-pipe). See [operations](operations.md#first-run-ctx-init) for setup (`ctx init` writes that config, and seeds the backend pool while it is at it).

**The key goes only to the origin of `CTX_BASE_URL`.** Every request the CLI sends with the key (`X-Context-Key`) — every command, `ctx ingest`, the statusline, `ctx init`'s key check and `ctx mcp serve` — goes only to the scheme, host and port of `CTX_BASE_URL` (the default port may be written or left out; the host compares case-insensitively in ASCII only, so a Unicode spelling of the name is another host). A redirect within that origin is followed as before, a `POST` body re-sent on `307`/`308`. A redirect anywhere else is refused before it is sent — neither the key nor the request body leaves — and the command fails naming the target and this rule. That includes an `http` → `https` redirect on the same host, as a proxy upgrading the connection sends it: the key has crossed the wire in clear text on the first request by then, so the error names the `https://…` URL to put into `CTX_BASE_URL` instead. Requests without the key (`/health` from the statusline and `ctx init`, the release check against GitHub) follow redirects as before.

## Exit codes: one contract for every command

**A failed call exits non-zero. Every command, no exception.** Since v5.15.0 that is a property of the CLI, not of individual commands: one checker (`internal/cli/envelope.go`) turns the server's `{"success":false,"error":…}` frame into the exit code, and a test walks the whole command tree so a newly added command cannot skip it (`internal/cli/envelope_test.go`).

| Situation | Exit | stdout | stderr |
|-----------|------|--------|--------|
| Call succeeded | `0` | the response — JSON when piped except for the line and text commands listed under [Output on a terminal and in a pipe](#output-on-a-terminal-and-in-a-pipe), a table/human form on a TTY | — |
| Server answered `success:false` | `1` | unchanged — the response is printed first, then the envelope sets the exit code, so `\| jq` keeps its bytes; the line answers (`ctx update` without `--json`, `ctx get --field`, `ctx search --lines`, `ctx guard list --ids-only`) print nothing | the server's reason |
| Transport failure, bad arguments | `1` | — | the reason |
| `ctx contract` | `0` ok, `1` drift, `2` unchecked, `3` cannot check | its own report | its own reason |

**Before v5.15.0, two dozen command paths printed the failure and exited `0`:** `stats`, `categories`, `get`, `delete`, `list-meta`, `digest`, `save`, `search`, `query --json`, `manage`, `dream` / `dream stats` / `dream review` / `dream enable` / `dream disable` / `dream throttle`, `mcp` / `mcp list`, `mcp delete`, `keys` / `keys list`, `keys delete`, and all three `block-grant` verbs. In a shell pipeline, a cron job or a git hook a rejected write was indistinguishable from a successful one. Rollout notes are in [operations](operations.md#cli-rollout-the-envelope-exit-code-contract-v5150).

**Two commands also change what they print, and only those two.** `ctx keys list` and `ctx mcp list` used to answer a `403` with *"No API keys provisioned."* / *"No MCP clients registered."* and exit `0` — an empty list and a rejected request were the same output. That line is gone from the failure path; the server's reason goes to stderr instead. In the other direction, `ctx api` now prints the failed response body it always documented and previously swallowed. Everywhere else stdout is byte-for-byte what it was.

Three deliberate exceptions, unchanged:

- **`ctx health`** reads `GET /health`, which is not an `/api` route and carries no `success` frame. It exits `0` whenever it got an answer; read the answer, not the exit code.
- **`ctx brief`, `ctx persist`, `ctx statusline`** degrade silently by design — they run inside Claude Code hooks and the status bar, where a non-zero exit would break the caller rather than inform anybody. `ctx ingest` was listed here as well, although no hook runs it; it now follows the contract and exits `1` when a file or directory was not ingested or a chunk was not written (see its entry under [Ingest & maintenance](#ingest--maintenance)). `ctx persist` drops a rejected write (non-2xx or `success:false`) the same way it drops an unreachable server — exit `0`, no error — and its `N block(s) saved` line on stderr counts only the blocks the server accepted.
- **`ctx api` and `ctx manage`** are raw passthroughs: *you* pick the route, so a body without a `success` field (a bare array, a proxied `/health`) prints and exits `0` there. An explicit `success:false` exits `1` like everywhere else.

## Output on a terminal and in a pipe

**Piped, a command prints the server's answer as JSON — unless it is a line or a text command below.** Measured by running the commands against a stand-in server, once with stdout on a terminal and once into a pipe (not run: `init`, `secrets set` / `rotate`, `backends seed`, `statusline`, `models consumers create` / `rotate`, which need a wizard, a secret on stdin, a live backend, Claude Code's JSON or a minted key; the last two are described under [Model API](#model-api-consumers--aliases)).

| stdout carries | On a terminal | Piped | Commands |
|----------------|---------------|-------|----------|
| The answer as JSON | JSON | JSON | `save`, `search`, `get`, `delete`, `list-meta`, `stats`, `categories`, `digest`, `manage`, `api`, `health`, `dream review` / `enable` / `disable` / `throttle`, `mcp delete`, `keys delete`, `block-grant create` / `list` / `revoke`, `backends create` / `update` / `delete` / `test`, `tenant delete`, `tenant grant create` / `delete`, `query --json`, `update --json`; `get` with several `--field` prints the `block` object alone, not the whole answer |
| A rendering on a terminal, JSON in a pipe | table or human lines | JSON | `dream` / `dream stats`, `settings` and its verbs, `secrets` / `list` / `rm`, `types` and its verbs, `backends` / `backends list`, `eject`, `quota` / `quota set`, `blocks audit` and `blocks classify` with their verbs, `tenant` / `list` / `get` / `create` / `update` / `usage` / `limit set` / `grant list`, `project` / `show` / `list` / `detect` / `init`, `project issues` / `list` / `show` / `create` / `comment` / `status` / `sync`, `kanban` (an interactive board on a terminal), `admin embed-migration` and its verbs except `create`, `models consumers list` / `revoke` / `deactivate`, `models aliases list` |
| Lines and raw values | lines | lines | `search --lines` (id, category, title per hit), `update` (id, title, updated_at), `guard list --ids-only` (one id per line), `get --field NAME` with one name (the value, as many lines as it holds) |
| Text | text | text | `query` (the answer and its sources), `guard` / `guard list` / `stats` / `resolve`, `dream resolve`, `mcp` / `mcp list` / `mcp add`, `keys` / `keys list` / `keys create`, `admin embed-migration create`, `brief`, `contract`, `version` |
| Nothing; a summary on stderr | — | — | `ingest`, `persist` |

**`ctx query` stays text when piped.** It does not follow the JSON rule, and it cannot be made to without breaking a script that reads today's piped text: the answer, a blank line and the `Sources` list. Use `ctx query --json` for the JSON answer (`answer`, `sources`, …). The other text commands stay text for the same reason.

**The line answers of `search --lines` and `update`** separate their fields with a tab and end every record with a newline. A tab, carriage return or line break inside a title or category becomes a space, so one record stays one line; on a terminal the text also passes the escape allowlist described under [Issues](#issues), in a pipe every other byte is the server's. `get --field` prints a text value raw in a pipe — the bytes `jq -r` printed — and through the same allowlist on a terminal. The V-11 framing of a block (`untrusted`, `untrusted_origin`), which a line or a bare value cannot carry, goes to stderr: one line per note, led by the hit's id for `search --lines`. A failed call prints no line, only the reason on stderr.

## Core

| Command | Description |
|---------|-------------|
| `ctx init` | First-run wizard, idempotent — it reports every item and changes only what is missing: `~/.config/ctx/config` (base URL + key, mode 0600 — the key is form-checked against the 64-lowercase-hex shape and probed with `GET /api/whoami` before it is written; a malformed or rejected key is asked again, never saved), a `/health` read, the same key probe on every re-run, the **backend pool** (seeds it exactly like `ctx backends seed` when no `_global` row serves `synthesis`/`embed`, then probes the serving rows and names the dead ones), a version check against the latest release (the only request to a foreign host — `--no-update-check` or `CTX_NO_UPDATE_CHECK=1` skips it), and Claude Code's `SubagentStart`/`SubagentStop` hooks + statusline (a foreign statusline is shown and kept unless you answer `y`; every rewrite of an existing `settings.json` leaves a `settings.json.bak-<UTC timestamp>` next to it). `ctx init --remove` takes the ctx hooks and ctx's statusline out again and keeps the client config. A key below server-admin only skips the pool step (it says so and points at `ctx backends seed`); hooks and statusline need no admin key. See [operations](operations.md#first-run-ctx-init) |
| `ctx query question` | Hybrid search + LLM synthesis (formatted, `--json` for raw) |
| `ctx save <cat> <title> - <content>` | Upsert knowledge block |
| `ctx save --tag tag1,tag2 <cat> <title>` | Upsert with tags |
| `ctx save --sensitivity LEVEL <cat> <title>` | Classify on write (`credentials`/`personal`/`internal`/`public`) |
| `ctx search [category] [query:text]` | Compact search (no LLM) |
| `ctx search … tags:<a,b> tags_all:<c,d>` | `tags:` keeps the blocks that carry at least one of the tags, `tags_all:` the blocks that carry all of them (`tags` / `tags_all` of `POST /api/search`); both given, both apply |
| `ctx search … types:<a,b>` | Restrict to these block types (`types` of `POST /api/search`). With the server's `search.leave_out_never_ranked` on, a search with `query:` and without `types:` leaves out the types `query` never ranks (`checkpoint`, `system-meta`, the derived layers); name the type to search them, e.g. `ctx search index query:topic-map types:system-meta` |
| `ctx search … --lines` | One hit per line: id, category and title, tab-separated, after `ctx guard list --ids-only` — `ctx search learnings query:prompt --lines \| cut -f1`. The request is the same as without the flag; no hit prints no line. A hit marked `untrusted` or carrying `untrusted_origin` gets a line on stderr, led by its id |
| `ctx search cluster:<handle>` | Restrict to ONE topic of the cluster map. The handle is the stable `topic` the graph surfaces emit (`GET /api/graph/overview`, ego annotation) — a scope-pure topic, so the answer is exactly that topic's blocks, never a neighbouring scope's half of the same cluster. Server-gated (`cluster.facet_enabled`, default off): while it is off the argument is ignored and you get an ordinary unfiltered search. A malformed handle is a `400` before any database roundtrip; an unknown, foreign or empty topic is an ordinary empty result — never a distinguishable "not found" |
| `ctx get <id>` | Fetch full block |
| `ctx get <id> --field NAME` | Only these fields of the block (repeatable or comma-separated, `--field title,updated_at`; the names of `fields` in [manage get](api.md#manage-actions)), so the server leaves `content` and `metadata` unread unless they are named. One name prints its value as `ctx get <id> \| jq -r .block.NAME` did: text raw, any other value as JSON, a key the answer does not carry as `null`, followed by one newline. The framing the server keeps on every part of a block — `untrusted`, `untrusted_origin`, `archived` — goes to stderr, one line each. Several names print the block object the server answers: `id`, the named keys and the framing keys. An empty `--field` is refused before any request. A failed get prints nothing on stdout |
| `ctx get <id> [--field content] --offset N --limit N` | A window of the content, counted in characters (`content_offset` / `content_limit`): the answer carries `content_length` and `content_truncated`. With one `--field content` the value is the window, and a window that cut the content names the next `--offset` on stderr (not for `--limit 0`). The window alone is not the content: written back with `ctx update --content-file`, it replaces the whole content |
| `ctx update <id> [flags]` | Change fields of a block without a JSON body; fields without a flag stay. `--content-file PATH` (`-` = stdin) replaces the content: one trailing newline is dropped, so what `ctx get --field content` printed comes back unchanged, and a file that is missing, unreadable or holds only whitespace is an error before any request is sent. `--edit-old TEXT --edit-new TEXT` pairs (repeatable, applied in order; `--replace-all` replaces every occurrence of each old) or `--edits-file PATH` (a JSON list, `[{"old":…,"new":…,"replace_all":…}]`, other keys refused) change part of the content — the `edits` of [manage update](api.md#manage-actions): an old that does not match exactly once writes nothing. `--title`, `--category`, `--type` (an empty value is refused); `--tags a,b` replaces the tag set — an empty `--tags` is refused as well, since it would clear the set (to clear it, `ctx manage update <id> '{"tags":[]}'`); `--meta key=value` sets one metadata key to a string and `--meta-unset key` removes one, every other key stays (`metadata_merge`). `--edit-new ''` deletes the old text, as `"new": ""` does on the wire. Contradicting flags (content with edits, a key named twice) are refused before any request. The answer is one line, `id`, `title` and `updated_at` tab-separated; `--json` prints the server's whole answer. A refused update exits `1` with the server's reason, e.g. `edits[0]: old matches 0 times …`. A server that predates `edits` and `metadata_merge` (issue #406) ignores both keys: an update that carries nothing else fails there, and beside another flag they are dropped without an error. `ctx manage update` stays as it is |
| `ctx get --include-archived <id>` | Also read an archived block — full block id only, from the key's own home and allowed scopes (never through a block or cross-tenant scope grant); the answer carries `"archived": true`. A server without this flag ignores it and answers `Block not found` |
| `ctx list-meta [--after <next_after>]` | All live blocks of the key's read scopes without content, at most 10 000 per answer. A cut answer carries `"truncated": true` and a `next_after` object; pass that object to `--after` for the rows that follow (`manage list-meta`, see [API](api.md#manage-actions)) |
| `ctx delete <id>` | Soft-delete (archive) |
| `ctx categories` | List all categories |
| `ctx stats` | Database statistics + Dream backlog (`dream_queue`: pickable/cooldown/incoming-forecast) |
| `ctx health` | Healthcheck |
| `ctx version` | Print version |

## Ingest & maintenance

| Command | Description |
|---------|-------------|
| `ctx brief` | Project briefing from store |
| `ctx persist` | Persist `[PERSIST:cat:title]` markers |
| `ctx ingest <path>` | Ingest a folder of Markdown files (an Obsidian vault, a repository). A block's title is the file's path relative to `<path>` without `.md` (`docs/guide/README`, plus ` — <heading>` when the file is split by heading), so files with the same name in different folders stay separate blocks. Files in subfolders ingested before this rule carry the bare file name as title; a re-ingest writes them under the new title and leaves the old blocks in place. Within one file every chunk gets its own title. When two chunks would share one because a heading heads more than one section, each such section takes its parent H1 in front (`docs/guide/README — Alpha > Notes`; the context header's `Sektion:` line, written for chunks of 500 bytes and more, carries the same path). A title that still repeats (an H1 twice, the same H2 twice under one H1) gets ` (2)`, ` (3)` on its later chunks. These titles are kept within the server's 500-byte title limit, which otherwise refuses the whole upload batch: the parent is left out where it would pass it, and the heading is cut at a character boundary to make room for the counter, down to the bare number when the file's path leaves no more room; a path that leaves less room than the number holds the file back (below). A file in which no two chunks shared a title keeps its titles. A file in which some did was ingested before this rule into one block per shared title, holding the last of those chunks; a re-ingest writes each chunk to a block of its own, and when the parent takes every chunk off the shared title, that old block stays in place. **Server limits:** the server refuses a whole request when one chunk has a title over 500 bytes, a category over 100 bytes, content over 50 KB, an empty title or category, or a category reserved for derived blocks (`catalog`, `session-insights`, in any case — a top-level folder of that name, or `--category`), so `ctx ingest` checks every chunk before the upload. A file with such a chunk is held back whole, not sent, and listed under `Errors` with its path, the size and the limit (`notes/x.md: not uploaded: chunk 10 of 10: the title is 501 bytes, the server accepts at most 500`); the other files are uploaded. Before this check one such file failed every chunk of its batch, the other files' included. The limits count bytes as the server decodes them: a byte that is not valid UTF-8 (a Latin-1 file name or heading) travels as U+FFFD, three bytes. A batch the server answers with per-chunk failures (`200`, `success: false`, `failed > 0`) is counted chunk by chunk, and every failed chunk is listed under `Upload errors` with its file and the server's reason; before, the whole batch counted as failed with `server: unknown error`. `--workers` below 1 is refused, and so is `--batch` outside 1 to 200, the most chunks the server takes in one request (above it every batch was refused with `413`; 0 and below used to become 50). The request body has a second limit of its own, 10 MB. Every chunk of a note carries the note's tags, and its first chunk the note's links and dates (**Metadata**, below), so a note with thousands of links makes one large chunk, and paragraphs near 50 KB make large chunks too. `ctx ingest` counts each batch as it is sent (the JSON body, escapes included: `<`, `>`, `&` and an invalid UTF-8 byte take six bytes) and ends it before the chunk that would take it past 10 MB, or at `--batch` chunks, whichever comes first; a vault whose batches stay below 10 MB is sent in the same requests as before. A chunk whose request alone is over 10 MB cannot be sent in any batch: its file is held back whole, like a file over a per-chunk limit (`notes/index.md: not uploaded: chunk 1 of 1: the request for this chunk alone is 11005694 bytes, the server accepts at most 10485760`). Before, batches were cut by count only, and a batch over the limit was refused whole, the chunks of the other files in it too (`Invalid request body`, exit `1`), on every run. The server answers a body over the limit with `413` (`request body exceeds 10 MB cap`); a `413` whose answer gives no reason, as a proxy in front of the server sends it, is reported as `HTTP 413: the request of N bytes is too large for the server or a proxy in front of it`. A directory the scan cannot read is listed under `Errors` like an unreadable file (`notes/locked: could not be read, files under it may be missing: …`) and the scan goes on; hidden directories inside the vault (`.obsidian`, `.git`, any name starting with `.`) and `node_modules` are skipped on purpose and never read. The vault itself is walked whatever its name (`ctx ingest ~/.notes`), and a vault path that is a symlink to a directory is followed. Before, an unreadable directory was dropped without a word, and a vault named with a leading `.` or reached through a symlink gave `No .md files found.`. **Metadata:** the metadata of every chunk names its origin, `source: "obsidian"`, and the file's path in the vault, `vault_path` (for a note under a linked folder the path through the link, below). The note's wikilink targets, `links`, and the dates found in its frontmatter and text, `dates`, belong to the whole note: they are in the metadata of its first chunk only, and the note's other chunks carry the two keys as `null`; a note without wikilinks or without dates has that key on no chunk. A reader finds a note's lists on the chunk of its `vault_path` whose `links` or `dates` is an array; a block of a chunk the note no longer produces (a heading renamed or removed) stays in place with the metadata it stored, a list included, as it did before. Before, every chunk carried both lists, so a note with thousands of links repeated them with every chunk, in the request and in every stored block. The first ingest of such a note after the change sets the two keys to `null` on its other chunks, once, and skips them from then on: a change of the metadata only, which keeps the blocks' embeddings and full-text vectors (the summary counts these chunks under `Updated`). A `ctx ingest` from before the change, run over the same vault, puts the lists back on every chunk, and the next run of a newer one sets them to `null` again. The other chunks carry `null` rather than no key because the server merges the metadata of a chunk whose content has not changed into the stored block, and a key left out would keep the list stored before, also on a chunk that is no longer the note's first. For the same reason a note that loses its last link or date keeps the old list on the chunks whose content did not change, as it did before. **Links:** a symbolic link to a folder is followed, also when the folder lies outside the vault (a folder an Obsidian vault shares with another one by a link), and its notes keep the path through the link: `shared/sub/note.md` gets the category `shared`, the title `shared/sub/note` and that `vault_path`, so a re-ingest writes into the same blocks. A link to a note is ingested under the link's path, as before, also when the note is reachable another way (directly, in a linked folder or through a second link): each way gives its own block. Every link followed out of the vault is listed under `Followed out of the vault` with its target: the scan reads what the links lead to with the user's rights, so a vault from someone else can lead it to folders outside the vault (as a link to a note could before), and `--dry-run` shows where. Every real folder is walked once, which ends a cycle and keeps two links to one folder from ingesting it twice: the scan walks the vault without following a link first, then the links it found there, then the links found behind those, each round sorted by the link's path in the vault (byte order: `a-b` before `a/l1`). A folder reached without a link thus wins over every link to it, a way through fewer links over one through more, and among equal ones the link whose path sorts first, whatever order the file system lists a folder in. Every other way to a folder is listed under `Not followed` with its target (`t2 -> /home/u/shared: already ingested through t1`), and so is a link to the vault or to a folder that holds it, which is not followed (`notes/up -> /home/u/vault: the vault or a folder that holds it`); neither changes the exit status. A link named with a leading `.` or `node_modules` is skipped like a folder of that name, and so are such folders under a link's target; the target itself may have any name. A link that leads nowhere or cannot be resolved is listed under `Errors` and counts for the exit status when it may have led to notes: a link named `.md` (as before) or one without an extension (`Shared: could not be followed, files under it may be missing: …`). A dead link named with another extension (`img.png`, but also a folder name like `v2.0`) is taken for a missing attachment, which ingest would not read: it does not count, and all such links share one line under `Not followed` (`img.png and 3 more: lead nowhere, taken for missing attachments (named with an extension other than .md)`). A linked folder the scan cannot read is listed like an unreadable directory. `--dry-run` reports all of this the same way. Before, a linked folder was skipped without a word and the run exited `0`, and a link named `.md` that led to a folder failed as an unreadable file. Links cost the scan a `stat` each and a path resolution each for a link to a folder; a vault without links costs no system call more than before. **Scope:** the chunks go to the key's home scope, or to the scope `--scope` names (sent as `target_scope`, [API](api.md)). The key must be allowed to write that scope — a scope belongs to one tenant, and `shared` is the default tenant's shared layer, as for `ctx save --shared` — or the server refuses the batch (`Cannot write to requested scope`) and writes nothing; the run then sends no further batch (`Not sent:` in the summary) and exits `1`. The summary's `Scope:` line names the scope from the server's answer, not the flag. Through 5.48.2 the flag defaulted to `private`, the server ignored it, and every run wrote to the key's home scope and reported success. Against such a server the line reads `Scope: not reported by the server`; a run with `--scope` asks `GET /api/whoami` for the key's home scope, goes on when `--scope` names it, and otherwise stops after the first batch, which went to the home scope, and exits `1`. `--dry-run` names the scope as not checked: it does not contact the server, and only the server knows which scopes the key may write. **Exit status:** `1` when a file or directory was not ingested (unreadable, a link that could not be followed, or held back), a chunk was not written (a refused or failed batch, the server unreachable) or the server did not confirm the scope `--scope` named, after the full summary on stderr, also when the scan found no `.md` file because a directory could not be read; `0` when every chunk was written or there was nothing to write. `--dry-run` sends nothing and exits `1` when the upload would leave a file or directory out. Before, `ctx ingest` exited `0` in every one of these cases |
| `ctx digest` | Rebuild the topic map, and — when `root_map.enabled` is on — the **root map** (`root-map-<scope>`, one line per topic cluster instead of one per block). Never starts a Louvain rebuild; it renders from the cluster state that exists. With `digest.mode=stub` the old block becomes a ~300 B pointer to the root map, so `ctx search index query:topic-map types:system-meta` still tells you where to look (the topic map is a `system-meta` block; without `types:` a server with `search.leave_out_never_ranked` on does not find it) |
| `ctx statusline` | Claude Code status bar |

## Admin: config, secrets, backends

(All require an **admin key** — see [security](security.md#admin-tier).)

| Command | Description |
|---------|-------------|
| `ctx settings [list\|get\|set\|unset]` | Runtime settings overrides (alias `cfg`; reads included). TTY: table, pipe: JSON; `get` leads with the key's registry description; `set` takes the value as argument or stdin; API failures (422/409/403) exit 1 with the server's reason. On `mcp.instructions`, `get` adds the comparison with the shipped wording, and `get mcp.instructions --text value\|current\|base\|<id>` prints one text raw, for `diff` |
| `ctx secrets [list\|set\|rotate\|rm]` | Sealed provider credentials (alias `sec`). Write-only: values go in via stdin ONLY (`echo "$KEY" \| ctx secrets set <name>` — an argv value is rejected, it would leak via /proc and shell history); list shows metadata + `referenced_by`, never values; `rm` exits 1 with a 409 while settings or backend pool rows (`api_key_ref`) reference the secret |
| `ctx backends [list\|create\|update\|delete\|test]` | LLM backend pool. TTY: table with live status, pipe: JSON; `create`/`update` take a JSON spec as argument or stdin; API failures exit 1 |
| `ctx backends seed` | First seed of an empty pool (**server-admin key**): a SeedSpec (`--file`, stdin, or the `--host`/`--model`/`--embed-model` shorthand) becomes two `_global` rows, `chat-primary` + `embed-primary`, at `full-trust` so they serve your own blocks. An `api_key` is sealed into an F2 secret first and the row gets only the reference — without a configured `CTX_SECRETS_KEY` the run aborts with 0 rows written, never a plaintext fallback. Idempotent per row (a re-run completes a partial seed); rows outside the pair abort the run unless `--force`. See [operations](operations.md#backends) |
| `ctx types [list\|get <name>]` | Block-type registry reads (**any valid key**): list the types visible to your key (shipped `_global` set + your tenant's overlay, each with a `source` badge) or inspect one type's policy config. TTY: table, pipe: JSON; a 404 (unknown/foreign type) exits 1 |
| `ctx types set <name>` | Upsert a type (**admin or tenant-admin**): `--display`, `--description`, `--config <json>`, `--default`. Only flags you set are sent. The scope is pinned by your key's role (tenant-admin → your tenant namespace, which is your key's home scope; operator → `_global`), never a flag; targeting a `_global` type as tenant-admin exits 1 (403) |
| `ctx types rm <name>` | Delete a type (**admin or tenant-admin**): a type still referenced by blocks or a builtin exits 1 (409 + count); `_global` types are operator-only |
| `ctx eject [on\|off]` | Eject toggle (canonical, AM-7): drop the GPU-host backends from every chain so the GPU is free (CPU/external stay in as failover). No arg = status (any valid key); `on`/`off` need an admin key. Sends the canonical `eject-mode` manage action; toggles the reserved `eject` disable-profile (092) — persists as that profile row, survives a restart and hits the next chain without one (the legacy `gaming.active` settings key was retired in U01-W5). Legacy alias: `ctx gaming` (kept shape-compatible for existing scripts, N19 — same effect, canonical action) |
| `ctx blocks audit [status\|sample\|start]` | Sensitivity LLM audit: classify `sensitivity_source='default'` blocks over the hard-local `classify` chain. `sample --n 30` = dry-run verdicts without writes, `start [--limit N]` = live run, bare/`status` = progress. See [security](security.md#sensitivity-classification) |
| `ctx blocks classify [status\|dry-run\|start]` | Credentials PATTERN re-audit: the deterministic detector raises every home-scope hit to `credentials` (`sensitivity_source='pattern'`), upgrade-only. `dry-run [--limit N]` = full scan WITHOUT writes (run it first), `start [--limit N]` = live run, bare/`status` = progress |
| `ctx mcp [add\|list\|delete]` | Manage MCP OAuth client registrations. `add <label> [--redirect-uri <uri>]…` (02-W2): repeatable exact redirect allowlist entries — `https` for real hosts, plain `http` only on loopback (RFC 8252); anything else is rejected server-side. Clients registered without it keep `redirect_uris='{}'` and the static S2 allowlist until 03 wires per-client matching (a redirect-less client then matches nothing) |

## Model API: consumers & aliases

Consumers are the external programs that call the OpenAI-compatible `/v1` API with a `ctxm_` key; a consumer belongs to one tenant. Model aliases are the model names a consumer may be granted. All commands wrap the existing `model-consumer-*`, `model-key-*` and `model-alias-list` manage actions.

| Command | Description |
|---------|-------------|
| `ctx models consumers list [--status S,…] [--q TEXT] [--tenant ID] [--limit N] [--cursor C]` | List consumers with their keys' status (**tenant-admin key**). `--status` takes `active`, `expiring`, `rotating`, `no_key`, `inactive` or `all`; keyset-paginated: pass `next_cursor` back with `--cursor`. `--tenant` (another tenant than your key's own) needs a server-admin key. Keys are listed by hint only, never by plaintext |
| `ctx models consumers create --label L` | Create an `app` consumer and mint its first key (**self-service**, when the server allows it). Policy flags: `--description`, `--tenant` (server-admin), `--tenant-scope` (a scope of the consumer's own tenant), `--model <alias-id>` (repeatable) or `--all-models`, `--sensitivity credentials\|personal\|internal\|public`, `--lane urgent\|bulk`, `--fair-weight 1..100`, `--cidr` (repeatable), `--allow-plaintext`, `--expires <RFC3339>`. Only the flags you set are sent; the server's tier rules decide which a tenant-admin may set |
| `ctx models consumers rotate <consumer-id> [--grace D] [--expires T]` | Mint a successor key (**self-service**). `--grace` is a Go duration (`24h`, `0s`) sent as whole seconds (a fraction of a second is refused, never rounded): `0s` revokes the predecessor at once (the leak case); absent = the server's `gateway.key_rotation_grace` |
| `ctx models consumers revoke <key-id>` | Revoke one key now and end its running requests (**tenant-admin key**). Prints `cancelled_inflight` — the requests ended in that ctx process, `unknown` when the server cannot count |
| `ctx models consumers deactivate <consumer-id>` | Soft delete (**tenant-admin key**): the consumer stays listed as `inactive`, all its keys are revoked, its running requests end; prints `cancelled_inflight` like `revoke` |
| `ctx models aliases list` | The model aliases your key can read, with `writable` (**tenant-admin key**) |

**The key plaintext is shown exactly once.** `create` and `rotate` print the minted `ctxm_` key once on stdout — never on stderr, never in an error message — and it cannot be retrieved later (rotate mints a new one). The key is taken out of the answer before anything else is judged: even when the answer is otherwise broken (no `success` field, `success:false`, a missing or invalid consumer/key object) the minted key is printed once, then the command exits 1 with an error that names the defect and never quotes the answer.

On a TTY the output is a table (lists; a further page is announced as `more: --cursor C`), a key-value block followed by the `api_key:` line and the save warning (`create`, `rotate`), or `cancelled_inflight: N` (`revoke`, `deactivate`); labels and other tenant-supplied text pass the same terminal-escape allowlist as issue titles. Piped, or with `--json`, it is JSON: `{consumers, next_cursor}`, `{model_aliases, count}`, `{consumer, api_key}`, `{key, api_key}`, `{cancelled_inflight}` (`null` = unknown). Both forms are a projection over the documented fields — a list never passes the raw server body through. A missing `--label` and invalid flag values (`--lane`, `--sensitivity`, `--fair-weight`, a negative or fractional `--grace`, a non-RFC3339 `--expires`, `--limit` ≤ 0, an unknown `--status`) fail before any request is sent. A `success:false` envelope (403, 404, 400, …) exits 1 with the server's reason.

## Projects

A project binds one repo corpus to exactly one tenant scope (Model C): the scope is the isolation boundary, so a scope belongs to one tenant and each project's issues live only in its own scope.

| Command | Description |
|---------|-------------|
| `ctx project` | = `show`: detect this repo's identity, then look up its registered project. TTY: detail; pipe: JSON |
| `ctx project detect` | Resolve the identity locally, no server call. Precedence: a GitHub `origin` remote → `github:owner/repo`, else a single-root git repo → `git-root:<sha>` (survives clones), else a manual slug (prompted on a TTY, an **error when piped**). TTY: human lines; pipe: JSON `{identity, source}` |
| `ctx project init [--identity ID \| --repo URL]` | **Provision** this repo: the server-admin `project-provision` compound mints a whole isolated tenant-per-repo in ONE transaction — tenant + scope `<slug>:main` (slug derived from the identity; on overlength truncated + a hash suffix so two long identities never collide) + owner key + a **repo-agent key** + an LLM-quota seed. Idempotent — re-running with the same identity is a No-op that returns the existing project (the reveal-once keys are shown ONCE, at first provision). The repo-agent key is minted STRICTLY to the agent-key template (`home_scope=<scope>`, `allowed_scopes=[]`, `write_scopes=[]` — it can write ONLY its own scope, never `shared`) and stored **0600 under `~/.config/ctx/projects/`, NEVER in the working directory** (a secret in the repo would be a commit hazard). Writes `.ctx-project` (the identity + scope/key-path pointers as comments, never a secret). Needs a **server-admin key** (tenant creation is server-admin, like `ctx tenant create`). The legacy register-into-an-existing-tenant path lives on `ctx api POST /api/project` |
| `ctx project show` | Detect, then show the registered project (or a "not registered" hint) |
| `ctx project list` | Every project your key can read (scope intersection). TTY: table, pipe: JSON |

**`.ctx-project` is a detect shortcut, not a trust anchor.** For `github:`/`git-root:` identities `detect` honors the file **only when it matches** the independent git detection; a mismatch (e.g. a cloned foreign repo with a planted file that would redirect issue writes into someone else's corpus) forces interactive confirmation on a TTY and **errors when piped** (exit ≠ 0). Only `manual:` identities — which have no independent source — are authoritative from the file.

### Issues

Work with a project's issues. The project is detected from the current repo (like `ctx project`), or named explicitly with `--project` (a project id **or** an identity). The state-change verb is **`status`** (not `state`/`move`). On a TTY the output is a table / human lines; piped, it is the raw server JSON (stable, scriptable). A `success:false` envelope exits 1 with the server's reason.

| Command | Description |
|---------|-------------|
| `ctx project issues [list]` | List issues, newest first. Filters: `--state <status>`, `--label <l>` (repeatable), `--q <text>`. Keyset-paginated for 10k+ issues: the response carries an opaque cursor; pass it back with `--after <cursor>` for the next page. `--sort created` gives a gap-free immutable traversal for export |
| `ctx project issues show <block-id>` | Show one issue in full plus the first page of its comment thread (a foreign/unknown id reads as not found) |
| `ctx project issues create [title]` | Create an issue. Title is the positional arg **or** `--title`; body is `--body` **or** stdin (`echo body \| ctx project issues create --title t`). `--label` (repeatable), `--status` (a valid entry state for the type policy) |
| `ctx project issues comment <block-id>` | Add a comment to an issue's thread. Body is `--body` or stdin; `--author` labels it (default: anon) |
| `ctx project issues status <block-id> <new-status>` | Move an issue to a new workflow status. The transition is validated against the type's policy data server-side; an out-of-policy target exits 1 (422) with the reason |
| `ctx project issues sync [--status]` | Trigger a forge (GitHub) pull sync for the project (needs **write** access to its scope — decision E6=a), or with `--status` poll the current/last run without starting one. A double-start of the same project, the per-project rate limit, or the daemon-wide concurrency cap exit 1 (409/429) with the server's reason |

Issue/comment titles, bodies and labels are attacker-controlled text (any user can open an issue in a mirrored repo). Human/TTY output runs every such value through a terminal-escape **allowlist** — all C0 controls except newline/tab, DEL, and all C1 controls (raw byte or code point) are stripped — so a crafted title cannot drive escape sequences into your terminal, an agent log or CI output. The piped JSON is the machine contract and is left verbatim.

### Board

The kanban board view: the project's issues grouped into the workflow-status columns of its type config (never hardcoded). One data path — the CLI eats the same `/api/project/{id}/board` wire the web UI does.

| Command | Description |
|---------|-------------|
| `ctx kanban [--project ID] [--limit N]` | On a **TTY**, an interactive, read-only board (bubbletea/lipgloss): arrows or `hjkl` navigate columns/cards, `q` quits (v1 does not mutate — re-status via `ctx project issues status`). **Piped**, the raw board JSON `{columns:[{status,count,issues,cursor}]}` (stable, scriptable). Each column carries a total `count` and only a **first page** of cards, so the board scales to 10k+ issues per column; `--limit` sets the page size (server default when 0). Page a hot column via its `cursor` with `ctx project issues list --state <col> --after <cursor>`. Titles are sanitized through the same escape allowlist on a TTY; the piped JSON stays verbatim. A `success:false` envelope (e.g. a foreign project) exits 1 |

## Raw REST access

| Command | Description |
|---------|-------------|
| `ctx api <method> <path> [json]` | Generic authenticated passthrough to any `/api` route (method is GET/POST/PUT/PATCH/DELETE; JSON body via arg or stdin, sent verbatim). Prints the response JSON; a `success:false` envelope exits 1 with the server's reason. This is the script-level reach for the REST surfaces (project/types/issues) that are not `manage` actions — e.g. `ctx api GET /api/project`, `echo '{"display_name":"X"}' \| ctx api PATCH /api/project/<id>` |
| `ctx manage <action> [id] [data-json]` | The short spelling of `ctx api POST /api/manage '{"action":…}'` for the manage actions — `ctx manage stats` instead of `ctx api POST /api/manage '{"action":"stats"}'`. Since v5.15.0 it **runs that exact code path**: same request on the wire, same output, same exit contract (it used to print a `success:false` envelope and exit 0). `id` becomes the `id` field, `data-json` the `data` field (invalid JSON is sent as a plain string, unchanged). `ctx manage purge` waits for the answer without the 120 s client timeout (the one difference to `ctx api POST /api/manage`, which keeps it): a confirmed purge runs to its end on the server either way ([api](api.md#manage-actions)) |

## MCP over stdio

| Command | Description |
|---------|-------------|
| `ctx mcp serve [--allow-files DIR]…` | Runs the CLI as a local MCP server on stdin/stdout that forwards to `<CTX_BASE_URL>/mcp` with the key of this configuration — register it with `claude mcp add ctx -- ctx mcp serve`, no header and no OAuth client. Tools, descriptions and server instructions are the server's, mirrored at run time; a call has the effect and answer of the same call against `/mcp`. An unreachable server, a refused key or a missing configuration answers the request with the cause and the process keeps serving; stdout carries protocol frames only. `--allow-files DIR` (repeatable) adds `content_file` (send a file's text as `content`) to every tool with a `content` string and `output_file` (write the block's content to a file) to `get`, confined to those directories after symlink resolution; without it neither is offered. Not part of the envelope exit contract above: it answers in MCP and exits `0` when stdin closes. Details: [MCP reference](mcp.md#local-stdio-server-ctx-mcp-serve) |
