# Multi-Tenancy

ctx is a shared knowledge layer across multiple LLM/tenant identities. The multi-tenant line (**v4.0.0**, migrations 058–068) is feature-complete across all six axes; the optional migration 066 (tenant-owned OAuth) is deferred. The full integration suite and race detector are green, and a pre-release isolation audit found no cross-tenant leak across the read/write, settings/secrets, admin-tier, MCP, chat and background paths.

**Pausability invariant.** Every wave is built behavior-neutral and pausable: the single-tenant deployment (one default tenant, no provisioned tenants) is byte-identical to the pre-multi-tenant state. Each mechanism activates only when its data arrives (a tenant is provisioned, a grant is minted, a per-tenant setting is written). Rolling out to a running deployment — migrating the production DB from 057 across the 058–068 chain — is a separate operational step; see [operations](operations.md).

## Model C: three levels

ctx uses **Model C** — three levels of isolation: **tenant → scope → block**.

- `scope` is the data discriminator: a `VARCHAR(50)` column on every data table (blocks, blobs, sources, dream-links, write-log). It is **not** a `tenant_id` on the data tables. Migration 058 dropped the legacy 3-value CHECK constraints, so scope strings are unconstrained at the schema level (`private` | `work` | `shared` | any tenant scope).
- The tenant register (migration 059) maps scopes to tenants: `context_tenants` (owner-register) + `context_tenant_scopes` (scope → tenant partition map), plus `tenant_id` and a `tenant_role` (`owner`/`admin`/`member`) on API keys.
- Block-level grants (migration 067) are the finest level — sharing a single block with a foreign tenant.

Each key sees: all blocks in its own scope, all blocks in `shared` (the default tenant's shared knowledge layer — **not** cross-tenant; foreign tenants only via grants), plus any scopes/blocks explicitly granted to it. Nothing from other tenants' private scopes.

> **`shared` is a scope OF the default tenant** — a shared layer *inside* that tenant, reversibly re-hangable by moving one `context_tenant_scopes` row (`TENANT-DECISION(shared-scope-owner)`).

## Authentication & read-scope resolution

`ctx_auth` (the per-request auth function, rebuilt in migration 060) consumes the tenant schema and returns the key's `tenant_id`/`tenant_role`. It applies:

- **Status gate (fail-closed).** A `suspended`/`offboarding` tenant — or a key whose `tenant_id` is NULL — authenticates to the `__UNAUTHORIZED__` sentinel. Setting a tenant's `status` to `suspended` (via `tenant-update`) mutes it at the next auth.
- **Positional read-scope resolution.** `read_scopes` = `[home_scope] ++ allowed_scopes ++ cross-tenant grants`, with order-preserving dedup so `read_scopes[0]` stays `home_scope` for wire stability. System `_`-prefixed scopes are filtered out.

The **`RequireScopes` guard** establishes the fail-closed read contract: an empty resolved scope set is an error, never a silent `scope = ANY('{}')` that matches nothing. It is wired into every scope-filtered store read (block + blob search/get/list/stats, the graph overview + ego reads), and the four MCP tool handlers (store/search/get/recent) no longer fall back to the default-tenant `private` scope when no caller identity resolves. Tenant lifecycle status (active/suspended/offboarding) supports muting a tenant (access + background paused, data preserved and reactivatable) versus an explicit super-admin full-prune. A key-bearing tenant can't be deleted naked (`ON DELETE RESTRICT`), and neither can one with model consumers: `tenant-delete` hard-deletes the tenant's model keys and then its model consumers (step 7b of the prune) in the transaction that deletes its knowledge keys, before them, and only then the tenant row — the one path that deletes rows of either table (otherwise a consumer is deactivated and a key revoked).

`store.TenantScopes(tenant)` exposes a tenant's owned scope set (the per-tenant data foundation, distinct from a key's `read_scopes`).

## Cross-tenant grants (scope level)

`context_tenant_grants` (migration 061) is the opt-in, least-privilege cross-tenant read channel: one tenant grants another read access to one of its scopes (FK-guarded so system scopes can't be granted). A grant only ever **widens the grantee's READ scope set** — never its write side (the `context_store.go:99` home-scope write gate is unchanged). It takes effect at the grantee's next auth.

Managed by server-admin manage-actions `tenant-grant-create` / `tenant-grant-list` / `tenant-grant-delete`: create rejects a `_`-system scope (400, with the `granted_scope` FK as fail-closed backstop), an unregistered grantee/scope (400) and a duplicate pair (409), and records the creating admin key for provenance; delete is a 404-no-oracle by id.

## Per-key write scopes (E4b, migration 078)

By default a key may WRITE blocks only to its `home_scope` (plus `shared` when that is in its `allowed_scopes`); every other `allowed_scope` stays read-only (write-in, never-out). Migration 078 adds an explicit `context_api_keys.write_scopes TEXT[] NOT NULL DEFAULT '{}'` so a key can be granted extra write targets **beyond** its home scope without widening its read set. The effective write gate — the single eval point `writableBlockScopes`, used by `/api/store` create, `/api/blob/store`, the MCP `store`/`blob_store`/`blob_link` tools (E-M4) and `manage` update/delete/guard-resolve — is:

```
writableBlockScopes = [home_scope] ∪ (write_scopes ∩ (allowed_scopes ∪ {home_scope})) ∪ {shared if allowed}
```

The invariant `write_scopes ⊆ allowed_scopes ∪ {home_scope}` (a write right implies a read right — no blind-writers) is enforced **twice**, fail-closed:

- **(a) at mint/update** — `api-key-create` and `api-key-update` reject a `write_scope` outside `allowed_scopes ∪ {home_scope}` (or a `_`-reserved name) with **400** (Go-side, no DB CHECK — the v2.0.0 open-set line).
- **(b) at the eval point** — the formula intersects `write_scopes` with the readable set, so a `write_scope` left **stale** by a later `allowed_scopes` shrink is neutralised for free; no per-write-site re-check is needed.

`ctx_auth` returns the RAW `write_scopes` column as its 9th return value (appended after `tenant_role` — old binaries selecting the original 8 columns keep working); the intersection is applied in Go, so the DB stays the record of intent and the gate stays the single fail-closed decision. **Backfill: none** — the empty default reproduces v4.2.x behaviour byte-for-byte (pausability/rollback invariant). Set at creation via `ctx keys create … --write <scopes>` (or the `write_scopes` field on `api-key-create`); mutate an existing key via `api-key-update {write_scopes:[…]}` (`[]` clears the set, absent = leave unchanged).

## Per-key confirm-writes capability (F6-C6, migration 090)

Migration 090 adds `context_api_keys.confirm_writes BOOLEAN NOT NULL DEFAULT false` and rebuilds `ctx_auth` with it as the **10th** return column (appended after `write_scopes` — the same DROP+CREATE/append-at-end convention as 078, so old binaries selecting the original 9 columns keep working). It flows into `auth.AuthResult.ConfirmWrites` and is consumed **only at the store handlers** (`/api/store`, MCP `store`) — internal writers (digest, dream) go through `store.UpsertBlock` and never see it.

This is **not a security boundary**: gating LLM-initiated writes is the calling harness's responsibility (tool approval in Claude Code/claude.ai; the ctx web chat's own confirm card). The flag is a per-principal **distrust tool** — the option to force server-side stage-then-confirm onto a harness that has no trusted gating layer of its own. Default `false` = fail-open for every existing key: nothing changes on deploy, opt-in is a per-id `UPDATE context_api_keys SET confirm_writes = true` (the `is_admin`/052 bootstrap convention).

The staging building blocks (D-W2): `store.CanonicalWrite` defines the canonical JSON form of a staged write — fixed field order, sorted tags, sorted metadata keys — and `PayloadHash` yields the sha256 the confirm call will select by; the hash binds the resolved write **including its post-gate sensitivity**. `handler.runStageWriteGates` runs every direct-path write gate (size, sensitivity, explicit type, G40 credentials detector, scope, write rate limit) **before** anything is staged, so a confirm card can only ever promise a write the execute step will accept.

The staged path is live on MCP (D-W5): a flagged key's `store` call runs that full gate set, holds the canonical payload server-side (`context_pending_writes`, 089) and answers **`IsError=true`** with a `payload_hash` — a legacy client must never read "staged" as success. The new `confirm` tool executes exactly that server-held write: per-key, replay-safe (atomic single consume), with the write scope re-validated against the key's *current* rights at confirm time (a shrunk right rejects on a lookup, without burning the stage token). REST `/api/store` and the CLI stay direct by decision D-E1 — they serve human-driven clients, not LLM harnesses.

The MCP `blob_store` tool joined the staged path in W02-8, with one addition the block path does not need: a staged blob payload sits server-side in `context_pending_writes` for the whole TTL, so `pool.blob_stage_max_bytes` (default 1 MiB) bounds it, and a payload above the cap is **refused by name** instead of falling back to a direct write — a size must never be the way around a key's confirmation policy. `0` disables blob staging for such keys entirely. The budget (`blob-write`) is charged at stage time like the block one, so `confirm` books nothing. The tool takes an optional `scope` since E-M4 (2026-08-25, superseding decision D4, as for `store`): absent ⇒ the key's `home_scope`, named ⇒ resolved through `writableBlockScopes` **before** the stage, so a card is never issued for a scope the key may not write. Either way the resolved scope is what the stage row and the hash-bound payload carry, and what the confirm re-validates against the key's current rights. W02-10 adds `blob_link` to the same path (op `blob_link`): it carries no payload, so no staging cap applies, and it is staged under the BLOB's own scope rather than the key's home scope — that is the scope the confirm re-validates, and a link to a blob outside `writableBlockScopes` is `blob not found` at both stage and confirm time. A staged write that references a context block (either op) also re-checks that block's visibility in the key's read scopes before the consume, so a read right that shrinks between staging and confirming rejects the card instead of writing a cross-scope edge.

The MCP `update` tool (D-W6a) extends the dance to field-level block updates — REST manage-update parity (resolve within `writableBlockScopes`, size limits, re-classify/temporal/re-embed afterwork), no scope/type/sensitivity field (those guard flows stay REST-only — on an EXISTING block a scope change is a MOVE that sweeps the link tables, and a sensitivity downgrade needs the confirm; the `store` tool's own `type` field arrived later in N-26 and its `scope` field in E-M4, both on the write-new path only, where the value NAMES where a new row goes instead of moving an old one; re-typing or re-scoping an existing block still goes through `manage update`). For a flagged key the update stages as op `update` with two extra hash-bound fields: `update_fields` (the authoritative field list — "clear tags" and "leave tags unchanged" can never collide) and `base_updated_at` (the block's `updated_at` at stage time, the **TOCTOU pin**, D1-M3). A confirm re-reads the block and rejects — without consuming the token — when the block changed since staging (lost-update protection); the client re-reads and re-stages.

The web chat goes further (D-W6b): it is itself a harness **without** an own gating layer and runs the smallest model, so its new `ctx_store` tool stages **every** write — default-confirm by birth, independent of the per-key flag (there is no legacy chat writer to break). The staged card travels on the `tool_result` SSE event and inside the persisted tool message, and the SPA ConfirmCard executes it via `POST /api/confirm` — mounted behind the header-auth middleware only (`X-Context-Key` / `Bearer`; no cookie path exists server-wide, so a cross-site POST carries no usable credential). Dismissing a card is client-side: the stage expires (`writes.confirm_ttl`) and the retention ticker evicts it.

Since D-W6c ONE confirm sequence serves every surface: `confirm_core.go` holds the shared lookup → validate → D1-M1 scope re-check → D1-M3 TOCTOU re-check → atomic consume → execute chain, and the MCP `confirm` tool and `POST /api/confirm` only map its typed outcome onto their wordings (MCP surfaces raw errors, HTTP launders them; TOCTOU rejects answer HTTP 409). That makes the confirm surfaces interchangeable — a write staged over MCP confirms over HTTP and vice versa — and the chat gains `ctx_update` (staged field-level updates with the same `update_fields`/`base_updated_at` hash-bound form as the MCP update tool; the ConfirmCard shows the field list and the lost-update reject).

## Block-level grants (row level)

`context_block_grants` (migration 067) shares **one** `block_id` with a `grantee_tenant` — a granularity finer than the scope-level grants. `block_id` and `grantee_tenant` are both FK `ON DELETE CASCADE` (a deleted block or offboarded grantee drops its grants — contrast `context_dream_links`, which blocks the delete); `granted_by` is an `ON DELETE SET NULL` audit pointer; `uq_block_grant (block_id, grantee_tenant)` is the idempotency guard and `idx_block_grants_grantee (grantee_tenant, block_id)` the hot-read index. Deliberately **no `permission` column** (a single-value `'read'` enum gates nothing today — additive later). New table on an empty relation, so no `context_blocks` lock and no 1M index build.

**Read paths.** `store.GrantedBlockIDs(tenant)` resolves a tenant's granted block ids. The canonical visibility triple becomes `NOT archived AND type_name <> 'system-meta' AND ( scope = ANY OR id = ANY(grants) )` — the grant OR is strictly **inside** a mandatory parenthesised group after the archived/system-meta conjuncts (SQL binds AND tighter than OR; without the parens a granted archived or system-meta block would leak). The same parenthesised OR rides `GetBlock`, `ResolveBlockID`, `SearchBlocks`/browse, `mcp recent`, the `EgoGraph` legs and the `rrf` GraphExpand hop. On `mcp recent` it is no longer a second, hand-written copy of that predicate: the tool reads through `store.RecentBlocks`, which takes the resolved grant list as a parameter and carries the `RequireScopes` guard and the `limit` clamp (≤0 ⇒ 10, >50 ⇒ 50) once — the handler only renders the rows and maps the guard's error back to its own prose. A caller without grants binds an empty list, so the OR-arm is a no-op and the answer is unchanged.

**Semantic-retrieval arm** (migration 068). `ctx_rrf` gained a 13th `p_granted_block_ids UUID[] DEFAULT NULL` param; all six CTE WHERE clauses replace the flat `AND cb.scope = ANY(p_scopes)` with the parenthesised scope-OR-grant form. `rrf.Search` threads a `grantedBlockIDs` param; `query.go` resolves the grant set once (fail-closed `resolveGrants` — a resolver error yields an empty set, never a widen). The hard empty-scope reject stays — a non-empty grant set never relaxes it.

**Graph bridge (leaf contract, T41).** A block visible ONLY via a grant is a **leaf** — it appears in the node set and induced edges but is never a hop seed, so expansion cannot traverse the grant bridge into the grantee's own in-scope blocks behind it.

**Per-request bound on the grant set.** The resolved list is bound as a `uuid[]` into every read path, and `id = ANY(uuid[])` has no selective index path in the post-filter position — its cost is per candidate row, and the grant count also counts against the retrieval selector's exact-scan budget (`retrieval.selector.exact_max`). `store.GrantedBlockIDs` therefore fetches at most **1024 + 1** grants and refuses beyond that: a tenant holding more than 1024 row-level grants gets `store.ErrTooManyBlockGrants`, and every read surface REFUSES the request with one prose (`too many block grants for this tenant: …`) — MCP tools as a tool error, the HTTP read paths as a 500. The refusal is deliberate: a truncated grant list would hide granted blocks silently and indistinguishably from "the block is not there". The bound is a code constant, not a settings key — more than a four-digit number of individually shared blocks is a scope-level sharing case, and the error says so. A transient resolver failure still degrades quietly to scope-only, as before.

**Grant CRUD (T43)** closes the write side: admin-gated `block-grant-create`/`block-grant-list`/`block-grant-revoke` (CLI `ctx block-grant`) behind a hard per-block **ownership** gate — a caller may only share a block whose scope its tenant OWNS via `context_tenant_scopes`; a foreign or unmapped scope fails closed to 403. A `tenant.allow_cross_tenant_block_grant` opt-in (global-only, default off) gates cross-tenant shares (intra-tenant department→department stays allowed). The egress floor is raised for grant-mediated results to `max(ownerFloor, granteeFloor, GRANT_FLOOR_DEFAULT=personal, block.sensitivity)`, so a shared block never reaches an external backend below the grantee's strictest floor or the config-independent `personal` backstop.

## Admin tiers

Two typed authorization predicates on the auth result (`auth.Role` = `owner`/`admin`/`member`, pinned to the 059 `tenant_role` CHECK by a live-schema test):

- `IsServerAdmin()` — the server-global M052 tier.
- `IsTenantAdminOf(tenant)` — server-admins administer every non-empty tenant; `owner`/`admin` only their own. An empty target tenant is denied for every tier.

The `whoami` endpoint carries this on the wire: alongside the server-global `admin` flag it returns the resolved `tenant_id` and per-tenant `role`, so the SPA gate can tell a server-admin from a tenant-admin.

**Action-tier gate (T25).** `actionRequiresAdmin` became `actionTier` (server-admin / tenant-admin / open) via a `requireTenantAdmin` predicate. Only the tenant-isolated `api-key-*` actions were lowered to tenant-admin — `mcp-client-*`, `backend-*` (until T37a), `blocks-audit`/`classify-*`, and the `tenant-*`/`tenant-grant-*` lifecycle actions STAY server-admin because their handlers carry no tenant filter (lowering them would be fail-OPEN). The rule is **isolate first, then promote**.

**Model consumers (W01-5).** The external callers of the gateway and their `ctxm_` keys are administered per tenant ([api](api.md#model-consumer-administration)): a tenant-admin lists, reads, narrows, revokes and deactivates its own tenant's consumers; creating a consumer, rotating a key and every granting field change are server-admin only unless `gateway.enabled` and `gateway.tenant_self_service` are both on — **self-service ships off** (decision E3: the GPU is a host-global good), and some fields stay server-admin even then ([security](security.md#admin-tier)). A consumer's `tenant_scope` must be one of its tenant's scopes — for every caller, a server-admin included; `tenant_id` is server-admin only. Consumers count against `max_model_consumers`.

**Model-API visibility in the SPA (W05-01).** `GET /api/whoami` carries the gateway policy as `capabilities.model_api` ([api](api.md)), and the SPA derives two capabilities from it, tier first: `viewModelApi` — the gateway administration area — is true for a server-admin always (the alias catalog and ctx-peer consumers can be prepared before the gateway is switched on), for a tenant-admin once `gateway.enabled` is on, and never for a member; `mintModelKeys` — creating consumers and rotating keys — is true for a server-admin always and for a tenant-admin only while `gateway.enabled` **and** `gateway.tenant_self_service` are on, which is the rule of `tierSelfService`. A server that does not send `model_api` leaves both false below server-admin. Both are visibility only: the server enforces every tier on its own, so a hidden control is no protection and a shown one is no permission.

**The `/gateway` area in the SPA (W05-05).** The Model API nav item (tenant section) and the `/gateway` route follow `viewModelApi`: a **member** never sees the item and a deep link to `/gateway` (or any `/gateway/…` page) redirects to `/home`; a **tenant-admin** sees it only while `gateway.enabled` is on — before the switch, or against a server that sends no `model_api`, the item is absent and `/gateway` redirects to `/status`; a **server-admin** sees it always, with a note while `gateway.enabled` is off, a tenant column and a tenant filter over every tenant. The route guard prefix `/gateway` is disjoint from `/admin` and `/tenant`, so the gateway switch opens nothing else; the peer page stays under `/admin`. The page lists the consumers through `model-consumer-list` (newest first, keyset "Load more", status filter preset to the four statuses of an active consumer, label-prefix search) and polls every 30 s only while the browser tab is visible; the route guard redirects a key below `viewModelApi` before the page mounts, so such a key fires no list call. A tenant-admin sees only its own tenant's consumers — the server filters, the SPA does not. The SPA reads `model_api` once per session: after the gateway is switched on or off, a tenant-admin's view changes with the next `whoami` (reload or new login). Since W05-06 the page also creates, deactivates, reactivates and revokes (next paragraph); policy edits and key rotation stay with the manage actions for now.

**Creating and revoking model consumers in the SPA (W05-06).** "+ New consumer" appears only with `mintModelKeys` (a server-admin, or a tenant-admin while `gateway.enabled` and `gateway.tenant_self_service` are on). The dialog asks for a label, an optional description, the tenant (server-admin only), a `tenant_scope` — a server-admin may pick any scope of the chosen tenant, a tenant-admin only its key's home scope, because `model-alias-list` shows a tenant-admin no other tenant scope's aliases and the picker must not offer an alias the server would refuse —, the models (the offer of that scope: enabled aliases, a tenant alias in place of the `_global` one of the same name; or "all offered models incl. future"), an expiry (30/90/365 days or a date, capped by `gateway.key_max_lifetime_app`; a preset equal to that ceiling sends no `expires_at`, so the server sets it at its own clock; "never expires" only when the ceiling is `0`), the prompt sensitivity (a tenant-admin keeps `credentials`; lower values are server-admin only) and an optional CIDR allowlist; two templates ("App · Chat", "App · Embedding") preselect the offered models of that type and 365 days. There is no kind control — the SPA creates `app` consumers; peers are a server-admin matter. On success the key's plaintext is shown **once** in the same reveal component as an api key, next to the instance's `/v1` base URL; it lives only in that component until "I've stored it — done" (or Esc) and never reaches the page state, browser storage, the URL or the console — the list shows the key's hint only. Each row offers Revoke per live key and Deactivate (which revokes every key of the consumer); both ask to type the last four characters of the key's hint (for Deactivate: of the newest live key; a consumer without a live key: its label), case-sensitive, and say up front that new requests are refused immediately. Afterwards the page reports what the server answers for running streams: the number of requests the action ended on this ctx process (`cancelled_inflight`, since W01-8 a number; running requests on another process sharing the database end through the database signal), or — while `cancelled_inflight` is `null` (a server without the model API's door) — that running streams continue until they finish. Reactivate (no typing, it grants) appears only where the server allows it: a server-admin, or a tenant-admin with self-service on an `app` consumer; a reactivated consumer has no live key. Every control mirrors a server rule; the server decides.

**Consumer detail in the SPA (W05-09).** `/gateway/consumers/:id` (same `viewModelApi` guard as `/gateway`) shows one consumer from `model-consumer-get`: label, kind and the server's status, the policy, the key chain newest first with each rotation drawn as an edge to the key it was rotated from (`rotated_from`; a chain cut at the server's cap is marked as cut), the audit trail of the consumer and its keys (action, the actor as the server masked it, `via`, the names of the changed fields — never raw values of a key row) and the consumer's last calls from `GET /api/llmlog?consumer_id=` (metadata only; the error column shows the error class, which carries the HTTP status such as `http_502`, never the capped raw error text). Only a server-admin gets an "Open call" control per call (the body detail): for anyone else `/api/llmlog/{id}` answers a uniform 404 for consumer rows, so the SPA offers none. A foreign or unknown id renders the server's "model consumer not found", the same for both cases. Each consumer label in the `/gateway` list links to this page.

**Usage panel (W05-10).** The detail page charts the consumer's usage from `GET /api/usage?group=consumer&consumer=<id>` over 24 h or 7 d (hourly buckets) and 30 d or 90 d (daily buckets), with a table of the same rows for screen readers. A value the server does not have — `null`, or any value of a bucket marked `complete: false` (before the rollup's coverage, or the bucket still running) — reads "not recorded", never 0; a window total over such buckets reads "≥ N". Without latency histograms (`hist: false`) the latency column shows the mean, marked "Ø", instead of staying empty; queue wait and time to first token have no mean and read "not recorded". Refusals show per reason (`rejected: null` — before the refusal ledger existed — and the refusals of an incomplete bucket read "not recorded"); a refused authentication (401) has no consumer, so the panel never shows an auth refusal count per consumer. The panel re-reads every 60 s only while the browser tab is visible; a failed re-read keeps the last window on screen marked as stale, and switching the window never shows the previous window's figures.

**Limits panel (W05-12).** The limits card shows per operation the stored rows and the effective limit (`gateway-limits-get` with `subject_kind: consumer`). A server-admin edits the server row; a tenant-admin edits the tenant row and can only narrow: each field's maximum is the ceiling the server reports (the consumer's server row, else the tenant's server row, else the setting — a missing server row is never "unlimited"), there is no "unlimited" control, and an empty field means "inherits the server limit". Saving replaces the caller's row for that operation (empty fields are sent as unset); "Remove my row" deletes it (`gateway-limits-delete`). The SPA never sends a tier; the server derives it from the caller. A value over the ceiling shows a hint at the field while typing; the server decides, and its refusal (400 with `param`) appears at that field. An input that is not a finite number is refused before it is sent. An effective budget the server reports as unbounded reads "no limit".

**Status tile "Model API" (W05-17).** `/status` draws the tile after the dispatch tile when the status answer carries the `gateway` section (present while `gateway.enabled` is on). For a server-admin it shows the counters, the refusals of the last 5 minutes, the instance envelope, the internal/external slot partition per target (from the dispatch section), the top consumers of the last hour and the number of consumers whose key expires soon. For a tenant-admin the same section carries only its own consumers' figures, and per target the tile shows only the coarse queue depth (idle, low, high) from the tenant dispatch view — never a number; the read-only status page polls `/api/status` every 30 s for this tile while the tab is visible (the rest of the dashboard stays server-admin). A figure the server does not feed yet (`null`, e.g. open reservations or the 5-minute refusals) reads "not recorded", never 0 or "none". Without the section the tile is not drawn. The tile makes no request of its own; it reads the status poll.

**Bridge from the tenant page (W05-20).** `/admin/tenants/:id` carries a "Model API" card with the tenant's consumer count and a link to `/gateway?tenant=<id>`; the consumer list then opens filtered to that tenant. The parameter is honoured for a server-admin only — the list's `tenant_id` filter is server-admin only.

## Per-tenant key management

- **`DeleteApiKey`** takes the caller's tenant + server-admin flag and enforces the constraint in one atomic UPDATE (`WHERE id AND active AND (is-server-admin OR tenant_id = caller)`, TOCTOU-free). A miss collapses to one uniform `key not found` — no existence oracle over another tenant's keys (leak-path L2).
- **`ListApiKeys(tenantFilter, activeOnly)`** scopes a non-server-admin to its own tenant (leak-path L1) and — a **named behavior change** — defaults to returning only ACTIVE keys; soft-deleted keys reappear only with explicit `active_only=false`.
- **`CreateApiKey`** is tenant-bound (leak-path L3/L5): the `{shared}` allowed-scopes default is tenant-aware (only the default tenant inherits `shared` — a fresh foreign-tenant key gets an empty set, no implicit cross-tenant read); a non-server-admin's every requested scope must be one its own tenant owns (resolved against `store.TenantScopes` — Model C, not a `home_scope == tenant_id` string compare), else 403 on the first foreign scope.

## Per-tenant settings & secrets

Every config registry leaf carries a mandatory **`tenancy`** axis (T28) — `tenant-overridable` or `global-only` — enforced by a boot panic on any untagged leaf. Of the 185 registry keys, **63 are tenant-overridable** (the per-tenant query/retrieval/dream-tuning surface: thresholds, rate limits, rerank/graph knobs, dream back-off, scope + sensitivity policy, web-chat budgets, prompt-budget fallbacks) and **122 are global-only** (process-shared resources: DSN/listener, scheduler/collector cadences, the graph-overview and recall-check machinery, egress-audit retention). Backend topology no longer appears on either side of that split: hosts, models, protocols and provider credentials left the registry with the [tuple retirement](operations.md#environment-variables) and live in `context_backends`, whose own per-tenant isolation is the [pool section](#backend-pool-isolation-egress) below — a tenant that wants its own provider key creates a pool row with an `api_key_ref`, it does not override a settings key.

`config.IsGlobalOnly` is fail-closed (unknown key = global-only). A tenant-scope override on a global-only key is dropped with a value-free WARN before it reaches `config.Build`, so a tenant can never flip a server-wide switch — even via a hand-inserted psql row.

**Resolution chain.** `settings.TenantOverlay(pool)` (T09) resolves a tenant's effective config as `_global` base plus the tenant's `context_settings` rows (two-scope load `{_global, tenant}` via `LoadSettingOverridesMulti`, precedence tenant > `_global` > env > default). Migration 064 adds the scope-leading indexes `idx_settings_scope_key` / `idx_secrets_scope_name`. The overlay is wired into `config.Store` at boot (`SetOverlay`); a tenant with no own rows inherits the base pointer verbatim (§10.2 footprint guard at N tenants), a load failure fails safe to base without caching (self-healing). Source attribution distinguishes a tenant-won key (`Source "tenant"`) from a `_global` one (`"settings"`).

**Request vs background.** `SnapshotForRequest(ctx)` derives the tenant from the request context via a cycle-free hook keyed on `ar.HomeScope` — a request can't be pointed at a foreign tenant (there is no scope argument a body could spoof). `SnapshotForTenant(ctx, scope)` takes the scope explicitly and is background-only (sourced exclusively from the register). A `forbidigo` lint gate forbids a tenant-less `Snapshot()` on a request path (a forgotten call-site serving the `_global` generation would be a fail-open config leak); every legitimate tenant-less site carries an inline `//nolint:forbidigo` naming its class.

**Hot-reload channel (T32).** Migration 065 adds the changed row's `scope` to the `ctx_settings_write` NOTIFY payload (additively — old listeners ignore it; the 063 quota and 053 backend triggers inherit it). A tenant-scope write drops ONLY that tenant's cached generation (`config.Store.InvalidateTenant`, O(1) map delete, lazy rebuild); a `_global`/reserved/absent scope falls through to the full `settings.Reload` (base rebuild + O(1) `Replace`-wipe of every derived tenant generation). So a `_global` toggle no longer eager-rebuilds N tenant snapshots.

**Write API (T31).** The `/api/settings` + `/api/secrets` mounts move from `RequireAdmin` to `RequireAdminOrTenantAdmin` (the gate only admits; the handler scopes the target). A server-admin writes/reads `_global`; a tenant-admin writes ONLY its own scope (`writeScope = ar.HomeScope`, the body never carries a scope) and reads the effective tenant > `_global` view. The secret_ref resolver is tenant-scoped with a fail-closed `_global` fallback: `tenantSecretResolver` resolves a tenant's own secret first and falls back to the operator's `_global` provider key ONLY when the tenant carries the `tenant.allow_shared_secrets` opt-in — a global-only key, **default false = strict isolation**, unsettable by the tenant itself. The AAD (name+scope) makes a wrong scope a crypto auth error, not a leak. A `_global`-secret DELETE reference scan goes cross-scope (`referencedBy` over `_global` + every opt-in tenant scope via `store.OptInTenantScopes`) → 409 rather than a silent fail-open.

## Backend pool isolation (egress)

Migration 062 gives `context_backends` a `scope` dimension (`_global` = shared server backend, `<tenant>` = tenant-private), swaps `UNIQUE(name)` to `UNIQUE(scope, name)` (two tenants can each own a same-named backend), and records the row's own scope in the audit trigger.

**`Chain()` is tenant-filtered (T34, R-LEAK7).** A `visibleTo` first-class filter — the OUTERMOST gate, before role/trust/gaming — bounds every backend chain to the caller's scope (`ar.HomeScope` on request paths; `sess.Scope`, the session OWNER, on web-chat). A `_global`/unscoped backend stays shared; a tenant-private backend is **non-existent** to a foreign caller (no `ExclusionReason`, so no topology disclosure), and an empty/`_`-reserved caller (`__UNAUTHORIZED__`) sees ONLY shared backends. So Tenant A can never route a prompt to Tenant B's external backend on B's provider key. `backend-list` filters by the same `VisibleTo` predicate (the read counterpart).

**Per-tenant backend admin (T37a, R-LEAK8).** `backend-create` pins a tenant-admin's new backend to its own scope (`ar.HomeScope`, payload scope ignored — like the `/api/store` write guard) while a server-admin chooses freely (default `_global`). `store.UpdateBackend`/`DeleteBackend` take a `scopes []string` and add `WHERE id = $N AND ($scopes::text[] IS NULL OR scope = ANY($scopes))` — a tenant-admin mutating a foreign or `_global` row matches zero rows → 404-no-oracle (TOCTOU-free in the statement). `backend-test` stays server-admin (it reaches an arbitrary backend by id — isolate-first-then-promote).

**Scope-bound `api_key_ref` (2026-10-31, GHSA §1).** A pool row resolves its `api_key_ref` in the **row's** scope: a `_global` row reads the operator's `_global` secret, a tenant row reads its own tenant's secret of that name — and the operator's `_global` secret only behind that tenant's `tenant.allow_shared_secrets` opt-in **and only on the origin of a `_global` row that carries the same `api_key_ref`** (scheme, host and port of `base_url`, compared after normalization: letter case, an explicit default port and the path do not count). The opt-in shares the operator's key with the operator's provider — a tenant row on that provider with its own `model_map`, priority and limits, under the operator's key. It does not let the tenant choose where the key goes: a tenant-admin picks its rows' `base_url` freely (any publicly routable host), so a fallback by name alone would send the operator's key to whatever host the tenant names. A tenant row on another origin — or one whose operator row was moved to another host or deleted — resolves no `_global` key (keyless at the next reload). `backend-create`/`backend-update` enforce the same rule at write time: an `api_key_ref` that resolves in none of the row's resolver scopes for the row's `base_url` is a `422` field error (one message for *unknown*, *foreign* and *operator key on another host*, so a tenant cannot probe `_global` secret names), and `backend-list` shows `api_key_ref` only on rows the caller may write — a tenant-admin sees the `_global` rows without the operator's secret names, as in `/api/secrets`. A tenant-scope settings write reloads the pool, so revoking the opt-in takes the operator key off the tenant's rows at once. Before this, every row resolved `_global` regardless of scope, so a tenant-admin could name an operator secret on a row whose `base_url` it controls and receive the operator's provider key at the next chain call. Operators upgrading from ≤ 5.29.0: audit `SELECT name, scope, api_key_ref FROM context_backends WHERE scope <> '_global' AND coalesce(api_key_ref,'') <> ''` — such rows go **keyless** unless a tenant-scope secret of that name exists, or the tenant has the opt-in and the row shares the origin of a `_global` row with that `api_key_ref`; rotate any operator key a tenant row referenced. The `/api/secrets` delete guard follows the same scope set (a tenant-admin's `referenced_by` lists its own rows, the operator's lists `_global` rows plus opt-in tenants' rows).

**The embed cache is the operator's (2026-10-31, GHSA §8).** `context_embed_cache` keys on `(text_hash, model)` across every tenant, and the model name is a free field on a tenant row — so only `_global` rows read from or write to it; a tenant embed row goes to its own wire on every call and leaves no cache row behind (no cross-tenant poisoning under the operator's model name, no hit/miss signal on what other tenants embedded). For the same reason only `_global` embed rows make up the coupled set whose host/protocol change flushes the cache: a tenant-admin creating, toggling or re-hosting its own embed row flushes nothing. An install that ran tenant embed rows before 5.29.1 empties `context_embed_cache` once (`DELETE FROM context_embed_cache`; the cache refills on demand — see the upgrade notes under [Deploy & migrations](operations.md#deploy--migrations)): entries such a row wrote under the operator's model name cannot be told apart from the operator's own, every `_global` hit refreshes their `last_access` so the 30-day TTL never reaches them, and the automatic flush at the first boot fires only if the tenant row's host/protocol pair differed from every `_global` embed row's. `metadata.embed_equivalence_verified` — the flag that lifts the external-embed 422 — is a server-admin statement: `backend-create`/`-update` reject it from a tenant-admin with a 422 on `metadata` unless the row already carried it and the update leaves its `base_url`, `protocol`, its embed roles (which of `embed`/`dream-embed` it carries) and the model each of them resolves to unchanged (the proof covers exactly that identity; changing one of them means dropping the flag — other roles, priority and limits stay the tenant-admin's to change); the server-admin's `backend-test` `probe:"embed-equivalence"` returns it as the `metadata_patch` a server-admin saves. Since a tenant row must be `external` (below) and an external embed row needs that flag, a tenant-admin cannot create an embed backend of its own: a tenant embed backend is set up by a server-admin, who runs the equivalence probe and creates the row with `scope` set to the tenant. The shared vector space is the operator's responsibility.

**Tenant backends reach only public hosts (2026-10-31, GHSA §3).** A tenant-admin chooses its rows' `base_url`, so `backend-create`/`backend-update` accept only a publicly routable host for a tenant row (`DeriveLocality` = `external`; loopback, private, link-local, unspecified and single-label docker names are `422`, and so is a literal IP in any other range the dial-time deny-list refuses — CGNAT, benchmarking, reserved, NAT64 local-use or a NAT64 well-known-prefix address embedding any of these, documentation …), and no row may carry `?` or `#` in `base_url` (they would turn the appended `/v1/...` wire path into query or fragment text). LAN backends — a docker Ollama, a llama.cpp box — remain a server-admin choice on `_global` rows. Operators upgrading from ≤ 5.29.0: audit `SELECT name, scope, base_url FROM context_backends WHERE scope <> '_global' AND (locality <> 'external' OR base_url ~ '[?#]')`; such rows load as before but are rejected on their next write, and their calls fail at the wire: every egress path of a tenant row — chat, both streams, anthropic, embed, rerank, OpenRouter window discovery, `backend-test` — dials through `internal/ssrfguard` (the dial-time deny-list camo and forge use), which re-checks each resolved address, redirect hops included, so a public name that resolves to an internal address is refused as well. The refusal classifies as a transport failure (failover to the next backend, cooldown). `_global` rows keep the unguarded client, and the anonymous `/health` probe pings `_global` rows only. Backend response bodies are capped for every row: a non-streaming chat or embed answer at 16 MiB, a stream at 4 MiB per SSE line or data frame and 64 MiB in total (rerank 1 MiB, window discovery and OpenRouter details as before); an answer over its cap fails as `backend response exceeds the size limit` instead of being decoded into the shared daemon's memory.

**Tenant model aliases (W02-04).** A tenant-admin keeps the `/v1` model aliases of its own scope (`model-alias-*`, [api](api.md#model-aliases-model-alias-)); `_global` aliases are the server-admin's and read-only to it. A tenant alias may shadow a `_global` alias of the same name, but never below its sensitivity (the floor holds on both write paths), a tenant-admin can never lower a sensitivity, and every value a tenant alias states is capped by the server admin's `gateway.tenant_alias_ceiling.*` — refused above it on write, clamped to it at reload (the defaults of keys it leaves unset are bounded where the serving endpoint resolves them).

## Cost/call quotas

Migration 063 adds `context_tenant_quota` (one row per scope, enforced per tenant — see below; `daily_cost_usd`/`monthly_cost_usd`/`daily_calls` budgets, an `on_exceed` policy of `external_off` or `block`, NULL budget = unlimited so a missing row is fail-open) plus the accounting indices (`idx_llm_log_apikey`, cost-covering `idx_llm_log_cost`, `idx_access_log_ratelimit`) and a NOTIFY trigger for hot-reload. Distinct from the 069 structural count-limits — quotas are money.

**Cost attribution.** The query-synthesis `context_llm_log` row now carries the calling key's `api_key_id` (threaded through `Synthesize`), as do the chain/embed wire-calls (`ChainCall`, `LogEmbedWire`) and the cross-encoder rerank row (`query-rerank`). Background paths stay NULL by construction (no caller); the query-triggered embed-backfill is also left NULL by decision (it's maintenance, not the caller's request).

**The cost budget sees provider-reported cost only.** `cost_usd` is filled from `usage.cost` of **openrouter-class** backends — on the non-streaming wire and on the web-chat stream (the final usage chunk), so a chat turn on OpenRouter counts against `daily_cost_usd`/`monthly_cost_usd` like a synthesis call. ctx keeps no price list: an external backend whose wire reports no cost — the anthropic Messages API (streamed and non-streamed), a generic `/v1` server — books `NULL` and never moves the cost budget. For a tenant whose chains reach such a backend, only `daily_calls` bounds the spend.

**Enforcement (T36a).** `QuotaAccountant` (`internal/backends/quota.go`) serves each tenant's rolling external-cost SUM + attributed call COUNT from a **lock-free** generation snapshot (`atomic.Pointer` map, CAS-guarded TTL refresh ~30s, single-flight off the read path — mirrors StatusCollector, not a mutex, never per-request over the 1M+ `context_llm_log` hypertable). The synthesis path consults it after resolving the chain: the **cost budget** gates only external backends (over budget → `external_off` drops external while local stays reachable, or `block` returns `*ErrQuotaExceeded` → 429); the **call budget** gates every backend including local (a cap skipping local would be toothless), counting only attributed calls. Fail-OPEN throughout (no quota row / disabled policy / empty scope / cold cache passes unchanged) — the fail-CLOSED axis is egress visibility, not cost. `block` is a SOFT cap with a documented TTL overshoot window (worst case ≈ parallelism × cost × TTL).

**Spend source: the hourly rollup plus the edge hour (W06-4).** The accountant reads each window through `internal/llmusage` from the hourly rollup `context_llm_usage_hourly` (migration 159) — every hour from the first full UTC hour after `now − window` on — plus the raw `context_llm_log` rows of the partial hour before it, so the sums read at most one hour of raw rows per window, whatever its length (plus at most one hour for each relief below), each key probed through its index; the 30-day raw scan per policy tenant and refresh is gone. The figures are exact and unchanged: `daily_calls` counts every attributed row of the last 24 hours (failed and local ones included), the cost budgets sum provider-reported external cost over 24 hours and over 30 days rolling (not the calendar month; 30 × 24 hours, which is what the former `interval '30 days'` meant under the UTC session ctx runs). One caveat: the rollup does not subtract deleted rows, so log rows deleted by hand keep counting until they leave the window ([operations — Migration 159](operations.md#migration-159-the-hourly-llm-usage-rollup)). Each figure also carries its earliest relief — the oldest row it counts plus its window — which nothing reads yet; it is the `Retry-After` source for the gateway's tenant gate. **Consumer usage never counts (K17):** the spend filters on the tenant's knowledge keys (`api_key_id = ANY`), and a row of an external `/v1` consumer carries `consumer_id` and never `api_key_id` (CHECK `ck_llm_log_one_identity`, migration 158). An application's traffic therefore can never exhaust the tenant's `daily_calls` or cost budget and lock the tenant's people out of `/api/query` and the web chat; consumer volume is bounded by the consumer limits instead.

**Refusal ledger (Migration M-06-4, migration 167).** A refused model-API request is counted per hour in `context_llm_rejections_hourly` ([operations — Migration 167](operations.md#migration-167-the-refusal-ledger-of-the-model-api)), never in the usage rollup: refusals do not count toward any tenant's `daily_calls` or cost budget, and a refusal flood cannot add a row to the rollup the tenant gate reads. The table carries no tenant column — a consumer's tenant is a lookup, as in the rollup — and a refusal before the model-key door accepted (`auth`) has no consumer and so belongs to no tenant: it is instance-wide data. Nothing reads the table yet; when the usage API does (RC-D), a tenant sees the counts of its own consumers only, the instance-wide rows and the columns `dispatch_class` and `target` (the serving instance's queue and target origins) stay server-admin-only.

**The consumer meter is separate from the tenant quota (W06-10).** On `/v1` every model consumer has its own requests- and tokens-per-minute buckets per operation (`gateway.<op>_{rpm,tpm}_default`, [api](api.md#limits-quotas-and-rate-limit-headers)). They are keyed by the consumer — not by its tenant and not by its key — so two consumers of one tenant never share a bucket, a tenant's other consumers cannot exhaust one consumer's minute, and rotating, revoking or reactivating a key keeps the consumer's state. The tenant quota still gates the consumer's chain first (`GateTenant`; its `429 insufficient_quota` books nothing on the meter), and the meter's tokens never count against the tenant's budgets (above). The concurrency limit (`gateway.consumer_concurrency_default`, default 2; W06-11) is per consumer and operation as well: a consumer's requests open at once — queued or running — never take a slot of another consumer of the same tenant. On the bulk lane a consumer holds at most `max(1, ⌊C × (1 − gateway.xu_reserve_ratio)⌋)` slots, so its urgent requests keep the rest; with `C = 1`, or with `gateway.xu_reserve_ratio` at 0, there is no such reserve, and a consumer that mixes lanes needs `C >= 2` and a ratio above 0. Per-tenant envelopes over all consumers of a tenant follow with the daily budgets.

**Envelopes over a tenant's consumers (W06-13).** Next to each consumer's daily and monthly budgets ([api](api.md#limits-quotas-and-rate-limit-headers)), the meter keeps an envelope per tenant and operation: all consumers of the tenant together use at most `gateway.tenant_envelope_factor` (default 5) × the consumer budget per UTC day — at the defaults 10 M chat tokens, whether the tenant has 3 consumers or 64. A tenant cannot multiply its budget by minting consumers; the envelope binds before the sum of the consumer budgets does. A second envelope per operation spans every consumer of the instance (`gateway.instance_envelope_factor`, default 10 ×); its refusal names no value. Both envelopes count **consumer** tokens only — ctx's own pipelines (`/api/query`, the web chat, dream) never count into them, and the consumer tokens never count into the tenant quota above. The direction between the two is one-way: the tenant quota gates the consumer's chain, a consumer's use never locks the tenant's people out (K17). Until per-tenant limits exist (RC-D), the factor holds for every tenant.

**One-way: `/v1` never locks the tenant's people out (W06-14, K17).** The tenant quota counts only rows of the tenant's knowledge keys: a consumer's `/v1` calls carry `consumer_id` and never `api_key_id`, so an application cannot exhaust `daily_calls` or the cost budget and lock `/api/query` and the web chat of its tenant's people out (pinned by an integration test that turns red as soon as the spend counts consumer rows). The other direction holds: when the tenant's own use has exhausted its quota, its consumers' `/v1` requests are refused as well (`429 insufficient_quota`, `Retry-After` = the moment the oldest counted row leaves the window). Consumer volume is bounded by the consumer budgets and the envelopes above instead.

**Egress of consumers: peers stay, billable rows need a permission (W06-14).** A `/v1` chain keeps what bills nobody — local and LAN rows and the rows of other ctx instances (`provider_class = ctx`), even on a public address (where they are `external` by locality). An OpenRouter row stays only with `gateway.consumer_allow_external_default` and while the consumer's and its tenant's monthly cost budget lasts (then it drops — a degrade, like `external_off`, not a 429); external rows that report no cost stay closed for consumers (their cost would never move a budget). This rule is the `/v1` chain's alone: the internal paths keep the tenant quota's `external_off`, which drops every external row by locality. Per-consumer and per-tenant permissions and budgets come with the limits rows (RC-D).

**A quota binds the tenant, not one scope (2026-10-31, GHSA §4).** The row lives on the scope `tenant-quota-set` named, but `Gate(scope, chain)` resolves the caller's scope to its tenant (`context_tenant_scopes`, mapped in the accountant's generation) and applies that tenant's policy to **every** scope of it — the spend side always counted all of the tenant's keys. Before this a tenant-admin could `scope-create` a second scope, mint a key homed there and run unlimited, because the lookup found no row under the new scope. If several scopes of one tenant carry a row (the schema keeps `UNIQUE(scope)`), the strictest limit per field applies (smallest budget, `block` over `external_off`) and the accountant logs a warning. A scope mapped to no tenant (`_global`, sentinel callers) stays ungated; `scope-create` and `POST /api/project` (whose compound create assigns a scope too) refresh the accountant so a new scope is gated from its first call; `tenant-quota-get` shows the merged policy that binds the scope.

**Web-chat is gated too (2026-10-31, GHSA §4).** `chat.PoolProvider.ChatChain` runs the same `Gate` on every chain it resolves (each model call of a turn, keyed by the session owner's scope `sess.Scope`), so `/api/chat/stream` no longer spends past the tenant's budget — including on `_global` operator backends. Semantics match synthesis: the call budget and a cost budget under `block` end the turn with the SSE error event `{"code":"quota_exceeded","retryable":false}` before any wire call; `external_off` drops external backends, and a chain it leaves empty ends with `no_eligible_backend`. The **ctx_query tool** delegates to `/api/query` with the session owner's scope as home scope, so the query's own gates (below) apply to the owner tenant too — a refused query is a failed tool call — and a tenant-private embed/rerank backend serves it. The delegated request carries no tenant id: like the other chat tools it reads scope-only, without block grants.

**Query embed and rerank are gated too.** The query path runs the same gate (`llm.GateQuota`) on the query-embed chain — before the embed cache, so `quota_exceeded` is a real `429` ahead of the heartbeat and a budget-exhausted tenant gets no cached vector either — and on both rerank legs (cross-encoder chain, LLM-judge via `ChainCall.Quota`), which keep their fail-open semantics (pre-rerank order). The two calls that run before the embed step — query translation and the temporal LLM fallback — are gated too (`ChainCall.Quota`): a stopped call makes no wire call and keeps their fail-open semantics (original query, no LLM date expansion), the embed gate then answers the `429`; `external_off` drops an external translate backend. Not gated: the query-triggered embed backfill (block scope, unattributed maintenance), the scheduler embed backfill behind `/api/store` and the background pipelines (distill, topiclabel, dream) — operator cost by decision.

**Management (T36b).** `tenant-quota-set` / `tenant-quota-get` manage-actions + CLI `ctx quota` write/read the rows (`store.UpsertTenantQuota`/`GetTenantQuota`); a set refreshes the accountant synchronously. `tenant-quota-set` is SERVER-admin only (an operator cost ceiling — a tenant-admin raising its own budget would void it); `tenant-quota-get` admits a tenant-admin for its OWN scope. The `pool.default_tenant_quota` global fallback (T36c) is backlog.

## Telemetry (per-tenant views)

- **`GET /api/llmlog` (T37b).** Moves to `RequireAdminOrTenantAdmin`; a tenant-admin sees ONLY rows attributed to its own tenant's keys (resolved to a literal `uuid[]` via `store.TenantAPIKeyIDs` first, then `api_key_id = ANY($keys)` — index-friendly). A keyless tenant → empty filter → zero rows (fail-closed); NULL-`api_key_id` background rows are server-admin-only. Gate + filter ship together.
- **`GET /api/audit` (W06-7).** Same gate; a tenant-admin reads only audit rows whose `metadata.tenant_id` is its own tenant (filtered in SQL, a foreign id answers `rows: []` like an unknown one), with server-admin and foreign actors masked as `"server-admin"` ([security](security.md#audit-trail)). Rows without a tenant and the `instance` type are server-admin-only.
- **`GET /api/status` (T37c).** Opens to a tenant-admin with a REDUCED view — only its own backends (`VisibleTo`) + its own 24h rollup, from a separate lock-free per-tenant rollup generation. Server-global fields (health/dream/gaming/activity) stay zero for a tenant-admin.
- **`GET /api/events` (SSE) stays server-admin-only (T37d).** The broadcast fans one global diff to all subscribers; a per-tenant live stream is an architecture change (per-subscriber filtering + tenant-scoped SSE re-auth), deferred. The interim tenant-admin path is polling (`/api/status` + `/api/llmlog`), so there is no push leak. `events.go` carries a six-touch-point migration map for the eventual SSE wave.

## Background pipeline isolation

The background pipeline (dream, digest, daily synthesis, sensitivity audit, credentials classify) iterates the **authoritative tenant register** (T13), taking one `SnapshotForTenant(ctx, tenantScope)` per tenant (dream round-robins one tenant per cycle); the scope string comes exclusively from the register, never request input. The register (not a `DISTINCT home_scope` query) is the source: one tenant = one row, so the iteration collapses to a 1-element `_global` loop at single-tenant. Suspended/offboarding tenants are dropped; a `ListTenants` failure or no active tenant falls back to a single `_global` pass (the background never aborts).

**Entitlement clamp (T38, R-LEAK).** Each iterated tenant's read window is clamped to `read_scopes ∩ TenantScopes(tenant)` — the tenant-overridable `scheduler.read_scopes` is NOT grant-gated on its own, so an unintersected consumer would be a cross-tenant background read. The dream/synthesis backend chain is filtered to `_global ∪ tenant`, the per-tenant `ScopeSensitivityFloor` rides the per-tenant snapshot, and digest/synthesis/audit write scopes are clamped to the tenant's entitlements.

**`POST /api/digest` uses the same clamp (2026-10-31, GHSA §5).** The request path builds the topic map, the root map and the envelope counts over `read_scopes ∩ TenantScopes(caller's tenant)` (`store.IntersectWindow`, shared with the background), not over the key's raw `read_scopes`. A cross-tenant grant lets the key read the granted scope through the read surfaces, but both maps are written under the caller's home scope, where every reader of that scope sees them; before this fix the granting tenant's titles, id prefixes, cluster labels and `[scope]` tags were copied there. A key without a tenant keeps its raw `read_scopes`; a failed tenant-scope lookup — or an empty intersection — narrows the window to the home scope alone (fail-closed). Operators upgrading from ≤ 5.29.0 with cross-tenant grants: maps written before the fix keep their foreign entries until rebuilt — run `POST /api/digest` once with a key of each grantee home scope, or delete that scope's `index` blocks `topic-map-<scope>` / `root-map-<scope>`.

**Duplicate guard stays inside the tenant (migration 156, 2026-10-31, GHSA §2).** `ctx_guard_check` bounds its nearest-neighbour candidates to the scopes owned by the checked block's tenant (`context_tenant_scopes`); a block whose scope is registered to no tenant gets same-scope candidates only. Before 156 the candidate query had no tenant predicate for the built-in types (candidates=all), so the guard compared a new block against **every** tenant's corpus, wrote the match's similarity and UUIDv7 into the writer's metadata and, above the duplicate threshold, archived the writer's block as a duplicate of a foreign tenant's — a confirm/deny oracle on other tenants' content for any member key. Cross-scope matching *inside* a tenant (`guard_is_cross_scope`) is unchanged. 156 also un-archives blocks that were archived against another tenant's block and hands them back to the guard — except where that would collide with a live twin, or where a person archived the block ([operations — Migration 156](operations.md#migration-156-the-duplicate-guard-never-looks-across-tenants)). Migration 157 takes on the live blocks whose guard decision still names such a block, whatever their status or lifecycle: without a person's verdict the decision is cleared and the next batch re-checks the block inside its own tenant; a verdict a person gave through `guard-resolve` (`keep` or `archive`) stays and only loses the keys that point at the foreign block (`guard_matched_id`, `guard_similarity`, `guard_is_cross_scope`) ([operations — Migration 157](operations.md#migration-157-live-guard-decisions-that-name-a-match-outside-the-tenant)). On the read side `get` and non-compact `search` drop `metadata.guard_matched_id` when the matched block lies outside the caller's read scopes — the rule `guard-list` already applied to `matched_id`. Since §F-§2 the block that `manage update` answers with and the issue reads (`issue-get` with its comment thread, `issue-update`, the project issue API and MCP `issue_*`) do the same; the two update responses check against the caller's write scopes, a subset of its read scopes, so `get` can show a match the update response leaves out.

## Per-tenant graph overview (B line, migration 087)

Migration 087 adds a denormalized `scope` (TEXT, the 057 family convention) to `graph_cluster_member`, backfilled from `context_blocks` and `NOT NULL` afterwards. The rebuild writes it from the **Louvain input** (never a re-read at persist time), so a member row always records the partition the clustering ran in — the prerequisite for the scope-scoped teardown/aggregation (B-W3) and the per-tenant rebuild loop (B-W6). `block_id` stays the sole PK: the overview input is strictly owned-disjoint (no grants in the input) — a load-bearing invariant the B-W6 input-purity assert will enforce. Rollback note: a pre-087 binary's scope-less member INSERT fails the NOT NULL constraint loudly; the advisory-locked replace keeps the previous tables readable.

B-W3 makes the persist path partition-capable: `overview.Options.ScopeFilter` (nil = global run, behaviour-identical full replace) switches teardown AND aggregation to one partition **atomically** — scoped DELETEs (member/node per scope, edges with AND on both endpoint scopes) paired with scope-filtered aggregation SQL in the same advisory-locked transaction. The pairing is load-bearing (B1-C1): a scoped DELETE with the unscoped aggregation resurrects the surviving foreign partition into the `(cluster_id, scope)` PK ⇒ `23505` from tenant #2 on. persist fails loudly on input outside the filter (input scoping itself lands with the B-W6 loop); the meta singleton is only written by global runs until the 088 scope-PK migration (B-W5). The scheduler still passes a nil filter — nothing changes operationally until B-W6.

B-W4 partitions the advisory lock itself: `lockKeyForScopes` hashes the sorted, deduplicated scope set with seedless FNV-64a (process-stable — `hash/maphash` would give every ctxd instance its own seed and break cross-instance exclusion) and XORs it onto the base key. Two tenants persist in parallel; the same tenant keeps serializing. A nil/empty filter returns the pre-B-W4 base key **byte-identically**, so old and new binaries keep excluding each other through a mixed-version deploy window. A global run and a partition run do NOT exclude each other by design — the scheduler runs either globally or per-tenant, the transition logic ships with B-W5/B-W6.

B-W5 (migration 088) retires the `graph_overview_meta` singleton: the PK becomes `scope`, the legacy row is **data-migrated** onto every real node scope with its `computed_at` preserved (no spurious boot rebuild, B3-M2), and every run writes the rows it owns in the same advisory-locked tx — the global run replaces all rows (scope set = `DISTINCT scope FROM graph_cluster_node`, no sentinel scope, B3-M1), a scoped run only its filter scopes (an empty partition still records its fresh `computed_at`). Per-scope stats: `cluster_n`/`node_n` from the node rows, `edge_n` counts intra-partition edge rows. The read path answers freshness as `max(computed_at) WHERE scope = ANY(readScopes)` — never an unscoped row pick, which would leak a foreign partition's timestamp (B1-m1); the boot probe stays `count(*)` (server-global, no caller scopes). 088 also adds `idx_gcm_scope` on `graph_cluster_member(scope)` — the scoped teardown DELETE at 1M+ members (B-W3 finding).

B-W6 arms the loop: each scheduler tick rebuilds ONE tenant with `ScopeFilter = owned` (round-robin cursor; `owned` may legitimately be nil — migration seed, register fallback — and then runs the byte-identical global pass under the base lock key). The INPUT is now scoped too: `loadNodes` filters blocks, `loadEdges` keeps only edges with **both** endpoints inside the partition via `context_blocks` joins (never via the member table — that is the previous run's state; B2-M4: an unscoped edge load would pull the full ~3.24M-edge set into RAM once per tenant). Boot (never built) rebuilds every tenant once sequentially instead of one global run — no cross-tenant co-clustering window, per-scope meta consistent from the first build. Mixed cross-partition edge rows left by a pre-B global run are swept by the OR edge teardown of the first partition run touching either endpoint and are never re-created (the AND aggregation). The whole line rests on owned-disjointness: `owned` comes from `context_tenant_scopes` (ownership, one owner per scope); grants are read-widenings and never enter a Louvain input.

## Self-service onboarding (v4.1.1)

Migration 069 adds structural per-tenant count-limits on `context_tenants`: `max_scopes`/`max_keys` (typed `INTEGER`, `CHECK >= 0`, `DEFAULT 25`/`50` so every existing tenant is capped without a backfill, `NULL` = operator-set unlimited — the system/default tenant seeded `NULL`), plus `idx_tenant_scopes_tenant`/`idx_api_keys_tenant`. These are structural counts (how many scopes/keys a tenant may self-provision), distinct from the 063 cost quota. Migration 161 adds `max_model_consumers` (`DEFAULT 64` for every tenant, the default tenant included) for the callers of the OpenAI-compatible model API; a model consumer belongs to exactly one tenant for its whole life — its `tenant_id` is immutable (trigger, SQLSTATE `23514`), and so is the `consumer_id` of each of its keys.

| Action | Tier | What |
|---|---|---|
| `scope-create` | tenant-admin | Registers a scope in the caller's OWN namespace — the server builds `<tenant-slug>:<name>` (slug from the register, never the payload, so the prefix is unforgeable and two tenants can never collide — S1), charset-gates the name (lowercase alnum + hyphen, no `:`/`_`/whitespace), caps at the VARCHAR(50) budget, enforces `max_scopes` transactionally (429) under a `context_tenants`-row lock. A server-admin may target another tenant via `tenant_id`. |
| `scope-list` | tenant-admin | Tenant-filtered scope list. |
| `tenant-limit-set` | server-admin | Sets a tenant's structural ceiling (both `max_scopes`/`max_keys` required, range `0..1_000_000`, explicit null = unlimited); optionally seeded at `tenant-create` over the 069 defaults. A tenant-admin raising its own limit would void it. The optional `max_model_consumers` (same range, null = unlimited, absent = unchanged; migration 161 default 64 for every tenant) caps the tenant's **active** model consumers: `model-consumer-create` and a reactivation beyond it answer `429`; `0` freezes. Tenant answers carry the value. |
| `tenant-usage-get` | tenant-admin (own) | Scope/key counts vs limits; a server-admin may target any. |
| `api-key-create` | tenant-admin | Enforces `max_keys` transactionally (429, active-only count); a server-admin may mint into another tenant via `tenant_id` (foreign-target T22 — the new key's scopes must belong to the target; a non-server-admin's `tenant_id` → 403, AM2). New keys are always `member` (a smuggled `tenant_role` is ignored, AM3). Optional `write_scopes` (078, E4b) must be ⊆ `allowed_scopes ∪ {home_scope}` else 400 (see [Per-key write scopes](#per-key-write-scopes-e4b-migration-078)). |
| `api-key-update` | tenant-admin | Role delegation (`{tenant_role?, active?, write_scopes?}`): only an owner (or server-admin) may change a key's role — a non-owner tenant-admin → 403, so admin→owner self-elevation is structurally impossible (no `is_admin` field means the server-global tier can never be set here). Demoting/deactivating the last active owner → 409 (last-owner invariant); an admin cannot neutralize an owner key → 403 (enforced at both update and the `api-key-delete` revoke path). A server-admin key (`is_admin`) is managed by server-admins only: any tenant-owner/-admin patch or revoke of it → 403, so a default-tenant admin cannot disable the operator's key. `write_scopes` (078, E4b) is validated ⊆ the key's existing `allowed_scopes ∪ {home_scope}` → 400 on a blind-writer; `[]` clears, absent leaves unchanged. |

**`tenant-create` as real onboarding.** Provisions atomically in ONE transaction: the tenant row, an auto-prefixed initial scope `<slug>:main` (cap-free so a zero limit can't wedge the bootstrap), and an owner key (role `owner`, plaintext returned once) — scope before key so the key's home scope is registered (T22). Any step's failure rolls the whole transaction back (no half-provisioned tenant; a scope-name collision → 409 with zero orphans). The freshly minted owner key authenticates immediately, closing the inert-tenant gap (K10) that blocked self-service onboarding.

These flows are surfaced in the web admin SPA — see the [admin SPA](development.md#web-ui-svelte-5--typescript--vite-bun) section.
