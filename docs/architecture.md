# Architecture

**Stack:** Go 1.26 (matches `go.mod` and the `golang:1.26-alpine` build image), PostgreSQL 18 + pgvector 0.8.2, 84 SQL migrations (numbered 001–086; 066 is the deliberately deferred tenant-OAuth slot, 082 is the reserved W13 webhook slot). Dual-protocol inference (Ollama native or OpenAI-compatible) via any provider — configured per role in the [backend pool](#backend-pool-f3-migrations-053055) (`ctx backends`), one row per backend (see [operations](operations.md#backends)).

## 4-Way RRF retrieval

Reciprocal rank fusion across four channels: **semantic** (pgvector, weight 0.45), **EN fulltext** (0.25), **DE fulltext** (0.20), and **trigram** title (0.10) — bilingual FTS + trigram.

The `ctx_rrf` SQL function is type-policy-parameterised since migration 073 (WF T5). It takes a visibility **allowlist** (`p_types_visible`, fail-closed — an unregistered/rogue `type_name` is invisible until a registry row carries it; NULL/empty ⇒ 0 rows, Go rejects the call before that) plus parallel damping arrays (`p_damped_types`/`p_damped_factors`) sourced per request from the block-type registry, which generalises the former hardcoded audit-trail scalar into query-aware intent lift. Results carry `type_name`; a registry edit (damping factor, intent patterns) changes rankings live via hot-reload — no restart, no migration. See also the multi-tenant grant param `p_granted_block_ids` (migration 068) in [multi-tenancy](multi-tenancy.md#block-level-grants-row-level).

Since migration 112 (Generation 15) the semantic channel is a **dual-arm CTE**: the production HNSW path (`p_semantic_mode='ann'`, default) and an exact brute-force arm (`'exact'`) for small scopes — recall 1.0, deterministic `(distance, id)` tiebreak, MATERIALIZED barrier so the HNSW index is structurally unreachable (proven by a `pg_stat_user_indexes` gate). The exact arm requires `p_exact_cap` and re-probes the scope size in-transaction (TOCTOU cap guard, SQLSTATE 54000 on growth — the caller degrades to ann); `p_scan_tuples` budgets the ann arm's `hnsw.max_scan_tuples` (grey-zone dispatch, Achse 02), bounded fail-closed in the SQL body. Both arms share one literally identical visibility predicate block, pinned by a permanent parity sentinel test. **Migration 134 (Generation 16)** closed the last asymmetry between them: `embedding IS NOT NULL` used to guard the exact arm only, so under a sequential-scan plan with fewer than 75 embedded candidates in scope the ann arm handed the remaining ranks of the heaviest channel (0.45) to unembedded blocks in heap order — they carry a NULL cosine, nothing downstream gates on it, and a block on semantic rank 5 outscores a perfect German full-text rank-1 hit by a factor of 2.1. That is the fresh-install and small-corpus path (new blocks are stored with a NULL vector and a content-changing upsert nulls an existing one until the backfill catches up), invisible under an HNSW index scan because pgvector does not index NULL vectors — Issue #40 Bug 5. The filter now sits in both arms, and the parity sentinel lost its NULL-embedding exception: the arms are set-equal. Generation 16 deliberately gives up the Generation-15 promise of byte-identical default behaviour for the ann arm — that promise protected a deploy sequence (migration and Go binary decoupled), and the semantics it was freezing were the defect itself. **Migration 139 (Generation 17)** closes the ordering hole the same function still carried: the final projection sorted by `r.score DESC` alone, so blocks with an identical fused score came back in whatever order the sort node produced — plan-, heap- and `work_mem`-dependent, and decisive whenever such a group crosses the `p_limit` cut; it now sorts `ORDER BY r.score DESC, cb.id`, the total order the exact arm has followed since Generation 15 (`cb.id` is the UUIDv7 primary key, so the oldest block wins a tie). Ties are not exotic and get denser with the corpus — a score is a sum of four reciprocal ranks times two factors, so equal rank combinations recur: the B-W1 fixture (220 blocks) carries exact ties in 13 of 54 queries. Candidate set and scores are byte-identical to Generation 16 (the change sits behind the entire fusion), and `ctx_rrf_arms` stays untouched because it neither fuses nor truncates. The Go-side selector that dispatches between the arms lives in `internal/rrf/selector.go` (W02-2): a LIMIT-capped index probe over `idx_context_scope_active` decides exact vs. ann per request, a probe failure or cap-guard trip degrades loudly to the ann path (the query is never lost). The grey stage is live since W02-4 (`selector_stats.go`): a TTL-cached, single-flighted pg_stats snapshot (schema-qualified catalog read with OID join — the cluster is shared with n8n/TimescaleDB) estimates mid-class scopes as MCV frequency × reltuples plus a residual for unlisted scopes, floored at the probe-proven `exact_max+1`; every §4.3b edge case (never-analysed `reltuples=-1`, ratio-form `n_distinct`, missing residual denominator, snapshot past 10×TTL) maps onto `stats_stale` → plain ann, the consequence-bounded direction. Migration 117 raises the `scope` column's statistics target to 1000 (+ANALYZE, ShareUpdateExclusive only) so the MCV list can cover a multi-tenant scope population — without it the sampling math routes the very mid-class the grey budget is built for straight past it. The policy arrives as a caller-supplied struct whose **zero value is off**. W02-3 wires it: the query path derives the policy from its ONE request snapshot (`cfg.SelectorRRF()`, same converter pattern as `RerankRRF`/`GraphRRF`) out of the new `retrieval.selector.*` group — `enabled` / `exact_max` / `grey_max` / `grey_scan_tuples` / `stats_ttl`, all `mut:hot` and **all global-only**, because both size knobs dimension buffer touch and materialisation of the SHARED database (the graph group's "zero cross-tenant effect" rationale does not carry here; a tenant opening is the separate wave W02-8). The dream path keeps passing the zero policy. **`enabled` ships FALSE** — the master gate opens as an operational settings flip after the Achse-01 recall evidence, not as a deploy — so the shipped wire behaviour stays the legacy 15-arg statement. Instrumentation is gated on the same flag: while the gate is closed neither the `rrf search complete` log line nor the `context_access_log` metadata differ by a byte from the pre-selector state; armed, they carry `selector_mode`/`selector_reason`/`selector_estimate`/`probe_ms` resp. the compact `sel_mode`/`sel_reason`/`sel_est` per result row — strategy metadata only, never content — as the Achse-01 correlation input (recall@k per mode × reason × estimate bucket straight out of the existing table).

**Migration 137 (`ctx_rrf_arms`)** adds a read-only sister function next to `ctx_rrf`, not inside it: same 18 parameters in the same order (plus five optional cap parameters whose defaults are the literals `ctx_rrf` hardcodes — semantic 75, FTS 100/100, trigram 30, trigram threshold 0.05), same prologue, same four arms, same `block_mass`/`type_factor` CTEs — but it stops before the weight expression and returns the **raw per-arm ranks** (`NULL` = not in that arm) plus the two multiplicative factors, and no content at all: only UUIDs and numbers, so a predicate mistake can leak at most the existence of an id. **Migration 142** adds a ninth return column, `type_name` — the block's registry classification, never its text, and something the same (necessarily admin) caller already gets from `GET /api/context/<id>`, so the leak budget is unchanged. It is there because `type_factor` is **not injective**: two damped types may share a factor and every undamped type carries 1.0, so only the name lets a dump answer what its own candidate set is made of and lets an offline sweep vary the damping per type instead of reading it off the row. The column sits at the end and reaches no score term; callers that project their eight columns by name are untouched, though `CREATE OR REPLACE` cannot grow an `OUT` list, so the migration drops and recreates the function (the argument list is unchanged). It is the provenance seam for the arm-weight sweep (Achse 04): the fusion can be recomputed offline with different weights without touching the live one. The duplicated body is guarded not by a comment but by a parity gate (`internal/rrf/arms_parity_integration_test.go`) that re-fuses the arm ranks in Go and requires them to reproduce `ctx_rrf`'s output row for row on a 220-block fixture across 54 queries in both semantic modes. Both calls must sit in **one transaction** — the ann arm's `SET LOCAL hnsw.iterative_scan` lasts to the end of the transaction, not the end of the call, so a split would let the two functions search different candidate spaces. `p_limit` is accepted and ignored (the function never truncates; the truncation is exactly what the sweep re-derives) and kept only for positional parity.

**Migration 140 (trigram KNN)** gives the fourth channel an index. Until then `trigram_title` filtered with `similarity(cb.title, p_query) > 0.05` and capped the survivors at 30 — a predicate no index carries: `idx_trgm_title` is a GIN (`gin_trgm_ops`), which serves `%` and `similarity` as a *filter* but never a `<->` KNN scan, so the arm was a sequential scan over the visible corpus on **every** RRF query. Switching the predicate to `%` would not have helped: over 60 real access-log queries `title % q` matches a median of 430 of 1 387 retrievable blocks (31 %), which is an unselective bitmap for a CTE that keeps 30. The arm now orders by `cb.title <-> p_query` over a new GiST index `idx_trgm_title_gist` (`gist_trgm_ops`), takes the cap inside that ordered scan, and applies the unchanged threshold as a post-filter — set-identical by construction (with ≥ 30 rows above the threshold the 30 nearest are the same 30; below it the post-filter cuts exactly the surplus), and measured at 100 000 rows the plan goes from a parallel sequential scan to `Index Scan using idx_trgm_title_gist` with `Order By: (title <-> …)` whose Limit costs 0.04 % of a full pass. Both `ctx_rrf` and `ctx_rrf_arms` carry the new form — an asymmetric change would make the parity gate measure a fusion that does not exist. What the migration also closes is an ordering hole the old form had: `ORDER BY similarity DESC` without a tiebreak left it undefined which member of a tie group survives the cap (live sample: 4 of 10 queries carry such a group at rank 30), so both the selection and the rank now carry `, cb.id` — the same total order Generation 15 gave the exact arm. The index build is guarded like migration 115's: present ⇒ no-op, so an operator may build it out-of-band with `CREATE INDEX CONCURRENTLY` first; under 500 000 rows the migration builds inline (1.9 s / 55 MB at 100 000 rows); above it the migration lands but only warns, because `CREATE INDEX` holds a SHARE lock for the build and `RunMigrations` sits in the boot path. Without the index the arm degrades to exactly the pre-140 sequential scan, never worse.

**The `arm_ranks` debug seam (B-W2)** is the HTTP path to that function, and it is deliberately narrow. `POST /api/query` accepts `arm_ranks:true` only from an **admin** key and only together with `synthesize:false` — non-admin is `403`, a missing `synthesize:false` is `400`, and both are refused before the rate-limit roundtrip, the sensitivity scan and every LLM stage. The flagged request runs `ctx_rrf` and `ctx_rrf_arms` in **one `REPEATABLE READ` / `READ ONLY` transaction** (`SET LOCAL statement_timeout` and `idle_in_transaction_session_timeout`, both 30s): one snapshot and one `SET LOCAL hnsw.*` state for both statements, and a transaction that is structurally incapable of writing. The response gains an `arm_ranks` block — the raw rows, the `fusion_order` as `ctx_rrf` handed it over (captured **before** gravity, cluster, graph, fold and truncation), the effective query/spaced/temporal strings, the embed model plus cache-hit flag, and the selector decision. Two optional pins, legal **only** together with the flag (`400` otherwise), remove the non-deterministic stages from a sweep run: `pinned_translation` replaces the whole detect-and-translate branch including its wire call, `pinned_temporal` replaces the FTS expansion **after** the deterministic rules ran (`""` = explicitly none) and suppresses the LLM temporal fallback. Access-log rows of a measurement carry `metadata.source = "armsweep"` instead of `"agent"` — they are labelled, not suppressed, so a later real-traffic selection can exclude them. Without the flag the path is byte-identical to before: no transaction, no second statement (pinned by a response-body SHA-256 against the pre-seam tree and a `pg_stat_database.xact_rollback` census). The seam exists because an external sweep driver cannot reproduce translation, temporal normalisation, the query-prefixed embedding and the selector decision — so the measurement rides the production path instead of imitating it. Go side: `rrf.SearchTx`/`rrf.ArmRanksTx` over a `rrf.Querier` (pool or transaction); `rrf.Search` delegates with `q == pool`, so every existing call site is untouched. The CLI path is `ctx-armsweep`.

**Shadow visibility (`shadow_types`, M-W2)** rides the same seam and widens exactly one thing: the type allowlist handed to those two statements. A measurement that compares "with the catalog" against "without" needs the catalog blocks to exist, and blocks that exist retrievably are live before anything about them has been shown — so they live as an excluded type and one admin request lifts them for its own two statements. Seven gates, all fail-closed: admin (`403`), `arm_ranks:true`, `synthesize:false`, a name that is a key of the registry, a name carrying `retrieval.shadow_measurable` (default false, and `checkpoint`/`system-meta` are refused by a hard deny-list the flag cannot override), no `include_content`, and the reranker forced **off** rather than assumed off — `rerank.enabled` is hot and tenant-overridable, and the LLM-judge builds its prompt from block content. On top of that every backend chain the request can still resolve (embed, translate) must be `locality=lan`, otherwise the request is refused: `openrouter` sits in the live pool as `external`/`no-credentials`. Two slices, not one: the post-fusion stages keep `visibleTypes`, only the measurement statements see the widened copy, and shadow rows are dropped before `sources` is built — a shadow block leaves as a UUID plus numbers inside `arm_ranks`, never with a title. The measurement corpus belongs in a restored copy (`server.instance_kind = measure-copy`), because an excluded type is invisible in the *result* and not in the *indexes*.

### Aggregate-to-parent fold (WF T11)

A block of a type whose `retrieval.policy` is `aggregate-to-parent` (resolved from the registry via `Set.AggregateTypes`) is not delivered as itself — it is folded onto its structural parent (`parent_id`). The canonical use is **comment → issue**: the comment passage is the real hit, but the response carries the issue identity, so a query surfaces one issue rather than a scatter of its comments. The fold is a Go post-pass in the query handler, placed **after graph expansion and before the sensitivity annotation** (so a hydrated parent flows through the existing sensitivity/rerank/supersedes/`filterSuperseded` machinery — a placement literally at `filterSuperseded` would leave the hydrated parent's sensitivity zero-valued = credentials = a silent over-block). Since Welle I-E flipped `comment` to `aggregate-to-parent`, the fast path is instead **a zero-DB no-op when no aggregating block ranks** (the child scan finds nothing), so a corpus without comments keeps `eval.sh` byte-identical.

The mechanism does one batched round-trip: a single query maps every aggregating child to its `parent_id` and `LEFT JOIN`-hydrates the parent under the **same** visibility triple `ctx_rrf` used (types/scopes/grants). Then a pure in-memory assembly folds:

- **Score merge** = `max(parent, child)` — **no** child bonus (00-masterplan K13: an unproven tuning constant, deferred to a later eval-backed wave; a Golden test freezes the formula). Several children of one parent **collapse** to a single parent entry scored by the max over all of them. An in-set parent keeps its rank slot; a parent absent from the result set is hydrated into the best-ranked child's slot.
- **Orphan** (`parent_id` NULL) ⇒ the child stays as itself + a WARN (fail-open: the child is readable; dropping it would be data loss).
- **Invisible / cross-scope parent** ⇒ the child stays **raw** and the foreign parent is **never** delivered (no leak). design/01 §4.6's "Kind fällt raus" describes a *successful* visibility-checked hydration; the invisible sub-case is pinned by design/02 §4.4/§5.2 ("Fold liefert das Comment roh, nie den Fremd-Parent") — a hand-set cross-scope `parent_id` cannot pull a foreign title into results, and a distinct WARN makes the anomaly observable.

**Issue integration (Welle I-E).** The issue-specific response contract is built on top of the generic mechanism:

- **`matched_comment`** — a folded issue row (hydrated OR in-set) carries the best-ranked child comment (`id` + rune-safe content `preview`), so the caller sees *why* the issue ranked: the passage that actually hit. It is set only on a folded parent (`omitempty`), never on a native hit or a child kept raw — every non-fold wire shape stays byte-identical.
- **Over-fetch** — the fold *collapses* rows (N comments of one issue ⇒ one issue row), so a fixed fetch truncated to the user limit can under-fill and under-diversify a comment-heavy scope. When the read-scopes actually hold an aggregating-type block (one `EXISTS` probe — a corpus without comments never widens, keeping `eval.sh` byte-identical), the internal candidate window is widened ×2 (`overFetchFactor`, capped at `overFetchHardCap` 500) so more distinct parents survive the collapse. **Deviation from design/02 §4.4's literal "limit × 2 (Cap 200)":** that phrasing predates the live baseline where the gravity reranker already fetches 200 unconditionally, which for any user limit ≤ 20 already exceeds `limit×2`; shrinking to `limit×2` would defeat the purpose, so I-E realises the *intent* (widen to compensate the collapse) as a ×2 factor on the base internal limit.
- **Per-parent cap** — the collapse itself is the cap: per parent exactly the best-ranked child sets the score and the `matched_comment`; further children of the same thread fold away silently and never displace a foreign candidate in the delivered set.
- **Ceiling caveat.** `ctx_rrf` caps its per-arm candidate pools (semantic 75, FTS 100/100, trigram 30 ⇒ fused pool ≲ 305), so the `p_limit` over-fetch only recovers parents within that ceiling. Under *extreme* per-issue skew a single hot thread can fill the arm slots and starve tail parents from the pool entirely — a case the p_limit over-fetch cannot fix. The complete fix is a per-parent cap **inside** `ctx_rrf`'s arms (a `ROW_NUMBER() PARTITION BY parent_id` window), which belongs to Achse-01's `ctx_rrf` and is the named follow-up.

## Temporal gravity & cyclic phases

**Cyclic phase model** — 7 cyclic temporal dimensions (weekday/month/quarter/week/monthday/seasonal/daily), each with normalized phase [0,1) and its own Gaussian decay field. Queries route to dimensions via an 18-matcher deterministic parser engine: "immer dienstags" activates `weekday`, "Weihnachten" activates `{month:0.4, seasonal:0.6}`. Timezone-aware via `CTX_TIMEZONE`.

**LLM-fallback derivation.** Queries the rules parser cannot resolve fall back to the LLM for *date* resolution only — the dimension weights are then derived deterministically in code from the same detector primitives (never asked from the model). Two hard gates protect the ranking: a phase-coherence check (a cyclic dimension is only activated when the resolved date actually carries that phase) and a linear floor ≥ 0.2 (a fallback result is never pure-cyclic, so a subtly wrong LLM date keeps a linear safety net). The consumer additionally drops any dimension key outside the canonical vocabulary before it can inflate the boost budget. `/api/query` reports the active weights as `activated_dim_weights`.

**Multiple anchors per block.** Every block carries dimensions from both its content (dates mentioned in text) AND its `created_at` timestamp. A block about "Meeting am Dienstag" written on a Friday gets `weekday=2` (content anchor) AND `weekday=5` (meta anchor); both signals contribute independently. "Meeting am Dienstag, Ergebnis am Mittwoch" still pulls the Wednesday block (just weaker). Storage is EAV (`context_temporal`) with partial B-Tree indexes for O(log n) dimension lookups at 1M+ scale; `ON CONFLICT` dedups overlapping timestamps.

**Forward Telescoping.** Older blocks get a wider linear gravity well (effective power scaled by `1 / (1 + 0.3·ln(1+age/30))`) so a 6-month-old block isn't drowned out by a 1-week-old block when the user asks about a date in that window. Future dates keep their 1.2× sharper cutoff. Matches Rubin & Baddeley 1989's age-dependent recall imprecision.

## Dream Mode

A continuous background loop that autonomously discovers relationships between blocks, marks outdated information (supersedes), and promotes high-quality content. It is **type-policy-gated** since WF T8 (`dream.linkable` both-sided via the block-type registry — the former `is_meta` exclude generalized; per-type `dream.link_classes` caps the writable link vocabulary).

- **Dual-model support** — a separate model for evaluation (e.g. a larger model for better causal/supersedes reasoning). Dream pipeline version 5, v5 prompt for qwen3.6:27b non-thinking sampler, with a `recurrent` relationship class detected via `context_temporal`+title-similarity (Phase 1) + LLM (Phase 2).
- **Parallel workers** (`CTX_DREAM_PARALLELISM`, default 1) with atomic `FOR UPDATE SKIP LOCKED` block-claim — race-safe under contention.
- Adaptive cooldown, supersedes detection, temporal validation, a **hard cap of 5 links per cycle** with type-diversity tie-break, replace-semantics with snapshot revert, and runtime mode control (on/throttled/off via API). Throttled mode pauses between GPU-intensive steps for thermal management.
- **Robust LLM-output parsing** — tolerates array-form, single-object, named-wrapper, fenced-array and compact-multi-key-object link formats from heterogeneous LLM outputs. A wrapper whose *only* array-valued key holds an empty array (`{"classifications": []}`, `{"reasoning": "none", "relationships": []}`) counts — like the bare `[]` — as an **inert verdict**, not a transient parse error: the block books the inert cooldown (`dream_eval_count` advances, the `InertOffset` back-off step applies) instead of retrying output the model will reproduce unchanged. Wrappers with two or more arrays stay a retry even when all of them are empty — an empty sibling must never hide a populated one.

**Link curation (migration 119).** Dream links carry two governance columns: `pinned` (human-confirmed via `manage dream-link-resolve` / `ctx dream resolve`) and `rationale` (durable per-link justification, TEXT). A pinned link **survives the replace sweep** — `deleteStaleLinks` deletes `WHERE NOT pinned`, so an operator verdict outlives any later LLM cycle that no longer re-emits the link; the only removal path for a pinned link is an explicit delete-resolve. A delete-resolve of a `supersedes` link reverts the target's snapshot marking (`lifecycle_state` → `knowledge`, `superseded_by` → `NULL`, only while it still points at that source) — the same revert the replace sweep runs for unpinned links. `rationale` stays NULL on automatic writes: the benchmarked V5 eval prompt emits `{target_id, type, confidence}` only; capture-at-write would be a prompt change and therefore a separate eval-gated wave. The write gate is the source block's write scope (uniform not found, no existence oracle — the GuardResolve doctrine); every resolve lands in `context_write_log` as `dream_link_resolve`.

**Dream-graph traversal** (Wave 1, default-on since Wave 3, `CTX_GRAPH_EXPAND_ENABLED`) — query-time 1-hop expansion of the Dream-inferred link graph (topical/factual/causal/recurrent), confidence/type-gated + hub-damped, fused as a scale-invariant post-gravity boost before rerank. Turns inferred links into positive recall instead of write-only metadata; fully parameterized for A/B sweeps, fail-open.

## Structural links (migration 076)

Deterministic **fact** edges between blocks, kept in `context_structural_links` — a table **strictly separate** from `context_dream_links`. Dream edges are *discovered* (LLM, confidence-gated, replace-swept every cycle); structural edges are *facts* (confidence 1.0 by definition — the table carries **no** confidence column). The Dream replace/cleanup paths operate only on `context_dream_links` and therefore never touch structural edges (enforced by a negative gate: `dream.WriteLinks` replace leaves a structural edge of the same source intact). The primary key is `(source_block_id, target_block_id, link_class)`, so two different classes may coexist on the same pair; `link_class` carries no CHECK (validated in Go against the type registry's `structural_link_classes`). Both FKs are `ON DELETE CASCADE`.

The **one** structural parent (comment→issue) is not stored here — it lives on the `context_blocks.parent_id` column (present since migration 001), which migration 076 upgrades with the FK `REFERENCES context_blocks(id) ON DELETE CASCADE` (added `NOT VALID` then `VALIDATE`d for lock-thrift; the column and its index pre-exist, so `context_blocks` gains no column). `parent_id` = the one structural parent; `context_structural_links` = all further classes (`references`, `duplicate-of`, …). Scope isolation is fail-closed and double-lined: writes validate source ∈ writable-scopes and target in the *same* scope inside one transaction (deriving the row scope from the source; unknown/foreign/invisible targets collapse to a single error → 404, no existence oracle), and reads filter neighbours through the shared visibility predicate (read-scopes + block-grants) so a raw-SQL-injected cross-scope edge never yields a foreign neighbour. A manage-update scope MOVE sweeps both link tables in the same transaction (GD5/K8): links whose far endpoint already lives in the target scope follow (row.scope update), links whose far endpoint stays behind are deleted — dream links regenerate, and a structural link with scope-divergent endpoints could never be re-written under the write invariant. Query-time graph expansion stays dream-only by doctrine (edge-consumer table below); the role of structural edges is the UI ego-graph and fact statistics, not retrieval — AS BUILT (GD4): the ego traversal follows both data classes per hop (fair zipper over the shared node budget, GB3), the wire carries them as own arrays (`structural_edges` + delivered legends, GA8/GB2), `min_confidence` gates dream edges only — structural facts are 1.0 by definition and always pass — and the SPA renders them default-visible as curved teal arrows with a blocklist filter (GC1/GC2).

**Edge-consumer doctrine (graph-structural plan 2026-07-14).** Consumers that INFER from edges (clustering, retrieval boost, scoring, dream curation) read exclusively `context_dream_links`; consumers that SHOW or COUNT facts (ego graph, detail views, statistics, audit) additionally read `context_structural_links`. Every per-block show or count ALWAYS runs through the visibility predicate at the far endpoint (the fillDegrees pattern in `store/graph.go` — its doc comment defends exactly this leak class: "a raw count would leak the existence of foreign private links on shared blocks"); ONLY identity-free scope aggregates without block IDs in the result may skip the predicate. Any exception to this default is policy and arrives as data (a config key or type-registry field), never as a silent code fork. Short form for comments: *inference reads dream, display counts both — per-block always visibility-filtered.*

**Cluster membership reads (Achse 03 wave C1, no consumer yet).** `internal/clustersql` is the single shared SQL fragment for "cluster membership, scope-pure" — a leaf package for the same reason `internal/visibility` is one (`rrf` cannot import `store`; `store → blocktype → rrf` would cycle), and the same constellation once produced three inline copies of the visibility predicate. The conjunction it owns is not a convenience: `graph_cluster_member` carries no visibility logic of its own — `block_id` is the sole primary key (057), `cluster_id` has no foreign key, and the only partition information is the `scope` column (087). A membership join without `AND scope = ANY(readScopes)` therefore returns the cluster affiliation of foreign-private blocks, which is a **side channel on foreign community structure**: a caller holding a single block grant on a foreign block would see its `cluster_id` and could test which of its own blocks carry the same value, reconstructing foreign community boundaries without ever reading a foreign block. Because every cluster read of the axis (retrieval boost, ego annotation, cluster route, facet) binds the predicate through `clustersql.MemberOf`, removing it in that one place reddens all of them — the negative probe is a single edit. `store.ClusterMembership` is the batch read (`RequireScopes` first, before any query: PostgreSQL evaluates `scope = ANY('{}')` as a deterministic FALSE, so an unresolved scope set would otherwise return an empty map indistinguishable from "nothing found"). The T41 leaf rule falls out one level up and for free: a grant-only block's scope is by definition not in `readScopes`, so its membership row filters out and the block reads as "no visible cluster", never as a foreign one.

**Traversal indexes (migration 104).** The ego-graph structural legs ride two M050-pattern B-trees — `idx_struct_links_graph_fwd (source_block_id, created_at DESC) INCLUDE (target, class, origin)` and the mirrored `graph_rev` — so each LATERAL cap leg is an ordered index scan with early termination ("newest reference wins the cap slot", E5; structural links carry no confidence to order by). 104 also retires `idx_struct_links_rev` (076): `graph_rev` is target-leading too and serves the reverse per-block lookup shape (formerly the `StructuralNeighbors` reverse leg — that single-block reader itself retired in GB6, its access pattern lives on as the Q1s reverse leg) — drop-probe evidence is asserted in `TestStructuralHop_IndexPlan`, which also keeps a permanent red probe (index drop in a rolled-back tx must degrade the plan to explicit leg sorts). **Statistics/prune indexes (migration 106):** `idx_struct_links_scope_created (scope, created_at) INCLUDE (link_class, origin)` makes the daily-report window count an index-only scan, and `idx_dream_links_scope_created (scope, created_at)` covers the dream side of the same statistics surface plus the N11 prune seam (`store/tenant.go`) — both built in final form while the tables are small (the single-tx runner cannot CONCURRENTLY); the dream side is deliberately non-covering (replace-swept hot write path).

**CSR graph cache (Achse 05 W05.1, dormant until W05.2+).** `internal/graphcache` holds an immutable in-memory CSR adjacency over BOTH edge classes, built for moving the two live traversal engines (`rrf.GraphExpand`, `store.EgoGraph`) off per-request SQL hops. Two strictly separate CSR pairs keep the GA5 isolation structural (a consumer handed only the dream pair can never surface a structural edge). Layout is normative: node universe = ALL block ids incl. archived (with an `Archived` pruning hint bit — never the visibility authority), sorted by raw UUID bytes with the array index as `NodeID`; per-node adjacency pre-sorted to the consumer order (dream `raw_confidence DESC` mirroring M050, struct `created_at DESC` mirroring M104) so a per-node cap is "take the first k"; confidences as u16 fixpoints with the asymmetric conversion rule — edge weights FLOOR (`ConfToFix`), comparison thresholds CEIL (`ThresholdToFix`) — which makes cache gates provably at-least-as-strict as SQL, never laxer; `supersedes` is excluded from the CSR entirely (traversal contract); scope/type/class/origin are interned over sorted distinct names (loud build error on overflow, never a silent wrap). The builder streams three queries WITHOUT `ORDER BY` (a 10M `ORDER BY id` would force a sort spill or 10M heap fetches) and establishes total order in Go — same DB ⇒ byte-equal `Fingerprint()` regardless of row arrival. Dangling edges (transient races) are skipped and counted, never fatal. Publication is a lock-free `atomic.Pointer` double buffer (`Store.Current()` nil = not ready = consumers use their SQL path). W05.2 adds the rebuild job and lifecycle: `graphcache.Manager` owns the state automaton (Empty/Fresh/Degraded/Failed) plus the dirty clock, the scheduler goroutine `runGraphCacheRebuild` owns the cadence (inert while `graph_cache.enabled=false`, boot-build on enable, then `pending && (quiet ≥ debounce_window || pendingAge ≥ max_pending_age) && sinceLastBuildStart ≥ min_rebuild_interval`, plus an unconditional hard `rebuild_interval`). **Staleness is Dirty-Age, never build age**: 0 while nothing is pending (an idle DB holds Fresh indefinitely — a build-age model would sit ~96% of a quiet 6h cycle in Degraded), else the age of the OLDEST unconsumed signal (the youngest write never resets the clock; a write during a build survives the swap re-anchored). Degradation (`Degraded` past `max_staleness`, `Failed` at `failed_threshold` consecutive build errors) transparently returns consumers to their SQL paths — which this axis never removes. The dirty signal channel `ctx_link_write` is fed since migration 116 (W05.3): row-level triggers on both link tables, statement-level TRUNCATE triggers, and a column-filtered `is_archived`/`scope` flip trigger on `context_blocks` — every cache-relevant mutation and nothing else (a `dream_checked_at` stamp stays off the wire); `/api/status` carries a server-admin-only `graph_cache` block (state/seq/built_at/staleness_ms/counts/build diagnostics), absent on the tenant path. Since W05.5 the FIRST consumer arm exists: `store.EgoGraph` can serve its two per-hop adjacency queries (Q1/Q1s) from the snapshot — behind `graph_cache.serve_ego` (default FALSE) AND the state gate (Fresh only, decided in the scheduler). The arm is a topology accelerator, never a visibility authority: every walk candidate is batch-hydrated through the same `store.VisibilityPredicate` before it may enter the node set or the next frontier (bridge/scope-move leaks are red-proven against a deliberately hint-trusting stub kept in the test suite as a permanent inversion anchor), rejected candidates consume no cap slot (refill loop — differential-proven node/edge/truncated parity against the SQL arm on a fresh snapshot), and an unknown seed aborts the arm entirely (complete SQL fallback, no partial merge). Focus hydrate stays SQL; since W05.6 the post-traversal stages ride the same arm: Q2/Q2s come from `Snapshot.InducedEdges` over the DB-confirmed node set (scope-safe by construction — every endpoint passed the live predicate; the SAME `arbitrateEdgeBudget`/`mapStructEdges` helpers consume the rows, only the source differs), including a **structurally separate supersedes display segment** (unexported, no Neighbors accessor — the traversal cannot reach it by construction, only `InducedEdges`/`Degree` read it); Q3 is the E-05-3(a) hint-filtered degree via `MakeDegreeHints` (scope AND per-request type allowlist AND archived, capped by `graph_cache.degree_walk_budget`, HitCap 201 = "200+"), with the declared bounded delta — stale hints ≤ MaxStaleness, grant-only neighbours under-counted (fail-closed) — while the RAW offset degree never leaves the process (oracle gate red-proven against it). Membership in `InducedEdges` is a map, not binary search (micro-bench: ~2× faster from 500 nodes; the sorted arm stays as a test-only comparison arm for the 1M bench). Since W05.7 the SECOND consumer arm exists: `rrf.GraphExpand` can serve its edge fetch from the snapshot behind `graph_cache.serve_expand` (default FALSE) — GA5 isolation is enforced by the type system (the arm's snapshot field is a three-method `dreamGraph` interface; structural/supersedes accessors are unreachable), the hub-damping degree is counted caller-locally in the walk over the gate-passing seed-edge set (a raw CSR degree would make the fusion an observable function of foreign private link counts — oracle-gate red-proven against exactly that stub), the per-hop hydrate runs the same `visibility.Predicate` as the SQL JOIN, and hop ≥ 2 frontiers form only from DB-confirmed nodes with the T41 leaf check on the hydrated scope (bridge gate red-proven against a hint-trusting stub with lying hints). An unknown seed aborts the whole request onto SQL; every other failure keeps the byte-identical fail-open contract. With that, all three engine cut-overs (ego hops, edges/degrees, expand) are built and dark — activation is the E-05-1 decision after the W05.8 bench.

**Prune validity boundary.** `context_structural_links` needs no entry in the tenant-prune delete list — both FKs are `ON DELETE CASCADE` (076), so the bounded block-slice DELETE cascades the edges (amplification per slice is bounded by max out-degree). This holds only as long as the write invariant (row scope = source scope = target scope) holds: if a scope-move path moves BOTH endpoints out of a scope, the link row survives a tenant prune carrying the scope of a purged tenant — no CASCADE fires because the endpoint blocks are not deleted. That is an orphaned metadata row without a read-path leak (read paths gate on `context_blocks.scope`, authoritative), but a hygiene gap; the scope-move link sweep (plan wave GD5) closes it.

## Workflow state (migration 077)

`context_blocks.workflow_status` (nullable `VARCHAR(50)`) is the per-block workflow **value**; the SET of valid states, the entry point, terminal flags and the forge open/closed mapping are Achse-01 type-config **policy** (the block-type registry `workflow` section — `{states, initial, terminal, forge_state_map}`). NULL means the block has no workflow (the entire knowledge corpus — no backfill). There is deliberately **no** CHECK constraint (M045 line): the Go transition validator `blocktype.Set.ValidateTransition` enforces the per-type state machine against the registry data, so changing the status set is a data edit, never a schema change. The transition graph is complete over the configured states (a transition is valid iff both endpoints are configured states); `terminal` is not an outgoing constraint (reopen closed→open is real), it flags which states map to the forge "closed" state.

The board/list path rides the partial keyset index `idx_blocks_workflow_board (scope, type_name, workflow_status, updated_at DESC, id DESC) WHERE workflow_status IS NOT NULL AND NOT is_archived`. A status-filtered board column is ONE ordered index range scan with a row-comparison keyset cursor `(updated_at, id) < (cursor)` — no Sort. The status-unfiltered list ("all issues, newest first") is a **per-status merge in Go** (one range scan per config status, k-way merge on `(updated_at DESC, id DESC)`), because the index cannot order across `workflow_status` values — a single naive `ORDER BY` over all statuses would force a Sort over the whole scope. Scopes are iterated the same way (scalar `scope =` per stream: a `scope = ANY(array)` on the leading index column would defeat the ordered scan). Label filters are a documented post-filter inside the range scan (`metadata->'labels'`); the server clamps the page to ≤ 100. `EXPLAIN` gates prove both paths at 10k seeded issues.

## Cluster topic identity (migration 124)

The 057 overview family replaces all three of its tables on **every** rebuild, so a Louvain cluster has no identity across runs: `cluster_id` is the smallest member UUID of the community and turns over silently as soon as that one block leaves it. `graph_cluster_topic` is the identity the teardown does not touch — the endpoint an edge can point at and a retrieval signal can refer to. The cluster flows, the topic stays.

A topic belongs to exactly **one scope**, continuing the 057 scope invariant one level up: identity hangs off the `(cluster_id, scope)` node row, not off the scope-spanning `cluster_id`. That is what keeps a label from ever carrying foreign-scope content and keeps two tenants from sharing a handle (which would be an existence oracle above the one `handler/overview.go` closes). The handle is `gen_random_uuid()` (**v4, never uuidv7**): a v7 timestamp would ship "when did a rebuild first see this community" on the wire, while `created_at` sits in a column that is read scope-filtered. `origin_kind`/`origin_topic_id` describe the birth (fresh vs. split), `merged_into` the death by merge; both self-references carry `ON DELETE SET NULL` so retention can purge old tombstones without tearing a lineage chain, and both get partial companion indexes — Postgres indexes no referencing FK side on its own, which would make that purge quadratic. `core_blocks` lives on the **topic row**, not only on the node row: a batch import that tears a partition apart over several rebuilds only finds its old identity again if the dead topic's substance survives the teardown, so the assignment pass matches birth candidates against the `core_blocks` of retired topics **of the same scope** and re-attaches instead of giving birth. Organic growth keeps running over the live predecessor generation — both paths active in the same run.

The core itself is picked by **intra-cluster weighted degree** (`clustering.intraDegree`), computed in the same symmetrization pass `computeClustering` already runs — the summed link confidence of a block's edges that stay inside its own community. It replaces the degenerate `repr_title` mechanism as the label basis: representative choice today orders by `quality_score DESC, id`, and with two thirds of the candidates sitting on the column default the uuid tiebreak decides, so a cluster's name is its oldest block rather than its subject. Edges **crossing** community boundaries are excluded — the core must describe what holds a cluster together, not what pulls at it; without that filter the bridge endpoints would outrank their peers and the core would be chosen by the very edge the partition rejected. The pass walks the sorted edge keys rather than the map, because float addition is not associative: last-ULP drift under Go's randomized map order would be cosmetic in the Q score but load-bearing here, where degree order is hashed into `core_hash` and a swapped neighbour pair would re-label a topic that never moved. Every node gets an entry, isolated ones at zero. Cost is O(|edges|) time and 8 B per node — 1.6 MB at the 200k node cap.

`graph_cluster_node` gains the assignment (`topic_id`, nullable — NULL means "not yet assigned" and the read path treats it fail-closed) plus the run's core (`core_hash`, `core_blocks`). The partial unique index `uq_gcn_scope_topic` is the injectivity gate: the mutual-plurality assignment guarantees no topic is claimed by two clusters, and without the index an assignment bug would silently merge two identities — with it the persist transaction breaks on 23505 and the previous map stays readable. There is deliberately **no backfill**: it would have to adopt today's `cluster_id` as the topic identity, i.e. exactly the value whose instability this line fixes.

**Label schema (migration 125).** Split off from 124 because identity and label are separately deployable — 124 plus the assignment pass yields an identity-stable map without touching labels, 125 lays the label on top. `label_source` ranks `manual` > `llm` > `fallback` > `none`: the automatic path only ever writes over `fallback` and `none`, `llm` is replaced solely by the label pipeline itself, and `manual` by nobody. The `manual` value ships in the vocabulary now even though its write endpoint is a later wave — the automatic path has to be able to respect it before anyone can set it, otherwise adding pinning later would be a schema change in the middle of a running pipeline. `label_core_hash` is the drift anchor: the pipeline re-labels exactly when it diverges from the node row's `core_hash`, so membership churn at the cluster's *rim* costs no LLM call. `label_stale` is the materialized form of that comparison — the comparison itself spans two tables and is therefore not index-addressable, which would force the per-tenant, per-interval selection into a sequential scan over a table where tombstones coexist with live topics; it defaults to `true`, fail-closed towards labeling rather than towards overlooking. Three CHECKs pin the vocabulary, a rune-exact 1–120 length (`char_length`, same rune accuracy the digest title truncation uses against SQLSTATE 22021 — a 120-umlaut label weighs 240 bytes and must still fit), and the rule that a non-`none` source requires a label, so "marked as labeled but empty" cannot become an invisible gap in the map. There is deliberately **no confidence field**: project empirics (dream v3) put the model's self-assessment out of use as a gate, so validation is structural and lives in code. `idx_gct_label_pending (scope, label_stale, label_attempts) WHERE retired_at IS NULL AND label_source <> 'manual'` is the selection index — the predicate is exactly the selection condition, so no tombstone and no pinned label ever enters it.

**Cluster centroids (Achse 03 wave C8, migration 128).** `graph_cluster_centroid` holds one averaged member embedding per `(topic_id, scope)` and answers the question the C3 seed derivation cannot: *where does this QUESTION live*, as opposed to *where do this query's hits live*. The seed arm is circular by construction — a query whose RRF hits are poor gets a prior built from those same poor hits — and the centroid arm is the way out, at **zero extra model cost**: the query embedding already exists, it was produced for `rrf.Search`. Three properties carry the build. It runs in its **own transaction after the persist commit**, and in the parent process (the W8 retention purge is the precedent, so nothing crosses the worker IPC protocol): the rebuild is all-or-nothing under `graph_overview.rebuild_timeout`, and a centroid step inside it would, at the target scale, roll back a complete and good rebuild whenever the sum overruns — reproducibly, every cycle, while `C4` correctly switched the signal off and thereby hid the freeze. It is **incremental over `member_hash`**, a sha256 over the sorted member set with each member tagged by whether it currently has an embedding: a full pass is ~6,9 GB of embedding I/O at 10M members, so an unchanged partition is skipped entirely — and that diff is the whole reason the table keys on the stable topic identity rather than on `cluster_id`, which is the smallest member UUID and turns over per run, so a diff over it could not tell "unchanged" from "new". The coverage marker in the hash is not decoration: a block whose embedding is backfilled later changes the centroid without changing the member set. And a **minUUID rename is not a recompute** — `cluster_id` is a run-local use column here, so a community that was renamed without a member moving costs one `UPDATE`, not an `avg()` over unchanged embeddings.

The read path binds `scope = ANY(...)` and sets `hnsw.iterative_scan`/`hnsw.ef_search` even while no index exists, so arming one is never a silent recall change; the distance `ORDER BY … LIMIT` sits in its own innermost select, because the design's original shape (`DISTINCT ON` in the same select as the distance ordering) forces a sort by `topic_id` and would have made the threshold index unusable after building it. The two arms fuse as `share_final = (1-w)·share_seed + w·share_centroid` over the **union** of their clusters — a cluster the seeds never voted for can win on centroid evidence alone — with `share_centroid` min-max normalised inside the probe window. An **empty probe means "the arm did not run"**, not "similarity 0": scaling every seed share by `(1-w)` against an empty table would push winners below `min_share`, so merely arming the feature would weaken the C3 signal it exists to extend. Everything ships dark (`cluster.centroid_build` and `cluster.centroid_enabled` default false).

There is deliberately **no HNSW index in the migration**. `cluster.centroid_ann_threshold` is a declared resource limit and the build arm creates or drops the index around it, with hysteresis so a corpus sitting on the boundary does not pay an index build every cycle. Its default is **5.000, calibrated against the C8 measurement** rather than assumed: `halfvec(1024)` is 2052 bytes and therefore lands just over the 2-kB TOAST threshold, so every centroid is an out-of-line read — 3.604 B touched per row on a full scan, 1,7× the "~2 kB/row ⇒ ~170 MB at 83.000 rows" the design budgeted — and the measured exact-scan p95 holds the 25 ms retrieval budget up to roughly 3.300 centroids. The design's build-and-swap prescription is deliberately **not** implemented: it presumes the table is fully rewritten every cycle, and re-introducing that rewrite to swap a table would trade the index churn for exactly the 6,9 GB the incremental diff removes.

**Cluster injection (Achse 03 wave C9).** The stage's last half is the only one that can change the result **set** rather than its order: unseen siblings of a winning cluster, appended with a deliberately low synthetic score. It is the graph stage's NEW-neighbour path on cluster evidence instead of edge evidence, and it runs **after the boost, still inside the stage, i.e. before GraphExpand** — after the boost because the winners and their shares decide who may be injected at all, before GraphExpand because an injected sibling then becomes a legitimate graph seed, which is the whole reason the categorical prior sits ahead of the edge traversal. `cluster.inject_max` defaults to **0**, so the shipped state adds nothing and arming it is a step that follows the eval measurement rather than a deploy.

Two conjunctions gate the hydrate, and they answer different questions: `clustersql.MemberOf` decides which **membership rows** may be read (the community side channel), `visibility.Predicate` decides which **blocks** may be delivered. They are not interchangeable — a red probe that keeps only `NOT cb.is_archived` still leaks a block that was **re-scoped between two rebuilds**, because the membership row records the partition the rebuild ran in while `context_blocks.scope` is authoritative. An empty type allowlist is a hard error rather than zero rows, so a registry wiring bug surfaces instead of reading as "nothing to inject"; the stage's fail-open contract then keeps the boosted results and reports the error. Placement adds **no second knob**: an injected block carries only cluster evidence, so it enters at `topScore * boost_weight * share` — a stage permitted to move a native result by at most `1+boost_weight` may introduce one at at most `boost_weight` of the top, which keeps a single dial governing both and keeps cluster evidence structurally below direct retrieval evidence. The cap sorts by share first, then quality, then id: `quality_score` ranks blocks *within* a cluster while share ranks how much the query is about that cluster at all, and a quality-first cut would let one strong cluster starve a more relevant one. Injected results carry `via_cluster` plus the share in `cluster_boost`, and every derived score field (`rrf_score_original`, `rerank_score`, `cosine_sim`) is cleared — a synthetic result that keeps a zero value where a measurement belongs is how it starts to look native.

**Root-map reads (Achse 02 wave W-B, no consumer yet).** Three additive reads in `internal/store` supply every number the root map prints, and each mirrors the `GraphOverview` posture line for line — `RequireScopes` as the first statement, `WHERE scope = ANY($1)` in every FROM, no unscoped row pick. The stakes differ from a request path: the map is a **persisted** artefact, so a scope leak here is a database row travelling through backups, exports and the context of every agent that loads it, not one byte on a wire. `OverviewTotals` folds the per-`(cluster,scope)` rows into one visible size per cluster **before** classifying small vs. large, so the collector line follows what the caller can see instead of the partition layout. `OverviewMeta` aggregates the migration-123 liveness columns with SUM for the counts (max would report one partition's numbers as the window's and break the coverage arithmetic), max for the stamps, and a cap reason that deliberately excludes `advisory-lock` — contention means another instance is building this very partition successfully, and rendering it as a freeze would print a cap that does not exist. It also isolates **stale** rows: the rebuild teardown only deletes meta rows for scopes that still have cluster rows, so a scope whose blocks left the corpus keeps a success row for good; such a row is excluded from every sum and reported by name (`StaleScopes`) so the map can call it neither fresh coverage nor a gap. `ActiveBlockCount` is the only new O(corpus) step of the axis and the only one with a hard cap: the cap runs in its **own transaction** via `set_config('statement_timeout', …, is_local => true)` — `SET LOCAL` outside a transaction block is a no-op PostgreSQL answers with a warning, and a `SET` without `LOCAL` would stay on the pooled connection and cap unrelated queries at random; the Go deadline sits half a second **behind** the database cap so it is a backstop rather than a mask. On expiry the result is `(0, false)` — never a `pg_class.reltuples` estimate, which can filter neither `scope` nor `is_archived` and would freeze the GLOBAL corpus size into one tenant's block. The count itself rides `idx_context_scope_active` (022) as an index-only scan, so no migration and no lock. `GraphOverview` additionally short-circuits `EdgeLimit <= 0` without touching `graph_cluster_edge`; the live route cannot reach that branch (the handler parser enforces `edge_limit >= 1`), which is why the wire envelope and its golden test are unaffected.

**Root-map renderer (Achse 02 wave W-C, no caller yet).** `internal/rootmap` turns those numbers into the map text and is deliberately **pure** — no database, no clock, no config lookup, the same discipline as `handler.buildOverviewResponse`. Two properties carry it. First, the output never exceeds `BudgetBytes`, by **measuring** rather than estimating: lines are appended while the reserved footer still fits, and an oversized footer or a budget too small for the skeleton is an error, never a silently truncated map (a guessing renderer outgrows the 50 KB write cap of the public store API, and nobody would notice — the old topic map bypasses that cap by construction and sits at 80 KB). Second, every cluster lands in exactly one of three buckets — rendered, below `small_cluster_max`, cut by the budget — under the rule "rendered beats small beats cut", and `Render` **asserts** both bucket sums instead of trusting them: at ~10^5 clusters against ~95 lines the "small" and "cut" sets overlap by default, and the pre-revision two-line footer would have counted tens of thousands of clusters twice. The head line names the rendered mass, which is only known after the measuring loop, so the loop measures the head with the TOTALS substituted for the rendered counts — an upper bound (never fewer digits), which breaks the circle without a second pass. No wall clock enters the text (only `computed_at`/`last_attempt_at`, which describe the partition rather than the moment of rendering) — the precondition for content idempotency later. Coverage follows decision E11-02: checkpoints are **not** a gap but operational compaction artefacts, so the coverage figure is measured against the knowledge corpus (active minus operational types), the operational types get their own line naming them as a type-policy decision, and the raw corpus number stays visible beside it — 97,9 % instead of 16,8 %, same numbers, correct statement. A capped corpus count (`ActiveKnown = false`) removes denominator and percentage entirely instead of substituting an estimate. Degradation D0–D5 is complete and never throws: LLM label → heuristic → `repr_title` (cut rune-exact at 60 runes, the 22021 trap) → no stable id (the `repr=` handle remains, the head says so) → empty map with the three cases told apart in words → cap line above everything else (a truncated context must still carry the warning); `advisory-lock` renders **no** cap line, because contention is not a freeze. `AllowsUpsert` is the BP-6 rule as a pure predicate — an empty or stale map never replaces a good one, and only a genuinely fresh tenant (no clusters, never built, no stale scopes) may write the "no clusters yet" map; a render landing inside a global rebuild's TRUNCATE window sees zero clusters while the meta row still reports the old `cluster_n`, which is exactly the case the rule exists for.

## Schema contract (W03-2)

`internal/schemacontract` pins the expected database schema as a generated, embedded artifact: `manifest.json` is produced by a generator run (`go test -tags=genmanifest ./internal/schemacontract`) against a fresh migration chain on the prod-parity Postgres image, checked into the repo, and compiled into the binary via `go:embed` — the contract lives *outside* the thing it checks. `Check` = catalog-only `Introspect` + a pure bidirectional `Diff` (missing objects are breaking; unknown *active* objects — triggers, functions, rules, policies — are breaking because they are live code in the write path, while unknown passive objects are param; definition drift is param except an RLS flip) + migration integrity (sha256 of every applied file vs `_migrations.checksum`, version gaps both ways — for the 112 versions folded into `113_baseline.sql` the expected sha256 comes from the folded chain in `migrations.Folded()` rather than from a file, same comparison and same severity, see [operations](operations.md#the-migration-baseline-001113-ship-as-one-file)) + a three-step GUC probe whose library-load-first shape is load-bearing (a fresh session accepts any `hnsw.*` placeholder — probing without a prior vector op is provably fail-open). The historic `*_snapshot_*` table exception survives as a fixed code constant, scoped to ordinary tables only and always counted in the report, never silent. Migration 115 canonicalizes the live-proven `ef_construction=128` in the chain (closing the one known definition drift): the rebuild guard treats `reltuples < 0` (never analyzed — the state after any `pg_restore`) as *unknown* and probes via a bounded count (`LIMIT 500000`, never a full scan) — the naive `COALESCE(reltuples,0)` form would have triggered an hours-long inline HNSW build in the boot path on a restored 10M corpus. test.sh's T07 hand-maintained count check (two documented stale incidents) is replaced by `ctx contract`; until the deployed CLI knows the command, T07 falls back to exactly the old count probe — same strength, automatic upgrade after deploy. A pre-commit gate blocks a staged migration without a staged manifest regeneration. Since W03-3 the check is boot-wired: `schemaContractBoot` runs after settings bootstrap and before the router — `enforce` + breaking drift exits the process (the abort log names both escape hatches, `CTX_CONTRACT_MODE=off` and `CTX_SETTINGS_DISABLE=1`), `warn` (default) boots loud. `contract.mode` carries a documented env-dominant special precedence (env > DB > default — the opposite of the registry norm; an `off` row written to the DB is not honored and surfaces as a `mode_source_db_off` finding: the switch that turns off DB overrides cannot itself be a DB override). A periodic re-check (`contract.recheck_interval`, default 60s, hot) refreshes the process-wide report so drift at the *running* process — the historic ef_construction case — is visible within a minute; the re-check never enforces, stop semantics stay boot-exclusive. W03-4 lands the surfaces: `/health` gains the name-free public field `schema_contract` (`ok | attention | off` — drift and unchecked deliberately collapse into one public `attention` value per E-03-4, a timing-oracle argument; `attention` floors overall health to degraded at HTTP 200, `off` never degrades). The full object-level report — mode, mode source, per-object drifts — is server-admin-only behind `GET /api/contract` (`?refresh=1` rides the same CAS single-flight as the ticker). The CLI `ctx contract` refreshes by default (`--cached` opts out) and exits 0/1/2/3 for ok/drift/unchecked/transport-or-auth — a dead daemon or 403 is never exit 0. `/api/status` additionally carries a server-admin-only `db` section (W03-7, absent on the tenant path): migration counts, a contract short-form, extensions, informational server GUCs, size/vacuum stats for the eight core relations (hypertable-aware — parent-size reads are blind to TimescaleDB chunks), an HNSW capacity row (`bytes_per_row` divides by the *index's own* `reltuples`; note ANALYZE re-mirrors that onto the table estimate on PG18 — only REINDEX/CREATE INDEX restores the exact count), and the embed backlog behind an introspection guard (no covering partial index ⇒ `null`, never an unguarded scan). Refreshed on its own 60s cadence (`events.db_stats_interval`), not the 5s status tick. The section's `channel_probe` field (W03-8, `status.channel_probe_interval`, default 0 = off) measures — when armed — the wall-clock latency of the four ctx_rrf retrieval channels as standalone statements in one transaction with the production `SET LOCAL hnsw.iterative_scan` state (plan parity: without it the semantic channel's result collapses — measured 75 vs 2 rows on a spread corpus — even though the bare EXPLAIN node type stays identical). The query vector comes from the busiest `context_embed_cache` row *of the current embed model* (a foreign-model row is never used); an empty cache skips the probe silently — it never embeds, never calls an LLM, and never measures quality, only duration.

## Recall measurement (migration 110)

`context_recall_runs` stores the aggregates of the recall_check probes (Achse 01): scope-stratified ANN-vs-exact recall runs quantifying how close the production HNSW index tracks a brute-force reference. **Aggregates only** — the table never carries query texts, block IDs, or vectors; `internal/recall.Insert` enforces a fail-closed 12-key allowlist on the `meta` JSONB (unknown key or non-scalar value rejects before the write), with unit + integration tests pinning the guard. `scope` here names the *measured* scope (measurement-object label, not a visibility discriminator — the table is server-admin-only). No backfill path exists by design: historic `context_access_log` rankings would be ANN-scored-against-itself (no brute-force reference leg ever existed) and thus fake recall data. W01-1 ships table + persistence (`Insert`, `LatestByStratum`) without callers; the scheduler arm (W01-3/4) follows. The stratification/loo access path (and, read-only per conflict rule K3, the future Strategy-Selector cardinality estimate) rides the partial covering index `idx_blocks_stratify_covering (scope, type_name) WHERE NOT is_archived AND embedding IS NOT NULL` (migration 111) — per-scope counts of embedded active blocks are Index-Only-Scans instead of a ~14 GB full heap scan at 10M rows.

W01-2 lands the probe mechanics (`internal/recall`, still caller-free): `RunOnce` = stratify (per-scope `SnapshotForTenant` allowlists, largest scope per class small/medium/large — bounds pinned to the E-02-1 selector thresholds 4096/65536 per K3 — plus a base-set pseudo-stratum `all`) → sample (real logged queries via a bounded 30d/500-distinct backward stream joined touch-free against `context_embed_cache` — `embedcache.PeekByHash`, a plain SELECT, never the `hit_count`/`last_access` touch-UPDATE of the hot path — with deterministic leave-one-out fill for thin strata; wire-free, no embed call ever) → two-leg probes → aggregate → persist. Each probe runs two `BEGIN READ ONLY` transactions with production-identical predicates *minus the grant arm* (documented deviation): an exact leg (`enable_indexscan/bitmapscan=off`, the brute-force reference) and an ANN leg (`enable_seqscan/sort/bitmapscan=off`, `hnsw.iterative_scan='relaxed_order'`, optional `ef_search`). Three barriers kill the frozen-generic-plan silent bypass (pgx `QueryExecModeCacheStatement` + PG's 5-execution generic-plan switch would otherwise let one leg silently ride the other's plan from probe ~6): `plan_cache_mode=force_custom_plan` per transaction, leg-distinct statement texts (`/* recall_leg:exact|ann */` markers = separate cache entries), and an `EXPLAIN (FORMAT JSON)` plan proof in EVERY probe transaction on the same connection (ANN leg must contain `idx_embedding_hnsw`, exact leg must not — violation writes `valid=false` + `meta.invalid_reason`, never a recall number). Recall is distance-based and ties-robust: `n_eff = min(k,|E|)`, hit = ANN distances ≤ last-exact-distance + ε, `recall = hit/n_eff` — a 17-block scope at k=75 can reach 1.0 instead of being pinned at ~0.23. Every row carries environment stamps (pgvector/PG version, HNSW indexdef, effective embed model) — measurement series survive index rebuilds and extension bumps interpretably.

W01-3 wires the arm into the scheduler (`runRecallCheck`, its own goroutine — no new ticker case): cheap strata (small/medium) run on `recall_check.interval`, expensive strata (large/all) anchor to the `recall_check.offpeak_hour` wall clock with ONE expensive stratum per off-peak run rotated round-robin. Interactive demand defers the launch entirely and, once running, parks the run before every probe (up to `park_max_ms`, then the remaining rows abort visibly as `demand_deferred`). Budgets are two-dimensional: the time clock (`exact_budget_ms`) plus a touch budget (`exact_touch_budget_bytes`, `0` = auto 25% of shared_buffers) that pre-estimates each stratum at ~5.5 kB per row per exact leg, scales the query count down (floor 5 — below that the row refuses a pseudo-statistic), and stamps `meta.exact_touch_bytes`; `meta.buffercache_delta` lands best-effort when pg_buffercache exists. A janitor line deletes rows past `recall_check.retention_days`. The last-run stamp is the ADDITIVE `LastRecallRun()` — `LastArmRuns()` stays byte-identical because the status collector binds to it via an optional interface assertion that a signature change would break silently (compile-time pins guard both shapes).

W01-4 surfaces the telemetry: `/api/status` carries a server-admin-only `recall` section (absent on the tenant path — recall metrics reveal scope existence/size) with the process `last_run_at`, the latest measurement per (stratum, scope, k) including `age_ms` staleness and the `scope_changed` flag (a scope hop is surfaced as its own event so a trend reader never mistakes it for a recall regression), and `invalid_runs_7d` — the fail-closed visibility counter for plan-assertion violations and demand/budget aborts. `state.sh` prints the last valid run's date + average, degrading to `n/a` on pre-110 schemas.

## hermes state reader (Achse A03 wave W03-2, no consumer yet)

`internal/hermesstate` is a read-only reader over the SQLite `state.db` of a hermes agent (NousResearch/hermes-agent) — the source a later distiller arm reads compacted tool output from. It ships **unwired**: nothing imports it, `cmd/ctxd` does not link the SQLite driver, and the arm, its config group and the access seam are separate waves. Five invariants carry it, each with its own gate. **No write path**: the package exports no statement-running surface at all (the absence is the guarantee, and `grep -c 'Exec\|Prepare'` over the non-test files is its probe), the DSN is pinned to `mode=ro`, and `immutable=1` is an explicit `Options.Snapshot` opt-in for a private snapshot copy — never the live file, where it would license SQLite to assume bytes that a foreign process is still writing. **Hardening before the first payload query**: `trusted_schema=off`, `cell_size_check=on`, `query_only=1` and `SQLITE_DBCONFIG_DEFENSIVE`, all applied through the DSN so they hold for every pooled connection rather than for the first one, read back and asserted; plus a type check that `messages` and `sessions` really are TABLEs — a prepared file that swaps a table for a VIEW over arbitrary expressions is refused with `schema_untrusted`, which no size cap would have caught. **The query plan is chosen and verified, never assumed**: hermes' schema does not guarantee an index on `(session_id, id)` (it is absent from the upstream schema the design was written against and present in both live stores, which acquired it from another version), and hermes never runs `ANALYZE`, so the natural phrasing degrades on a store without it to `SEARCH … idx_messages_session (session_id=?)` plus `USE TEMP B-TREE FOR ORDER BY` — a full session scan and a materialised sort. `Open` therefore probes the index catalogue, picks `index-seek` or `rowid-range` (the latter disqualifies every `session_id` index with a unary plus and rides the INTEGER PRIMARY KEY range instead), and asserts the choice with `EXPLAIN QUERY PLAN` against the real file; a plan naming `USE TEMP B-TREE` or `idx_messages_session ` refuses the open rather than reading slowly. Measured on a 2 000 000-row fixture over 12 interleaved sessions: pinned batch 2.4 ms, the same batch unhinted 66 ms. **Every query is its own autocommit read** — never a transaction spanning batches, because a WAL reader holding a read mark keeps the foreign writer's `-wal` from being checkpointed back, and a distillation run spans minutes; batch consistency comes from the monotone `id` range instead. **Content is decoded at the package edge**: hermes serialises multimodal parts as `"\x00json:"` + JSON, so only the text parts survive, non-text parts (image URLs, base64 blobs) are dropped rather than passed to a credential scanner, an unparseable payload costs its row against a `rows_dropped_enc` counter, and no NUL byte reaches a caller. WAL reachability is a property of the writer, not a bug: a WAL store is readable via `mode=ro` only while its `-shm` exists — i.e. while hermes holds the file open — and a cleanly closed one fails with `SQLITE_READONLY (8)` / `SQLITE_CANTOPEN (14)`, both mapped to `ErrSourceUnavailable`, never to a hard failure (while hermes is stopped no new material is produced either). The watermark helper counts **rows**, not ids: `id` is a global AUTOINCREMENT shared by every session in the file, so `max_compacted_id − N` yields an id delta that under interleaved sessions is a fraction of the rows asked for.

## Derived-knowledge gate module (Achse D-01 wave W01-1, no consumer yet)

`internal/derived` is THE gate module of the derived knowledge layer (`insight`, `catalog`) and, like `internal/hermesstate`, it ships **unwired**: nothing imports it, no arm calls it, no config group exists. It owns four things. The **provenance contract** `metadata.provenance` — one namespaced key, so the collision surface against the metadata keys already in the corpus is one line wide — with fourteen fail-closed checks V1–V14 that prevent a write rather than degrade it, decoding that refuses any contract version but the one this build knows, and a `source_digest` that makes “has the source set changed?” an O(1) comparison against a list that can be 147 UUIDs long. The **citation gate** G0–G7, cheap before expensive: the claim names a declared source (G0, the reduce guard — a claim verified against a map stage's output would be a citation of model text), the source resolves to ORIGINAL content (G1), the quote clears 32 runes (G2), the normalised quote is contained in the normalised original (G3), it carries no redaction marker (G4 — the checkpoint redaction REPLACES rather than deletes, so `[REDACTED]` is a genuine substring that G3 passes cleanly), `promptguard.Neutralize` breaks nothing (G5), `sensitivity.Scan` does not fire (G6), and an n-gram echo index over the titles of the `credentials`/`personal` sources does not fire either (G7 — the check that catches a secret which was already summarised into a title one abstraction level earlier, where a credential scanner no longer sees it). Its four thresholds are **constants, not config keys**: at `MinQuoteRunes = 3` the string “ok” is a valid quote of every second line and the gate reports full coverage while checking nothing, so a gate whose threshold is a settings write is not a gate. The **renderer**, which is head-heavy by necessity: `llm.MaxBlockChars = 1500` is the entire window a block gets in the synthesis prompt and it cuts from the back, so title, computed metrics bracket, conflict rule and untrusted framing stand first, the claims follow, and the verbatim evidence and the source list stand last — head plus the three-claim minimum measures 736 runes against a 1 200-rune budget, where the first draft's layout (evidence before the metrics) measured 1 524. The metrics bracket is the `computed` class: aggregates, counts, the source period and the coverage gap are produced in Go from the source set, never offered to a model, and the answer schema has no shape that could express them — a line without a `quote` is dropped. It carries exactly ONE timestamp, because `block_mass` is `1/sqrt(n)` over `content_times` and a single date scores the same 1.0 as none. And `StripReserved` drops the fourteen reserved metadata keys, `guard_checked_at` (the guard's pending mark) and `is_meta` (the one metadata classify rule in the system) among them — defence in depth beside the `UpsertBlock`-side filter, not instead of it. Two cuts are structural. The package is a **leaf**: it imports only `promptguard` and `sensitivity`, never `store`, `llm`, `blocktype` or `topiclabel`, so the DB half of the contract (`store.ResolveSources`) will call INTO it — the same shape `internal/visibility` uses; the echo index is therefore an independent implementation of the one in `topiclabel/guard.go`, with an origin comment, rather than an import. And **no type name carries stratum 2**: `StratumOf` maps `insight` and `catalog` to 1 and everything else to 0, while a super-catalogue is a `catalog` block carrying `provenance.stratum = 2` and `Validate` takes the writer's own level as a parameter. Deriving the level from the type name would move it into the type registry, a table an operator can edit with SQL, which is precisely the way of breaking the stratification invariant that the design rejects. A third property runs through the validation and was sharpened after the adversarial review of the wave: every value `Validate` **checks** is bound to the value the block **writes**. `provenance.stratum` — the field `store.ResolveSources` reads back for the next level's check — must equal the level the write claims, so an arm cannot raise the checked level to let its sources pass while persisting a block that later runs count as an original. Every declared source either carries a stratum, an untrusted flag and a sensitivity, or is reported as unresolvable; a source that is silently absent from the caller's facts would be touched by no clause at all, and the caller would decide by omission what gets validated. And `claims_kept`/`sources_covered` are re-derived from the claims that actually survived the gate before the yield floor judges them — otherwise the one gate that decides whether a block is written at all would be judging the arm's self-report, and the coverage line in the head would state a completeness nobody verified.

The **adequacy counter-metric** (Achse D-05 wave M-W4b) stands beside the gate, not beneath it. `Adequacy(claim, quote)` returns `compression = |TokenSet(claim)| / |TokenSet(quote)|` and `novelty = |TokenSet(claim) \ TokenSet(quote)| / |TokenSet(claim)|` over `evalscore.TokenSet` — the tokeniser the eval side already scores title overlap with, so a claim's novelty here and its token F1 there sit on the same word boundaries; an empty denominator yields 0 and never NaN, because a NaN novelty compares false against every threshold and would silence the rule on exactly the degenerate charges. `Report(items)` folds a charge — the blocks of one run — to a `GateReport`: anchoring rate and its complement the rejection rate, the summed g0…g7 histogram, and the two medians over the claims that SURVIVED. Both numbers live in the **same** verdict because a pure anchoring rate is trivially maximised: a generator that quotes a whole source paragraph and asserts it as an insight reaches rate 1,0 at value 0, and every one of those lines is a perfectly anchored citation that G0–G7 cannot touch. Hence the refusal `GoodhartMinGrounding = 0.95` **and** `GoodhartMinNovelty = 0.15` — a charge above the one and below the other does not pass; it copies instead of extracting, and the report says which of the two failure modes it hit, because a copying generator and a low-anchoring one call for opposite fixes. Both thresholds are constants for the same reason `MinQuoteRunes` is: a novelty floor an operator can set to 0 switches the counter-metric off without anything turning red. And every report carries the **double role** verbatim — `measured = "rejection_rate"` in the JSON, one sentence in the rendering: once the gate writes fail-closed, the runtime hallucination rate is 0 **by construction**, so what is measured is the rejection rate, how much of what the generator produced is not anchorable — a generator-quality metric and a cost metric (discarded GPU seconds) at once. Without that sentence somebody reads the zero as quality instead of as construction.

## Distiller journal (Achse A03 wave W03-1, migration 135, no consumer yet)

Migration 135 lands the distiller's storage and nothing else — no reader, no writer, no config consumer. `distill_run` is a **journal, not a state row**: one row per (run × source), written two-phase and then *advanced* — `INSERT` with `outcome='running'` before the run, `watermark_to` moved forward after each batch, `UPDATE` on completion. The difference from migration 130's journal is that advance: 130's child is atomic and updates once, the distiller processes an id range in batches and has to record partial progress, so a `running` row with `watermark_to > watermark_from` is a **partial success**, not a fault, and the boot sweep demotes it to `killed` without discarding the watermark. **The watermark is derived, never stored**: `max(watermark_to)` over a source's rows with `outcome <> 'running'` is its only definition — there is no second state holder that could drift, `skipped`/`failed` rows are included because both can carry real progress, and a `skipped` row is watermark-invariant by construction (`watermark_from = watermark_to =` the value derived at skip time, so `max()` is untouched even when the source is unreachable). The correctness condition that makes this safe lives in the writer, not the schema: the block is upserted *before* `watermark_to` advances, so a kill between the two costs a re-read, never an insight. Four CHECK constraints keep the journal honest rather than trusting its callers — the seven-value `outcome` enum, the nine-value `skip_reason` enum, the ten-class `error` taxonomy (**a class string only, never a foreign error text**: the journal is readable over `/api` and lives 90 days, so SQLite messages and HTTP bodies belong in the log), and `outcome='running' ⇔ finished_at IS NULL`, the invariant the startup sweep stands on. `distill_seen` (PK `(source_key, row_hash)`, SHA-256 as `bytea`) is the cross-run dedup ledger without which the same repeated tool output is re-batched and re-billed in every compaction generation.

The one touch on an existing table is the expression index `idx_blocks_checkpoint_root` on `context_blocks ((metadata->>'root_session_id'), created_at DESC)`, which turns the later manifest lookup from a scan proportional to the checkpoint corpus into a lookup proportional to one root session. Its predicate is `IS NOT NULL`, deliberately not `metadata ? 'root_session_id'`: Postgres derives `expr IS NOT NULL` from `expr = 'x'` (strict operator on the same expression) but proves nothing about the `?` existence test, so the `?` variant would be an index the lookup can never use. Measured, not estimated (the gate design/03 §3.1 demands): on a synthetic 1M-row `context_blocks` with 1 % carrying the key, the index builds in **0.16 s** — far under the 30 s threshold above which it would have had to move into a `CREATE INDEX CONCURRENTLY` follow-up, which this repo's runner could not carry anyway (every migration file runs inside one transaction). On the same fixture the lookup drops from 10 000 heap blocks / 46.8 ms to 25 heap blocks / 1.0 ms, entering the plan as a `Bitmap Index Scan` under a `BitmapAnd` with `idx_context_category`. A measured correction to design/03 §4.5 rides along: the explicit `IS NOT NULL` line in the lookup query is documentation, not mechanism — with it and without it the plan is byte-identical, because the same strict-operator derivation that makes the index predicate provable applies to the query. The line stays (it states the intent and costs nothing), and an integration probe pins the derivation so a future server that stopped doing it goes red instead of silently losing the index.

## Forge sync (migrations 079/080)

The project register `context_projects` (migration 079) binds one project identity to exactly one tenant scope — that scope **is** the repo corpus. Under masterplan **K14 there is no separate `context_forge_repos` table**: the register IS the forge registration. Migration 080 (Welle I-F) extends it additively — `token_secret` (the NAME of a sealed PAT in `context_secrets`, never the PAT), `sync_enabled`/`push_enabled` (fail-closed: pull-only until an explicit toggle), `last_error`/`backoff_until` (offline-first resilience) — and the ETag/`since` fetch cursor lives inside the pre-existing `sync_cursor` JSONB, not new columns.

The per-entity issue↔block mapping is `context_project_sync_map` (080): `(project_id, entity_kind, forge_id, block_id)` with the 3-way `base_hash` (§3.6 canonical projection at last sync). Sync writes never go through `UpsertBlock` — the sync identity is `(project, kind, forge_id)`, so forge-side title changes are identity-neutral. It CASCADEs off **both** `context_projects` and `context_blocks`, so a tenant prune drains it for free (the K14 gate).

**I-F ships the pull client + sync shell only.** The GitHub REST client is PULL-only: conditional ETag requests (304 ⇒ 0 writes, off the rate-limit budget), Link-header pagination, `pull_request`-field PR filtering, rate-limit backoff (exponential, cap 1h — never a conflict), and a dial-time SSRF guard (`net.Dialer.Control` re-checks the resolved IP against the private/loopback/link-local deny-list, closing DNS rebinding past the PATCH-time `forge.api_base` check). The `forge-sync-start` shell runs fail-closed gates (owner-less scope ⇒ disable + refuse; no resolvable `issue` policy with `digest.include=false` ⇒ refuse) then a background goroutine (single-flight per project ⇒ 409 on double-start). It fetches, gates and records run history (`context_project_sync_runs`), and hands each fetched page to the I-G apply seam.

**I-G is the Pull-APPLY (`forge.Applier`).** For every fetched issue it runs a **3-way direction decision** over the canonical hash projection (§3.6) — `base` (`context_project_sync_map.base_hash`), `ctxH` (projection of the stored block), `forgeH` (projection of the fetch). The projection is **content only, never a timestamp** (W16): `{title, body, state, labels: sorted, assignees: sorted, milestone}`, and the title is the forge title with the ctx `#<nr>`/`#L<seq>` prefix stripped (the block title is a derivat — hashing the raw prefixed title would drift `ctxH != forgeH` forever). The direction table (`§4.5.2`): no mapping ⇒ **pull-create** (block `#<nr> <title>` + mapping + `base := forgeH`); `base=ctxH, ≠forgeH` ⇒ **pull-update** (block-update + `base := forgeH`); `≠ctxH, base=forgeH` ⇒ **ctx-ahead** — nothing (push is Welle I-H); `≠,≠, ctxH=forgeH` ⇒ **converged** (`base := ctxH`, no block write); `≠,≠,≠` ⇒ **conflict** (`conflict=true` + `conflict_at`, zero writes both ways, resolved only explicitly). A local-only mapping (`forge_id=0`, an unpushed `issue-create`) is never a fetch id, so a pull leaves it untouched. Each issue applies in its **own transaction** (block + mapping + references atomic); the fetch cursor (`sync_cursor.issues.{etag,since}`) advances durably only **after** a page's apply succeeds, so an apply error mid-page leaves it un-advanced and the resume re-applies the committed rows as idempotent no-ops. The mapping lookup is one batch query per page (no N+1 at 10k+ issues/repo).

**Status apply + fallback (§4.5.4).** The forge `state` maps to `workflow_status` via the type's `forge_state_map` (open→backlog, closed→done). When the registry is not resolvable, the pull writes **only `metadata.forge_state`** and leaves `workflow_status` NULL — a documented fail-safe, never a guessed status set; an idempotent backfill lifts the corpus once the registry ships. The ctx projection reads state from `workflow_status` (terminal ⇒ closed, else open) when the registry resolves, and from `metadata.forge_state` otherwise — so a freshly pulled issue projects to exactly its forge state (`ctxH == base` byte-identical, the golden gate) in both modes. Over-cap bodies are truncated on a rune boundary + flagged `metadata.truncated` (§5.5), and the hash runs over the truncated bytes so a >50 KB issue does not drift.

**References edges (§4.5.7).** Issue/comment bodies are parsed for `#<nr>` tokens; each resolves via the mapping to a target block and gets a `references` edge in `context_structural_links` (class `references`, origin `forge-sync`, idempotent via the PK). An unknown number yields **no phantom edge** (the next run that pulls the target adds it); self-references are dropped. Zero forge requests — pure local parsing. Comments pull on their own leg (`sync_cursor.comments.{etag,since}`) after the issue leg (so the parent issue mapping exists); a comment whose parent is not yet pulled is skipped and picked up on a later run.

**I-H is the PUSH pass (`forge.Pusher`), the mirror of the pull.** It runs as a third sync leg AFTER both pull legs (§4.5.3: "on GitHub's return the next run drains ctx-ahead via push"), gated fail-closed by `push_enabled` (default **false**, §5.6 — a fresh repo is pull-only until an explicit tenant-admin toggle) AND a resolved token (a write needs auth). A mapping is a push candidate iff it is **not conflict-flagged** and either `forge_id=0` (a local draft) or the block's `updated_at` is newer than the mapping's `synced_at` — because the pull already set `base := forgeH` for anything the forge changed, a surviving `base != ctxH` is by construction **ctx-ahead** (`base == forgeH`), so the push needs no extra fetch to decide direction. Cases: **create** (`forge_id=0`) ⇒ POST the issue, then in ONE transaction write `forge_id`, rename `#L<seq>`→`#<nr>` (block title) + cascade the comment titles `#L<seq>.cL<n>`→`#<nr>.cL<n>` (one UPDATE, identity-neutral — the mapping is the identity) + `base := ctxH`; **update** (`forge_id>0`) ⇒ a **field-diff** PATCH carrying only the projected fields that diverge from the last-synced snapshot, so a local status flip pushes `state` and **never** the body; comments push AFTER their issue (CreateComment needs the forge number). Idempotent: after a create/update the mapping is in-sync (`updated_at==synced_at`, `base==ctxH`), so a re-run drops it — no double-rename, no base drift. Milestone is never pushed (it needs a forge milestone *number*, and there is no local milestone-edit surface, §4.5.7). The 3-way base snapshot is persisted per base write (`context_project_sync_map.metadata.base_fields`) — the field-diff compares VALUES, not just the opaque `base_hash`.

**Push data-loss guard (§4.5.2).** An entity with `metadata.truncated=true` HARD-excludes `body` from the push: a status flip on a truncated issue PATCHes `state` **without** the body, and if the (truncated) body is what diverged the entity is flagged **conflict** and written NOWHERE — the 50 KB cap must never overwrite a 64 KB forge body (up to ~15 KB of foreign content). Conflict-flagged mappings and `push_enabled=false` both mean **zero wire writes**.

**Push throttle (token-scoped, §6.1).** GitHub's 80 content-POSTs/min secondary limit is per **credential**, not per repo, so the push throttle is an in-process token bucket (`forge.Throttle`) keyed on the credential — repos sharing one PAT draw from ONE bucket (2 repos on 1 PAT with per-repo buckets would sum to 2× and trip a 403 cascade). **Deviation from §6.1's literal "token_secret name" key:** under masterplan K14 each project seals its OWN secret (`forge.token.<project_id>`), so the *name* is per-repo; to realise the per-credential intent the key is `forge_kind + sha256(resolved PAT)` (in-memory, never logged). The bucket steady rate (30/min, burst 30) keeps any 60-second window under the 80/min limit. When the bucket runs dry the pass STOPS (batch-wise) and the rest drain on the next run; a push wire/rate-limit error backs off exactly like a pull (never a conflict).

## Principal identity (migration 094)

The identity layer on which the three auth paths converge — `api_key` bearer, OAuth token (Achse 03), external-login session (Achse 04/05). `context_principals` (`id`, `display_name`, `primary_email`, `is_active`) is the **person**; `context_api_keys.principal_id` is `NOT NULL FK ON DELETE RESTRICT` (one key belongs to exactly one principal — no rights-bearing orphans, a principal hard-delete requires prior key deactivation). `context_external_identities` (`UNIQUE(issuer, subject)`, `ON DELETE CASCADE`) holds the external-IdP link that Achse 04 fills under INV-C (allowlisted+validated issuer, never the raw `iss` claim). Decision **E1=B′** (Big-Bang with *additive* audit, DECISIONS.md): the 12 audit FKs keep `api_key_id` (key/client forensics) and gain `principal_id` additively (person attribution) — no information loss (that additive FK wave is migration 096).

The backfill is **green-field** — every existing key gets its own fresh principal (10 keys → 10 distinct principals, 1:1). It runs `WHERE principal_id IS NULL` and is guarded by `pg_advisory_xact_lock` at the migration body: the runner takes no global lock before a migration, so two ctxd instances starting in parallel could both pass the applied-check and double-backfill — the advisory lock serialises the body, the second instance blocks until commit and then finds nothing to backfill. Every step is idempotent (`CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`, `SET NOT NULL` no-op, FK behind a `duplicate_object` guard). Migration 094 ships the **schema only** (`ctx_auth()` untouched, existing auth byte-identical); **migration 095 (F2)** wires the convergence. `ctx_auth()` now RETURNs `principal_id` as its last column (append pattern — every named SELECT stays valid, old binaries read the first ten columns) and enforces a **third** fail-closed gate: the principal must be `is_active` — the revoke-all mechanism (`is_active=false` locks every key of a person key-agnostically, no key-by-key deactivation). The inner scope build is factored into **`ctx_auth_by_id(uuid)`**: `ctx_auth(plaintext)` resolves `key_hash→api_key_id` and delegates via `RETURN QUERY`, and Achse 03 (token at `/mcp`) + Achse 05 (browser session) resolve their `AuthResult` through the **same** function — no gate-drift twin, since the three gates (key `active`, tenant status, principal `is_active`) + the `last_used_at` write live in one place. The soft-revoke negative gate (`active=false` → no `AuthResult`) is pinned in the by-id UPDATE's WHERE, so a session/token path can never bypass the `active` clause. `AuthResult.PrincipalID` surfaces at `/api/whoami` (`principal_id`) and threads into `dispatch.Principal` as an identity dimension — carried like `TenantID`, **not** the fairness key (`fairKey` stays `HomeScope`), so scheduling is byte-unchanged. The invariants are binding on 03 and 05: **INV-A** (one `AuthResult` = one key, a multi-tenant principal never unions scopes across its keys), **INV-B** (`principal_id` is never an authorisation gate — tenant isolation + scope filter stay the sole decision), **INV-C** (issuer trust, above).

**Migration 096 (F3)** delivers the additive audit-FK wave: the 12 audit FKs on `context_api_keys` (11 tables; `context_secrets` carries two) keep their key anchor and gain a nullable person anchor (`api_key_id` → `principal_id`; `X_by` → `X_by_principal`), FK → `context_principals` with NO ACTION — mirrored on the existing key FKs. The write paths do **not** thread `PrincipalID` through Go signatures: each INSERT/UPSERT derives the person anchor in SQL from the acting key (`SELECT principal_id FROM context_api_keys WHERE id = <acting key>`) — key→principal is 1:1 `NOT NULL` since 094, so the two anchors can never drift apart (INV-A: the acting principal IS the key's principal). Existing rows are NOT backfilled (F3 gate "Bestand unverändert"): historical person attribution stays derivable at any time via the retained key anchor (the NO-ACTION FK blocks key deletes while audit rows reference them — no data-loss window). `context_write_log` gets the column schema-only: its two writers (guard, dream) are internal paths without an acting key.

**Migration 098 (OAuth S1)** makes the authorization-code store persistent: `context_oauth_codes` replaces the process-local in-memory map, so codes survive restarts and redeem across instances (HA). The row stores `code_hash` (SHA-256, never the plaintext code) plus the INV-A single-key selector `api_key_id` + `principal_id`; single use is an atomic `DELETE … RETURNING` (two racing `/token` calls get exactly one row), and a janitor-tick GC sweeps expired rows (correctness never depends on the sweep). The transitional `api_key_sealed` column (code-derived AES-256-GCM, S1→S3 bridge for the api-key passthrough) is dropped by migration 099 — S3 mints opaque tokens from `api_key_id` and never needs the plaintext key again.

**Migration 099 + S3 (OAuth W03-3)** land the **universal opaque-token store** `context_access_tokens` — per the E-03h reconcile the ONE credential store (Achse 05 builds no second one; its web overlay `context_web_sessions`, migration 102, only FKs onto these rows; a login mints `issued_via='login'` rows with `audiences=[ctx-mcp, ctx-web]` into this same table → a login token is structurally MCP-capable, E2). `/token` now answers with an **opaque, revocable `ctxt_` access token** (SHA-256 in DB, TTL 1h per E-03c; `expires_in` in the response; the refresh token + rotation follow in S4) — the raw api key no longer circulates through OAuth-client token storage. Resolution is the shared **`resolveCredential`** gate used by the Auth middleware AND both SSE in-stream re-auth ticks: prefix branching on the raw extracted value **before** `SanitizeKey`, header-agnostic (`X-Context-Key` or Bearer); a `ctxt_` miss never falls back to the raw-key path, `ctxr_` is rejected outright, and a pure-hex value takes the byte-identical pre-S3 raw-key path (raw keys stay valid as Bearer — deliberate E2 legacy behaviour, documented spec deviation). Both paths materialise through `ctx_auth_by_id` (095): a soft-revoked key or deactivated principal kills its tokens instantly, no token-side revocation bookkeeping. Rows carry `audiences` (RFC 8707 — the membership check at `/mcp` lands in S5) and the `refresh_family`/`parent_id` lineage columns; a janitor-tick GC sweeps rows 7 days past expiry (the long grace preserves reuse-detection evidence).

**S4 (OAuth W03-4, Go-only)** adds the **refresh grant with rotation and reuse detection**: the code exchange now mints an access+refresh pair (one fresh `refresh_family`; TTLs per E-TTL — access 1h, refresh 30d rolling, family absolute cap 90d; overridable via `CTX_OAUTH_ACCESS_TTL`/`CTX_OAUTH_REFRESH_TTL`/`CTX_OAUTH_FAMILY_CAP`, fail-safe to the defaults). A `refresh_token` grant atomically takes the presented refresh (the take predicate carries the client binding — a wrong-client presentation is a side-effect-free miss, so a value-sniffing third party cannot revoke the victim's session by spraying client_ids) and mints the successor pair chained via `parent_id` in the same family. Presenting an **already-rotated** refresh is the theft signal: the **whole family is revoked** (both directions of the race are indistinguishable, so the human re-authorizes); the wire answer stays the generic `invalid_grant` — detection is logged server-side, never oracled to the caller. A capped-out family (anchor older than the 90d cap) refuses rotation and is revoked as hygiene; a rolling refresh TTL never outlives the cap. `grant_types_supported` now advertises `refresh_token` — the C3 coupling rule applied in both directions (advertise exactly what is served).

**S5 (OAuth W03-5/6, Go-only)** hardens the endpoint parameters and completes discovery: `code_challenge_method` MUST be `S256` (plain AND absent → 400 — RFC 7636 defaults absent to plain); RFC 8707 `resource` is validated at `/authorize` and `/token` (ctx is a single-resource server — anything but the canonical `<issuer>/mcp` answers `invalid_target`, and only the validated value ever reaches the code row); `redirect_uri` rebind at `/token` (presented-but-different → `invalid_grant`; absent is accepted — OAuth 2.1 drops the token-side requirement in favour of the enforced PKCE). At `/mcp` the token path now enforces the RFC 8707 **audience membership check** (token `audiences` must contain the canonical MCP resource; requires `CTX_CANONICAL_ISSUER` — unset skips the gate, since no trustworthy expected value exists; raw api keys bypass it by design, the documented E2 deviation). The 401 carries `WWW-Authenticate: Bearer resource_metadata="…", scope="mcp"` (RFC 9728 §5.1 — MCP clients bootstrap their flow from this header), discovery advertises `scopes_supported: ["mcp"]` (E-03d: a requestable label, never an authorisation input — INV-B), and the protected-resource metadata answers under both the root and the RFC 9728 path-insertion form (`…/oauth-protected-resource/mcp`).

**S6 (OAuth W03-7, Go-only)** completes the server strand by wiring the 097 client model into enforcement: at `/authorize` a client with **registered `redirect_uris` is matched exclusively against them** (exact array membership via the C2 lookup — no loopback rule, no static fallback: the registration is the contract, and a fallback would let a narrowly registered client escape to the broader static list), while an empty registration (plain `ctx mcp add`, pre-097 rows) keeps the static S2 allowlist + RFC 8252 loopback rule. At `/token` the registered `token_endpoint_auth_method` is enforced for **both grants** before any code/refresh handling: confidential clients (`client_secret_basic`/`client_secret_post`, secret via either advertised channel) must authenticate — the stored SHA-256 hash is compared **constant-time in Go** (`subtle.ConstantTimeCompare`, never matched in SQL); public `none` clients presenting a secret fail closed, as does a Basic username contradicting the form `client_id`. Failures answer `invalid_client` **401** (with `WWW-Authenticate` on the Basic path, RFC 6749 §5.2) and never touch token state — a wrong-secret attempt cannot revoke a refresh family. An unregistered `client_id` without a secret still falls through to the S2/S4 binding checks (`invalid_grant`, the no-oracle path).

**S2 (Go-only, advisory core fix)** closes the GHSA-p3jf-x27v-4jg6 core (credential takeover via attacker-controlled `redirect_uri`, PKCE does not help — the attacker holds the challenge/verifier pair): `client_id` is **mandatory** at `/authorize` (the anonymous flow is gone) and always validated; `redirect_uri` must match a **static exact allowlist** of the known claude.ai/claude.com/ChatGPT callbacks (extendable per deployment via `CTX_OAUTH_REDIRECT_EXTRA`; loopback per RFC 8252 §7.3 stays allowed by rule; since S6/W03-7 the static list is the fallback for clients without registered `redirect_uris`); `/token` enforces the **`code.client_id == presented client_id` binding** (OAuth 2.1 §4.1.3 MUST — for public clients this equality is the only client binding there is). The RFC 9207 `iss` parameter and the discovery documents use the configured canonical issuer (`CTX_CANONICAL_ISSUER`, compose-derived from the proxy hostname) — never an `r.Host` derivation, which would be client-influencable and defeat the mix-up protection.

**Migration 097 (OAuth C1)** lands the OAuth 2.1 client model on `context_oauth_clients`: `redirect_uris` (exact allowlist, no wildcards), `scopes` (requestable **ceiling** — never authoritative, INV-B: the key authority stays the hard cap), `grant_types`, `response_types`, `token_endpoint_auth_method` (`none`/`client_secret_basic`/`client_secret_post`), `registration_source` (`admin`/`dcr`/`cimd`), `metadata` (RFC 7591 low-prio fields), `updated_at`, plus `client_secret_hash DEFAULT ''` so DCR public clients insert without a secret (an empty hash is never a valid secret — the 03 wiring checks `auth_method != 'none'` before any comparison). All defaults are behavior-neutral: existing clients keep `redirect_uris='{}'` and the static S2 allowlist stays the enforcing layer until 03 wires per-client matching (S6/W03-7). Data only — the store/CLI (C2), metadata advertisement (C3) and DCR `/register` (C4) consume it in later waves.

**Migrations 100+101 (OAuth L1)** open the consumer strand (external login, Achse 04) — schema only, zero consumer code active, existing auth byte-identical. `context_oauth_providers` is the **allowlist carrier** for INV-C: only registered IdPs are trusted, the expected issuer always comes from this config row and never from a raw `iss` claim; `slug` is CHECK-pinned to the sealbox name regex (the client secret lives AES-256-GCM-sealed in `context_secrets` as `oauth_provider.<slug>.client_secret`, never in the row), `single_tenant_issuer=false` requires an `allowed_claim` filter at runtime (Azure `common`/Google without `hd` — fail-closed, provider stays inactive without it). `context_sso_states` ports the battle-tested single-use login-state pattern: DB-backed (HA — login starts on instance A, callback lands on B), consumed via atomic `DELETE … RETURNING` keyed on the httpOnly-cookie row id (double-UUID: the URL `state` param is a second UUID inside `state_data`, so the consume key never appears in IdP logs/referrers), `purpose` (`login`/`link`) blocks cross-use. `context_external_identities` gains display-only `last_login_at`/`display_name` (never trust anchors) and a principal index.

**internal/oidc (OAuth L2, Go-only)** is the OIDC/OAuth consumer library for external login — a pure lib with zero active callers (the flow handler mounts in a later wave), ported from the hand-written serviceportal consumer and generalized to a provider abstraction: one `Provider` interface, two shapes of IdP. The discovery/JWKS cache carries TTL 5min/10min, singleflight (a login storm never thundering-herds the IdP), timeout + 1 MiB body cap + non-200 reject without negative caching. ID-token verification is parameterized instead of hardlocked: `alg ∈ id_token_algs` per provider (RSA + EC key material; alg:none and HS/RS key confusion rejected before key lookup), `iss` must equal the **configured** issuer, `aud` must contain the client_id — with multiple audiences `azp == client_id` is additionally enforced (OIDC Core §3.1.3.7) — `exp` required, `nonce` bound to the login round trip, email only surfaced when `email_verified=true`. The Entra `tid` check generalizes to the `ClaimFilter` hook (`allowed_claim` `{claim,values[]}`, enforced after the cryptographic verify). The generic OIDC provider enforces `doc.issuer == configured issuer` before any discovered endpoint is used (substitution guard); the GitHub provider is the deliberately divergent proof of genericity — fixed endpoints, no ID token, identity via `/user` + `/user/emails` (subject = stable numeric id, email only when `verified=true`, a failing emails call is a hard reject, not degraded data).

**C3 (Go-only, discovery metadata)** extends the RFC 8414 document under the §4c coupling rules: `token_endpoint_auth_methods_supported` advertises `none`/`client_secret_basic`/`client_secret_post` (no `private_key_jwt` — no jwks path in the MVP; constant-time secret enforcement at `/token` is 03/S6), `client_id_metadata_document_supported: false` (CIMD is post-MVP), and `registration_endpoint` appears only when `CTX_OAUTH_DCR_MODE` (`open`/`admin`, anything else fails closed to `off`) is switched on — the `/register` route lands in 02-W4. Deliberately absent: `scopes_supported` (no enforced catalog exists) and `refresh_token` in `grant_types_supported` (03/S4 issues it later) — the discovery document never advertises what the server does not do.

**C4a (Go-only, DCR /register)** serves RFC 7591 Dynamic Client Registration on an always-mounted `POST /register`; `CTX_OAUTH_DCR_MODE` gates per request (`off` → 404 and no advertisement — the fail-closed default; `admin` → server-admin bearer key in the handler itself; `open` → unauthenticated, production-gated on the consent screen K7). `redirect_uris` (required, ≥1) run through the same registration rule as the CLI path (`validateRegisteredRedirectURI`: https for real hosts, plain http only on loopback — the §4b core fix, since this list is what 03 matches exactly at `/authorize`); `response_types` ⊆ {`code`}, `grant_types` ⊆ {`authorization_code`,`refresh_token`}, `token_endpoint_auth_method` ∈ the advertised set with default `none` (a deliberate deviation from the RFC 7591 default `client_secret_basic` — the MCP client population is public-client-PKCE-dominated); anything else is a 400 per RFC 7591 §3.2.2. `client_name` truncates to the label column (no 22001), `scope` lands as requestable ceiling (INV-B: never authoritative — open registration grants zero data access), the low-prio URIs ride in the 097 `metadata` jsonb. Confidential registrations get the `client_secret` echoed exactly once with `client_secret_expires_at: 0`; `registration_source='dcr'`, `created_by` = acting admin key or NULL (open).

**C4b (Go-only, DCR guardrails)** layers pure resource protection over `/register` — INV-B already makes registration authority-free, this is table-DoS defense only. Guard 1: a process-local fixed-window per-IP rate limit (`CTX_OAUTH_REGISTER_RATE`, default 10/min/IP) before any body work; the source IP is `RemoteAddr`, and only when `CTX_TRUSTED_PROXY` is set AND `RemoteAddr` matches that hop does the **last** `X-Forwarded-For` entry count (the hop's own appendix — every other XFF position is client-forgeable by rotation and never consulted). Guard 2: the hard row cap (`CTX_OAUTH_MAX_CLIENTS`, default 10000) → 403, checked after validation and before insert — the backstop that holds even when IP counting is evaded (and across instances, where the in-memory limiter divides). The rate-limit log line carries the IP: that is the forensic trail for open-mode registrations (`created_by` is NULL there). Inactivity GC is deliberately not built — the table has no honest usage signal (`context_oauth_codes` rows die on redeem/expiry), and a `created_at`-keyed GC would delete active clients; revisit once 03's token store leaves a last-used trace.

**SSO state store (OAuth L4, Go-only)** is the Go layer over `context_sso_states` (schema above, L1): `StoreSSOState` generates the opaque row id server-side — never the OAuth `state` param (double-UUID) — and `ConsumeSSOState` is the atomic single-use `DELETE … RETURNING` keyed on that cookie row id, filtered by `purpose` and `expires_at`. Every miss (replay, cross-use, expiry, malformed id) is the same silent `(nil, nil)` — no oracle for which check failed. A janitor-tick sweep evicts rows an hour past expiry; correctness never depends on it, consume checks expiry itself.

**Provider store + admin actions (OAuth L3, Go-only)** wire migration 100 to an operator surface: `internal/store/oauth_providers.go` (create / list / get-by-slug / delete) plus the manage actions `oauth-provider-create/list/delete` — all three `tierServerAdmin` (the provider table is the INV-C trust anchor: whoever writes it decides which issuers ctx trusts; pinned by the S9 enumeration gates). The `client_secret` travels only in the create payload, is sealed via the existing sealbox stack into `context_secrets` (`oauth_provider.<slug>.client_secret`, scope `_global` — the migration-100 slug CHECK keeps every legal slug `ValidSecretName`-compatible) in the **same transaction** as the row insert, and is never echoed; list/get expose secret existence only as a `has_secret` bool. Create validates fail-closed **before** any write: `token_auth='none'` (public client, PKCE-only) rejects a configured secret and every other method requires one; `single_tenant_issuer=false` without a well-formed `allowed_claim` (`{claim, values[]}`, strict decode — unknown fields rejected) is refused, since the schema deliberately carries no DB CHECK for that pair. Delete sweeps the sealed secret with the row (one transaction, no orphaned secrets). The login/callback flow handlers are a later wave — this surface is config only.

**External login flow (OAuth L5, Go-only)** mounts the consumer routes `GET /auth/login/{provider}` + `GET /auth/callback/{provider}` in the public route region (they ARE the auth flow) and wires L1–L4 into the actual round trip. Login: allowlist resolve fail-closed (unknown, inactive and `single_tenant_issuer=false`-without-`allowed_claim` rows are an indistinguishable 404), PKCE S256 + `nonce` for OIDC only (a classic GitHub OAuth app gets neither — its replay protection is state single-use + one-time code), server-side sealed state with the **double-UUID split** (the `context_sso_states` row id lives only in an httpOnly `Path=/auth` cookie; the OAuth `state` URL param is a second UUID), `return_to` filtered against open redirects (`^/[^/\\]`, else `/`), `redirect_uri` derived from `redirect_base`|`CTX_CANONICAL_ISSUER` — never `r.Host`. Callback: cookie cleared immediately, atomic single-use consume, URL-`state`-vs-sealed-state match, provider resolved **exclusively** from the sealed state (a diverging URL `{provider}` is a hard reject — mix-up defense, OAuth 2.1 §4.15; RFC 9207 `iss` checked when present), IdP `error` short-circuits before any exchange, `client_secret` unsealed only for `token_auth != 'none'`, token exchange with timeout + 1 MiB body cap over an **ssrfguard-hardened client** (dial-time deny-list, same guard as forge/camo), identity verified inside the L2 provider abstraction, then `(issuer,subject) → principal_id` with `verified_at`/`last_login_at`/`display_name` refresh and email refresh only when the provider marked it verified. An unknown verified identity is a neutral 403 (E4b admin-invite — no auto-create, no email-based auto-link), every other callback reject is ONE generic message (no oracle). Both routes sit behind a process-local per-IP fixed-window rate limit (X-Forwarded-For honored only behind `CTX_TRUSTED_PROXY`). The success response is a handover **stub** — `principal_id` carries no authority (INV-B); the session issuance replaces it in the Achse-05 wave.

**Migration 102 (OAuth R1)** lands the web overlay `context_web_sessions` (E-05-3 variant (a): own table — CSRF/UA/IP are web-only noise on the universal token table) — schema only, zero Go changes, existing auth byte-identical. The overlay holds **no token cleartext and no token hash**: cookie binding runs through `access_token_id` (FK onto the ONE 099 token store; INV-A — exactly one token row, exactly one `api_key_id`, which lives on the token row and is never duplicated here), `principal_id` is audit/whoami only (INV-B, never an authorization input), and `refresh_family` (NOT NULL here, nullable in 099 — a web session only exists with refresh lineage) lets the cookie rotation follow the 03 lineage while `csrf_secret` (per-session synchronizer token, server-side) stays stable across rotations. Instant revoke does NOT ride the FK-CASCADEs — key revoke is a soft-delete (`active=false`), the overlay row survives it and the per-request resolver (`ctx_auth_by_id` gates) answers 401; the CASCADEs are cleanup netting for hard deletes (tenant offboarding) only. Store functions and session issuance follow in R2+.

**R2 (OAuth 05-W2/W3, Go-only)** wires the cookie-session resolution: a request with NO header credential falls through to the httpOnly `ctx_session` cookie (header ALWAYS wins — the §4.2 precedence), whose value is the `context_web_sessions` row id (v7 UUID, ≥74 bits randomness). Resolution runs overlay→token→`ctx_auth_by_id`: `ResolveWebSession` re-applies the token gates exactly as `LookupAccessToken` (`token_type='access'`, not revoked, not expired; write-on-read `last_used_at` stamp), then materialises through the SAME `AuthenticateByID` as the token and raw-key paths — a soft-revoked key or revoked token family kills its cookie sessions instantly, and every session miss is one uniform silent 401 (malformed ids folded before 22P02, NO fallback to the key path). The discrimination is an explicit `isSession` flag, never value-shape sniffing (a dashed UUID would SanitizeKey-strip into a key-shaped hex string). Both SSE re-auth seams capture `(credential, isSession)` at connect time and re-resolve the pair each tick — a cookie-carried stream dies with its session like a token-carried stream dies with its token. Session ISSUANCE (login/logout/CSRF synchronizer) lands in R3 — until then no route mints an overlay row, so the ambient cookie path has no live surface without its CSRF gate.

**R3 (OAuth 05-W4, Go-only)** adds the web-session lifecycle: `POST /auth/login` (key entry) mints a login pair through the SAME 03 mint path as `/token` (`issued_via='login'`, audiences carry the MCP AND web resource — E2: a login token is structurally MCP-capable, `client_id` NULL ↔ the rotation binding ""), lays the overlay row (32-byte csrf secret, ua/ip forensics) and sets both httpOnly cookies: `ctx_session` (overlay row id, Path=/, SameSite=Lax) and `ctx_refresh` (the `ctxr_` plaintext, Path=/auth so it never rides data requests, SameSite=Strict); the Secure flag derives from the canonical-issuer scheme, never from spoofable proto headers. `POST /auth/refresh` rotates through 03's `RotateRefreshToken` — reuse detection and the family kill are inherited, so a replayed refresh cookie revokes the whole family and the session dies with it — and repoints the overlay **family-bound in the predicate** (a refresh of family A can never capture a session of family B). `POST /auth/logout` revokes the family and deletes the overlay in one tx (idempotent). The CSRF synchronizer gate lives in the Auth middleware: cookie-path mutations (POST/PUT/PATCH/DELETE) must echo the per-session secret as `X-CSRF-Token` (constant-time compare, 403 otherwise); the secret reaches the SPA via the login response and a new `whoami.csrf_token` field (omitempty — header-credential responses stay byte-identical, and header paths are never CSRF-gated: the MCP-Bearer regression gate). Login sits behind the shared per-IP fixed-window limiter (the key-guessing surface).

**R5 (OAuth 05-W6, Go-only)** completes the SSO onboarding under E4b admin-invite: the `/auth/callback` handover stub is replaced by real session issuance — a linked identity resolves to its principal, `PickPrincipalKey` chooses the most recently USED active key ("continue where the person last was"; the R6 selector switches afterwards), the full `AuthenticateByID` gate set runs BEFORE minting, and the browser lands on the filtered `return_to` with the same cookie pair as a key-entry login. A principal with NO active key answers a fail-closed 403 and no cookie — SSO establishes identity, never authorization (INV-B), and a session row structurally requires a key (INV-A); the inactive-key shape is double-gated (pick predicate AND `AuthenticateByID` — a tautologised predicate alone cannot open access, probed). Provisioning is the operator surface `oauth-identity-link/list/unlink` (tierServerAdmin, S9-pinned): link binds `(provider_slug, subject)` to an existing principal with the issuer resolved server-side from the provider row (github → the fixed constant — the stored value always matches what the login path looks up), re-binding to a DIFFERENT principal is a 409 (unlink explicitly first — the account-takeover shape), and the login flow itself never creates identity rows.

**R6 (OAuth 05-W7, Go-only)** adds the multi-tenant key selector for principals holding keys across tenants: `GET /api/session/keys` lists the session principal's ACTIVE keys (label, tenant slug/display name, role, home scope — never a hash or plaintext) with the current one marked `active_now`, and `POST /api/session/select-key` switches the session onto another OWN key — cookie-path only (a header-credential request has no session to switch, 400) and CSRF-gated like every cookie mutation. The switch **mints a fresh token/session family** on the target key (same login shape: `issued_via='login'`, MCP+web audiences, new csrf secret) and only then destroys the old one — it never mutates `api_key_id` of an existing token row in-place, because that row may run in parallel as an MCP bearer (universal credential, E2) and would silently change tenant underneath it. Ownership is one fail-closed predicate (`active=true AND principal_id = session principal`; foreign, revoked, unknown and malformed ids are ONE 403 — no oracle, no 22P02), negativ-geprobt: tautologising the predicate turns the foreign-key gate red. INV-A holds through the switch — one key replaces one key, the post-switch `AuthResult` carries no scope of the previous tenant.

**R4 (OAuth 05-W5, web-only)** moves the SPA off the stored-key Bearer model onto the cookie session: the login mask POSTs the entered key to `/auth/login` and the raw key never touches client storage anymore (the old `sessionStorage['ctx.api-key']` is gone). The per-session CSRF synchronizer from the login response / `whoami.csrf_token` is held **in-memory only** (a JS-readable copy would undo the httpOnly hardening) and rides every state-changing `/api/*` request as `X-CSRF-Token` — GETs and the SSE streams send nothing extra, the httpOnly cookie is ambient. Page reload restores via a whoami probe over the cookie with ONE silent `POST /auth/refresh` fallback; a 401 on any data request gets the same single-flight refresh + one replay (concurrent 401s share one rotation — a parallel second rotation would trip 03's reuse detection and kill the family) before the interceptor tears down to the login screen. Logout POSTs `/auth/logout` and drops the in-memory token. Header-credential paths (X-Context-Key / raw-key Bearer for MCP and scripts) stay byte-identical and are never CSRF-gated.

**F4 (Go-only)** closes the mint window that 094's `NOT NULL` opened: both production mint paths — `insertApiKeyTx` (the single INSERT path behind `CreateApiKey`/`MintOwnerKey`/self-service/provision) and `BootstrapAdminKey` — mint a **fresh principal per key** in the same atomic statement (data-modifying CTE), the exact 1-key-1-principal semantics of the 094 backfill. A failed key INSERT rolls the principal back with it (no rights-less orphan); the bootstrap guard CTE gates both inserts, so a populated table yields zero principals AND zero keys with unchanged single-statement TOCTOU semantics. Linking a new key to an EXISTING principal (a person's second key) is a later, explicit flow (Achse 05 key selector / Achse 04 SSO onboarding) — never an implicit default.

## Guard (deduplication)

Async deduplication via PG LISTEN/NOTIFY + HNSW similarity. Policy-parameterised since migration 074 (WF T7): `ctx_guard_check` takes the thresholds + the candidate-type **allowlist** as mandatory parameters (NULL candidates ⇒ 0 matches; a legacy 1-arg call ⇒ loud 42883, no silent default fallback), plus a `p_same_scope_only` switch for same-scope dedup with `hnsw.iterative_scan='relaxed_order'` against filtered-ANN false-cleans. The batch picks only `guard.check=true` types (per-type thresholds via `guard.threshold_duplicate`/`_review`, seed defaults 0.98/0.92 = former literals), and the pending pick/count queries ride the partial index `idx_guard_pending` instead of full scans.

Two further per-type dimensions are resolved in Go and passed to every call **explicitly** — never relying on the SQL default (a forgotten parameter would silently re-open cross-scope matching): `guard.candidates` (`all` | `same-scope`) drives `p_same_scope_only`, and `guard.mode` (`archive` | `flag`) drives the persist branch. In `flag` mode a near-duplicate is recorded as a `possible_duplicate` flag (`guard_status` + `guard_matched_id`) and is **never** auto-archived — the issue axis (design/02 §4.7) surfaces duplicates instead of silently removing them, while the knowledge line keeps the `archive` + cross-scope bestand byte-for-byte. `hnsw.iterative_scan='relaxed_order'` is load-bearing only when the planner chooses the HNSW index (large same-scope sets); a selective scope is served exactly by `idx_context_scope`, where recall is unconditional.

**Review pipeline (guard W1–W4).** Flags are no longer pull-only. The grey zone (`needs_review`/`near_duplicate`/`possible_duplicate`) flows through a closed loop: **push** — `/api/status` carries a `guard_review` section on both auth paths (global vs. home-scope-filtered) and the daily report closes with a queue-stand section while flags are open (live reports only); **triage** — the SPA `/guard` page renders the pair view (flagged block vs. matched partner, similarity) with keep/archive and batch selection; **resolve** — `guard-resolve` accepts `data.ids[]` (one transaction, cap 500, every id accounted for as resolved or skipped+reason; the batch touches only flagged states — deliberately narrower than the single-id path, blast-radius line); **agents** — the MCP tools `guard_list`/`guard_resolve` are the third transport (REST parity; `archive` refused for `confirm_writes` keys, fail-closed). Flagged blocks keep ranking in retrieval until resolved — `ctx_rrf` reads no `guard_status`; changing that is a deliberate future eval-gated decision, not a side effect of this pipeline.

## Block-type registry (migration 072)

`context_block_types` is the declarative per-type behaviour registry of the workflow-engine line. The four M035 block-type classes (`knowledge`, `audit-trail`, `reference`, `system-meta`) ship as builtin seed rows (migration 072) whose JSONB configs reproduce today's hardcoded behaviour (retrieval damping, guard participation, dream linkability, digest/overview inclusion, classify rules); Welle I-C adds two more builtin rows (migration 084), the `issue`/`comment` workflow types, and migration 107 adds the `checkpoint` evidence type (see below). Migration 136 adds the two tool-evidence axes `tool-evidence` (damping 0.15, classify priority 19) and `tool-overview` (damping 0.35, priority 18) — like `checkpoint` they stay out of guard, dream, digest and overview, but unlike it they are `damped` rather than `excluded`, because they are answered by a QUESTION ("which command was that again?") instead of by an exact block ID; both priorities sit deliberately **below** `audit-trail`'s 20, since `Set.Classify` takes the first match ascending and the block title carries the root session name. Both also carry `retrieval.untrusted` (set by **migration 138**, a separate forward-only `jsonb_set` rather than an edit to the landed 136) — the presentation-side flag that marks a type as **foreign text** (tool output an attacker can shape, not knowledge somebody wrote): `Set.IsUntrusted` resolves it per source and the synthesis prompt then renders that source as `trust="untrusted"` and adds one framing sentence (see [Backend pool](#backend-pool-f3-migrations-053055)). Absent = `false`, so every other type is unaffected; on an `excluded` type the flag is inert but valid. **Migration 141** puts `checkpoint` in the same class, and being excluded is precisely why: transcript prose reproduces tool output, fetched web content and foreign agent prompts, so it is foreign text in exactly the sense the flag names — it simply never needed the framing while the type reached no prompt. It is set now because a **derived** type that distils checkpoints has to read the property AT ITS SOURCE, under a fail-closed rule (untrusted unless every source class is provably first-party); with `checkpoint` unflagged that rule would answer "first-party" and the derived layer would launder foreign text into knowledge. The migration touches `{retrieval,untrusted}` only — the policy stays `excluded`, so no ranking, no visibility and no rendered answer changes today. The daemon starts on a compiled-in builtin set, overlays the DB rows at boot (merge — a deleted builtin row can never blank the default type) and hot-reloads on any table write via the same NOTIFY channel the settings use; edits via `psql` take effect without a restart.

A boot that finds the table but cannot load it (corrupt row) degrades **loudly**: `/health` carries `blocktype_registry: "builtin-fallback"`, the overall status drops to `degraded`, and a 30s retry loop self-heals once the row is fixed.

**Checkpoint evidence type (migration 107).** `checkpoint` structurally anchors ID-referenced evidence chains — compaction-checkpoint manifests plus their transcript source parts, written by external agent plugins before a lossy context compaction. That repair only ever reached the rows M107's own title rule matched — **migration 121 repairs the head corpus** the same way, in the same order (retype first, un-archive second), with a third guard on top: only rows the retype actually turned into `checkpoint` are un-archived, so a head an operator typed by hand (`type_source='manual'`) stays `knowledge`, stays guard-checked and stays archived instead of being handed straight back to the archive lane. Unlike M107 the repaired rows land on `guard_status='active'`, not `needs_review` — their guard freedom is structural by then, so there is nothing left for a human to decide; `metadata.guard_repair='M121'` carries the audit trail instead.

Since T10 the registry is **API-exposed** (no schema change) via the `type-*` manage family: `type-list`/`type-get` are open reads (scoped to `_global` ∪ the caller's own tenant namespace), `type-create`/`type-update`/`type-delete` are server-admin (tier 1: only the shipped `_global` namespace is writable). Configs are validated by the SAME decoder the reload path uses (422 with the offending key path); builtin rows are undeletable (their config IS editable), a delete is refused while ANY block references the type, and every mutation runs in one attributed transaction (`via='api'` + acting key) followed by a synchronous reload. Since T9 (migration 075) the legacy `is_meta` column + index dropped — the third type axis consolidated into the registry (`metadata.is_meta` survives as a JSONB classify-input key only).

**Tenant overlays (Stufe 2, WF T12 — no migration; the schema carries `UNIQUE(name, scope)` since M072).** On top of the `_global` base generation the registry keeps a lazy per-tenant cache — the exact `config.Store` overlay mechanism (immutable snapshot behind an atomic pointer, a monotone `baseGen` stamp per cached generation, single-flighted MISS builds, O(1) cache wipe on a base reload). `SnapshotForTenant(scope)` / `SnapshotForRequest(ctx)` resolve `_global ∪ tenant`, where a **tenant row WINS** on a name collision (**D6: "Overlay gewinnt" v1** — no monotonic narrowing; the alternative that would forbid a tenant lifting a `_global`-excluded type is a named open decision, pinned by a semantic-fixier test so a later flip is a visible break). A tenant with no own rows inherits the base pointer byte-for-byte, so the single-tenant / default-tenant server is functionally identical (zero per-tenant generation footprint). The request path derives the tenant scope from the auth context (never a caller argument, §5.4); a tenant-scope registry write drops **only** that tenant's cached generation via the NOTIFY dispatch (`InvalidateTenant`), while a `_global` write bumps `baseGen` and wipes the whole tenant cache. **Consumer reach:** request handlers (RRF/graph) resolve per caller tenant; the background **dream** and **digest** loops resolve per iterated tenant — the dream `PickBlock` is bound to the iterating tenant's scopes (`scope = ANY(owned)`) so tenant A's `dream.linkable`/allowlist never governs tenant B's blocks. The type policy is a **ranking/visibility** steering, **not** a confidentiality boundary (that stays scope + grants + sensitivity): a grantee's overlay steers the ranking of granted FOREIGN blocks too (Reader-Overlay wins). **Known Stufe-2 boundaries (documented, no leak):** the guard batch and the overview rebuild stay single global runs on the base allowlist (guard-state counts are global telemetry; overview visibility overrides need a per-tenant overview) — reads on both remain scope-filtered.

## Backend pool (F3, migrations 053–055)

`context_backends` replaces the hardwired primary+fallback pair with a declarative, role-routed, priority-ordered pool. Each row is one backend: `base_url`, wire `protocol` (`openai`/`ollama`/`rerank`), `provider_class` (`generic`/`llamacpp`/`openrouter`), a **trust level**, an egress `locality`, a `roles` list (`synthesis`, `translate`, `embed`, `rerank`, `dream`, `digest`, `chat`, `classify`, free-form), a per-role `model_map`, per-role `timeouts`, `priority` and `enabled`. Order/priority are pure DATA — no code path references backend names or priority constants.

`context_disable_profiles` + `context_disable_profile_backends` (092) add named **disable profiles** — a profile takes its member backends out of every chain while active (maintenance / eject use-case). Membership is a real FK join (no name matching, rename/delete-safe by CASCADE), profiles carry a `scope` (`_global` for operator profiles) with `UNIQUE(scope, name)`, and the migration backfills the legacy gaming toggle as the reserved profile `eject` (label „Eject-Modus“) — value and member set copied losslessly from `gaming.active`/`gaming.disabled_backends`. The pool loads profiles + memberships into the same atomic snapshot as the backends (ORDER BY name — the status frame's diffKey needs a byte-stable order). The chain-time exclusion arm is live: an active profile takes its members out of every chain (`disabled by profile <names>`, effective state `profile-disabled`, precedence disabled > profile-disabled > cooldown > active). Since U01-W5 the eject profile is the **sole** chain-time exclusion mechanism — the legacy `gaming.active`/`gaming.disabled_backends` settings keys and the parallel gaming arm were retired (the `gaming-mode`→`eject` alias shim stays as a compat surface, and the status payload's `gaming.active` field is derived live from the eject profile).

The table is the **only** source of truth. Nothing seeds it at boot: until an operator fills it — `ctx init`, `ctx backends seed`, or the web UI — it stays empty, and an empty pool is the ordinary, announced state of a fresh install (boot advisory `backend_pool: empty`, `/health` `unhealthy`) rather than a silent fallback to some default topology. The env bridge that filled it on a first boot until v4.38 is gone with the tuple keys it read (v5.0.0, see [operations](operations.md#environment-variables)). Multi-tenant scope isolation of the pool is documented in [multi-tenancy](multi-tenancy.md#backend-pool-isolation-egress); the trust × sensitivity gating and the OpenRouter ZDR guarantees in [security](security.md). CRUD is in [api](api.md#backend-pool).

**Synthesis on the pool chain** (054) — query-path synthesis walks the role chain from `context_backends` (priority-ordered, cooldown-sorted; the chain is the ONLY way to a backend, so the trust gate sits structurally before prompt transmission). Transport-class failures advance to the next backend (e.g. the `llama-cpu` sidecar at priority 10: same GGUF, CPU speed, its own per-role timeout); HTTP-500 and attempt timeouts stop the chain — the server *ran* the request, slow-but-alive is not down. The response heartbeat starts whenever synthesis is on (`synthesize != false`), so a CPU-leg answer survives buffering proxies even with rerank off. Since 055 the WHOLE query path resolves through the chain (translate, temporal, query-embed, rerank dispatch, inline backfill) with a real requirement: `max(query sensitivity, sensitivity of the FINAL prompt set)` — measured after rank filtering, so a credentials block on rank 180 that never enters the prompt cannot lock the failover. **Untrusted source framing** (W02-4) — a source whose block type carries `retrieval.untrusted` renders as `<source … trust="untrusted">`, and the system prompt gains exactly one sentence, spliced into the same `<security>` element as the promptguard nonce rule, defining such sources as **observation data**: quotable, never followed as an instruction, and never a fact about anything beyond that output. It is a truth-value rule, which is what the two pre-existing rules do not cover — they forbid FOLLOWING foreign text, not BELIEVING it. The sentence is added only when at least one untrusted source is actually in the prompt (a prompt without one is byte-identical to the pre-W02-4 rendering, which is what leaves the eval baseline untouched on a corpus with no foreign-text block), the budget pass charges it before the source set is fitted, and the type name never reaches the model — only the trust class does. An empty dream chain (gaming/disabled/trust) skips the cycle BEFORE the block pick — no claim, no cooldown touch, so a gaming session never smears the back-off statistics.

**Rerank sidecar.** Post-RRF rerank (`rerank.enabled`, ships off, fail-open) via a local **bge-reranker-v2-m3** cross-encoder sidecar (`http://ctx-rerank:8082`, cohere-style `/v1/rerank`, all-local/$0) — a pool row of role `rerank` like any other backend — or LLM-as-judge on the chat model when the pool serves no such row. Voyage AI rerankers (`rerank-2.5`/`-lite`) work as a remote alternative: the client accepts their OpenAPI dialect — results under `data` instead of `results`, `usage.total_tokens` instead of `prompt_tokens` (the same total_tokens dialect is accepted by the OpenAI-protocol embed client) — and maps Voyage's calibrated [0,1] relevance through logit() at the wire boundary, so the raw-logit score contract (and the downstream sigmoid+blend) is backend-invariant. Container name and score domain are coupled backend properties — by default: the backend row's `metadata.score_domain` slot (`auto` | `logit` | `probability`, default `auto` = the container coupling) overrides the interpretation for dialect-mixing backends (a gateway speaking `results` but scoring probabilities, or vice versa). A probability-domain score outside [0,1] or an entry missing `relevance_score` errors → fail-open to the pre-rerank order. The surface-gold counter-probe showed the cross-encoder earns its keep (nDCG@10 +0.164, MRR +0.169) while blend 0.5 keeps it neutral on latent gold — `graph+ce-bw0.5` is the best arm on both gold sets; the ~80–90s query path stays proxy-safe via the body heartbeat.

## Supporting mechanisms

- **Digest freshness state (retired, migration 129)** — `context_digest_state` plus `trg_digest_dirty`/`mark_digest_dirty()` from the initial schema are gone. The table was verified dead (no Go consumer; the scheduler keeps its dirty flag in memory), but the trigger still fired on **every** block write and updated a SINGLETON row — one shared row lock per writer, i.e. a pure serialisation point at target scale with nothing on the other side of it. Two historical timestamps were dropped with it, deliberately and by explicit decision. Drop order is load-bearing (trigger → function → table): the function resolves its table by name at execution time, so a table dropped first would break not the migration but every subsequent write.
- **Supersedes filtering** — temporal-gated removal of outdated blocks from query results.
- **Transport retry** — all inference HTTP calls (chat ollama/openai, embed, rerank) retry exactly once on transient transport failures (connection reset / EOF before any response bytes) via `internal/httpx`. Covers the keep-alive race with llama.cpp's cpp-httplib servers (~5s idle close vs Go connection reuse); HTTP status errors and context deadlines are never retried. Inference POSTs are stateless, so a replay is safe.
- **Streaming tool-call wire** (`llm.ChatStream`) — streaming OpenAI-compatible chat with function calling: multi-turn message arrays, per-delta events, index-keyed tool-call assembly, arguments normalisation (llama.cpp JSON-string fragments and whole-object form yield identical calls), hardened against OpenRouter SSE comment frames and mid-stream error events inside HTTP-200 streams; usage falls back to llama.cpp `timings` incl. MTP draft-acceptance. Drives the web-chat harness (see [api](api.md#web-chat-sessions)). Since issue #26 the **non-streaming** chat path carries the provider stop reason too (`ChatResponse.FinishReason`, decoded from Ollama `done_reason` resp. OpenAI `choices[0].finish_reason`, raw and unnormalised, `""` when the provider reports none) — until then only the SSE path saw it, which left every background pipeline unable to tell a `length` truncation from malformed output.
- **Embed cache** — content-hash-keyed embedding cache (`context_embed_cache`) to avoid re-embedding identical text across pipelines.
- **LLM log** — per-call request/response capture (`context_llm_log`) with input/output token counts (Ollama + OpenAI), dream-pipeline version tagging, and parse-format drift tagging (`metadata.parse_format`). The dream-eval rows additionally carry `metadata.links_parsed` (how many links the answer actually yielded — a legitimate zero-link "nothing relates" verdict is otherwise uncountable), `metadata.links_dropped_invalid` (how many of those parsed links the candidate filter rejected — non-UUID target, id outside the candidate set, unknown relationship type, out-of-range or below-floor confidence; written only when it dropped something. Paired with `links_parsed` it names a failure that is otherwise silent: a row reading *parsed n, dropped n* is a cycle in which the model did answer and nothing survived, yet it is booked **inert** onto the multi-day back-off exactly like an honest "nothing relates" verdict. Observability only — no cooldown or retry behaviour changes), `metadata.candidates_capped` (how many retrieved candidates the aggregate candidate cap — `MaxCandidatesPerKeyword * MaxKeywords`, the item count the prompt-budget gate models for this pipeline — dropped before the evaluation saw them; written only when the cap actually bound, and mirrored on the `dream: candidates found` log line as `candidate_cap_hit`/`candidates_capped`. Since issue #26 the flag is no longer heuristic-only and no longer observability-only. `metadata.finish_reason` carries the provider's raw stop reason whenever one arrives (on successful rows too — "which backends report one at all" is only answerable from the rows where nothing went wrong), and `metadata.cap_hit_source` says which signal produced the verdict: `finish_reason` when the provider stated `length`, `tokens` when it reported no stop reason and the completion count reached the cap. A cap hit now triggers **one bounded retry** at `dream.eval_cap_retry_factor` times the *resolved* cap — resolved meaning after a `model_map` `num_predict`/`max_tokens` override, because the scaling is applied where that override is (`llm.applyModelParams`); the retry sends the identical prompt and writes its own llmlog row, marked `metadata.cap_retry`, so token and cost accounting stays one row per wire call. A **second** cap hit is booked as a completed-but-inert eval (`dream_eval_count` + 1, `dream_last_inert`, `dream.backoff_inert_offset` on the curve) instead of the 5-minute transient cooldown: the transient path has no attempt counter, so a prompt that cannot fit would otherwise re-burn one eval call every five minutes forever. Two paths deliberately keep the old behaviour and never escalate: `dream.eval_cap_retry_factor` ≤ 1 (the kill switch) and a serving row whose `extra_body` pins a numeric `max_tokens` — that value outbids `Options.NumPredict` on the wire, so the retry would send the same cap; it is skipped, logged once, and the plain parse error returned.
