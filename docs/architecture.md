# Architecture

**Stack:** Go 1.27 (matches `go.mod` and the `golang:1.27-alpine` build image), PostgreSQL 18 + pgvector ≥ 0.8.7 + TimescaleDB ≥ 2.31.0 (the minimum versions of the schema manifest, `go/internal/schemacontract/manifest.json`). The SQL migrations are numbered from 113: `113_baseline.sql` folds every earlier file into one baseline, and each later change is one file after it. Multi-protocol inference (Ollama native, OpenAI-compatible, or the native Anthropic Messages API) via any provider — configured per role in the [backend pool](#backend-pool-f3-migrations-053055) (`ctx backends`), one row per backend (see [operations](operations.md#backends)).

## 4-Way RRF retrieval

Reciprocal rank fusion across four channels: **semantic** (pgvector, weight 0.45), **EN fulltext** (0.25), **DE fulltext** (0.20), and **trigram** title (0.10) — bilingual FTS + trigram.

The `ctx_rrf` SQL function is type-policy-parameterised since migration 073 (WF T5). It takes a visibility **allowlist** (`p_types_visible`, fail-closed — an unregistered/rogue `type_name` is invisible until a registry row carries it; NULL/empty ⇒ 0 rows, Go rejects the call before that) plus parallel damping arrays (`p_damped_types`/`p_damped_factors`) sourced per request from the block-type registry, which generalises the former hardcoded audit-trail scalar into query-aware intent lift. Results carry `type_name`; a registry edit (damping factor, intent patterns) changes rankings live via hot-reload — no restart, no migration. See also the multi-tenant grant param `p_granted_block_ids` (migration 068) in [multi-tenancy](multi-tenancy.md#block-level-grants-row-level).

Since migration 112 (Generation 15) the semantic channel is a **dual-arm CTE**: the production HNSW path (`p_semantic_mode='ann'`, default) and an exact brute-force arm (`'exact'`) for small scopes — recall 1.0, deterministic `(distance, id)` tiebreak, MATERIALIZED barrier so the HNSW index is structurally unreachable (proven by a `pg_stat_user_indexes` gate). The exact arm requires `p_exact_cap` and re-probes the scope size in-transaction (TOCTOU cap guard, SQLSTATE 54000 on growth — the caller degrades to ann); `p_scan_tuples` budgets the ann arm's `hnsw.max_scan_tuples` (grey-zone dispatch, Achse 02), bounded fail-closed in the SQL body. Both arms share one literally identical visibility predicate block, pinned by a permanent parity sentinel test. **Migration 134 (Generation 16)** closed the last asymmetry between them: `embedding IS NOT NULL` used to guard the exact arm only, so under a sequential-scan plan with fewer than 75 embedded candidates in scope the ann arm handed the remaining ranks of the heaviest channel (0.45) to unembedded blocks in heap order — they carry a NULL cosine, nothing downstream gates on it, and a block on semantic rank 5 outscores a perfect German full-text rank-1 hit by a factor of 2.1. That is the fresh-install and small-corpus path (new blocks are stored with a NULL vector and a content-changing upsert nulls an existing one until the backfill catches up), invisible under an HNSW index scan because pgvector does not index NULL vectors — Issue #40 Bug 5. The filter now sits in both arms, and the parity sentinel lost its NULL-embedding exception: the arms are set-equal. Generation 16 deliberately gives up the Generation-15 promise of byte-identical default behaviour for the ann arm — that promise protected a deploy sequence (migration and Go binary decoupled), and the semantics it was freezing were the defect itself. **Migration 139 (Generation 17)** closes the ordering hole the same function still carried: the final projection sorted by `r.score DESC` alone, so blocks with an identical fused score came back in whatever order the sort node produced — plan-, heap- and `work_mem`-dependent, and decisive whenever such a group crosses the `p_limit` cut; it now sorts `ORDER BY r.score DESC, cb.id`, the total order the exact arm has followed since Generation 15 (`cb.id` is the UUIDv7 primary key, so the oldest block wins a tie). Ties are not exotic and get denser with the corpus — a score is a sum of four reciprocal ranks times two factors, so equal rank combinations recur: the B-W1 fixture (220 blocks) carries exact ties in 13 of 54 queries. Candidate set and scores are byte-identical to Generation 16 (the change sits behind the entire fusion), and `ctx_rrf_arms` stays untouched because it neither fuses nor truncates. The Go-side selector that dispatches between the arms lives in `internal/rrf/selector.go` (W02-2): a LIMIT-capped index probe over `idx_context_scope_active` decides exact vs. ann per request, a probe failure or cap-guard trip degrades loudly to the ann path (the query is never lost). The grey stage is live since W02-4 (`selector_stats.go`): a TTL-cached, single-flighted pg_stats snapshot (schema-qualified catalog read with OID join — the cluster is shared with n8n/TimescaleDB) estimates mid-class scopes as MCV frequency × reltuples plus a residual for unlisted scopes, floored at the probe-proven `exact_max+1`; every §4.3b edge case (never-analysed `reltuples=-1`, ratio-form `n_distinct`, missing residual denominator, snapshot past 10×TTL) maps onto `stats_stale` → plain ann, the consequence-bounded direction. Migration 117 raises the `scope` column's statistics target to 1000 (+ANALYZE, ShareUpdateExclusive only) so the MCV list can cover a multi-tenant scope population — without it the sampling math routes the very mid-class the grey budget is built for straight past it. The policy arrives as a caller-supplied struct whose **zero value is off**. W02-3 wires it: the query path derives the policy from its ONE request snapshot (`cfg.SelectorRRF()`, same converter pattern as `RerankRRF`/`GraphRRF`) out of the new `retrieval.selector.*` group — `enabled` / `exact_max` / `grey_max` / `grey_scan_tuples` / `stats_ttl`, all `mut:hot` and **all global-only**, because both size knobs dimension buffer touch and materialisation of the SHARED database (the graph group's "zero cross-tenant effect" rationale does not carry here; a tenant opening is the separate wave W02-8). The dream path keeps passing the zero policy. **`enabled` ships FALSE** — the master gate opens as an operational settings flip after the Achse-01 recall evidence, not as a deploy — so the shipped wire behaviour stays the legacy 15-arg statement. Instrumentation is gated on the same flag: while the gate is closed neither the `rrf search complete` log line nor the `context_access_log` metadata differ by a byte from the pre-selector state; armed, they carry `selector_mode`/`selector_reason`/`selector_estimate`/`probe_ms` resp. the compact `sel_mode`/`sel_reason`/`sel_est` per result row — strategy metadata only, never content — as the Achse-01 correlation input (recall@k per mode × reason × estimate bucket straight out of the existing table).

**Migration 137 (`ctx_rrf_arms`)** adds a read-only sister function next to `ctx_rrf`, not inside it: same 18 parameters in the same order (plus five optional cap parameters whose defaults are the literals `ctx_rrf` hardcodes — semantic 75, FTS 100/100, trigram 30, trigram threshold 0.05), same prologue, same four arms, same `block_mass`/`type_factor` CTEs — but it stops before the weight expression and returns the **raw per-arm ranks** (`NULL` = not in that arm) plus the two multiplicative factors, and no content at all: only UUIDs and numbers, so a predicate mistake can leak at most the existence of an id. **Migration 142** adds a ninth return column, `type_name` — the block's registry classification, never its text, and something the same (necessarily admin) caller already gets from `GET /api/context/<id>`, so the leak budget is unchanged. It is there because `type_factor` is **not injective**: two damped types may share a factor and every undamped type carries 1.0, so only the name lets a dump answer what its own candidate set is made of and lets an offline sweep vary the damping per type instead of reading it off the row. The column sits at the end and reaches no score term; callers that project their eight columns by name are untouched, though `CREATE OR REPLACE` cannot grow an `OUT` list, so the migration drops and recreates the function (the argument list is unchanged). It is the provenance seam for the arm-weight sweep (Achse 04): the fusion can be recomputed offline with different weights without touching the live one. The duplicated body is guarded not by a comment but by a parity gate (`internal/rrf/arms_parity_integration_test.go`) that re-fuses the arm ranks in Go and requires them to reproduce `ctx_rrf`'s output row for row on a 220-block fixture across 54 queries in both semantic modes. Both calls must sit in **one transaction** — the ann arm's `SET LOCAL hnsw.iterative_scan` lasts to the end of the transaction, not the end of the call, so a split would let the two functions search different candidate spaces. `p_limit` is accepted and ignored (the function never truncates; the truncation is exactly what the sweep re-derives) and kept only for positional parity.

**Migration 140 (trigram KNN)** gives the fourth channel an index. Until then `trigram_title` filtered with `similarity(cb.title, p_query) > 0.05` and capped the survivors at 30 — a predicate no index carries: `idx_trgm_title` is a GIN (`gin_trgm_ops`), which serves `%` and `similarity` as a *filter* but never a `<->` KNN scan, so the arm was a sequential scan over the visible corpus on **every** RRF query. Switching the predicate to `%` would not have helped: over 60 real access-log queries `title % q` matches a median of 430 of 1 387 retrievable blocks (31 %), which is an unselective bitmap for a CTE that keeps 30. The arm now orders by `cb.title <-> p_query` over a new GiST index `idx_trgm_title_gist` (`gist_trgm_ops`), takes the cap inside that ordered scan, and applies the unchanged threshold as a post-filter — set-identical by construction (with ≥ 30 rows above the threshold the 30 nearest are the same 30; below it the post-filter cuts exactly the surplus), and measured at 100 000 rows the plan goes from a parallel sequential scan to `Index Scan using idx_trgm_title_gist` with `Order By: (title <-> …)` whose Limit costs 0.04 % of a full pass. Both `ctx_rrf` and `ctx_rrf_arms` carry the new form — an asymmetric change would make the parity gate measure a fusion that does not exist. What the migration also closes is an ordering hole the old form had: `ORDER BY similarity DESC` without a tiebreak left it undefined which member of a tie group survives the cap (live sample: 4 of 10 queries carry such a group at rank 30), so both the selection and the rank now carry `, cb.id` — the same total order Generation 15 gave the exact arm. The index build is guarded like migration 115's: present ⇒ no-op, so an operator may build it out-of-band with `CREATE INDEX CONCURRENTLY` first; under 500 000 rows the migration builds inline (1.9 s / 55 MB at 100 000 rows); above it the migration lands but only warns, because `CREATE INDEX` holds a SHARE lock for the build and `RunMigrations` sits in the boot path. Without the index the arm degrades to exactly the pre-140 sequential scan, never worse.

**The `arm_ranks` debug seam (B-W2)** is the HTTP path to that function, and it is deliberately narrow. `POST /api/query` accepts `arm_ranks:true` only from an **admin** key and only together with `synthesize:false` — non-admin is `403`, a missing `synthesize:false` is `400`, and both are refused before the rate-limit roundtrip, the sensitivity scan and every LLM stage. The flagged request runs `ctx_rrf` and `ctx_rrf_arms` in **one `REPEATABLE READ` / `READ ONLY` transaction** (`SET LOCAL statement_timeout` and `idle_in_transaction_session_timeout`, both 30s): one snapshot and one `SET LOCAL hnsw.*` state for both statements, and a transaction that is structurally incapable of writing. The response gains an `arm_ranks` block — the raw rows, the `fusion_order` as `ctx_rrf` handed it over (captured **before** gravity, cluster, graph, fold and truncation), the effective query/spaced/temporal strings, the embed model plus cache-hit flag, and the selector decision. Two optional pins, legal **only** together with the flag (`400` otherwise), remove the non-deterministic stages from a sweep run: `pinned_translation` replaces the whole detect-and-translate branch including its wire call, `pinned_temporal` replaces the FTS expansion **after** the deterministic rules ran (`""` = explicitly none) and suppresses the LLM temporal fallback. Access-log rows of a measurement carry `metadata.source = "armsweep"` instead of `"agent"` — they are labelled, not suppressed, so a later real-traffic selection can exclude them. Without the flag the path is byte-identical to before: no transaction, no second statement (pinned by a response-body SHA-256 against the pre-seam tree and a `pg_stat_database.xact_rollback` census). The seam exists because an external sweep driver cannot reproduce translation, temporal normalisation, the query-prefixed embedding and the selector decision — so the measurement rides the production path instead of imitating it. Go side: `rrf.SearchTx`/`rrf.ArmRanksTx` over a `rrf.Querier` (pool or transaction); `rrf.Search` delegates with `q == pool`, so every existing call site is untouched. The CLI path is `ctx-armsweep`.

**Shadow visibility (`shadow_types`, M-W2)** rides the same seam and widens exactly one thing: the type allowlist handed to those two statements. A measurement that compares "with the catalog" against "without" needs the catalog blocks to exist, and blocks that exist retrievably are live before anything about them has been shown — so they live as an excluded type and one admin request lifts them for its own two statements. Seven gates, all fail-closed: admin (`403`), `arm_ranks:true`, `synthesize:false`, a name that is a key of the registry, a name carrying `retrieval.shadow_measurable` (default false, and `checkpoint`/`system-meta` are refused by a hard deny-list the flag cannot override), no `include_content`, and the reranker forced **off** rather than assumed off — `rerank.enabled` is hot and tenant-overridable, and the LLM-judge builds its prompt from block content. On top of that every backend chain the request can still resolve (embed, translate) must be `locality=lan`, otherwise the request is refused: `openrouter` sits in the live pool as `external`/`no-credentials`. Two slices, not one: the post-fusion stages keep `visibleTypes`, only the measurement statements see the widened copy, and shadow rows are dropped before `sources` is built — a shadow block leaves as a UUID plus numbers inside `arm_ranks`, never with a title. The measurement corpus belongs in a restored copy (`server.instance_kind = measure-copy`), because an excluded type is invisible in the *result* and not in the *indexes*.

**Migration 145 (partial FTS GIN)** narrows that last sentence on purpose, and the part it keeps is why the predicate is shaped the way it is. Measured live on 2026-08-27: `idx_context_ts_de` is 41 MB, `idx_context_ts_en` 40 MB, and **97,2 % of the indexed text mass belongs to `checkpoint`** (5 961 blocks, 185 MB), with `system-meta` adding a rounding error — two types carrying `retrieval.policy='excluded'`, therefore never in `Set.VisibleTypes()`, therefore never returnable by an FTS arm. Both indexes now carry `WHERE type_name NOT IN ('checkpoint','system-meta')`. The predicate is the **hard deny-list of the shadow seam, not "every excluded type"**: `catalog` and `insight` are excluded too, but they are the shadow-measurable derivative types and `shadow_types` widens `p_types_visible` with them for one request — an "all excluded" predicate would drop them out of the index and quietly shrink the very FTS contribution the B/C measurement is about. `checkpoint`/`system-meta` can never reach that widened list (`shadowDenyTypes`, checked before the flag), which is what makes them safe to index away. Both function bodies carry the same conjunct in their two FTS CTEs, and that is not decoration: a partial index is used only when the query predicate **implies** the index predicate, and the arms filter through `p_types_visible`, a plpgsql parameter. While the plan cache serves a custom plan PostgreSQL folds that parameter into a constant array and proves the implication itself; once it switches to the generic plan (possible from the sixth execution per connection) no proof is possible and the FTS index drops out of the plan — measured at 40 000 rows, the stripped form is estimated at 3 866 against the conjunct form's 388, a factor of 10. The static conjunct makes the implication clause-identical and therefore plan-independent. The rebuild is guarded like 115's and 140's: the target index already present ⇒ no-op (an operator may build it out-of-band with `CREATE INDEX CONCURRENTLY` under a second name, then drop and rename), the expected full GIN under 500 000 rows ⇒ replaced inline, above it ⇒ a warning and the full index stays — a full GIN carries the new conjunct too, so the arm is never slower than before and only the space saving waits. **One named consequence:** on a registry where a tenant overlay lifts `checkpoint` to `full-pass` (D6 "Overlay gewinnt" permits exactly that, and the type write path does not check a new name against the `_global` builtins), the conjunct stops being a no-op and cuts those blocks out of both FTS arms while the semantic and trigram arms still deliver them. The live registry carries eleven rows, all `_global`, so the case is empty today; `TestOPSW1TenantOverlayShadowsFTS` pins it so a later D6 decision cannot walk past it.

**Migration 147 (FTS id tiebreak)** finishes what Generation 17 started. Since migration 139 the semantic exact pool ranks with `ROW_NUMBER() OVER (ORDER BY ep.dist, ep.id)` and selects with the same key, and migration 140 gave the trigram arm the same treatment — but the two full-text arms kept ranking with a bare `ORDER BY GREATEST(ts_rank_cd …) DESC`. That order stops being total the moment two blocks score bit-identically, and PostgreSQL's sort is not stable, so the ranks follow the physical heap order; once a tie group runs past the arm cap of 100, the same instability also decides **which** blocks enter the arm at all. Measured, not suspected: two replicate runs of the same 1 000 gold cases against the same corpus disagreed in 84 cases, **every one of them sitting at exactly 100 full-text candidates**, 83 of them changing the candidate *set*, with the first difference at rank 2 in the median — and the ANN share of that spread was exactly 0. Migration 147 appends `, cb.id` to both full-text sort keys in `ctx_rrf` **and** `ctx_rrf_arms`, in the `ROW_NUMBER` window (so the rank is total) and in an outer `ORDER BY` before the `LIMIT` (so the *set* is decided by the query text rather than by the WindowAgg node happening to pass its input order through). `cb.id` is the primary key, so as a **last** key it can never move a genuine score ordering — it is compared only on a bit-equal `GREATEST` value, which is why a tie-free corpus comes back byte-identical across the migration. The second copy costs nothing measurable: the plan node census is unchanged (same `Sort` and `WindowAgg` counts) and exactly two sort keys grow, because the outer `ORDER BY` matches the pathkeys the WindowAgg input sort already produces. Not in this migration, deliberately: the arm caps, the FTS partition predicate, and a tiebreak for the approximate `ann` arm — that one is plan-dependent by construction and its measured contribution to the spread was zero.

**Title floor (issue #507).** A question that is the title of a candidate brings that block to the first place. Among blocks whose titles differ in a date or a version number only — one block per release, handover, daily report or archive part — the fusion puts the named block behind its siblings: the trigram arm finds it first and weighs least (0.10), the semantic arm sees near-identical texts, and a date in the question fills both full-text arms to their cap of 100 with the date expansion. Measured on a restored production corpus (440 sampled blocks, each asked its own title, limit 10): 85 were not among the ten sources, 74 of the 124 with twenty or more trigram-similar titles and none of the 151 without such neighbours; 81 of the 85 were already past the tenth place after the fusion, the gravity lost three and the graph expansion one; every one of them was inside the fusion's candidate window. The query handler therefore runs `floorTitleMatch` behind every reordering stage and ahead of the truncation: when the question equals one candidate's title in their folded form (both sides alike: Unicode NFKC, typographic quotes and apostrophes as ASCII, lower case, white space collapsed, a closing `?`, `.`, `!`, `:` or `…` dropped — punctuation inside, such as `v5.75.1` or `(2026-11-22)`, stays, and `ß` is not folded to `ss`, which would join two words), no other candidate's title contains the question (of several candidates whose titles fold alike, the one the pipeline ranks highest is the named block), the named block moves to the first place — the one every synthesis prompt keeps: a low_confidence answer is written from its first `query.low_confidence_max_sources` sources only (at the last place of the limit the named block stood among the sources but outside that prompt — 27 of 38 placements with `limit` ≥ 3 in a holdout), and the prompt budget evicts the latest part of the prompt first, where `LostInMiddleReorder` puts the second source, so with a small context window the second place is the first to go. The sources it passes move down by one and the source at the end of the limit leaves the answer. The block takes the score fields of the row whose place it takes, the former first (`score` and `rrf_score_original`), the way the graph and cluster stages place a block by a score relative to the list: the sources stay sorted, the synthesis path's `query.score_threshold` judges the place, and the list's highest score stays for both confidence labels — the synthesis reads `score`, the retrieval-only path `rrf_score_original` — so the floor never lifts a label; one falls only when a value that carried the list's highest score leaves the list (the source at the end of the limit, or the block's own fields when its own `rrf_score_original` was the highest — the gravity sorts by the boosted score). There is no threshold: a question about a family's topic or one that merely contains a short title moves nothing, and a title of one frequent word that other titles contain ("Deploy" beside "Deploy runbook") moves nothing either. The pass works on the candidate window only (the fusion's internal limit — 200, or the aggregate over-fetch), so a title match the fusion did not hand over is not placed; it adds no statement. A question translated before retrieval is compared in the form the caller sent.

### Aggregate-to-parent fold (WF T11)

A block of a type whose `retrieval.policy` is `aggregate-to-parent` (resolved from the registry via `Set.AggregateTypes`) is not delivered as itself — it is folded onto its structural parent (`parent_id`). The canonical use is **comment → issue**: the comment passage is the real hit, but the response carries the issue identity, so a query surfaces one issue rather than a scatter of its comments. The fold is a Go post-pass in the query handler, placed **after graph expansion and before the sensitivity annotation** (so a hydrated parent flows through the existing sensitivity/rerank/supersedes/`filterSuperseded` machinery — a placement literally at `filterSuperseded` would leave the hydrated parent's sensitivity zero-valued = credentials = a silent over-block). Since Welle I-E flipped `comment` to `aggregate-to-parent`, the fast path is instead **a zero-DB no-op when no aggregating block ranks** (the child scan finds nothing), so a corpus without comments keeps `eval.sh` byte-identical.

The mechanism does one batched round-trip: a single query maps every aggregating child to its `parent_id` and `LEFT JOIN`-hydrates the parent under the **same** visibility triple `ctx_rrf` used (types/scopes/grants). Then a pure in-memory assembly folds:

- **Score merge** = `max(parent, child)` — **no** child bonus (00-masterplan K13: an unproven tuning constant, deferred to a later eval-backed wave; a Golden test freezes the formula). Several children of one parent **collapse** to a single parent entry scored by the max over all of them. An in-set parent keeps its rank slot; a parent absent from the result set is hydrated into the best-ranked child's slot.
- **Orphan** (`parent_id` NULL) ⇒ the child stays as itself + a WARN (fail-open: the child is readable; dropping it would be data loss).
- **Invisible / cross-scope parent** ⇒ the child stays **raw** and the foreign parent is **never** delivered (no leak). design/01 §4.6's "Kind fällt raus" describes a *successful* visibility-checked hydration; the invisible sub-case is pinned by design/02 §4.4/§5.2 ("Fold liefert das Comment roh, nie den Fremd-Parent") — a hand-set cross-scope `parent_id` cannot pull a foreign title into results, and a distinct WARN makes the anomaly observable.
- **Parent outside the request filter** (`category`, `tags`, `categories_exclude`, `types_exclude` — what `ctx_rrf` applied to the child) ⇒ the child stays **raw** as well and the parent is not delivered; this is the caller's choice, not an anomaly, so nothing is logged. The filter is read as a column of the same round-trip, evaluated on the visible parent only.

**Issue integration (Welle I-E).** The issue-specific response contract is built on top of the generic mechanism:

- **`matched_comment`** — a folded issue row (hydrated OR in-set) carries the best-ranked child comment (`id` + rune-safe content `preview`), so the caller sees *why* the issue ranked: the passage that actually hit. It is set only on a folded parent (`omitempty`), never on a native hit or a child kept raw — every non-fold wire shape stays byte-identical.
- **Over-fetch** — the fold *collapses* rows (N comments of one issue ⇒ one issue row), so a fixed fetch truncated to the user limit can under-fill and under-diversify a comment-heavy scope. When the read-scopes actually hold an aggregating-type block (one `EXISTS` probe — a corpus without comments never widens, keeping `eval.sh` byte-identical), the internal candidate window is widened ×2 (`overFetchFactor`, capped at `overFetchHardCap` 500) so more distinct parents survive the collapse. **Deviation from design/02 §4.4's literal "limit × 2 (Cap 200)":** that phrasing predates the live baseline where the gravity reranker already fetches 200 unconditionally, which for any user limit ≤ 20 already exceeds `limit×2`; shrinking to `limit×2` would defeat the purpose, so I-E realises the *intent* (widen to compensate the collapse) as a ×2 factor on the base internal limit.
- **Per-parent cap** — the collapse itself is the cap: per parent exactly the best-ranked child sets the score and the `matched_comment`; further children of the same thread fold away silently and never displace a foreign candidate in the delivered set.
- **Ceiling caveat.** `ctx_rrf` caps its per-arm candidate pools (semantic 75, FTS 100/100, trigram 30 ⇒ fused pool ≲ 305), so the `p_limit` over-fetch only recovers parents within that ceiling. Under *extreme* per-issue skew a single hot thread can fill the arm slots and starve tail parents from the pool entirely — a case the p_limit over-fetch cannot fix. The complete fix is a per-parent cap **inside** `ctx_rrf`'s arms (a `ROW_NUMBER() PARTITION BY parent_id` window), which belongs to Achse-01's `ctx_rrf` and is the named follow-up.

## Temporal gravity & cyclic phases

**Cyclic phase model** — 7 cyclic temporal dimensions (weekday/month/quarter/week/monthday/seasonal/daily), each with normalized phase [0,1) and its own Gaussian decay field. Queries route to dimensions via an 18-matcher deterministic parser engine: "immer dienstags" activates `weekday`, "Weihnachten" activates `{month:0.4, seasonal:0.6}`. Timezone-aware via `CTX_TIMEZONE`.

**LLM-fallback derivation.** Queries the rules parser cannot resolve fall back to the LLM for *date* resolution only — the dimension weights are then derived deterministically in code from the same detector primitives (never asked from the model). Two hard gates protect the ranking: a phase-coherence check (a cyclic dimension is only activated when the resolved date actually carries that phase) and a linear floor ≥ 0.2 (a fallback result is never pure-cyclic, so a subtly wrong LLM date keeps a linear safety net). The consumer additionally drops any dimension key outside the canonical vocabulary before it can inflate the boost budget. A `dir` the prompt does not ask for (anything but `past`, `future`, `today`, `range`, `until`) is no direction (issue #487). The model's prompt reads `bis`/`until` as the rules do: an end before today is the time up to it (`dir` `until`, no end), a later end a deadline, the window from today (prompt version 2026-11-21; before, every `bis` was a range from today). A window longer than the cycle of a cyclic dimension — a week for the weekday, a month for the day of the month, a year for the month, the quarter, the ISO week and the day of the year — gives that dimension no weight, and every window open towards the past or the future is longer than all of them: the weights anchor a dimension on one edge of the window, so `seit März 2025` (month 0.2) would rank the Marches of both years ahead of every other block in its window and `bis März 2015`, whose window no content date reaches, would reorder the candidates by their month alone. The weight of such a dimension goes to the linear share, so the boost budget stays what the rules gave the question (issue #463); a single day and a window within the cycle keep their weights. `/api/query` reports the active weights, after this step, as `activated_dim_weights`.

**Which dates a question names, and what a window does.** The rules read the two day forms of the content extraction anywhere in a question — ISO dates (`2026-03-29`, optionally with a time) and dot dates (`29.03.2026`), with the same digits, spaces and word boundaries as the extraction below (a differential test holds the two sides together) but the years 2000–2099, so a question about a day no block can carry still resolves without the LLM. A month before a year (`März 2024`, `Maerz 2024`, `March 2024`, any case, the long s included — both sides look the name up by one rule) counts only after a word that makes it a window's edge (below); without one (`im März 2024`, `am 15. März 2024`) the question goes to the LLM fallback, since the month form would read the 15th of March as the 1st. The rules read the month forms the extraction reads: behind quotation marks and brackets (`seit „März 2024“`), and with a no-break space (U+00A0) or a narrow no-break space (U+202F) wherever a space stands, also between the word and its date. Windows, both days included: two day dates with the word `bis`, `to` or `through`, an en or em dash, or a hyphen between spaces between them (`15.03.2026 - 20.03.2026`), or with `und`/`and` between them after `zwischen`/`between` (`zwischen dem 01.03.2024 und dem 31.03.2024`); a dot date without its year before such a word and a day date (`01.03. bis 05.03.2026`, `28.12.–03.01.2027`: the start takes the end's year, or the year before); `von X bis Y` (also `vom X bis zum Y`), `from X to Y` (also `until`, `through`) and `ab X bis Y` with a date X, `seit X bis Y` (`since X until Y`) — each of them from today when X is `jetzt` or `now` (`von jetzt bis Freitag`), and a `from` whose start the rules cannot read keeps its `until` (`from the start until 2026-03-05` is the time up to that day) —, `letzten X bis Y`, `X through Y`, `seit X` and `since X` (from X to today, also `seit dem X`) and `bis X` and `until X` (also `bis zum X`). A month at a window's end includes the month: the window ends on its last day (`von März 2024 bis April 2024` ends on 2024-04-30, `bis März 2024` on 2024-03-31), while a month at its start begins on the 1st (`seit März 2024`). Open windows: `ab X` is the time from X on, open towards the future, for a past X as for one to come (`ab März 2024`, `ab nächstem Montag`) — `seit`, which names the time up to today, has no window for a day to come, `ab` names only where the time begins; `nach X` and `after X` are the time from the day after X on (`nach März 2024` from 2024-04-01), `vor X` and `before X` the time up to the day before X, open towards the past (`vor dem 15.03.2024` up to 2024-03-14), and with X after today the deadline from today to the day before X, as `bis` with a later end is one (`Was muss ich vor dem 01.12.2026 erledigen?`). These five are words of their own far more often than words before a date (`nach Hause`, `vor allem`, `ab Werk`, `after 3 retries`, `vor 5 Minuten`), so their rules take only a phrase that starts with a date naming its own day — a day date, a month with its year, a day keyword like `heute`, a weekday or month after `nächsten`/`letzten`; not a word the keyword matching forgives as a typo, and not a bare weekday or month, whose year or week would have to be guessed and which is often a word of its own (`nach August`, `after may I ask`) — and `ab` before a start the rules cannot read is no start (`ab Projektstart bis 05.03.2026` is the time up to that day). An edge towards the future and one towards the past in the same question are the window between them (`Was kam nach 2024 und vor 2026?` is 2025; edges in the wrong order leave the first one standing), and so are two day dates behind such edges (`What happened after 2026-03-15 and before 2026-03-20?` is 16 to 19 March; two that leave no day between them stay the two days, issue #517), and an edge word coordinated with another shares its date and opens none (`vor und nach dem 15.03.2026` is that day) (issue #506). A time unit, a time of day or a word of nearness right before `vor`, `nach`, `before` or `after` (`zwei Tage vor dem 15.03.2024`, `am Abend vor dem 24.12.2026`, `the weekend after 2026-03-15`, `kurz vor dem 24.12.2026`, `shortly after 2024-12-24`) makes the word a distance, and the date stays the day it names. A year followed by a month name that is a word of its own (`may`, `march`, `august`) is no month for any rule (`Logs after 2025 may be deleted` names the year 2025, below), these five words take no phrase that starts with a year and a month, and after `since`, `until` and `from` a bare `may`, `march` or `august` is the word, not the month (`Wait until may I ask`; `since May 2024` and `seit August` are months). No window starts after it ends: a weekday or month end that resolves before its start is counted again from the start (`von Freitag bis Montag` ends on the Monday after that Friday), in the past tense the start is counted back from the end (`Was lief von Freitag bis Montag?` is the span that has happened); an end named from today or by its date (`heute`, `gestern`, `2026-03-05`) keeps its day, and a weekday or month before it is counted back from it (`von März bis heute` is this year's March up to today); two such fixed days in the wrong order swap; `seit` with a day to come is no window, and so is `seit X bis Y` whose start lies ahead (`seit 2027 bis 2028` asked in 2026: neither a window nor the deadline of its `bis`), while a bare weekday or month after `seit` is the last one (`seit Juni bis 2026` asked in January 2026 starts on 2025-06-01) (issue #506). A day date behind `seit`, `bis`, `von`, `to`, `through` or one of the words above is an edge of the window that takes it (`From 2024 to 2026-06-15` is that window, issue #506), or else the day it names — so is a day date whose `von … bis` has no start the rules know (`vom Projektstart bis 05.03.2026`), one another phrase of the question would drop (`Seit Montag …, was bis 2026-12-31 …` is the window up to 2026-12-31) and one after `von` before a weekday or month (`von 2026-03-01 bis Freitag`: the end could count from today or from the date; `von 2026-03-01 bis heute` is the window). `bis` with an end before today is the time up to that end, open towards the past (`bis März 2015`, `bis gestern`; a month that began before today, `bis November 2026` in November, is the time up to its last day), while a later end is a deadline, the window from today. A bare year is a window's edge at year precision, as a month is at month precision (issue #487): `seit 2024` and `since 2024` from 2024-01-01 to today (`seit` a year to come is no window), `bis 2024` and `until 2024` up to 2024-12-31 (a year that began before today is the time up to its end, `bis 2027` the deadline from today to 2027-12-31), `nach 2025` and `after 2025` from 2026-01-01 on, `vor 2025` and `before 2025` up to 2024-12-31 (`vor 2027` the deadline from today to 2026-12-31), `ab 2025` from 2025-01-01 on, and `von 2024 bis 2026`, `from 2024 to 2026`, `seit 2024 bis 2025`, `zwischen 2024 und 2026` and `between 2024 and 2026` from the 1st of January of the first year to the 31st of December of the last. A number is such an edge only with proof that it is a year: it lies in the years a content date can carry (2020–2099, the extraction's window) and no more than two years after the current one (in 2026: up to 2028), since the four-digit numbers of this domain that are no year — 2048 tokens or bytes, the ports of the 2000s, 20:30 written `2030` — lie after the current year; it ends its clause or stands before a word that is no counted noun — a conjunction (not before `mehr`, `weniger`, `more`, `less`), a preposition, an article or another determiner (`alle`, `every`), a pronoun, an auxiliary or modal, a verb or participle the tense detection knows or a strong simple past (`Bis 2025 galten …`) (`Seit 2024 gibt es …`, `Ab 2027 gilt …`, `Logs after 2025 may be deleted`, `seit 2024 im Einsatz`); its clause has no word that makes it a count, a position or a name — the nouns that are counted, numbered or named (lines, tokens, ports, issues, IDs, values, entries, requests, versions, also as the head of a German compound: `Logzeilen`, `Fehlercode`), the places a count stands in (a list, a table, a file, a queue, a buffer, the context), money, the time of day, and the verbs that count, cost, skip or read to a position (`Zeig mir die Zeilen ab 2024.`, `Welche Ports liegen zwischen 2020 und 2026?`, `Wie viel kostet es ab 2023?`, `Skip until 2025.`, `Ab 2024 im Speicher`); no other clause asks for a count of such a noun (`Nach wie vielen Requests, ab 2024?`) — a count phrase that counts no such noun governs no number, in the year's clause as in another (`Since 2024, how many outages have we had?`, `Wie viele Ausfälle gab es seit 2024?` are the window since 2024, issue #506); and the year is not the start of a range to another number that the range rules did not take (`ab 2026 bis 2028 Dimensionen`). The end of the clause alone is no proof. A number before its noun is a count (`seit 2024 Zeilen`, `bis 2048 Tokens`, `nach 2025 Anfragen`, `nach 2048 Generationen`, `ab 2024 und mehr`), and so are `#2025`, `2024-03`, `2024,5` and `2024ms`; a month name behind the year makes it the month (`seit 2024, Oktober`). Such a question goes to the LLM fallback as before, where its words carry temporal intent; `since 2024, lines have grown` names the year, since the comma ends the year's clause, and so does a dash (`Seit 2022 – wie viele Ausfälle hatten wir?`); a parenthesis around the year ends no clause (`After (2024) failures, restart` is no window, issue #506). A year followed by an English participle and a plural noun counts the noun where the noun phrase ends — with its clause, or before a determiner or a subject pronoun (`After 2021 failed logins the account locks`); before a verb the noun phrase is the subject and the year the edge (`After 2025 failed logins lock the account`), issue #517. A month without its year before a year as the end lies in that year, asked in any month (`von Juni bis 2026` starts on 2026-06-01, also in January 2026), after `seit` only a month that has begun (`seit Dezember bis 2026` asked in November 2026 starts in December 2025). The edges of a window are ordered by their calendar day in the zone of the question (`CTX_TIMEZONE`): a day date and a year give the same window east and west of UTC (`von 2026 bis 01.01.2026` is that one day), and a day date is today on that day in any zone (issue #506). A window with a year as either edge carries the linear weight alone (`von 28.12.2025 bis 2025` too): the year names no month, week or weekday, and an edge on the 1st of January or the 31st of December is no phase the question names. The linear gravity rewards every date inside a window as it rewards a date on the day of a single-day question — `seit März 2024` rewards 2025 and 2026 as much as March 2024 — and measures a date outside it from the nearer edge by its day, with a 60-day cutoff (14 days around a single day): every time of the day before the start and of the day after the end is one day away. A window that covers every year a content date can have (2020–2099) lifts every dated block alike over the undated ones; a window no content date can reach (`bis März 2015`) leaves the order as it is (its open window gives its cyclic dimensions no weight, see the LLM-fallback paragraph above). The FTS expansion carries the days the question names — for `bis` in the past not today's, for an open window only its edge and the edge's month. Measured after the gravity on a seeded corpus whose question words hit blocks inside and outside the window (issue #487, 21 open-window questions, in-window blocks among the first ten: this form 196, no expansion 148, the named date 128, the edge's month only where the whole month lies inside the window 195), no other form brings more in-window blocks into the first ten without bringing fewer in another question, so the form stays. The synthesis prompt's date context names the direction of an open window — `nach dem 15.03.2024 = 2024-03-16 and later`, `bis März 2015 = 2015-03-31 and earlier` — beside a closed window (`= A to B`) and a single day (`= date`), so the model can tell `ab` from `bis`. The linear gravity takes an hour as the instant of its target and filters a date to come by that instant, so an hour on today or on a day ahead moved its weight off that day's content without a time of day onto the next day's: a day ahead and today carry no hour, and an explicit time of day (`um 14 Uhr`, `9am`) is not read. Such a day keyword answers before the holidays, the time of day and the weekday rules, with the weights of a day keyword (a weekday's where a weekday comes first), and keeps every weekday of the question as a date, in the order of the question, a weekday that names the keyword's day in its clause aside (`Heute ist Montag`), and so another day keyword and a holiday or the weekend in a clause of its own; a day keyword beside a weekday is a date of its own as well (`Was ist gestern und am Montag passiert?`), unless a distance follows it (`gestern vor einer Woche`). A greeting (`Guten Morgen`, `Good evening`, `Morning team`) and an English part of the day in a noun phrase (`the night owl`, `the last night train`, not `in the morning`) name no time; a day keyword joined by a hyphen to a word that names no day (`Morgen-Job`) names no day, and one of another day answers before a time-of-day word that belongs to none (`Was passiert morgen, früh genug für das Review?`); `the day before yesterday` and `the day after tomorrow` are `vorgestern` and `übermorgen`; a holiday (`Weihnachten`, `Silvester`, `Neujahr`) is the one of the year written behind it, else the last one for a question in the past and the next one otherwise (issue #532). The German Perfekt counts by its structure: the auxiliary in front and the participle at the end of a main clause (`Was haben wir am Montag im Meeting besprochen?`), the participle right before the auxiliary at the end of a subordinate clause (`Weißt du noch, was wir am Montag festgelegt haben?`), with separable and inseparable prefixes (`zurückgerollt`, `übersehen`, `vorbereitet`) and English participles (`Was haben wir am Montag released?`), across clauses inserted into the bracket (`Was haben wir am Montag, nach dem Standup, besprochen?`, `Was hast du am Freitag, bevor du gegangen bist, deployed?`), and the past subjunctive (`Was hätten wir am Montag tun sollen?`); an abbreviation (`Dr.`, `z.B.`, `ca. 3 Std.`) or an ordinal (`am 15. März`) ends no clause; behind a form of `sein` only the participle of a verb that takes `sein` (`ist passiert`, `ist abgestürzt`, `sind aufgetreten`, `ist gefailed`, `sind geflaked`), since the same form names a state as well, which is no past (`Ist das Büro am Samstag geöffnet?`, `Was ist am Montag geplant?` ask for the coming days). A clause with a finite verb of its own ends the search for a participle that closes an earlier clause (`Haben wir Montag frei, oder wird da gearbeitet?` is the coming Monday). A clause without a finite verb that ends with a participle is a Perfekt whose auxiliary it dropped only when that can only be the Perfekt's: the participle of a verb that takes `sein` (`Server am Freitag abgestürzt?`), or an indefinite pronoun before it that makes the clause active (`am freitag was kaputt gemacht?`), not with the participle of a plan or an arrangement and not with a date after `für` (`Für Dienstag was reserviert?`); two such clauses side by side, each a date with a participle at its end (the second may end with a state behind `wieder` or `erneut`: `Am Montag repariert, am Dienstag wieder kaputt?`), are the Perfekt as well where the pair asks for a reason or one of the two ends the question with a question mark (`Am Montag gelauncht, am Mittwoch gerollbackt – warum?`, issue #532) — a participle of an arrangement or a state (`Montag Büro geschlossen, Dienstag Homeoffice angeordnet`, `Am Freitag anberaumt, am Montag festgelegt?` — a list, and an open one: a participle of an arrangement it does not hold reads as an act) and a question mark behind a clause of its own (`…, am Montag wieder hochgefahren – passt das?`) leave the pair unread; any other key-word question ending with a participle (`montag deployment geplant`, `freitag release freigegeben?`) may be the state passive or a plan: the form cannot tell, and where it cannot the tense stays neutral — either wrong reading moves the date by a week, and the superseded filter is off for every question a rule answers, whatever its tense (issue #506). A word behind an article, written with an upper-case letter inside its clause, or with a noun ending (`Bereitschaft`) is no participle (issue #487), and neither is a noun of participle shape that is the participle of no verb, which a lower-case question cannot mark (`haben wir am montag verlust`, issue #506), also in the five words behind an auxiliary (`haben wir am montag gehalt auf dem konto?`, issue #517). The rules cost time linear in the length of a question: every check that looks behind a candidate reads only the word before it (issue #506), and the bounds of a clause come from a table filled once per question (issue #517).

**Multiple anchors per block.** Every block carries dimensions from both its content (dates mentioned in text) AND its `created_at` timestamp. A block about "Meeting am Dienstag" written on a Friday gets `weekday=2` (content anchor) AND `weekday=5` (meta anchor); both signals contribute independently. "Meeting am Dienstag, Ergebnis am Mittwoch" still pulls the Wednesday block (just weaker). Storage is EAV (`context_temporal`) with partial B-Tree indexes for O(log n) dimension lookups at 1M+ scale; `ON CONFLICT` dedups overlapping timestamps. A content write sets the block's `content_times` in its own statement, from the content it stores. The write extracts the dates of the content it stores once — before its transaction; an update with edits extracts the result of its edits inside the transaction, before it locks the row, and once more under the lock when another write changed the content in between — and hands them, with that content, to its afterwork, which writes the rows from them without extracting the content again (issue #434). The temporal writers that no write precedes — the startup backfill and the dream's deterministic re-extraction and review — extract the content they read themselves. The rows are written after the write commits, in a transaction that keeps them only while the block still holds the content their dates were read from (its `content_hash`), and the temporal writers of one block take turns (a transaction-scoped advisory lock per block): when two writes of a block finish out of order, the earlier one's rows are dropped or replaced rather than left beside the later content's, and two temporal writes of one content leave one date set. That transaction takes the block row `FOR KEY SHARE` right after its turn, before it touches a row of the block — the order a hard delete (a purge, whose cascade removes the rows) takes them in, so the two cannot deadlock (issue #465) — and holds it in that mode only, so an update of the block and the query path's failure memo (`FOR NO KEY UPDATE`) neither wait for it nor skip the block because of it. A temporal write that still loses a deadlock or meets the foreign-key refusal while its block goes reports the block as gone once a second read finds it gone; otherwise the refusal stays its error. The dream's temporal review is due for a block whose current title and content it has not reviewed, and nothing else decides it: the review records, in the transaction that writes its rows, the version they stand for — `sha256(content_hash || title)` of what it sent to the LLM — in `context_temporal_reviews` (migration 189), under the guard of the title and the content it read; every other writer of a block's temporal rows (the write afterwork, the review's deterministic phase 1, the backfill) deletes that row with its own rows; the dream's pick answers due-ness for the block it hands out (no row carries the version of its title and content). No time is compared, so the order the writes commit in does not matter: a write that began before a review and committed after it leaves the block due whatever `updated_at` (its transaction start) it carries — the comparison of `updated_at` with `dream_temporal_validated_at` it replaces did not (issue #452). A title or content replaced while the review waited on its LLM leaves the block due, and its next pick reviews what it holds; a write of tags, metadata or the category leaves the review standing and costs no review. The review rewrites the block's rows whether or not the LLM found a date, so a date read off an earlier title goes with the next review of the current one. A review that failed — its write on the database, its LLM call, or an answer that does not parse — records nothing: the block stays due and keeps the rows it had (before, each of these stamped the block, and an LLM failure was not retried until the block changed). What bounds a block whose review always fails is the pick's claim and the cooldown its cycle ends with, since the pick does not select by due-ness. The afterwork of a write that stored the content the block holds (a same-content upsert) writes nothing when the rows are the review's of the block's title and content, the review recorded the extraction in force for that version (the creation time and the content's dates, as a digest bound to the version; migration 190), and the rows hold every date of that content and its creation time: it would otherwise replace the review's findings while the review still covered the block. An extraction that changed since the review — a date it no longer yields as well as one it yields now — and a version row without a recorded extraction (taken over by migration 189, or written by an older binary) cover nothing: the afterwork writes the extraction's rows and deletes the version, and the block is reviewed again. The startup backfill also writes `content_times`, for blocks written by a path that does not set it, and re-reads a block whose content changed between its read and its write (up to three writes in all); a block whose content changed on every one of them, and a block whose write failed, is read once per run and reported in the backfill's error line.

**Which dates a content yields.** Four forms, case-insensitive for the month names: ISO dates (`2026-03-29`, optionally followed by a time, `2026-03-29 14:30`, `2026-03-29T14:30:00Z`), dot dates (`29.03.2026`, optionally `29.03.2026 14:30`), and a German or English month name before a year (`März 2026` or `Maerz 2026`, `March 2026`), which stands for the 1st of that month. A month name starts where no ASCII letter, digit or underscore stands before it, whatever rune spells its first letter: the long s of `ſeptember 2026` as well, which until issue #463 yielded a date only behind such a character (`xſeptember 2026`) and none at the start of a text or behind a space, a quotation mark or a no-break space. Between month and year and between date and time, a no-break space (U+00A0, as word processors and `&nbsp;` produce it) or a narrow no-break space (U+202F) counts as a space; other Unicode spaces do not. Invalid calendar dates (`2026-02-30`) yield nothing. The years are 2020–2099, a fixed window, so the same content always yields the same dates; years before 2020 stay out because in code they are mostly layouts such as Go's `2006-01-02 15:04:05`, not dates. The extraction does not read the words around a match, so some numbers that are no dates yield one: a month name before a count (`buffers may 2048 bytes`, `im Mai 2048 Zugriffe`) yields the 1st of May 2048, a version or an amount in the dot form (`Ubuntu 24.04.2045`, `12.05.2070 EUR`) the 24th of April 2045 and the 12th of May 2070. A block's `content_times` keeps the dates of its last content write until the next one; the dream's temporal review, when it next reviews a block after a change of its title or content, re-extracts and rewrites the dimension rows if it finds fewer than the current extraction implies; a block whose title and content it has reviewed is not reviewed again, so dates an extraction no longer yields stay on it until its title or content changes or a write of the content it holds runs the afterwork, which rewrites the rows of a review made under another extraction (issue #466). An older build reads such rows like any other and replaces them only with its own next content write of the block. Each date also counts towards the block's `block_mass` (`1/sqrt(n)` over `content_times`).

**Forward Telescoping.** Older blocks get a wider linear gravity well (effective power scaled by `1 / (1 + 0.3·ln(1+age/30))`) so a 6-month-old block isn't drowned out by a 1-week-old block when the user asks about a date in that window. Future dates keep their 1.2× sharper cutoff. Matches Rubin & Baddeley 1989's age-dependent recall imprecision.

## Dream Mode

A continuous background loop that autonomously discovers relationships between blocks, marks outdated information (supersedes), and promotes high-quality content. A new installation runs it by default and an upgraded one keeps it as it was (`dream.enabled`, recorded per database by migration 192 — [operations](operations.md#dream-on-a-new-installation)); while it runs it calls the chat model of the pool, role `dream`. It is **type-policy-gated** since WF T8 (`dream.linkable` both-sided via the block-type registry — the former `is_meta` exclude generalized; per-type `dream.link_classes` caps the writable link vocabulary).

**Candidate allowlist (V-9).** The per-keyword RRF search binds `p_types_visible` to `intersect(VisibleTypes, DreamLinkableTypes)` of the cycle's policy snapshot, not to the plain visibility allowlist. Before V-9 a retrievable-but-not-linkable type — every `damped` or `aggregate-to-parent` type with `dream.linkable=false` — competed for the five slots per keyword at factor 1.0 (the call site passed no damping arrays) and was then discarded again by the post-RRF type sieve: the slot was spent on a block the loop could never link. Damping alone would not have closed this, because a damping factor is a ranking multiplier and not an exclusion — at factor 0.60 a damped hit still takes the slot whenever it leads the best linkable hit by ~42 ranks in an arm. The damping arrays therefore stay empty on this path: everything that survives the allowlist ranks at factor 1.0 (including `audit-trail`, damped 0.60 for user queries since migration 146), because the dream loop has no user query whose intent patterns could lift a type back out of the damping. An empty intersection is a registry-policy error, not a "nothing relates" verdict — the cycle parks the block transiently instead of booking it inert.

**Keywords follow the text.** The per-keyword search runs on keywords the dream model generates from the block's title and content once and stores on the block (`dream_keywords`), so later cycles reuse them. Every write that changes the title or the content drops them (with the vector, in `InvalidateEmbeddingTx`), and the block's next dream generates them from the text it holds; keywords generated from a text that was replaced while the model answered are used for that cycle but not stored (issue #452).

- **Dual-model support** — a separate model for evaluation (e.g. a larger model for better causal/supersedes reasoning). Dream pipeline version 5, v5 prompt for qwen3.6:27b non-thinking sampler, with a `recurrent` relationship class detected via `context_temporal`+title-similarity (Phase 1) + LLM (Phase 2).
- **Decide mode** (`dream.decide_mode`, hot, ships `off`; `eval` | `all`) — the link classifier (and with `all` the recurrence confirm) runs as prefill-only *decisions*: one request per (source, candidate) pair asks for a single letter (`A`=supersedes … `D`=topical, `E`=none) and the answer is read off the first token's top-logprobs (see *Decide primitive* under Supporting mechanisms). The relationship is the most probable link type, the confidence is the probability that any link exists (1 − P(none)) — a model probability, never a parser floor — and the post-parse constraints (supersedes direction, candidate filter, per-type gate, hard cap) run unchanged on the result — plus one decide-only step between gate and cap, the **near-tie distance** (`dream.decide_tie_odds`, hot, default φ ≈ 1.618): of a block's gated links only the most confident one (the anchor) and those whose odds lie within that factor of the anchor's are written; a candidate beyond the factor is not a tie, whatever its absolute probability. Reason (calibration 2026-10-03): the read P(link) is overconfident — 33–41 % hits in 0.70–0.90 — so no threshold separates, but the per-block ranking does (gold link = top-1 in 50/54); on gold φ took precision 0.61 → 0.73 at recall 0.87 → 0.85, and the live replay from 4.5 links per evaluation (pinned at the cap) to 1.7 (heavy-tailed). Measured on the odds scale because the probabilities saturate near 1, and relative to each block's anchor so a weakly evidenced block keeps its ties. `0` restores the pre-rule behaviour; the log line `dream: decide links finished` counts the dropped links as `links_untied`. Both direction constraints run *before* the tie distance, as downgrades to topical: an inverted supersedes, and since v5.21.1 a causal link whose source does not predate its target (V9, checked on the candidates' exact `created_at`) — otherwise an anchor that the write-time gate rejects decides which links count as ties and the block can end with no eval link at all (live 2026-10-04..07: 6.6 % of evaluations, 39 % of gated causal decisions pointed the wrong way). Counted as `causal_direction_downgraded`. Zero output tokens and no JSON to parse: the truncation/drift failures that cost 2.4 % of dream-eval calls 16–23 s each cannot occur. Every pair is one `dream-eval` llmlog row (with `all`, every recurrence pair one `dream-recurrence` row; verdict = most probable label, confidence = its probability) with `metadata.decide=true`, `decide_probs` (per relationship), `decide_mass`, `decide_confidence`, so calibration is measurable from the log. A chain that lands on a backend without logprobs (Ollama, some relays) falls back to the generating prompt for that block (`metadata.decide_fallback`). Measured 2026-09-20: link_score 0.605 vs 0.599 generating, recurrence 0.885 = 0.885, 2.1× throughput.
- **Parallel workers** (`CTX_DREAM_PARALLELISM`, default 1) with atomic `FOR UPDATE SKIP LOCKED` block-claim — race-safe under contention.
- Adaptive cooldown, supersedes detection, temporal validation, a **hard cap of 5 links per cycle** with type-diversity tie-break, replace-semantics with snapshot revert, and runtime mode control (on/throttled/off via API). Throttled mode pauses between GPU-intensive steps for thermal management.
- **Robust LLM-output parsing** — tolerates array-form, single-object, named-wrapper, fenced-array and compact-multi-key-object link formats from heterogeneous LLM outputs. A wrapper whose *only* array-valued key holds an empty array (`{"classifications": []}`, `{"reasoning": "none", "relationships": []}`) counts — like the bare `[]` — as an **inert verdict**, not a transient parse error: the block books the inert cooldown (`dream_eval_count` advances, the `InertOffset` back-off step applies) instead of retrying output the model will reproduce unchanged. Wrappers with two or more arrays stay a retry even when all of them are empty — an empty sibling must never hide a populated one. The markdown-fence tolerance underneath that parsing lives in exactly one place, `llm.StripJSONFence`, and since T04-13 aligned the recurrence parser to it, a trailing fence marker that opens nothing counts as model content on every path instead of being trimmed away on one of them. T04-14 put the distiller's answer on the same helper, so the last pipeline that still demanded a bare payload tolerates a fence too — and a fenced answer no longer costs its insights *and* counts as a breaker fault.

**Link curation (migration 119).** Dream links carry two governance columns: `pinned` (human-confirmed via `manage dream-link-resolve` / `ctx dream resolve`) and `rationale` (durable per-link justification, TEXT). A pinned link **survives the replace sweep** — `deleteStaleLinks` deletes `WHERE NOT pinned`, so an operator verdict outlives any later LLM cycle that no longer re-emits the link; the only removal path for a pinned link is an explicit delete-resolve (and the daily `CleanupDanglingLinks` or a scope move, once an endpoint is archived or in another scope). Since issue #197 a later cycle that **does** re-emit the pair no longer rewrites a pinned row either (`ON CONFLICT … DO UPDATE … WHERE NOT pinned`): the verdict keeps its relationship and confidence instead of being re-classified by the next guess, and dream writes no supersedes guess that would close a cycle (`store.SupersedesWouldCycle`, the walk a declaration runs, up from the source and bounded by 64 links). Every supersedes path takes a per-scope transaction advisory lock as the first lock of its transaction (`store.LockSupersedesScope` / `ShareSupersedesScope`). The paths that lock link rows before the target rows of their reconcile take it **shared**: every `WriteLinks` batch and the delete-resolve of a `supersedes` link. The paths whose row-lock order differs, or whose check reads links no row lock of their own covers, take it **exclusively** and so run alone in their scope (issues #197, #284): a declaration (source, then target, then the link row), the confirm of a `supersedes` link (it runs the declaration's already-superseded gate over the pins of other sources), an archive or scope move (`store.lockSupersedesSource`: the block and its supersedes targets in id order, then — for a move — the block's link rows; the single-id `guard-resolve archive` is such an archive), each scope-purge batch (blocks in scan order, then their link rows) and `CleanupDanglingLinks`, which reads the dangling rows without a lock and deletes them by primary key per scope, at most 1,000 rows per transaction (link rows, then their targets). A batch that carries a supersedes guess takes a second per-scope lock exclusively, before the scope lock (`store.LockSupersedesGuesses`, a separate advisory key space; first since issue #284, so that a batch waiting for a guard run that holds it shared holds nothing the scope's other writers wait for): two such batches each walk only committed links and could otherwise close a cycle together through declared links that run against `created_at`; batches without a supersedes guess, which can only delete or re-classify a supersedes link, do not take it and keep running side by side under the PR #44 reconcile discipline. A batch re-reads its source after the scope lock and writes nothing when the source left the scope it was picked in or was archived since the pick (`dream.ErrSourceLeftScope`; the cycle books a transient cooldown, so a moved block is dreamed again in its new scope). An archive or move whose lock pass found no live block of the caller's write scopes locks nothing; when its own statement then changes the block after all (it entered a write scope in between), the transaction runs again, at most three times, and the next lock pass finds it (issue #284). A `guard-resolve` batch takes the lock of every scope of its ids in sorted order (exclusively for `archive`, shared for `keep`) and then its blocks — with their supersedes targets for an archive — in one statement in id order, `FOR NO KEY UPDATE`, which lets the foreign key's key-share lock of a link insert or an audit row through. The guard's own archive verdict holds its block from the pick on, so the only writer that could add a supersedes link from it is a dream batch with a supersedes guess; the verdict takes that batch's lock (`store.LockSupersedesGuesses`) **shared**, and the block's supersedes targets, each only when no other transaction holds them in a conflicting mode (the run holds its picked blocks for the whole batch and must not wait) — otherwise the block stays pending for the next run. Guard runs of one scope keep archiving side by side, and the scope's other writers do not wait for a guard batch; a dream batch with a supersedes guess of the scope waits for the run's commit and then finds an archived source. Every guard archive reconciles the archived block's supersedes targets. The identity row of an upsert, a declaration or a block batch is locked `FOR NO KEY UPDATE` too, so a guard run's audit insert that names it as the matched block does not wait for it. **Writer-declared supersedes (issue #197)** are pinned supersedes rows as well, written by `POST /api/store` / MCP `store` with `supersedes` in the write's own transaction (`store.UpsertBlockSupersedes`) and marked `metadata.origin='declared'`; their gates are the scope, archive, chunk, type, cycle and already-superseded checks listed in [api.md](api.md#endpoints), not dream's category/title/direction evidence. Retrieval treats a pinned supersedes at the snapshot confidence from a live block of the target's scope as settled (`store.SettledSupersedesSQL`): a dateless query drops its target whether or not the successor is retrieved (`SupersedesMap`'s settled set → `dropSettledSuperseded`, before `filterSuperseded`'s presence rule, which stays for unpinned guesses), and the guard records a match on the other end of any pinned supersedes as `clean`. A delete-resolve of a `supersedes` link reconciles the target against the remaining supersedes links (`store.ReconcileSupersedesTargets`) — the same reconcile the replace sweep and `CleanupDanglingLinks` run: back to `knowledge` (`superseded_by` → `NULL`) only when no superseder is left, otherwise the snapshot stays and the pointer moves if it named that source. A `chunk` target is never marked, so it is never reverted either. `rationale` stays NULL on automatic writes: the benchmarked V5 eval prompt emits `{target_id, type, confidence}` only; capture-at-write would be a prompt change and therefore a separate eval-gated wave. The write gate is the source block's write scope (uniform not found, no existence oracle — the GuardResolve doctrine); every resolve lands in `context_write_log` as `dream_link_resolve`. Since issue #547 the tenant prune is one of the exclusive holders too: it deletes the dream links and the blocks of the tenant's scopes in batches, each batch a transaction that takes the locks of all the tenant's scopes first, sorted — a block's child in another of its scopes (a scope move keeps `parent_id`) goes with it through the cascade (`store.PruneTenant`; before, it deleted by `ctid` across the scopes without the lock, and a declaration, a block batch or a dream batch of one of the scopes met it in a lock cycle that left the tenant half pruned). A write that waits for the lock of a scope after its unlocked scope read and finds its block moved on runs again, at most three times (`errSupersedesSourceChanged`); a block batch carries the scope it found the block in into its next run and locks both, so a block moved back and forth between two scopes does not outrun it twice. A write that still finds the block elsewhere after the third run, and a write PostgreSQL ends with a deadlock or a serialization failure, wrote nothing and answers the retryable `409 write_conflict` ([api](api.md)). The guard run takes no scope lock: it waits for no row lock at all — its pick skips locked rows, its archive verdict takes only try locks, and the key-share lock its audit row's foreign key takes on the matched neighbour is taken `NOWAIT` before the insert; a neighbour held by a deleting transaction (a purge batch, a prune batch) defers the verdict to the next run instead of closing a cycle with it (`guard-stats` counts the deferrals).

**Dream-graph traversal** (Wave 1; `graph.enabled` / `CTX_GRAPH_EXPAND_ENABLED` — the server's own default is off, the shipped `docker-compose.yml` switches it on since Wave 3) — query-time 1-hop expansion of the Dream-inferred link graph (topical/factual/causal/recurrent), confidence/type-gated + hub-damped, fused as a scale-invariant post-gravity boost before rerank. Turns inferred links into positive recall instead of write-only metadata; fully parameterized for A/B sweeps, fail-open.

## Structural links (migration 076)

Deterministic **fact** edges between blocks, kept in `context_structural_links` — a table **strictly separate** from `context_dream_links`. Dream edges are *discovered* (LLM, confidence-gated, replace-swept every cycle); structural edges are *facts* (confidence 1.0 by definition — the table carries **no** confidence column). The Dream replace/cleanup paths operate only on `context_dream_links` and therefore never touch structural edges (enforced by a negative gate: `dream.WriteLinks` replace leaves a structural edge of the same source intact). The primary key is `(source_block_id, target_block_id, link_class)`, so two different classes may coexist on the same pair; `link_class` carries no CHECK (validated in Go against the type registry's `structural_link_classes`). Both FKs are `ON DELETE CASCADE`.

The **one** structural parent (comment→issue) is not stored here — it lives on the `context_blocks.parent_id` column (present since migration 001), which migration 076 upgrades with the FK `REFERENCES context_blocks(id) ON DELETE CASCADE` (added `NOT VALID` then `VALIDATE`d for lock-thrift; the column and its index pre-exist, so `context_blocks` gains no column). `parent_id` = the one structural parent; `context_structural_links` = all further classes (`references`, `duplicate-of`, …). The client write paths that set a parent — `POST /api/store` with `parent_id`, a store item of `POST /api/store/batch` with `parent_id` or `parent_item` — write the block and the link in ONE transaction (`store.UpsertBlocks`; issue #211): the parent row is locked `FOR SHARE` in the lock pass, and `store.LinkBlockParent` refuses a parent that would close a cycle (an ancestor walk from the parent, `WITH RECURSIVE … UNION`, so an existing cycle ends the walk) before `store.PutBlockParent` writes the link — the walk runs under the supersedes locks of every scope the ancestor chain passes through (a scope move keeps `parent_id`, so a chain can cross scopes; a chain beyond the scopes the transaction holds runs it again with those locks taken in sorted order, issue #547), so two parent writes in different scopes cannot each pass the walk and close a cycle together. The price: a parent write whose ancestor chain has a member that a scope move takes into a new scope between every two runs of the write runs out of its runs and answers `409 write_conflict` — measured in the review of #547 with a mover that sends a chain member into a fresh scope in a loop: 199 of 200 parent writes refused (before: 200 written, without the cycle check across scopes); against a chain that holds still it does not happen; a batch links its items after writing them, in list order, and `parent_item` may only name an earlier item. A block batch's update items run `store.UpdateBlock`'s statement through its transaction half (`prepareUpdate` / `execHeld`) inside the batch's transaction, after the batch locked the supersedes scope of the block's current scope and of a move's target scope and then the block row; the lock order is the one `docs/api.md` (*POST /api/store/batch*, *Locks*) states. Scope isolation is fail-closed and double-lined: writes validate source ∈ writable-scopes and target in the *same* scope inside one transaction (deriving the row scope from the source; unknown/foreign/invisible targets collapse to a single error → 404, no existence oracle), and reads filter neighbours through the shared visibility predicate (read-scopes + block-grants) so a raw-SQL-injected cross-scope edge never yields a foreign neighbour. A manage-update scope MOVE sweeps both link tables in the same transaction (GD5/K8): links whose far endpoint already lives in the target scope follow (row.scope update), links whose far endpoint stays behind are deleted — dream links regenerate, and a structural link with scope-divergent endpoints could never be re-written under the write invariant. Query-time graph expansion stays dream-only by doctrine (edge-consumer table below); the role of structural edges is the UI ego-graph and fact statistics, not retrieval — AS BUILT (GD4): the ego traversal follows both data classes per hop (fair zipper over the shared node budget, GB3), the wire carries them as own arrays (`structural_edges` + delivered legends, GA8/GB2), `min_confidence` gates dream edges only — structural facts are 1.0 by definition and always pass — and the SPA renders them default-visible as curved teal arrows with a blocklist filter (GC1/GC2).

**Edge-consumer doctrine (graph-structural plan 2026-07-14).** Consumers that INFER from edges (clustering, retrieval boost, scoring, dream curation) read exclusively `context_dream_links`; consumers that SHOW or COUNT facts (ego graph, detail views, statistics, audit) additionally read `context_structural_links`. Every per-block show or count ALWAYS runs through the visibility predicate at the far endpoint (the fillDegrees pattern in `store/graph.go` — its doc comment defends exactly this leak class: "a raw count would leak the existence of foreign private links on shared blocks"); ONLY identity-free scope aggregates without block IDs in the result may skip the predicate. Any exception to this default is policy and arrives as data (a config key or type-registry field), never as a silent code fork. Short form for comments: *inference reads dream, display counts both — per-block always visibility-filtered.*

**Cluster membership reads (Achse 03 wave C1, wired: `internal/rrf` and `internal/store` import it).** `internal/clustersql` is the single shared SQL fragment for "cluster membership, scope-pure" — a leaf package for the same reason `internal/visibility` is one (`rrf` cannot import `store`; `store → blocktype → rrf` would cycle), and the same constellation once produced three inline copies of the visibility predicate. The conjunction it owns is not a convenience: `graph_cluster_member` carries no visibility logic of its own — `block_id` is the sole primary key (057), `cluster_id` has no foreign key, and the only partition information is the `scope` column (087). A membership join without `AND scope = ANY(readScopes)` therefore returns the cluster affiliation of foreign-private blocks, which is a **side channel on foreign community structure**: a caller holding a single block grant on a foreign block would see its `cluster_id` and could test which of its own blocks carry the same value, reconstructing foreign community boundaries without ever reading a foreign block. Because every cluster read of the axis (retrieval boost, ego annotation, cluster route, facet) binds the predicate through `clustersql.MemberOf`, removing it in that one place reddens all of them — the negative probe is a single edit. `store.ClusterMembership` is the batch read (`RequireScopes` first, before any query: PostgreSQL evaluates `scope = ANY('{}')` as a deterministic FALSE, so an unresolved scope set would otherwise return an empty map indistinguishable from "nothing found"). The T41 leaf rule falls out one level up and for free: a grant-only block's scope is by definition not in `readScopes`, so its membership row filters out and the block reads as "no visible cluster", never as a foreign one.

**Traversal indexes (migration 104).** The ego-graph structural legs ride two M050-pattern B-trees — `idx_struct_links_graph_fwd (source_block_id, created_at DESC) INCLUDE (target, class, origin)` and the mirrored `graph_rev` — so each LATERAL cap leg is an ordered index scan with early termination ("newest reference wins the cap slot", E5; structural links carry no confidence to order by). 104 also retires `idx_struct_links_rev` (076): `graph_rev` is target-leading too and serves the reverse per-block lookup shape (formerly the `StructuralNeighbors` reverse leg — that single-block reader itself retired in GB6, its access pattern lives on as the Q1s reverse leg) — drop-probe evidence is asserted in `TestStructuralHop_IndexPlan`, which also keeps a permanent red probe (index drop in a rolled-back tx must degrade the plan to explicit leg sorts). **Statistics/prune indexes (migration 106):** `idx_struct_links_scope_created (scope, created_at) INCLUDE (link_class, origin)` makes the daily-report window count an index-only scan, and `idx_dream_links_scope_created (scope, created_at)` covers the dream side of the same statistics surface plus the N11 prune seam (`store/tenant.go`) — both built in final form while the tables are small (the single-tx runner cannot CONCURRENTLY); the dream side is deliberately non-covering (replace-swept hot write path).

**CSR graph cache (Achse 05 W05.1, dormant until W05.2+).** `internal/graphcache` holds an immutable in-memory CSR adjacency over BOTH edge classes, built for moving the two live traversal engines (`rrf.GraphExpand`, `store.EgoGraph`) off per-request SQL hops. Two strictly separate CSR pairs keep the GA5 isolation structural (a consumer handed only the dream pair can never surface a structural edge). Layout is normative: node universe = ALL block ids incl. archived (with an `Archived` pruning hint bit — never the visibility authority), sorted by raw UUID bytes with the array index as `NodeID`; per-node adjacency pre-sorted to the consumer order (dream `raw_confidence DESC` mirroring M050, struct `created_at DESC` mirroring M104) so a per-node cap is "take the first k"; confidences as u16 fixpoints with the asymmetric conversion rule — edge weights FLOOR (`ConfToFix`), comparison thresholds CEIL (`ThresholdToFix`) — which makes cache gates provably at-least-as-strict as SQL, never laxer; `supersedes` is excluded from the CSR entirely (traversal contract); scope/type/class/origin are interned over sorted distinct names (loud build error on overflow, never a silent wrap). The builder streams three queries WITHOUT `ORDER BY` (a 10M `ORDER BY id` would force a sort spill or 10M heap fetches) and establishes total order in Go — same DB ⇒ byte-equal `Fingerprint()` regardless of row arrival. Dangling edges (transient races) are skipped and counted, never fatal. Publication is a lock-free `atomic.Pointer` double buffer (`Store.Current()` nil = not ready = consumers use their SQL path). W05.2 adds the rebuild job and lifecycle: `graphcache.Manager` owns the state automaton (Empty/Fresh/Degraded/Failed) plus the dirty clock, the scheduler goroutine `runGraphCacheRebuild` owns the cadence (inert while `graph_cache.enabled=false`, boot-build on enable, then `pending && (quiet ≥ debounce_window || pendingAge ≥ max_pending_age) && sinceLastBuildStart ≥ min_rebuild_interval`, plus an unconditional hard `rebuild_interval`). **Staleness is Dirty-Age, never build age**: 0 while nothing is pending (an idle DB holds Fresh indefinitely — a build-age model would sit ~96% of a quiet 6h cycle in Degraded), else the age of the OLDEST unconsumed signal (the youngest write never resets the clock; a write during a build survives the swap re-anchored). Degradation (`Degraded` past `max_staleness`, `Failed` at `failed_threshold` consecutive build errors) transparently returns consumers to their SQL paths — which this axis never removes. The dirty signal channel `ctx_link_write` is fed since migration 116 (W05.3): row-level triggers on both link tables, statement-level TRUNCATE triggers, and a column-filtered `is_archived`/`scope` flip trigger on `context_blocks` — every cache-relevant mutation and nothing else (a `dream_checked_at` stamp stays off the wire); `/api/status` carries a server-admin-only `graph_cache` block (state/seq/built_at/staleness_ms/counts/build diagnostics), absent on the tenant path. Since W05.5 the FIRST consumer arm exists: `store.EgoGraph` can serve its two per-hop adjacency queries (Q1/Q1s) from the snapshot — behind `graph_cache.serve_ego` (default FALSE) AND the state gate (Fresh only, decided in the scheduler). The arm is a topology accelerator, never a visibility authority: every walk candidate is batch-hydrated through the same `visibility.Predicate` the SQL arm uses (the thin `store.VisibilityPredicate` wrapper that used to sit between them fell in T04-15; the SQL arm calls `visibility.Predicate` directly) before it may enter the node set or the next frontier (bridge/scope-move leaks are red-proven against a deliberately hint-trusting stub kept in the test suite as a permanent inversion anchor), rejected candidates consume no cap slot (refill loop — differential-proven node/edge/truncated parity against the SQL arm on a fresh snapshot), and an unknown seed aborts the arm entirely (complete SQL fallback, no partial merge). Focus hydrate stays SQL; since W05.6 the post-traversal stages ride the same arm: Q2/Q2s come from `Snapshot.InducedEdges` over the DB-confirmed node set (scope-safe by construction — every endpoint passed the live predicate; the SAME `arbitrateEdgeBudget`/`mapStructEdges` helpers consume the rows, only the source differs), including a **structurally separate supersedes display segment** (unexported, no Neighbors accessor — the traversal cannot reach it by construction, only `InducedEdges`/`Degree` read it); Q3 is the E-05-3(a) hint-filtered degree via `MakeDegreeHints` (scope AND per-request type allowlist AND archived, capped by `graph_cache.degree_walk_budget`, HitCap 201 = "200+"), with the declared bounded delta — stale hints ≤ MaxStaleness, grant-only neighbours under-counted (fail-closed) — while the RAW offset degree never leaves the process (oracle gate red-proven against it). Membership in `InducedEdges` is a map, not binary search (micro-bench: ~2× faster from 500 nodes; the sorted arm stays as a test-only comparison arm for the 1M bench). Since W05.7 the SECOND consumer arm exists: `rrf.GraphExpand` can serve its edge fetch from the snapshot behind `graph_cache.serve_expand` (default FALSE) — GA5 isolation is enforced by the type system (the arm's snapshot field is a three-method `dreamGraph` interface; structural/supersedes accessors are unreachable), the hub-damping degree is counted caller-locally in the walk over the gate-passing seed-edge set (a raw CSR degree would make the fusion an observable function of foreign private link counts — oracle-gate red-proven against exactly that stub), the per-hop hydrate runs the same `visibility.Predicate` as the SQL JOIN, and hop ≥ 2 frontiers form only from DB-confirmed nodes with the T41 leaf check on the hydrated scope (bridge gate red-proven against a hint-trusting stub with lying hints). An unknown seed aborts the whole request onto SQL; every other failure keeps the byte-identical fail-open contract. With that, all three engine cut-overs (ego hops, edges/degrees, expand) are built and dark — activation is the E-05-1 decision after the W05.8 bench.

**Prune validity boundary.** `context_structural_links` needs no entry in the tenant-prune delete list — both FKs are `ON DELETE CASCADE` (076), so the bounded block-slice DELETE cascades the edges (amplification per slice is bounded by max out-degree). This holds only as long as the write invariant (row scope = source scope = target scope) holds: if a scope-move path moves BOTH endpoints out of a scope, the link row survives a tenant prune carrying the scope of a purged tenant — no CASCADE fires because the endpoint blocks are not deleted. That is an orphaned metadata row without a read-path leak (read paths gate on `context_blocks.scope`, authoritative), but a hygiene gap; the scope-move link sweep (plan wave GD5) closes it.

## Workflow state (migration 077)

`context_blocks.workflow_status` (nullable `VARCHAR(50)`) is the per-block workflow **value**; the SET of valid states, the entry point, terminal flags and the forge open/closed mapping are Achse-01 type-config **policy** (the block-type registry `workflow` section — `{states, initial, terminal, forge_state_map}`). NULL means the block has no workflow (the entire knowledge corpus — no backfill). There is deliberately **no** CHECK constraint (M045 line): the Go transition validator `blocktype.Set.ValidateTransition` enforces the per-type state machine against the registry data, so changing the status set is a data edit, never a schema change. The transition graph is complete over the configured states (a transition is valid iff both endpoints are configured states); `terminal` is not an outgoing constraint (reopen closed→open is real), it flags which states map to the forge "closed" state. A type write (`PUT /api/types/{name}`, manage `type-update`/`type-create`) refuses a `forge_state_map` that contradicts it — `closed` onto a status outside `terminal`, or `open` onto one inside (422; issue #491): the forge sync projects a block's state by terminal membership, so such a map made every pulled closed issue read as open and the next push reopen it (or close every open one). A stored row of that shape (written before the rule, or past the API) still loads, with a warning at every registry load, so no instance fails on it at boot.

The board/list path rides the partial keyset index `idx_blocks_workflow_board (scope, type_name, workflow_status, updated_at DESC, id DESC) WHERE workflow_status IS NOT NULL AND NOT is_archived`. A status-filtered board column is ONE ordered index range scan with a row-comparison keyset cursor `(updated_at, id) < (cursor)` — no Sort. The status-unfiltered list ("all issues, newest first") is a **per-status merge in Go** (one range scan per config status, k-way merge on `(updated_at DESC, id DESC)`), because the index cannot order across `workflow_status` values — a single naive `ORDER BY` over all statuses would force a Sort over the whole scope. Scopes are iterated the same way (scalar `scope =` per stream: a `scope = ANY(array)` on the leading index column would defeat the ordered scan). Label filters are a documented post-filter inside the range scan (`metadata->'labels'`); the server clamps the page to ≤ 100. `EXPLAIN` gates prove both paths at 10k seeded issues.

## Cluster topic identity (migration 124)

The 057 overview family replaces all three of its tables on **every** rebuild, so a Louvain cluster has no identity across runs: `cluster_id` is the smallest member UUID of the community and turns over silently as soon as that one block leaves it. `graph_cluster_topic` is the identity the teardown does not touch — the endpoint an edge can point at and a retrieval signal can refer to. The cluster flows, the topic stays.

A topic belongs to exactly **one scope**, continuing the 057 scope invariant one level up: identity hangs off the `(cluster_id, scope)` node row, not off the scope-spanning `cluster_id`. That is what keeps a label from ever carrying foreign-scope content and keeps two tenants from sharing a handle (which would be an existence oracle above the one `handler/overview.go` closes). The handle is `gen_random_uuid()` (**v4, never uuidv7**): a v7 timestamp would ship "when did a rebuild first see this community" on the wire, while `created_at` sits in a column that is read scope-filtered. `origin_kind`/`origin_topic_id` describe the birth (fresh vs. split), `merged_into` the death by merge; both self-references carry `ON DELETE SET NULL` so retention can purge old tombstones without tearing a lineage chain, and both get partial companion indexes — Postgres indexes no referencing FK side on its own, which would make that purge quadratic. `core_blocks` lives on the **topic row**, not only on the node row: a batch import that tears a partition apart over several rebuilds only finds its old identity again if the dead topic's substance survives the teardown, so the assignment pass matches birth candidates against the `core_blocks` of retired topics **of the same scope** and re-attaches instead of giving birth. Organic growth keeps running over the live predecessor generation — both paths active in the same run.

The core itself is picked by **intra-cluster weighted degree** (`clustering.intraDegree`), computed in the same symmetrization pass `computeClustering` already runs — the summed link confidence of a block's edges that stay inside its own community. It replaces the degenerate `repr_title` mechanism as the label basis: representative choice today orders by `quality_score DESC, id`, and with two thirds of the candidates sitting on the column default the uuid tiebreak decides, so a cluster's name is its oldest block rather than its subject. Edges **crossing** community boundaries are excluded — the core must describe what holds a cluster together, not what pulls at it; without that filter the bridge endpoints would outrank their peers and the core would be chosen by the very edge the partition rejected. The pass walks the sorted edge keys rather than the map, because float addition is not associative: last-ULP drift under Go's randomized map order would be cosmetic in the Q score but load-bearing here, where degree order is hashed into `core_hash` and a swapped neighbour pair would re-label a topic that never moved. Every node gets an entry, isolated ones at zero. Cost is O(|edges|) time and 8 B per node — 1.6 MB at the 200k node cap.

`graph_cluster_node` gains the assignment (`topic_id`, nullable — NULL means "not yet assigned" and the read path treats it fail-closed) plus the run's core (`core_hash`, `core_blocks`). The partial unique index `uq_gcn_scope_topic` is the injectivity gate: the mutual-plurality assignment guarantees no topic is claimed by two clusters, and without the index an assignment bug would silently merge two identities — with it the persist transaction breaks on 23505 and the previous map stays readable. There is deliberately **no backfill**: it would have to adopt today's `cluster_id` as the topic identity, i.e. exactly the value whose instability this line fixes.

**Label schema (migration 125).** Split off from 124 because identity and label are separately deployable — 124 plus the assignment pass yields an identity-stable map without touching labels, 125 lays the label on top. `label_source` ranks `manual` > `llm` > `fallback` > `none`: the automatic path only ever writes over `fallback` and `none`, `llm` is replaced solely by the label pipeline itself, and `manual` by nobody. The `manual` value ships in the vocabulary now even though its write endpoint is a later wave — the automatic path has to be able to respect it before anyone can set it, otherwise adding pinning later would be a schema change in the middle of a running pipeline. `label_core_hash` is the drift anchor: the pipeline re-labels exactly when it diverges from the node row's `core_hash`, so membership churn at the cluster's *rim* costs no LLM call. `label_stale` is the materialized form of that comparison — the comparison itself spans two tables and is therefore not index-addressable, which would force the per-tenant, per-interval selection into a sequential scan over a table where tombstones coexist with live topics; it defaults to `true`, fail-closed towards labeling rather than towards overlooking. Three CHECKs pin the vocabulary, a rune-exact 1–120 length (`char_length`, same rune accuracy the digest title truncation uses against SQLSTATE 22021 — a 120-umlaut label weighs 240 bytes and must still fit), and the rule that a non-`none` source requires a label, so "marked as labeled but empty" cannot become an invisible gap in the map. There is deliberately **no confidence field**: project empirics (dream v3) put the model's self-assessment out of use as a gate, so validation is structural and lives in code. `idx_gct_label_pending (scope, label_stale, label_attempts) WHERE retired_at IS NULL AND label_source <> 'manual'` is the selection index — the predicate is exactly the selection condition, so no tombstone and no pinned label ever enters it.

**Cluster centroids (Achse 03 wave C8, migration 128).** `graph_cluster_centroid` holds one averaged member embedding per `(topic_id, scope)` and answers the question the C3 seed derivation cannot: *where does this QUESTION live*, as opposed to *where do this query's hits live*. The seed arm is circular by construction — a query whose RRF hits are poor gets a prior built from those same poor hits — and the centroid arm is the way out, at **zero extra model cost**: the query embedding already exists, it was produced for `rrf.Search`. Three properties carry the build. It runs in its **own transaction after the persist commit**, and in the parent process (the W8 retention purge is the precedent, so nothing crosses the worker IPC protocol): the rebuild is all-or-nothing under `graph_overview.rebuild_timeout`, and a centroid step inside it would, at the target scale, roll back a complete and good rebuild whenever the sum overruns — reproducibly, every cycle, while `C4` correctly switched the signal off and thereby hid the freeze. It is **incremental over `member_hash`**, a sha256 over the sorted member set with each member tagged by whether it currently has an embedding: a full pass is ~6,9 GB of embedding I/O at 10M members, so an unchanged partition is skipped entirely — and that diff is the whole reason the table keys on the stable topic identity rather than on `cluster_id`, which is the smallest member UUID and turns over per run, so a diff over it could not tell "unchanged" from "new". The coverage marker in the hash is not decoration: a block whose embedding is backfilled later changes the centroid without changing the member set. And a **minUUID rename is not a recompute** — `cluster_id` is a run-local use column here, so a community that was renamed without a member moving costs one `UPDATE`, not an `avg()` over unchanged embeddings.

The read path binds `scope = ANY(...)` and sets `hnsw.iterative_scan`/`hnsw.ef_search` even while no index exists, so arming one is never a silent recall change; the distance `ORDER BY … LIMIT` sits in its own innermost select, because the design's original shape (`DISTINCT ON` in the same select as the distance ordering) forces a sort by `topic_id` and would have made the threshold index unusable after building it. The two arms fuse as `share_final = (1-w)·share_seed + w·share_centroid` over the **union** of their clusters — a cluster the seeds never voted for can win on centroid evidence alone — with `share_centroid` min-max normalised inside the probe window. An **empty probe means "the arm did not run"**, not "similarity 0": scaling every seed share by `(1-w)` against an empty table would push winners below `min_share`, so merely arming the feature would weaken the C3 signal it exists to extend. Everything ships dark (`cluster.centroid_build` and `cluster.centroid_enabled` default false).

There is deliberately **no HNSW index in the migration**. `cluster.centroid_ann_threshold` is a declared resource limit and the build arm creates or drops the index around it, with hysteresis so a corpus sitting on the boundary does not pay an index build every cycle. Its default is **5.000, calibrated against the C8 measurement** rather than assumed: `halfvec(1024)` is 2052 bytes and therefore lands just over the 2-kB TOAST threshold, so every centroid is an out-of-line read — 3.604 B touched per row on a full scan, 1,7× the "~2 kB/row ⇒ ~170 MB at 83.000 rows" the design budgeted — and the measured exact-scan p95 holds the 25 ms retrieval budget up to roughly 3.300 centroids. The design's build-and-swap prescription is deliberately **not** implemented: it presumes the table is fully rewritten every cycle, and re-introducing that rewrite to swap a table would trade the index churn for exactly the 6,9 GB the incremental diff removes.

**Cluster injection (Achse 03 wave C9).** The stage's last half is the only one that can change the result **set** rather than its order: unseen siblings of a winning cluster, appended with a deliberately low synthetic score. It is the graph stage's NEW-neighbour path on cluster evidence instead of edge evidence, and it runs **after the boost, still inside the stage, i.e. before GraphExpand** — after the boost because the winners and their shares decide who may be injected at all, before GraphExpand because an injected sibling then becomes a legitimate graph seed, which is the whole reason the categorical prior sits ahead of the edge traversal. `cluster.inject_max` defaults to **0**, so the shipped state adds nothing and arming it is a step that follows the eval measurement rather than a deploy.

Two conjunctions gate the hydrate, and they answer different questions: `clustersql.MemberOf` decides which **membership rows** may be read (the community side channel), `visibility.Predicate` decides which **blocks** may be delivered. They are not interchangeable — a red probe that keeps only `NOT cb.is_archived` still leaks a block that was **re-scoped between two rebuilds**, because the membership row records the partition the rebuild ran in while `context_blocks.scope` is authoritative. The request's own filter (`rrf.RequestFilter`: category, tags, categories_exclude, types_exclude) is a third conjunct of the same `WHERE`, ahead of the `LIMIT`, so the window fills with siblings that pass it; the graph neighbour hydrate carries it at the position of its visibility predicate, after the per-seed cap (moved in front of the cap alone, a filtered request's neighbour count would tell whether an invisible block among a seed's top edges matches the filter). An empty type allowlist is a hard error rather than zero rows, so a registry wiring bug surfaces instead of reading as "nothing to inject"; the stage's fail-open contract then keeps the boosted results and reports the error. Placement adds **no second knob**: an injected block carries only cluster evidence, so it enters at `topScore * boost_weight * share` — a stage permitted to move a native result by at most `1+boost_weight` may introduce one at at most `boost_weight` of the top, which keeps a single dial governing both and keeps cluster evidence structurally below direct retrieval evidence. The cap sorts by share first, then quality, then id: `quality_score` ranks blocks *within* a cluster while share ranks how much the query is about that cluster at all, and a quality-first cut would let one strong cluster starve a more relevant one. Injected results carry `via_cluster` plus the share in `cluster_boost`, and every derived score field (`rrf_score_original`, `rerank_score`, `cosine_sim`) is cleared — a synthetic result that keeps a zero value where a measurement belongs is how it starts to look native.

**Root-map reads (Achse 02 wave W-B, wired: `rootmap/run.go:260,264,270` and `handler/digest.go:150`).** Three additive reads in `internal/store` supply every number the root map prints, and each mirrors the `GraphOverview` posture line for line — `RequireScopes` as the first statement, `WHERE scope = ANY($1)` in every FROM, no unscoped row pick. The stakes differ from a request path: the map is a **persisted** artefact, so a scope leak here is a database row travelling through backups, exports and the context of every agent that loads it, not one byte on a wire. `OverviewTotals` folds the per-`(cluster,scope)` rows into one visible size per cluster **before** classifying small vs. large, so the collector line follows what the caller can see instead of the partition layout. `OverviewMeta` aggregates the migration-123 liveness columns with SUM for the counts (max would report one partition's numbers as the window's and break the coverage arithmetic), max for the stamps, and a cap reason that deliberately excludes `advisory-lock` — contention means another instance is building this very partition successfully, and rendering it as a freeze would print a cap that does not exist. It also isolates **stale** rows: the rebuild teardown only deletes meta rows for scopes that still have cluster rows, so a scope whose blocks left the corpus keeps a success row for good; such a row is excluded from every sum and reported by name (`StaleScopes`) so the map can call it neither fresh coverage nor a gap. `ActiveBlockCount` is the only new O(corpus) step of the axis and the only one with a hard cap: the cap runs in its **own transaction** via `set_config('statement_timeout', …, is_local => true)` — `SET LOCAL` outside a transaction block is a no-op PostgreSQL answers with a warning, and a `SET` without `LOCAL` would stay on the pooled connection and cap unrelated queries at random; the Go deadline sits half a second **behind** the database cap so it is a backstop rather than a mask. On expiry the result is `(0, false)` — never a `pg_class.reltuples` estimate, which can filter neither `scope` nor `is_archived` and would freeze the GLOBAL corpus size into one tenant's block. The count itself rides `idx_context_scope_active` (022) as an index-only scan, so no migration and no lock. `GraphOverview` additionally short-circuits `EdgeLimit <= 0` without touching `graph_cluster_edge`; the live route cannot reach that branch (the handler parser enforces `edge_limit >= 1`), which is why the wire envelope and its golden test are unaffected.

**Root-map renderer (Achse 02 wave W-C, wired: imported by `internal/handler` (`digest.go:13`) and `internal/events` (`scheduler.go:29`)).** `internal/rootmap`'s renderer (`rootmap.go`, `format.go`) turns those numbers into the map text and is deliberately **pure** — no database, no clock, no config lookup, the same discipline as `handler.buildOverviewResponse`. That is a property of the renderer, not of the package: `run.go` is the one file that touches the world, by the package's own header ("The renderer next door stays pure; everything that touches the world lives here"), with ten `store.*` call sites of its own (`:175`, `:190`, `:201`, `:252`, `:260`, `:264`, `:270`, `:274`, `:284`, `:401`). Two properties carry the renderer. First, the output never exceeds `BudgetBytes`, by **measuring** rather than estimating: lines are appended while the reserved footer still fits, and an oversized footer or a budget too small for the skeleton is an error, never a silently truncated map (a guessing renderer outgrows the 50 KB write cap of the public store API, and nobody would notice — the old topic map bypasses that cap by construction and sits at 80 KB). Second, every cluster lands in exactly one of three buckets — rendered, below `small_cluster_max`, cut by the budget — under the rule "rendered beats small beats cut", and `Render` **asserts** both bucket sums instead of trusting them: at ~10^5 clusters against ~95 lines the "small" and "cut" sets overlap by default, and the pre-revision two-line footer would have counted tens of thousands of clusters twice. The head line names the rendered mass, which is only known after the measuring loop, so the loop measures the head with the TOTALS substituted for the rendered counts — an upper bound (never fewer digits), which breaks the circle without a second pass. No wall clock enters the text (only `computed_at`/`last_attempt_at`, which describe the partition rather than the moment of rendering) — the precondition for content idempotency later. Coverage follows decision E11-02: checkpoints are **not** a gap but operational compaction artefacts, so the coverage figure is measured against the knowledge corpus (active minus operational types), the operational types get their own line naming them as a type-policy decision, and the raw corpus number stays visible beside it — 97,9 % instead of 16,8 %, same numbers, correct statement. A capped corpus count (`ActiveKnown = false`) removes denominator and percentage entirely instead of substituting an estimate. Degradation D0–D5 is complete and never throws: LLM label → heuristic → `repr_title` (cut rune-exact at 60 runes, the 22021 trap) → no stable id (the `repr=` handle remains, the head says so) → empty map with the three cases told apart in words → cap line above everything else (a truncated context must still carry the warning); `advisory-lock` renders **no** cap line, because contention is not a freeze. `AllowsUpsert` is the BP-6 rule as a pure predicate — an empty or stale map never replaces a good one, and only a genuinely fresh tenant (no clusters, never built, no stale scopes) may write the "no clusters yet" map; a render landing inside a global rebuild's TRUNCATE window sees zero clusters while the meta row still reports the old `cluster_n`, which is exactly the case the rule exists for.

## Recall measurement (migration 110)

`context_recall_runs` stores the aggregates of the recall_check probes (Achse 01): scope-stratified ANN-vs-exact recall runs quantifying how close the production HNSW index tracks a brute-force reference. **Aggregates only** — the table never carries query texts, block IDs, or vectors; `internal/recall.Insert` enforces a fail-closed 12-key allowlist on the `meta` JSONB (unknown key or non-scalar value rejects before the write), with unit + integration tests pinning the guard. `scope` here names the *measured* scope (measurement-object label, not a visibility discriminator — the table is server-admin-only). No backfill path exists by design: historic `context_access_log` rankings would be ANN-scored-against-itself (no brute-force reference leg ever existed) and thus fake recall data. W01-1 ships table + persistence (`Insert`, `LatestByStratum`) without callers; the scheduler arm (W01-3/4) follows. The stratification/loo access path (and, read-only per conflict rule K3, the future Strategy-Selector cardinality estimate) rides the partial covering index `idx_blocks_stratify_covering (scope, type_name) WHERE NOT is_archived AND embedding IS NOT NULL` (migration 111) — per-scope counts of embedded active blocks are Index-Only-Scans instead of a ~14 GB full heap scan at 10M rows.

W01-2 lands the probe mechanics (`internal/recall`, wired: `internal/events` (`recall_check.go:174`, `RunOnceWithHooks`) and `internal/handler` (`status.go:1265`, `LatestByStratum`), both reachable from `cmd/ctxd`): `RunOnce` = stratify (per-scope `SnapshotForTenant` allowlists, largest scope per class small/medium/large — bounds pinned to the E-02-1 selector thresholds 4096/65536 per K3 — plus a base-set pseudo-stratum `all`) → sample (real logged queries via a bounded 30d/500-distinct backward stream joined touch-free against `context_embed_cache` — `embedcache.PeekByHash`, a plain SELECT, never the `hit_count`/`last_access` touch-UPDATE of the hot path — with deterministic leave-one-out fill for thin strata; wire-free, no embed call ever) → two-leg probes → aggregate → persist. Each probe runs two `BEGIN READ ONLY` transactions with production-identical predicates *minus the grant arm* (documented deviation): an exact leg (`enable_indexscan/bitmapscan=off`, the brute-force reference) and an ANN leg (`enable_seqscan/sort/bitmapscan=off`, `hnsw.iterative_scan='relaxed_order'`, optional `ef_search`). Three barriers kill the frozen-generic-plan silent bypass (pgx `QueryExecModeCacheStatement` + PG's 5-execution generic-plan switch would otherwise let one leg silently ride the other's plan from probe ~6): `plan_cache_mode=force_custom_plan` per transaction, leg-distinct statement texts (`/* recall_leg:exact|ann */` markers = separate cache entries), and an `EXPLAIN (FORMAT JSON)` plan proof in EVERY probe transaction on the same connection (ANN leg must contain `idx_embedding_hnsw`, exact leg must not — violation writes `valid=false` + `meta.invalid_reason`, never a recall number). Recall is distance-based and ties-robust: `n_eff = min(k,|E|)`, hit = ANN distances ≤ last-exact-distance + ε, `recall = hit/n_eff` — a 17-block scope at k=75 can reach 1.0 instead of being pinned at ~0.23. Every row carries environment stamps (pgvector/PG version, HNSW indexdef, effective embed model) — measurement series survive index rebuilds and extension bumps interpretably.

W01-3 wires the arm into the scheduler (`runRecallCheck`, its own goroutine — no new ticker case): cheap strata (small/medium) run on `recall_check.interval`, expensive strata (large/all) anchor to the `recall_check.offpeak_hour` wall clock with ONE expensive stratum per off-peak run rotated round-robin. Interactive demand defers the launch entirely and, once running, parks the run before every probe (up to `park_max_ms`, then the remaining rows abort visibly as `demand_deferred`). Budgets are two-dimensional: the time clock (`exact_budget_ms`) plus a touch budget (`exact_touch_budget_bytes`, `0` = auto 25% of shared_buffers) that pre-estimates each stratum at ~5.5 kB per row per exact leg, scales the query count down (floor 5 — below that the row refuses a pseudo-statistic), and stamps `meta.exact_touch_bytes`; `meta.buffercache_delta` lands best-effort when pg_buffercache exists. A janitor line deletes rows past `recall_check.retention_days`. The last-run stamp is the ADDITIVE `LastRecallRun()` — `LastArmRuns()` stays byte-identical because the status collector binds to it via an optional interface assertion that a signature change would break silently (compile-time pins guard both shapes).

W01-4 surfaces the telemetry: `/api/status` carries a server-admin-only `recall` section (absent on the tenant path — recall metrics reveal scope existence/size) with the process `last_run_at`, the latest measurement per (stratum, scope, k) including `age_ms` staleness and the `scope_changed` flag (a scope hop is surfaced as its own event so a trend reader never mistakes it for a recall regression), and `invalid_runs_7d` — the fail-closed visibility counter for plan-assertion violations and demand/budget aborts. `state.sh` prints the last valid run's date + average, degrading to `n/a` on pre-110 schemas.

## Distillation source abstraction (Achse A02 wave A02-2, wired)

`internal/distillsource` is the contract between the distiller arm and the stores it reads: types and error classes, no query, no driver, no config. It is **wired**: besides its one implementation, `internal/events` imports it in five non-test files (`distill.go:47`, `distill_select.go:52`, `distill_extract.go:63`, `distill_block.go:102`, `distill_spend.go:47`), and the config group and the arm exist. `Source` is seven methods (`Label`, `Sessions`, `HasNew`, `Head`, `Read`, `QuietFor`, `Close`) over four types: a `Ref` (the readable unit plus its watermark), an `Item` (one prompt-ready piece of foreign text with its `promptguard` attributes, its `Origin`, its sensitivity and its untrusted flag), that `Origin` (the citation anchor — `(BlockID, ChunkIndex)` for a ctx source, `(RowID, ChunkIndex)` for a foreign row, with the message ordinal carried as a readability field rather than an identity), and a `Batch`. Three properties are the contract rather than a caller's discipline. **A watermark is a half-open range `(from, to]` and comes from the ROWS, not from the items**: a row that was read and deliberately dropped — an undecodable payload, a multimodal content that folds to no text — is covered, and a watermark derived from the surviving items would re-read it on every tick forever. `Batch.Complete` is the counterpart: false means the read covered no row it could name, and a caller must not advance past it. **A source never truncates silently** — oversized material becomes several items or a head that is MARKED as truncated, and the mark travels with the item, so a quote gate verifies against exactly the text the model saw. **A source never invents a classification**: `Sensitivity` and `Untrusted` are the source's own answer, and a source without one reports the fail-closed rank explicitly instead of leaving it to a zero value. The four error classes are the strings a caller's journal records; two of them (`query_failed`, `schema_untrusted`) are members of the `dr_error_class_known` CHECK verbatim, while `source_unavailable` and `no_active_rows` are deliberately NOT error classes there and must be mapped by the arm — the journal is readable over `/api` and lives for 90 days, so a driver's own text never reaches it.

## Checkpoint reader over the ctx corpus (Achse A02 wave A02-3, wired)

`internal/distillsource/ctxcheckpoint` is the implementation of that contract, over ctx's own data: the compaction checkpoints the hermes `ctx_checkpoint` plugin writes into `context_blocks` (since v5.29.0 over MCP dispatch or REST, with the memory engine contributed by W4-NERF; one chain writer, the same head → manifest → parts shape on either transport). Like the abstraction above it is **wired** — `Scheduler.newDistillSource` constructs it (`events/distill.go:2012`) and `events/distill.go:431` reads its `TypeName` — while the layering rule that shaped it still holds: the package imports neither `internal/config` nor `internal/events`, so every tunable (read scope, category, session horizon, the two caps) arrives through `Options` and the arm owns the keys. Four decisions carry it, each measured against the live corpus rather than assumed. **The readable atom is a manifest with all of its parts, never a single part**: 5 133 of 5 477 listed parts (93,7 %) carry no `### Message` header at all, because the producing chunker cuts inside a single message whenever that message exceeds a third of its 36 000-character limit, so a part read on its own has no attribution — the role is reconstructible only by walking `metadata.source_block_ids` in order and carrying the last header across part boundaries. Measured over a full walk of the corpus the carry attributes **100 %** of 52 865 chunks; a per-part reader leaves the same 93,7 % with an empty role. The header grammar is exact rather than lenient (`### Message <digits> — user|assistant`, separator U+2014): the strict shape matches all 1 543 header occurrences in the corpus, so a looser dash class would only widen the surface on which body text can be mistaken for an attribution change. **The watermark is `created_at` in microseconds, not the uuidv7 prefix** — PG18's uuidv7 is only millisecond-monotonic and its `rand_a` bits are random within the millisecond — and because that watermark is not unique, the reader never advances into the middle of a watermark group: a batch either takes a group whole or ends in front of it and reports `Complete=false`. That is what makes correctness independent of collision-freeness, which holds today (0 deviations between `ORDER BY id` and `ORDER BY created_at, id` over 5 961 blocks, 0 microsecond collisions among manifests) and stops holding at target scale. A naive keyset instead writes the watermark into the group and loses every member that fell outside the window, permanently. **Material is chunked, never head-capped**: a part body is p50 = p95 = max ≈ 36 000 characters against a 4 000-rune cap, so a head cap covers 11,1 % of it — and since the dedup ledger hashes the text that was shown, the remaining 88,9 % would be marked seen for good, a permanent loss disguised as a cost parameter. The concatenation of a part's chunks is byte-identical to its stripped body, with no overlap, so the quote gate verifies against exactly the chunk a model saw and the ledger sees each piece once; cuts prefer a message header, then a paragraph break, then a line break, and fall back to the hard rune cap when the best candidate sits closer than a third of the budget. Runes throughout, never bytes. And the ~498-character boilerplate head is **stripped** before anything else: it is byte-identical in 100 % of the parts, which makes it exactly the text a substring quote gate would accept as grounded without the model having read one line of material.

The candidate query is the one part of this reader that is not corpus-independent by construction, and it is the gap through which the first design draft's "measured, not claimed" label fell — `Head`/`HasNew`/`Read` were verified, `Sessions` was verified along with them by assertion. `GROUP BY … ORDER BY max(created_at) DESC LIMIT n` has no skip-scan behaviour in PostgreSQL, so its cost scales with the number of checkpoint **blocks**, not with the number of roots: on the live corpus it is a `Seq Scan` over 5 955 rows / 3 672 buffers / 7,8 ms, it runs once per tick (96×/day), and §6.6 gives the checkpoint raw text no retention path at all. `Options.SessionHorizon` caps it to roots with activity inside a window, and the cost of that cap is explicit rather than hidden: a root older than the horizon disappears from the **candidate list**, while `Read`, `Head` and `HasNew` still take its session id and never consult the horizon. Verified on a one-million-row fixture the test owns: the design's full aggregation carries a `Seq Scan` over `context_blocks`, the shipped query does not — and the `Read` lookup enters as a `Bitmap Index Scan` on `idx_blocks_checkpoint_root`, while the `IS DISTINCT FROM` formulation loses the index entirely. That pair is the discriminating probe, not the `IS NOT NULL` line: Postgres derives the null test from the strict equality, so with it and without it the plans are identical. **What the horizon does depends on how much of the corpus it selects, and that is a property of the INGEST RATE rather than of the row count** — a distinction a first measurement got wrong and a second one corrected. The live corpus grows at 140,1 checkpoint blocks per day (5 961 over 42,5 days), so a million blocks span some twenty years and the 30-day default selects a fraction of a percent of them. The crossover sits between **1,26 % and 0,42 %** selectivity, measured as its own series at a million rows: no cap 53,4 ms · 1 year (5,11 %) 34,5 ms · 90 days (1,26 %) 34,7 ms · **30 days (0,42 %) 4,05 ms** · 7 days (0,10 %) 3,75 ms · 24 hours (0,014 %) 0,47 ms. Above the crossover the timestamp is only a heap filter on the corpus-wide bitmap and the window buys nothing; below it the planner takes `idx_context_created` and the cost falls by two orders of magnitude. A contributing reason the bitmap wins for so long is a planner estimate: `metadata ? 'source_block_ids'` is estimated at 97 rows against 17 858 actual, a factor of ~184, so the bitmap looks cheap until the window is narrow enough to beat it outright. **The margin is worth naming:** the 30-day default clears the crossover by roughly a factor of three in ingest rate, so a corpus that reaches a million blocks in six years rather than twenty would push the same default back above it. The number to watch is the ratio of window to corpus time span, not the block count — which is why the gate measures the series instead of a single point. The aggregation runs over **manifests** rather than over every checkpoint block, because the corpus also carries 160 session pointer blocks that hold a fresh timestamp and no new work — ranking by those would push a root with actual material off the end of the list. Two properties are worth naming. `maxItems` is an **atom selection bound**, not a hard item ceiling: the first manifest of a batch is delivered whole even when its chunks exceed the cap, because a manifest is indivisible and the largest live manifest yields 558 items against a `rows_per_read` of 400 — a batch that can never cover its first atom never advances its watermark, and a hard ceiling would turn that into a permanent stall. That is now the CONTRACT's atom exception rather than a deviation of this reader (`distillsource.go`, `Read`) — a source whose atom is a single row never reaches it, because one row can never exceed a positive item cap by itself. `maxRunes` stays hard, enforced per item by the chunker. And a part listed by two manifests is delivered **twice**: dropping the repeat is the ledger's job (A02-6), and a reader that deduplicated here would hide from the ledger the very load it is measured on.

The same indivisibility governs a **watermark group**, and that took a second pass to get right. The end-of-window guard in `manifestHeads` protects only the far edge of the read window; inside the returned set several manifests may share one microsecond, and the first version let the item cap stop between them. The watermark then named a group whose remaining members had never been delivered, `Complete` still reported `true`, and the next read — strictly above that value — could never reach them: silent, permanent loss at exactly the edge the group rule exists to protect. The cap therefore stops only where the next manifest begins a NEW group, which is the rule `watermarkGroup` already applied at the other edge. Three tests hold it: the window path, the `watermarkGroup` path, and a group sitting in the middle of the delivered set.

## The distiller arm skeleton (Achse A02 wave A02-5, gates and journal only)

`internal/events/distill.go` is the first WIRED piece of that axis: `runDistiller` runs as its own goroutine next to `runRecallCheck`, and everything above it — the reader, the contract, the config group — finally has a consumer. What it does not yet do is the larger half: there is no selection, no LLM call, no spend guard and no block write in it, so a tick that finds material opens the two-phase journal row and closes it as `partial` with the watermark **unmoved**. That is the truthful outcome rather than a placeholder: `ok` would claim a completed range, and raising `watermark_to` without durable insights is exactly the loss the two-phase order exists to prevent. **Own goroutine, never a case in `Run`'s central select**, for the reason `runTopicLabeling` writes out one screen up — once the LLM call lands, one tick is minutes of sequential inference, and a ticker arm would hold the loop that also drives guard and digest. The gate measures that rather than asserting it: with the tick parked for the whole guard interval the guard and digest stamps keep advancing (62 s run), while the same probe against a variant driven from the central select leaves both at the zero time for 110 s.

**The journal is the only state.** The watermark of a source is `max(watermark_to)` over its non-`running` rows, the "same reason as last tick?" decision reads the newest row of the same `source_key`, and a restart re-derives both from the table — nothing lives in a struct field, which is migration 135's own contract. Two consequences follow and both are load-bearing. The **startup sweep** (`running` ⇒ `killed`/`daemon_restart`) runs before the first tick and is a correctness condition, not hygiene: the derivation excludes `running` rows, so an orphan left by a killed daemon hides its own `watermark_to` and the arm would re-process a range whose insights are already durable — probed as a hand-inserted orphan at `watermark_to = 500`, where the derivation answers 0 before the sweep and 500 after it — and probed through the arm's **boot path**, not through a direct call, because what the design makes a correctness condition is the ordering *"only after that may the arm run"*, and a test that calls the sweep itself cannot notice the call disappearing from the goroutine. **Several ctxd on one database (issue #366):** a tick runs under the distiller's **arm lock**, a session-level advisory lock tried at the start of each tick and held on a connection of its own until the tick ends; an instance that finds it held skips that tick (debug line, no journal row) — every instance hears every checkpoint write, so the holder ticks for it. The sweep runs under the same lock, at the arm start and again at the start of every tick: a `running` row found by the lock holder belongs to a tick that is over (a killed process, a panicked tick), never to a live tick of another instance. Before, the startup sweep of a second instance closed the first instance's live run as `killed`, the first instance then wrote its result over it (`ok`, its watermark), and a second instance's tick opened a run of its own on the same root beside the first one, reading and distilling the same range twice; and an orphan of a dead instance stayed `running` until some instance restarted. The run's journal writes name the open row (`outcome = 'running'`): if the lock ends with its connection while the tick runs on and another instance's sweep closes the row, the run books nothing more and leaves the row as the sweep closed it — the state a crash leaves, which the dedup ledger already recovers. The lock costs one pooled connection per instance for the length of a tick; a tick skipped for a held lock retries after the demand retry (5 s) instead of waiting for the idle fallback. Since every tick sweeps, the boot-path probe above no longer tells the startup sweep from the boot tick's own — both run before the first derivation; the startup sweep alone still closes the orphans of an arm that is switched off. An instance of a release before this one takes no arm lock: during a rolling upgrade the newer instance's ticks close the older one's live runs, and the two distil side by side — finish the upgrade, or switch the distiller off on the older instances meanwhile. And the **state-change rule** — gates 1–4 write only on a changed reason, gates 5–7 write every tick — keeps the journal readable: at a 900-second cadence over four roots an unconditional `no_new_rows` row would be some 140 000 rows a year and would bury every diagnostically interesting line. Both halves are probed through the same entry point, so the contrast is the rule and not a flag a test set: ten ticks of an always-write gate produce ten rows, ten ticks of a state-change gate produce one, and a changed reason writes again. **Failures obey the same rule**, which extends the design's wording rather than reading it literally: it writes the rule for skips because that is where the flood was first seen, but the argument does not care which column carries the answer — without the extension the same reader error journals at two different rates depending only on which sentinel it wrapped, throttled as a skip for one and 384 rows a day for the other. A failure that alternates with anything else still writes; only an unchanging one is silent, and its first row stands with its timestamp.

The arm also carries a **last-run stamp** in the shape the recall arm established — its own narrow method, never folded into the shared `LastArmRuns` signature — and it needs one more than its neighbours do. Stamped past every gate that defers, it separates two states nothing else can tell apart from outside the process: an arm reaching its source and finding no candidate root (a wrong `distill.checkpoint_category`, or a scope holding no checkpoints) writes no journal row on purpose, because there is no session to key one on, and without the stamp that is byte-identical to an arm that never ran.

**The `source_key` is three-part** — `<label>:<scope>:<session>` — because neither `distill_run` nor `distill_seen` carries a scope column. With a two-part key the cross-run dedup ledger would be scope-blind: a chunk seen once in scope A would be dropped in scope B where it was never distilled, and the only trace would be a `rows_dropped_dup` counter; the same key would also turn `distill_seen` into an existence oracle across scope borders. The tick-level form with an empty session is what the gates ahead of the candidate list write under, and it does not collide with a session key because **an unnameable root is refused before it becomes one**. That refusal is enforcement, not an assumption about the corpus: `Sessions` only filters `IS NOT NULL`, so the empty string passes it, and `metadata.root_session_id` is writable over the public store path — the `checkpoint` type stays claimable after migration 148 and `compaction-checkpoints` is not a reserved category. An empty root would key its per-session row on exactly the tick key. Today every row of this wave is `0..0` so nothing moves; from A02-6 that key carries a progressing watermark and `distill_seen` is keyed on it too, which is the "one key, one watermark series" failure class V28 still refuses on the config side, where an empty label would collapse every source key the same way — reached through corpus data instead. The arm therefore drops such a root with a `schema_untrusted` failure row under the tick key (`root_session_id` NULL) and moves on.

**Gate 5 (scope) runs first**, ahead of gate 1 and gate 2, because a write-path guard has to stand before the arm touches foreign material: the scope is resolved and refused before the reader is constructed and before one row of `context_blocks` is read. It is the half `distill.scope`'s validator names as missing in its own comment — V22 refuses only what is *explicitly* configured, while an inherited `scheduler.home_scope` resolving to `shared` reaches the same place unvalidated — and it refuses `shared` even when the operator owns it, plus any scope outside the operator's entitlements. It also **fails closed when the entitlement set cannot be established at all** (a failed `ListTenants`, or no active default tenant leaving the register without a `_global` entry): an unresolved set means "unknown", not "unrestricted". That is a deliberate divergence from `effectiveHomeScope`, whose passthrough on the same input preserves a byte-identical pre-multi-tenant *read* path; this gate guards a write path, and the config-side validator that would catch an explicitly set foreign scope earlier is still unbuilt, so a passthrough here would let one through both halves. **And gate 0 stands ahead of gate 5**, which is an ordering with teeth rather than a formality: gate 5 writes every tick by design, so a disabled install whose scope gate would refuse — the near-default case on a tenant that owns `shared` — would otherwise accumulate a `scope_forbidden` row 96 times a day, against the rule that a ctx install without a distiller accumulates no journal at all.

**The error mapping belongs to the arm, and it is not a pass-through.** `internal/distillsource` carries four sentinels, migration 135 carries two CHECK-enforced vocabularies, and they do not line up: `source_unavailable` is no error class at all but a skip (a source that cannot be read produces no new material to miss, so the range is postponed rather than failed), and `no_active_rows` is a gate answer that never reaches the journal. `distill_run.error` therefore carries a class string and nothing else — the journal is readable over `/api` and lives for 90 days, and a driver message can carry a row of foreign material with it. The probe is literal: reader errors whose text embeds an `AKIA…` credential produce a row in which neither that string nor the prefix appears in any column. Anything the contract did not classify still lands as `query_failed` rather than as no row at all, and an unreadable root is skipped for the tick instead of stalling it.

One boundary is worth naming because the arm cannot report it. `watermark_regression` — the head fell below the stored mark, because manifests of that root were archived or deleted — is detected and journaled while the root still has one live manifest to keep it in the candidate list. A root whose manifests are archived **without exception** leaves the candidate list entirely (`Sessions` filters `NOT is_archived AND metadata ? 'source_block_ids'`), so the arm never asks `Head` and writes nothing. Nothing is read and nothing is lost — the watermark stands, and `distill_reset` remains the operator's way out — but the state is invisible in the journal, and the gate holds that as an assertion rather than leaving it as a surprise.

## The distiller's selection stage (Achse A02 wave A02-6, still no LLM call)

`internal/events/distill_select.go` fills the middle the skeleton left open, and the visible consequence is that a run now closes as **`ok` with a moved watermark** instead of as `partial` at `0..0`: it walks its range in batches, and per batch it counts what it saw, what it dropped and what it kept into the ledger columns migration 135 has been carrying unused (`rows_seen`, `rows_selected`, `rows_dropped_cred`, `rows_dropped_dup`, `chars_selected`). The counters are **chunks, not parts** — the chunk is the prompt unit, so it is the unit a cost estimate can be built on. `ok` says the range `(from, to]` was covered and nothing more; `calls`, `insights_kept` and `blocks_written` stay 0 until the call and the block write land. There is still no bound on the work of one tick, and that is named rather than hidden: the loop runs until the source has nothing above the watermark left, and the bound that belongs there is the spend guard of the next wave.

**The credential drop reassembles the part it scans**, which is the one place this wave reads the design against its letter. `sensitivity.Scan` is length- and adjacency-gated — 64+ hex characters in one run, 32+ base64, key and value inside one match, a hash label within 32 bytes — so a secret cut by a chunk boundary is under every one of those gates in both halves and the detector answers `false` twice. The chunks of one part concatenate byte-identically to the stripped body, so the arm rebuilds the body, scans that, and drops the **whole part** on a hit (`rows_dropped_cred += len(chunks)`). The design's second stage — a 256+256 byte window per seam — is deliberately **not** built: it exists because the design assumed the arm chunks the material itself and never holds the body, and every window is a contiguous substring of the body the arm now does hold, so it could only add the false-positive direction the design names itself (a `SHA-256:` label cut off at the seam makes an integrity hash look unlabelled). The per-chunk scan stays as the layer that still holds if the reassembly is ever wrong. Drop, never mask, for the plain reason that ctx **has** no redactor: `Scan` answers `Match{Kind, Reason}`, and both are the detector's own labels, which is why they may be logged. The gate proves the drop **at the dump**, not at the counter: a counter can be raised by a run that still put the secret in front of a model.

**The dedup key is the chunk**, and `distill_seen` makes it cross-run. Its `source_key` carries the scope, so a hash seen in one scope never silences a chunk in another; a repeat slides `last_seen` forward rather than inserting, because a hash is useful for as long as the same output keeps coming back. A part whose first chunk is already in the ledger therefore still delivers its remaining chunks — with a part-level hash the whole part falls, which is what the predecessor design would have done and what the gate reproduces as its red state. Measured over the live checkpoint corpus (5 955 blocks, 162 roots, in a throwaway container): **52 865 chunks seen, 73.32 % selected, 11.59 % dropped as duplicates, 14.32 % dropped on a credential signal, 0.77 % below the substance floor, 140.4 M runes selected.** The duplicate rate matches the 12.5 % of byte-identical parts measured on the corpus; the credential rate is a chunk rate against a design expectation stated in parts, and it is a number for the measuring wave to judge, not this one.

**The dry-run dump is treated as an egress channel.** While there is no LLM call, the selected chunks are written to `distill.dryrun_dir` so the wave is measurable at all — and that file carries exactly the material the detector did **not** catch. It therefore refuses a relative path and any path that **resolves** into a git working copy: symlinks are resolved first (the deepest existing ancestor, so a link cannot hide behind a leaf that does not exist yet), then the ancestors are walked for a `.git` entry, and a `.git` **file** (a submodule, a linked worktree — the shape the first design draft would have written into) counts exactly like a directory. The resolution is not decoration: a purely lexical walk accepts a `dryrun_dir` that is itself a symlink into the repository while `MkdirAll` and `OpenFile` follow it, which the wave's review demonstrated with the dump files sitting in a working copy afterwards. The walk runs again once the directory exists, and what no path check can see is stated rather than implied: a bind mount of a working copy under a clean path stays invisible, so the promise is "nothing that resolves into a working copy", not "never inside a repository". **Two layers, one question each.** The syntactic half — empty (the documented dump-off setting) or absolute, anything else a 422 — is validator V31 and therefore covers every writing path: boot over environment and defaults (`FromEnv` + `Validate`, which exits on a fatal issue), the assembled config, and the settings write. The topology half stays at the point of use, because whether a path lies in a working copy is a fact about the file system at the moment of use — a symlink, a mount or a fresh `git init` changes it without the configured value changing — and because it is the layer a hot settings change passes on its way to the next dump. (The first version of this wave carried only the second layer and justified it with a claim about the validator's reach that the review disproved at the code; the claim is gone, the layer stayed, and the missing one was added.) The directory is created **and then sealed** to 0700 (`MkdirAll` obeys the umask and leaves an existing directory alone), the file is 0600 and named after the run id — never after the source, whose key carries corpus text verbatim. An empty key turns the plaintext dump off and leaves the counted figures and the chunk hashes, which is the auditability the security amendment actually asks for. The write order per batch is dump, then dedup ledger, then watermark: a crash between dump and ledger re-dumps a batch, a crash between ledger and watermark re-reads it and drops it as a duplicate, while the reverse order would mark material covered that nothing holds. That order is probed by breaking the durable step mid-run — a cancelled context cannot prove it, because with a dead context the wrong version fails to write its watermark too.

**The spend guard is the arm's first cost clamp, and it bounds a call that does not exist yet.** Until it landed a tick was unbounded work by construction — the batch loop runs until the source has nothing above the watermark left — and the bound that belongs there is this one, because the LLM call of the next wave is what makes the loop expensive. It therefore measures neither the loop nor anything the arm does today: it counts the `distill-insights` rows of `context_llm_log` inside a sliding window, which is the durable, cross-restart record of what the GPU actually served. An in-process window would be blind in exactly the state the guard exists for, a restart loop; the price of the durable one is named rather than hidden, since the log row is written after the call and fire-and-forget, so the window can observe but never reserve — a run reads it **once** at the top of a tick and clamps itself on that reading, and a second daemon on the same database overshoots by at most one budget. **Two axes inside one window, and the second is the sharp one:** the call ceiling inherited from the first source counts a 640-token answer and a 64-token one as one call each, while they differ tenfold in GPU time at the measured 38,92 ms per output token, so the call window is kept as the coarse second deck and a GPU-second ceiling is the one that binds. Its default is a proportionality statement rather than a round number: the largest single consumer measured over 24 h is `dream-eval` at 5 642 GPU-s, i.e. 235 per hour, and an arm that refines knowledge may reach — never exceed — today's biggest background consumer. The window those ceilings are counted in may not be zero, and that is a validator rule rather than a convention: a zero window is the empty set, both axes then read nothing and every budget passes while the settings surface keeps rendering both as configured limits — the guard's one fail-open shape, where every fault inside it stops the arm. What the ceiling does **not** hold is a single tick: the plan is built from one window read, so a tick that starts under budget may license everything its call clamp allows before the next read sees any of it — measured, 1,7 to 5,6 times the ceiling in the expensive case. Closing that needs the calls themselves, whose durations the next wave has in process, and it is written down there as a gate line rather than left implied here. **The back-off has no state of its own.** A trip writes one `budget_tripped` row and the rest is derived from its `started_at` over the journal's own partial index, exactly as the watermark is derived from `watermark_to`; the ticks that follow while it stands are ordinary throttled skips. The trip row itself obeys the same state-change rule — a third application of the argument `distillFail` already makes, that the rule does not care which column carries the answer — because the back-off is what throttles the repeat only while a back-off stands, and `spend_backoff = 0` is a legitimate setting where none does: without the rule that configuration wrote one trip row per tick, 384 a day at the default cadence into a journal kept 90 days. A trip that follows any *other* answer still writes, so the clock keeps advancing. **The per-source clamp is computed once per tick, before the first source is touched**, and that placement is the fairness property rather than a saved query: read per source, the first root of a tick would spend the shared window and every root behind it would find it empty. Each eligible source gets `max(1, remaining / eligible)` calls and the number goes into `distill_run.call_budget`, so the clamp is checkable afterwards instead of merely claimed — the floor is what keeps a late source from starving behind an early one, and a source resting on its own trip leaves the divisor instead of shrinking everyone's share. `call_budget = 0` on a run row reads as *unclamped* (the call axis is off), which is why an armed call axis refuses rather than opening a run at zero. Each ceiling arms itself, `0` being that axis' kill switch, and every value comes from the **snapshot of the iteration**: a change reaches the next tick, never the one in flight. **No breaker here** — it keys on the backend name from `OnServed`, which does not exist while there is no call, so its gate could be shown neither red nor green in this wave.

**The extraction is the step the three waves before it built the scaffolding for; since A02-9 its answer reaches a block as well as the journal.** The call itself is the established one over role `digest`, but four of its properties are written into the code rather than configured, and each closes a measured path. `Required` is hard `credentials` and is never folded from the source blocks the way every other aggregator in the tree folds it: 5 942 of 5 955 live checkpoints stand on `internal`, which is a plugin configuration default and not a statement about their content, so a fold would yield rank 1 — the rank at which the live `openrouter` row (external, `no-credentials`, and it carries the `digest` role) becomes eligible and raw session prose of a private infrastructure leaves the house. `LocalOnly` is fixed true and **independent** of that, because `credentials` alone does not exclude a full-trust external row; it is a call parameter that drops external backends after the trust gate, and the precedent for setting it in code rather than from a key is the sensitivity audit, which does the same for the same reason. `BlockIDs` carries the parts of the call and is not optional: at `credentials` the log row loses `request_system`, `request_user` and `response_content` before the insert, so the ids are the only egress trace that row will ever have — the doctrine that "the trace stays ID-exact" holds precisely as far as the call sets them. And the tenant is empty, the global-only arm's narrowest view. The prompt is built once per call with a fresh nonce, every chunk in its own guarded block; the budget pass decides **what survives and at what length** and the wrapper markup is rendered around the survivors afterwards, because feeding the wrapped form to a shortening pass would let a truncation cut through the markers themselves.

**The evidence gate is seven independent screens, and three of them are not the neighbouring module's.** G1 checks that the cited `(block, chunk)` pair belongs to *this* call, G2 that the quote clears 32 runes, G3 that it is contained in **exactly the chunk the model saw** — the assembled payload, not the item the reader handed out, so a shortened part is never verified against text that was not in the prompt, and a quote from the neighbouring chunk of the same part fails rather than passing as a per-block match. G4 refuses a claim or quote that would speak as prompt structure. **G5 runs two separate scans and never one over a concatenation**, and that is a break path rather than a style question: the detector whitelists a 64-hex run whose preceding 32 bytes carry a hash label, so a claim ending in `sha256: "` and a quote opening with a hex secret answers *no hit* the moment the two strings touch — measured, and the separate scan of the quote fires. G6 refuses a quote out of the plugin's boilerplate head or one whose substance is a redaction mark: the head is byte-identical in every part and 31 % of the parts carry `[REDACTED]` in the body, so both satisfy G1–G3 formally while proving nothing. G7 is the only screen on the **claim**, and without it the block text is unchecked — the neutralisation only breaks five marker tokens, so an instruction written in ordinary prose has nothing broken, needs only some 32-rune quote from the same chunk, and would stand in the corpus as an *evidenced* sentence; it is refused by lexical coverage against the chunk, the four admissible kinds, and an instruction negative list. What that list does not catch is a named remainder for the measuring wave, not a passed test.

**The system prompt states the gate's own conditions, and since wave C4-R it states all three of them.** The first two paragraphs of `distillSystemPrompt` are wave C3-1's: a verbatim quote with the cited `(block, chunk)` pair, no identifier and no speaker attribution the cited block does not carry. Migration 149 made the reject histogram readable, and the first measured run decomposed 202 rejects of 57 calls as **g7 = 101, g3 = 90, g2 = 11 and zero everywhere else** — so the class the C3-1 paragraphs address (G1, an address of a foreign batch) does not occur at all, while half the rejects fall at G7, the only screen on the CLAIM, which in the regular case is lexical coverage below 0,60 against the cited chunk. That rule was nowhere in the prompt: it demanded a verbatim quote and said nothing about the wording of the claim. The third paragraph states it — build the claim as your own sentence but out of the cited block's words — and it deliberately does not say *copy*, because a claim that repeats its quote passes G7 and fails the adequacy counter-metric, which is the trivial extractor the arm must not become. Measured against the same 16 roots, the same starting state and the same 57 calls: G7 falls 101 -> 72, the mass-bearing control gate G3 does not move (90 -> 96), and the second control gate G2 falls 11 -> 2 — under the cluster-robust reading G2 even carries the cleanest interval, so the drop in rejects is established while its attribution to G7 alone is not. The anchoring rate over the gate population rises 0,4642 -> 0,5393 and the published claims' median novelty stays above the 0,30 success threshold at 0,4286 — a median, not a floor: the run's novelty tail (7 claims at 0, 19 % below 0,15) passes unscreened, because no per-claim novelty gate exists in the write path. A cluster-robust reading over journal rows puts a zero effect inside the interval, so the sign is what the run establishes, not the size.

**Two brakes end a tick, and they answer different questions.** The breaker is in-process and keyed on the backend that served, because "is this backend broken right now" is a question a restart may well have answered already; the durable brake is the spend guard. Three failures lock it, a success clears both the counter and the window, and a call that delivered insights of which the gate kept **none** counts as a failure too — the project's own empiricism says a model's self-assessment is unusable as a gate, so the verifiable axis takes its place. Opening the breaker **resets** the counter, which is a deliberate deviation from the reference implementation and has its own test excluding the other reading: with the counter surviving the open, one failure after the cooldown re-opens immediately and a backend that fails one call in four ends up locked for good, while a failure here is consequence-free and the evidence gate produces a legitimate failure class of its own. The second brake is the in-tick half of the GPU ceiling the previous wave could only name: the arm sums the elapsed time of its own calls and stops as soon as window consumption plus own consumption reaches the ceiling, which closes the 1,7-to-5,6-fold overshoot a single window read per tick allows. It measures wall time around the call rather than the served milliseconds the row will carry — an upper bound, so it brakes earlier rather than later, and the difference is queue time, which is durchgängig 0 on this deployment. The two brakes sit at DIFFERENT depths, and the difference is what keeps a stopped tick from costing material. The breaker is a **gate before the source is read**: an open one journals `skipped/breaker` and the tick touches nothing — no read, no dump, no ledger row, no watermark. The in-run ceilings can only trip mid-batch, and there the rule is that a watermark stands for material that was COVERED, which means "reached a call, or was deliberately discarded": only the chunks a call saw enter the dedup ledger, the watermark does not move at all (it is per manifest and cannot be advanced by half a batch), and the run closes as `partial` carrying the brake's own word in `skip_reason` rather than as an unexplained non-completion. The next tick re-reads the batch, drops the already-extracted chunks as duplicates and calls the rest. The earlier shape of this paragraph claimed the range was "postponed, not lost" while the code marked the whole batch seen before extracting and advanced the watermark unconditionally afterwards — measured, three of four chunks fell out of the extraction permanently. **The block address the model is asked to cite is prompt-local**, not the corpus UUID: a UUID is 36 characters against the guard's 32-character attribute clamp, so rendering it produced a marker with no address at all while the system prompt asked for one — every insight would have failed G1 and the breaker would have opened on a healthy backend. Each distinct part of a call is numbered instead, the number is what the marker carries and what the answer names, and the UUID stays behind as the egress trace.

## The distiller's block write (Achse A02 wave A02-9)

**The block is seeded from itself, and without that the arm loses yield in ordinary operation.** The identity is anchored on `watermark_from`, and a brake *inside the first batch* — the call clamp, the in-run GPU ceiling, the breaker — leaves that watermark where it is by design. The next run therefore renders the **same title**, and the upsert's conflict branch replaces the content wholesale: measured, a braked run held five insights durably and its successor replaced all five with two new ones. So the run's accumulator is loaded once, before the run row exists, from the arm's own previous block — read back out of its own section headings, never out of `metadata`, because design/02 §5 BA2 puts model-produced `claim`/`quote` in the block text and nowhere else, and a structured field is exactly the channel that rule closes. The seed's first question is **which block of the range it is opening**: a range may hold several shards (see the identity below), and the arm opens the first one that still has room — the highest existing shard, or its successor when that one's carried material already fills it. Which shard a row is follows from its **title**, never from `metadata.shard_ordinal` — the key is published for readers and cross-checked, but a jsonb field anyone may write must not decide which row the arm writes into, and a title-derived ordinal also reads a block written before shards existed as shard 1 without a NULL anywhere in the decision. The read then answers two more questions: a **foreign `type_name`** on the identity of that shard ends the attempt before a single call is paid for, and a body whose sections the arm cannot read is **refused rather than replaced** — overwriting an unrecognised body is the loss the seed exists to prevent; both refusals name the shard title they refused, because with several shards per range the source key no longer addresses a block. The carried lines are deduped against the new ones by exact equality, because a crash between the block write and the dedup ledger leaves the chunks unmarked and the next run extracts them again — and the comparison spans **every shard of the range**, not only the loaded one: after a hand-over the loaded shard is empty while the identical lines stand in the sealed one. A sealed shard contributes to that comparison only under the arm's **own type** and with a body it can read; a foreign type on a lower shard is left standing and left out, because refusing over it would let one planted row kill a grown chain while trusting it would let the same row suppress legitimate insights.

**The arm's answer becomes corpus text here, and the write order is what makes a crash recoverable.** Per batch: dump, extract, **block**, dedup ledger, watermark. The block is upserted before anything claims the range was handled, so a crash after it re-reads the batch, drops its chunks as duplicates and upserts the same content again, while a crash before it loses only insights no counter has claimed yet. A failed write is the reverse direction of the same rule: the run ends `failed/block_write_failed`, the chunks are **not** marked seen so the material stays readable, and the counters of the calls that were already paid for are still booked — a run that dies without booking them would leave the spend guard blind to its own consumption on exactly the runs that failed. The identity is `(category, title, scope)` with the title anchored on `watermark_from` and carrying the **full** root id: the title is half of an upsert identity, and a shortened root plus a colliding microsecond is a structural collision at target scale rather than a hypothetical one. Two batches of one run therefore write one growing block, two runs over different ranges write two. The title carries a **third axis** since the shard layout: `" — Teil <n>"` from the second block of one range onward, while `n = 1` stays byte-identical to the pre-shard title — every block written before the layout is shard 1 by construction, and renaming it would orphan it. From the second shard on the **block text** says so too: a chain line under the trust paragraph names the part (`Teil <n> dieses Bereichs`) and the title of its predecessor, so a reader over MCP `get`, the web UI or the synthesis prompt — which sees the first 1 500 runes of a block and nothing else — knows it is holding an excerpt. Shard 1 renders byte-identically to the pre-shard block; it has no predecessor to name. `watermark_from` remains the **coverage** axis and the ordinal is the **capacity** axis; letting the watermark move instead would book unread material as covered. A run **hands over** when its shard fills up: the full shard is sealed, the next one is opened and written immediately with the insights the cap could not admit, and the run continues instead of ending — a full block is no longer a standing state. A successor holds slightly less than the shard it relieves (its frame carries the title suffix and the chain line), so a hand-over can place fewer insights than it moved; where that happens the run ends with `budget` and holds its batch back rather than booking chunks whose insights no shard took. The hand-over moves the identity and never the watermark, so a batch the rune meter stopped mid-way stays uncovered and is read again; the already-called chunks then drop out of that read as duplicates, which is what makes a hand-over cost a re-read and not a call. It is only allowed once the shard being left has seen at least **one** call: a shard that is full without ever having been called is full for a reason the next shard would not fix, and rolling over there would open shard after shard forever. How long a chain may grow is the one thing an operator can bound — `distill.max_blocks_per_root`, default `0` = no cap, plus a hard bound of 256 that holds even with no cap configured — and it binds at both hand-over points, in both cases with `budget`. The two paths differ in what happens next, and the difference is the whole operating picture. A run stopped **at seed time** never reads its source, so the range's watermark stands and the arm answers `skipped/budget`: the range waits, at the cost of nothing. A run stopped **mid-batch** keeps whatever the shard could take and holds the rest back — the chunks whose insights found no shard are deliberately left out of the dedup ledger and the watermark is not advanced over them, so nothing paid for is dropped, but the range only continues once the cap is raised. Where the batch that filled the last allowed shard was itself fully covered, the watermark moves on and the material after it starts a **new** range with a chain of its own. How often a run handed over is readable on the block itself (`metadata.coverage.shard_rollovers`); it is a position, not a sum, `shard_ordinal − shard_rollovers` is the shard the run opened on, and the run's own hand-over count is the number on the **highest** shard it wrote.

**Writing per batch is only free because the type is retrieval-`excluded`, and that is measured rather than assumed.** A growing content would normally invalidate the vector once per batch — up to 89 invalidate/re-embed cycles for one block at the p95 call count — but `insight` is excluded by board decision E-4, and both embed-backfill picks AND-in the shared exclusion predicate, so the block never takes an embed slot and there is nothing to throw away. The gate probes exactly that (the written block is not backfill-eligible and carries no embedding), and the figure stops being zero the day E-4 flips the type to visible; that is the number the flip has to budget, not a property of this write path.

**Four properties of the written row exist because a block is durable where a counter is not.** The **type is explicit**, which stamps `type_source='manual'` and takes the row out of the auto-classifier for good — measured, an unset type lands on `knowledge`/`auto`, and the predecessor design's title additionally matched the insight type's own classify pattern, which the I7/S4 door then declines because the level of a derivative is assigned by its writer and never by a title. The **sensitivity value is never the zero value**: the upsert hangs its whole sensitivity clause on a non-empty value, so an empty one writes no sensitivity columns at all and the row takes the DDL defaults `credentials`/`default` — right by accident, and `default` is exactly the predicate the LLM sensitivity audit selects on, so the block would queue for an audit of its own transcript prose. The **metadata is built white, keys and values**: there is no reserved-key filter in this tree beyond the single `guard_checked_at` strip, so every id is parsed as a UUID and re-serialised from the parsed value and every foreign string is matched against a closed character class — measured, passing a manifest's own map through carried `platform` and three more foreign keys into a block that claims to be derived. And the **credential detector runs per insight**, claim and quote scanned separately, with a hit **dropping** the insight rather than only raising a level: the upsert scans the finished content on every path and a hit there resolves to `sensitivity_source='pattern'` before it ever looks at the derived badge, so keeping the secret out of the content is the only way to satisfy both halves — the provenance stays `derived` and the corpus never carries the string.

**The block text puts assertions before evidence, and that ordering is the format's whole point.** Every source of a synthesis prompt is cut to 1 500 runes; the predecessor format put a quote behind each claim, and measured, two of six claims and the trust framing itself fell outside that window. The trust sentence is now the first paragraph, the claims with their inline `[<block>#<chunk>]` anchors the first section, and provenance, coverage and quotes follow — so the cut takes evidence, never assertions. The freshness stamp is the **run's** creation time and not a per-render wall clock, because the content feeds a generated hash column and a moving timestamp would make every batch's upsert a content change — which is the property the write order depends on.

**The rune cap is a run boundary, not a silent trim.** `distill.max_block_runes` falls on insight boundaries, drops the **youngest** insights so the published prefix stays stable, and the block says in its own text how many it left out and in which direction. Two things follow, and both are about money rather than layout. The cap is determined in **one linear pass** over a measured frame plus a prefix sum — the first version re-rendered the whole block once per cap step, which is 69,9 ms, 125,5 MB and 433 698 allocations for a single write at 400 accumulated insights, and it falls again on every batch. And a cap strike **ends the run**: from the moment the block is full, every further call produces insights that are guaranteed to be dropped, so the batch loop stops with the journal's `budget` word (`max_block_runes` is a budget; the skip vocabulary is a CHECK this wave cannot extend, and the log line carries the exact reason). The companion gate stands before the run even opens — a block whose carry leaves no room for one more insight **of the size that block's own insights have** answers `skipped/budget` and makes no call at all. The size estimate is the block's own mean rather than the theoretical minimum, and that is the difference between the gate working and not: with the minimum, a block at 2 000 of 2 200 runes still looked like it had room for a 150-rune insight while a real one costs ~290.

**A deterministic title is a public identity, so it is defended twice.** The title is derivable from checkpoint metadata any read key can see, and a block pre-created under it would either take the arm's writes into a foreign type policy or hold them at a low sensitivity. The derived badge puts `sensitivity` and `sensitivity_source` into the conflict clause **upgrade-only** over the rank expression, so a squatted `public`/`manual` row is raised to `credentials`/`derived` and an equal-level manual classification survives; and a precondition read before every batch's upsert refuses the run outright when the identity is held by a foreign `type_name`. Both halves have their own probe, and the foreign-type one asserts the squatted row is left byte-identical.

**What the anchors mean is stated in the block, because it is weaker than it looks.** One sentence can live in two parts with different chunk hashes, so an anchor names *a* part that contains the quote verbatim — not the part it came from. `metadata.source_block_ids` therefore carries every part of the run, and an insight whose part carries no corpus id at all is not written and is counted in `coverage.insights_unanchored` rather than leaving an empty provenance list behind.

## Derived-knowledge gate module (Achse D-01 wave W01-1, wired)

`internal/derived` is THE gate module of the derived knowledge layer (`insight`, `catalog`) and it is **wired**: ten non-test files in five packages import it (`config/validate.go`, `distillreset/reset.go`, `events/distill_block.go`, `events/distill_extract.go`, `handler/stage_gates.go` and five files under `store`). Nine of them reach the live surface — the type and metadata vocabulary, the gate constants, the adequacy metric and the two Goodhart thresholds beside it (`GoodhartMinNovelty` is the value `distill.novelty_floor` defaults to); the tenth is `store/resolve_sources.go`, and it reaches the W01-1 citation-gate generation only for its data types — the gate entry points `CiteGate`, `Validate` and `MinSourceCount` have no production reader at all, and `store.ResolveSources` in turn has no production caller. It owns four things. The **provenance contract** `metadata.provenance` — one namespaced key, so the collision surface against the metadata keys already in the corpus is one line wide — with fourteen fail-closed checks V1–V14 that prevent a write rather than degrade it, decoding that refuses any contract version but the one this build knows, and a `source_digest` that makes “has the source set changed?” an O(1) comparison against a list that can be 147 UUIDs long. The **citation gate** G0–G7, cheap before expensive: the claim names a declared source (G0, the reduce guard — a claim verified against a map stage's output would be a citation of model text), the source resolves to ORIGINAL content (G1), the quote clears 32 runes (G2), the normalised quote is contained in the normalised original (G3), it carries no redaction marker (G4 — the checkpoint redaction REPLACES rather than deletes, so `[REDACTED]` is a genuine substring that G3 passes cleanly), `promptguard.Neutralize` breaks nothing (G5), `sensitivity.Scan` does not fire (G6), and an n-gram echo index over the titles of the `credentials`/`personal` sources does not fire either (G7 — the check that catches a secret which was already summarised into a title one abstraction level earlier, where a credential scanner no longer sees it). Its four thresholds are **constants, not config keys**: at `MinQuoteRunes = 3` the string “ok” is a valid quote of every second line and the gate reports full coverage while checking nothing, so a gate whose threshold is a settings write is not a gate. The **renderer**, which is head-heavy by necessity: `llm.MaxBlockChars = 1500` is the entire window a block gets in the synthesis prompt and it cuts from the back, so title, computed metrics bracket, conflict rule and untrusted framing stand first, the claims follow, and the verbatim evidence and the source list stand last — head plus the three-claim minimum measures 736 runes against a 1 200-rune budget, where the first draft's layout (evidence before the metrics) measured 1 524. The metrics bracket is the `computed` class: aggregates, counts, the source period and the coverage gap are produced in Go from the source set, never offered to a model, and the answer schema has no shape that could express them — a line without a `quote` is dropped. It carries exactly ONE timestamp, because `block_mass` is `1/sqrt(n)` over `content_times` and a single date scores the same 1.0 as none. And `StripReserved` drops the fourteen reserved metadata keys, `guard_checked_at` (the guard's pending mark) and `is_meta` (the one metadata classify rule in the system) among them — defence in depth beside the `UpsertBlock`-side filter, not instead of it. Two cuts are structural. The package is a **leaf**, and that is a rule rather than an import list: it never imports `store`, `llm`, `blocktype` or `topiclabel`, so the DB half of the contract (`store.ResolveSources`) will call INTO it — the same shape `internal/visibility` uses; the echo index is therefore an independent implementation of the one in `topiclabel/guard.go`, with an origin comment, rather than an import. And **no type name carries stratum 2**: `StratumOf` maps `insight` and `catalog` to 1 and everything else to 0, while a super-catalogue is a `catalog` block carrying `provenance.stratum = 2` and `Validate` takes the writer's own level as a parameter. Deriving the level from the type name would move it into the type registry, a table an operator can edit with SQL, which is precisely the way of breaking the stratification invariant that the design rejects. A third property runs through the validation and was sharpened after the adversarial review of the wave: every value `Validate` **checks** is bound to the value the block **writes**. `provenance.stratum` — the field `store.ResolveSources` reads back for the next level's check — must equal the level the write claims, so an arm cannot raise the checked level to let its sources pass while persisting a block that later runs count as an original. Every declared source either carries a stratum, an untrusted flag and a sensitivity, or is reported as unresolvable; a source that is silently absent from the caller's facts would be touched by no clause at all, and the caller would decide by omission what gets validated. And `claims_kept`/`sources_covered` are re-derived from the claims that actually survived the gate before the yield floor judges them — otherwise the one gate that decides whether a block is written at all would be judging the arm's self-report, and the coverage line in the head would state a completeness nobody verified.

The **adequacy counter-metric** (Achse D-05 wave M-W4b) stands beside the gate, not beneath it. `Adequacy(claim, quote)` returns `compression = |TokenSet(claim)| / |TokenSet(quote)|` and `novelty = |TokenSet(claim) \ TokenSet(quote)| / |TokenSet(claim)|` over `evalscore.TokenSet` — the tokeniser the eval side already scores title overlap with, so a claim's novelty here and its token F1 there sit on the same word boundaries; an empty denominator yields 0 and never NaN, because a NaN novelty compares false against every threshold and would silence the rule on exactly the degenerate charges. `Report(items)` folds a charge — the blocks of one run — to a `GateReport`: anchoring rate and its complement the rejection rate, the summed g0…g7 histogram, and the two medians over the claims that SURVIVED. Both numbers live in the **same** verdict because a pure anchoring rate is trivially maximised: a generator that quotes a whole source paragraph and asserts it as an insight reaches rate 1,0 at value 0, and every one of those lines is a perfectly anchored citation that G0–G7 cannot touch. Hence the refusal `GoodhartMinGrounding = 0.95` **and** `GoodhartMinNovelty = 0.15` — a charge above the one and below the other does not pass; it copies instead of extracting, and the report says which of the two failure modes it hit, because a copying generator and a low-anchoring one call for opposite fixes. Both thresholds are constants for the same reason `MinQuoteRunes` is: a novelty floor an operator can set to 0 switches the counter-metric off without anything turning red. And every report carries the **double role** verbatim — `measured = "rejection_rate"` in the JSON, one sentence in the rendering: once the gate writes fail-closed, the runtime hallucination rate is 0 **by construction**, so what is measured is the rejection rate, how much of what the generator produced is not anchorable — a generator-quality metric and a cost metric (discarded GPU seconds) at once. Without that sentence somebody reads the zero as quality instead of as construction.

## Distiller journal (Achse A03 wave W03-1, migration 135, wired)

Migration 135 landed the distiller's storage ahead of its arm; since A02-5 the arm writes it: `events/distill.go` carries five statements (`:451`, `:1561`, `:1859`, `:1885`, `:1909`) and `events/distill_retention.go:162` the retention DELETE, while `distill.go:1805`, `distill.go:1844` and `distill_spend.go:349` read it. `distill_run` is a **journal, not a state row**: one row per (run × source), written two-phase and then *advanced* — `INSERT` with `outcome='running'` before the run, `watermark_to` moved forward after each batch, `UPDATE` on completion. The difference from migration 130's journal is that advance: 130's child is atomic and updates once, the distiller processes an id range in batches and has to record partial progress, so a `running` row with `watermark_to > watermark_from` is a **partial success**, not a fault, and the boot sweep demotes it to `killed` without discarding the watermark. **The watermark is derived, never stored**: `max(watermark_to)` over a source's rows with `outcome <> 'running'` is its only definition — there is no second state holder that could drift, `skipped`/`failed` rows are included because both can carry real progress, and a `skipped` row is watermark-invariant by construction (`watermark_from = watermark_to =` the value derived at skip time, so `max()` is untouched even when the source is unreachable). The correctness condition that makes this safe lives in the writer, not the schema: the block is upserted *before* `watermark_to` advances, so a kill between the two costs a re-read, never an insight. Four CHECK constraints keep the journal honest rather than trusting its callers — the seven-value `outcome` enum, the nine-value `skip_reason` enum, the ten-class `error` taxonomy (**a class string only, never a foreign error text**: the journal is readable over `/api` and lives 90 days, so SQLite messages and HTTP bodies belong in the log), and `outcome='running' ⇔ finished_at IS NULL`, the invariant the startup sweep stands on. `distill_seen` (PK `(source_key, row_hash)`, SHA-256 as `bytea`) is the cross-run dedup ledger without which the same repeated tool output is re-batched and re-billed in every compaction generation.

The one touch on an existing table is the expression index `idx_blocks_checkpoint_root` on `context_blocks ((metadata->>'root_session_id'), created_at DESC)`, which turns the later manifest lookup from a scan proportional to the checkpoint corpus into a lookup proportional to one root session. Its predicate is `IS NOT NULL`, deliberately not `metadata ? 'root_session_id'`: Postgres derives `expr IS NOT NULL` from `expr = 'x'` (strict operator on the same expression) but proves nothing about the `?` existence test, so the `?` variant would be an index the lookup can never use. Measured, not estimated (the gate design/03 §3.1 demands): on a synthetic 1M-row `context_blocks` with 1 % carrying the key, the index builds in **0.16 s** — far under the 30 s threshold above which it would have had to move into a `CREATE INDEX CONCURRENTLY` follow-up, which this repo's runner could not carry anyway (every migration file runs inside one transaction). On the same fixture the lookup drops from 10 000 heap blocks / 46.8 ms to 25 heap blocks / 1.0 ms, entering the plan as a `Bitmap Index Scan` under a `BitmapAnd` with `idx_context_category`. A measured correction to design/03 §4.5 rides along: the explicit `IS NOT NULL` line in the lookup query is documentation, not mechanism — with it and without it the plan is byte-identical, because the same strict-operator derivation that makes the index predicate provable applies to the query. The line stays (it states the intent and costs nothing), and an integration probe pins the derivation so a future server that stopped doing it goes red instead of silently losing the index.

**Migration 149 makes the arm's own rejects readable (wave C4-1).** `insights_rejected` counted *that* the evidence gate refused a line; which of G1–G7 refused it left the process only as a `slog.Debug` line, and the daemon pins its handler to `LevelInfo` — so for an arm whose abort criterion hangs on the reject rate, half the instrument was missing. The fix is nine additive counters on `distill_run` (`rej_g1`…`rej_g7`, `rej_schema`, `call_groups_shrunk`), folded per batch exactly like every other ledger column. A log-level switch was the alternative and was rejected on three concrete grounds rather than on effort: the Debug line carries no `run_id`, so a reject could not be attributed to a run, a source or a watermark range while `max_sessions_per_run > 1` puts several runs in one tick; the question the counters exist for ("which gate moved between two prompt revisions") is a `sum()` over a period, not a log search; and the journal is DB-persistent (unbounded when C4-1 landed — `distill.retention_days` was declared and validated but had no consumer in the tree, finding N-13; the paragraph below is that consumer) while log lines live as long as the container, so a before/after across two revisions needs the older half to still exist. The histogram is the **exact decomposition** of the aggregate beside it — `sum(rej_g1..rej_g7) + rej_schema = insights_rejected` follows from `offered = len(lines)` and `rejected = offered - kept`, so the two are checkable against each other. There is deliberately **no CHECK** enforcing it: pre-wave rows violate it by construction (aggregate > 0, histogram 0), the weakened `<=` form cannot catch the one failure that matters (a histogram silently stuck at zero, because `0 <= n` always holds), and a violated CHECK would kill a whole run over an accounting slip in a pure observation quantity — so the invariant is enforced by a gate probe over the real write path instead. Existing rows are **not** backfilled: an invented decomposition would not be a measurement. `rej_schema` is not a gate but the parser's bucket, and it belongs in the histogram because the aggregate counts it; there is no `rej_g0` because the arm has no G0 — `derived.CiteGate`'s first screen asks whether a claim's source stands in `provenance.source_block_ids`, while the arm resolves prompt-local addresses against what it actually showed the model, so the column would be zero by construction. `call_groups_shrunk` counts **events, not saved rows**: that the rune cap bites at all was already visible through its WARN path, but how often it steered the yield axis *without* stopping anything was not.

**The retention consumer closes N-13 (wave C5-B, no migration).** `distill.retention_days` and `distill.seen_retention_days` had been declared, validated and described as "days the janitor keeps" since migration 135 — and unread: the full 6 h janitor bundle, run line by line over rows aged 400 days against windows of 90/30, left both tables untouched. The consumer is a ninth line in that bundle, and the two tables get **different delete rules, because they are different kinds of row**. `distill_seen` is a ledger of sightings: a row says only "this content was already paid for", so it is deleted plainly past `last_seen` — the axis `idx_distill_seen_age` exists for, measured at an Index Scan of 25,7 ms for 2 000 expiring of 200 000 rows. `distill_run` **is the watermark**: there is no second state holder, so a plain time-axis delete does not free storage but *resets the arm to the beginning of a source* — measured with the naive form, one deleted row took a watermark from 1 788 063 650 102 010 to 0. The journal rule therefore keeps two rows per `source_key` regardless of age, the watermark carrier (greatest `watermark_to` among non-running rows) and the newest row (what `distillSameAnswer` reads), expressed as two strict-order `EXISTS` clauses so exactly one row is unbeatable per order; `running` rows are exempt because the startup sweep is about to turn their progress into countable `killed` rows. At 40 000 journal rows over 2 000 sources the delete runs in 69,3 ms and leaves exactly one row per source, so migration 135's decision to decline a second full time-axis index stands unamended. **`0` keeps forever in both windows** — without that guard `make_interval(days => 0)` deletes everything, which would make an unconfigured window the sharpest one. The wave also had to make `last_seen` **actually slide** before it could delete on it: the sliding window the ledger's horizon presumes was documented but not implemented, because a returning chunk is dropped by the dedup filter *before* anything reaches the marking write, so the `ON CONFLICT DO UPDATE` never fired on a repeat and `last_seen` stood at insert time for the life of the row. Measured on the unchanged tree: a chunk re-listed by a later manifest fell as a duplicate while its ledger row stayed 400 days old — and with the retention consumer on top, that row is purged and the arm buys the same material again (`selected=1 dup=0`), which is the arm's dominant cost item by migration 135's own sizing. The touch sits on the dedup read, where the sighting actually happens.

**Migration 150 splits G3 by *where* the quote actually stands (wave C5-A).** With the histogram in place, the C4-R measurement named the next lever: after the G7 revision, `g3` — "the quote does not stand verbatim in exactly the chunk the model was shown" — carried 56.5 % of the remaining rejects (96 of 170). One number cannot say which failure that is, and the failures call for opposite fixes: a wrong `chunk="M"` is a prompt question, a quote running across a chunk boundary is a chunking question, and a quote that stands nowhere is a generator question. Four additive counters on `distill_run` (`rej_g3_chunk`, `rej_g3_span`, `rej_g3_part`, `rej_g3_none`) decompose `rej_g3` the way `rej_g3` decomposes `insights_rejected`, so the row now carries two nested equalities and both are summable over a period without a join. The split is **four-way and not the two-way cut the finding sketched**, for two reasons that are measurements rather than taste: a quote straddling the seam between chunk *M* and *M+1* stands in no single chunk, so a two-way cut books it next to hallucination although the chunks of a part concatenate byte-identically to the part body and the text really was there; and "nowhere in the shown material" is only true if the whole shown material was searched, foreign parts of the same call included — a quote lifted from part 3 and addressed as part 2 is an addressing error too. Classification is exclusive and decided by precedence, smallest addressing error first: wrong chunk index, then crossed boundary within the addressed part, then wrong part number, then nowhere. The seam test joins only **consecutive** chunk indexes — `distillBuildPrompt` drops a chunk the budget could not seat, and gluing chunk 2 to chunk 4 would manufacture a seam the source never had. As with 149 there is no CHECK on the sum and no backfill of existing rows, for the same three reasons; the invariant is a gate probe over the real write path. The runtime cost sits in the arm and only where something is already being discarded: the normalised view of a call's material is built at most once per call and only after a line has actually failed G3.

Alongside it, `derived.Report` gained the **novelty distribution** — `novelty_n`, `novelty_p10`, `novelty_p25`, `novelty_below_floor_share`, `novelty_zero_share` — next to the median it already published. The median is one number about a set, and C4-R measured what it cannot see: a run wrote 7 claims at novelty 0 and 18.8 % below `GoodhartMinNovelty` while the median stood at 0.4286, comfortably above the criterion fixed in advance. The five values are **output, not a gate**: `judge` is untouched, and whether the write path needs a per-claim novelty floor is a decision that belongs after the diagnosis, not before it. `median` is now `quantile` at *q* = 0.5 rather than a second implementation, so the median and the quantiles of one report cannot describe two different orderings of the same set; the interpolation is the one that reproduces the previous median exactly for every *n* (numpy's default, R's type 7), which keeps runs comparable across the wave that added the fields.

**Migration 151 gives the arm a substance floor — the first screen that is not about evidence (wave C5-E).** The seven evidence gates ask whether a claim is *anchored*; none of them can ask whether it is *worth anything*, and `derived/adequacy.go` has said so since it was written: a claim that copies its quote verbatim reaches an anchoring rate of 1.0 with a value of 0, and "G0–G7 cannot catch that" because every one of those lines is a perfectly anchored citation. Until this wave `novelty` — the share of a claim's tokens that do **not** stand in its quote — existed only as a report number. The C5-A-M measurement priced that gap on the root stand: p10 = 0.0385, **27.1 %** of published claims below 0.15 and **5.85 %** at exactly 0, three of them literal copies at compression 1.0. Since the E-6 full backfill writes the corpus once and has no re-distill path, the projection was ~4 970 claims below the floor and ~1 070 at zero, permanently. The floor is therefore a **write-path screen**: `distill.novelty_floor` (float, default 0.15, hot, `0` = off) discards a claim whose novelty is *strictly* below it, and one additive counter `rej_novelty` on `distill_run` books the discard — which **extends migration 149's equation to `sum(rej_g1..rej_g7) + rej_schema + rej_novelty = insights_rejected`**; the eight-term form is a gap from here on, and a gate probe asserts both that the new form holds and that the old one no longer does. Four properties are deliberate. The screen runs **last**, after G7: it needs a quote already verified to be the shown material, and no reject may move out of an existing bucket, because the `g1..g7` series of the measurement waves is the comparison base of every prompt iteration. The predicate **delegates to `derived.Adequacy`** rather than re-implementing it, so the gate and the report's `below_floor_share` describe one border and not two — the default *is* `derived.GoodhartMinNovelty`, pinned by a test since a struct tag cannot carry a constant. `0` is the documented off-switch that restores the pre-wave gate exactly (the value is not even computed), while a value **above 1** is refused by the validator: novelty is a share of a token set, so such a floor would let the arm keep calling and paying while discarding everything, rendering as a threshold all the while. And there is **no feedback path** from the floor into the prompt — it is discard plus counter, nothing else. Two consequences are named rather than left to be found: a call answering only in copies now ends with `kept = 0` and books a breaker fault, which is the intended reading of a generator that only copies; and `derived.Report`'s novelty distribution describes, for an armed run, the layer **after** the floor — the C5-2 criterion is from here on a statement about what was published, with `rej_novelty` carrying the before-picture next to it.

**The tick fans out over its SOURCES, and never over its calls (wave C6-A, no migration).** `distill.concurrency` (int, default `1`, hot, `[1, 16]` or a 422) is how many root sessions of one tick run at the same time; at `1` no goroutine is started at all and the arm is the sequential loop every wave before this one had, in the same order and under the same recover. What stays sequential at **every** setting is the inside of a source, and the reason is the watermark: a run's range is only covered by a COMPLETE batch prefix ("processed means reached a call"), so two calls of one root in flight would either book material no call reached or need a second state holder — and this arm's contract is that there is none. Between two roots none of that applies, which is what makes the fan-out cheap rather than clever: journal rows, dedup ledger and blocks are all keyed on the root (the shard group is read per `root_session_id` + `watermark_from`), so two sources share nothing but the tick's own ceilings. Three things make that true rather than likely. Candidates are cut into **chains by root** before the pool sees them, so one root is one worker even if a source hands out a duplicate — the production candidate query cannot (it is a `GROUP BY` over the root), but the arm reads through an interface that promises nothing of the sort. The one journal key that is NOT per source — the tick key, which the unnameable-root refusal writes under — is answered **before** the fan-out, in the tick's own goroutine, so the state-change rule never reads a row another worker has not written yet. And the in-run GPU meter, the one object every worker shares by construction, counts atomically. The cost is named rather than discovered: both spend axes count what has **landed** (the window query between ticks, the meter after each call), so with N sources in flight up to N−1 calls can be paid for before either axis sees them — bounded by the setting, not by the backlog, and the same class the guard already documents for its once-per-tick window read. The ceiling of 16 is the **daemon's connection pool** (20, shared with guard, digest, dream, recall and the HTTP surface), not the GPU: what a serving backend takes in parallel is the operator's number and it is set against their deployment. The embed lane is untouched by this key.

## Forge sync (migrations 079/080)

The project register `context_projects` (migration 079) binds one project identity to exactly one tenant scope — that scope **is** the repo corpus. Under masterplan **K14 there is no separate `context_forge_repos` table**: the register IS the forge registration. Migration 080 (Welle I-F) extends it additively — `token_secret` (the NAME of a sealed PAT in `context_secrets`, never the PAT), `sync_enabled`/`push_enabled` (fail-closed: pull-only until an explicit toggle), `last_error`/`backoff_until` (offline-first resilience) — and the ETag/`since` fetch cursor lives inside the pre-existing `sync_cursor` JSONB, not new columns.

The per-entity issue↔block mapping is `context_project_sync_map` (080): `(project_id, entity_kind, forge_id, block_id)` with the 3-way `base_hash` (§3.6 canonical projection at last sync). Sync writes never go through `UpsertBlock` — the sync identity is `(project, kind, forge_id)`, so forge-side title changes are identity-neutral. It CASCADEs off **both** `context_projects` and `context_blocks`, so a tenant prune drains it for free (the K14 gate).

**I-F ships the pull client + sync shell only.** The GitHub REST client is PULL-only: conditional ETag requests (304 ⇒ 0 writes, off the rate-limit budget), Link-header pagination, `pull_request`-field PR filtering, rate-limit backoff (exponential, cap 1h — never a conflict), and a dial-time SSRF guard (`net.Dialer.Control` re-checks the resolved IP against the private/loopback/link-local deny-list, closing DNS rebinding past the PATCH-time `forge.api_base` check). The `forge-sync-start` shell runs fail-closed gates (owner-less scope ⇒ disable + refuse; no resolvable `issue` policy with `digest.include=false` ⇒ refuse) then a background goroutine (single-flight per project ⇒ 409 on double-start). It fetches, gates and records run history (`context_project_sync_runs`), and hands each fetched page to the I-G apply seam. A run has a deadline of its own (`project.sync.run_timeout`, default 4 h, issue #474): its forge reads, its applies and the start of each push section run under it, its bookkeeping does not — the fetch cursor commit after each applied page, the error and backoff stamp, the run row and the release of its slot — so a run that meets the deadline leaves the cursor of its last applied page and a `last_error` that names the deadline, and the next run goes on from there. A push write on the wire when the deadline passes is not cut: the PATCH (or a create's POST and finalize) runs to its answer, which the forge client's 30 s timeout bounds, and the advance after a landed PATCH commits — a cut PATCH could still land after its push lock went back, the class of a session that ends during the PATCH. Before, a run had no deadline, and a forge that answered each page just under the client's timeout held one of the `project.sync.max_concurrent` slots for up to 1000 pages × 30 s per leg while every other project's start was refused as saturated (`TestASyncRunEndsAtItsDeadlineAndTheNextRunGoesOn`, `TestTheCursorOfAPageAppliedAtTheDeadlineIsSaved`, `TestAPushWriteOnTheWireAtTheDeadlineIsRecorded`).

**I-G is the Pull-APPLY (`forge.Applier`).** For every fetched issue it runs a **3-way direction decision** over the canonical hash projection (§3.6) — `base` (`context_project_sync_map.base_hash`), `ctxH` (projection of the stored block), `forgeH` (projection of the fetch). The projection is **content only, never a timestamp** (W16): `{title, body, state, labels: sorted, assignees: sorted, milestone}`, and the title is the forge title with the ctx `#<nr>`/`#L<seq>` prefix stripped (the block title is a derivat — hashing the raw prefixed title would drift `ctxH != forgeH` forever). The direction table (`§4.5.2`): no mapping ⇒ **pull-create** (block `#<nr> <title>` + mapping + `base := forgeH`); `base=ctxH, ≠forgeH` ⇒ **pull-update** (block-update + `base := forgeH`); `≠ctxH, base=forgeH` ⇒ **ctx-ahead** — nothing (push is Welle I-H); `≠,≠, ctxH=forgeH` ⇒ **converged** (`base := ctxH`, no block write); `≠,≠,≠` ⇒ **conflict** (`conflict=true` + `conflict_at`, zero writes both ways, resolved only explicitly). The direction is read without a lock; every decision that writes runs in a transaction that locks the block — after the targets of its references whose id lies below the block's (issue #503) — and then its mapping row — the order of every writer of both — and is decided again on them (issues #452, #491). While the mapping still holds the base and the flag the read saw, a convergence the read saw stands (block and forge held that version, so it is the base; a local edit committed since is ahead of it and keeps the mapping a push candidate — a flag another instance set meanwhile means the forge moved past this pull's fetch, and the matrix decides on the locked rows instead), and a pull-update or a conflict is decided again on the locked block — a local edit that committed in between makes a pull-update **converged** or a **conflict** instead of being overwritten. Once another ctxd instance moved the mapping's base, the matrix runs on the locked block and the locked row alone: a block that equals a base another instance just pushed reads as forge-ahead, not as a conflict. A fetch older than the observation the locked row records (its `forge_updated_at`, the forge's own `updated_at` of the version a pull last applied or converged on, of the write a push last recorded, or of a newer version a pull saw and did not apply: the version it flagged the mapping over, or one with the base's content — issue #509) writes nothing, whether or not the base moved since the read: another instance pulled the newer version — perhaps between this pull's fetch and its read of the mapping — or pushed a write the fetch predates, and the older fetch would set the block back while that instance's cursor may answer 304 from then on, so no later pull would correct it. Such a skip whose fetch differs from the recorded base is logged (one WARN per entity and run, with the block and both stamps) and counted (`pull_skipped` in the run state forge-sync-status serves and in the run row's stats) — on a mapping that is flagged already as well (issue #509); the ordinary older fetch of the base's own version says nothing. A run that fails carries the counts of the leg that failed in its status and its run row (the issues of a page applied before the failure committed). Once, the WARN is the trace of a race with another instance's pull or push. Run after run for the same block it marks a known limit: the forge's `updated_at` went back behind the recorded stamp (a clock set back, a restore of the forge from a backup, a manual change), every pull skips the entity, and a later local edit is pushed over the forge's version. A re-sync does not help (the mapping keeps its stamp); the way out is the manage action `forge-stamp-reset` (`ctx project issues stamp-reset <block-id>`, or `--all` for every mapping of the project; issue #509), which takes both steps in one transaction. It sets the mappings' `forge_updated_at` to NULL, so the apply decides on content again — a pull-update where the block did not move, a conflict where it did — and it holds the leg's fetch cursor to a full listing, because the next run asks the forge only for what changed at or after the saved `since` — the largest `updated_at` the leg has seen — and with the saved ETag, so an entity whose forge stamp went back behind that is not listed at all. The hold (below, with the resolve surface) also keeps a run that is under way from saving a cursor past it. Taken by hand, the two steps needed each other and an order: a run after the cursor drop alone listed the entity, skipped it again and saved a cursor again — `since` at the stamp that went back, and the ETag of that listing, which the forge answers with 304 while nothing else changes — so a mapping reset after such a run needed the cursor dropped once more (both orders executed against a fake forge that answers `since` and `If-None-Match` as GitHub does, `TestTheWayOutOfAForgeStampThatWentBackTakesBothSteps`; the action: `TestStampResetBringsTheSkippedRemoteEditBack`). GitHub's `updated_at` has whole seconds. When the base moved since the read and the fetch carries the stamp the row records, the two versions cannot be ordered: the pull flags the mapping and writes nothing either way (nothing to do when it fetched the very version the other instance pulled) — the answer the base write gave before issue #491; without a moved base the same stamp is the next version of one second and is pulled. A run that flags an entity anew, or finds such an unordered version, saves the leg's cursor no further than that entity's stamp and without an ETag (issue #509): `since` becomes the smaller of the newest stamp the leg has seen and the earliest such entity's, for that page and every later page of the leg, in the issue leg and the comment leg alike. The next run lists the entity again (`since` is inclusive) and decides on it — where the block did not move it pulls the forge's version and clears the flag. With `since` at the newest stamp, a later entity on the same listing moved it past the flagged one, and with the listing's ETag the next run answered 304 while nothing else changed; the flagged entity was not listed again before its next remote edit. Only that run holds the cursor: a mapping flagged already is decided on the read and holds nothing, so the run after the flagging one lists the entities from the held stamp on once and saves the cursor as before (`TestTheCursorHoldLastsOneRun`). That once is the cost of the rule: one listing from the held stamp instead of the newest — the entities updated between the two, their pages, one block read each and nothing written — and one rate-limited request where an unchanged `since` would have had a 304. A hold on page k of a run that meets the page bound makes the next run read from page k on again, so at most the bound's pages once per entity flagged anew; the cursor an earlier page of the run wrote never lies above the hold, because the listing is ascending by `updated_at`. The cursor is one per project and leg: another instance's run that commits its own cursor afterwards can still move it past the hold, and the flag then stays until block and forge agree on a later listing — the push sends nothing over it. Two orders of two instances lost a remote edit without a flag (issue #509; both executed against the fake forge over the production cursor, `TestAStaleConvergenceNoLongerClearsAFlagOverANewerRemoteEdit`, `TestAStaleCommentConvergenceNoLongerClearsAFlag`, `TestARemoteRevertToTheBaseInsideAPushWindowIsPulled`). (a) A flagged mapping whose block a local edit brought to the forge's version: one instance's pull read the convergence and was slow to write; a remote edit landed; the other instance's run listed it, found the mapping flagged — a conflict on its read, which wrote nothing and held no cursor — and saved its cursor past it; then the first pull's convergence stood on the locked rows and cleared the flag, the block stayed on the older version, and a later local edit was pushed over the remote one. Now a read of a flagged mapping whose fetch is newer than the row's observation goes on to the locked rows and records it: the row's `forge_updated_at` takes the fetch's stamp and the flag's forge snapshot the fetched version. The stale convergence is then older than the row's observation and is skipped — the flag stands, over the newer version, until it is resolved — or, where it wrote first, the other run finds the base moved and pulls the newer version over the converged block. A fetch with the stamp the row records still ends on the read, so a remote edit in the second of the version the convergence read is not recorded, and the convergence can still clear the flag over it (two forge writes within one second). (b) A remote edit that brings every projected field back to the listed base after the PATCH landed, listed by another instance's run before the advance: the run read ctx-ahead and held no cursor, the advance recorded the sent version as the base, and the revert was not listed again. Now a ctx-ahead read whose fetch is newer than the row's observation goes on to the locked rows as well: where they are still ctx-ahead, the row records the stamp (the forge's content is the base's, so the base stays) and the leg holds its cursor at it like a new flag; the next run lists the entity again and, the advance having moved the base to the sent version, pulls the revert. A second run of that instance inside the window reads the entity again with the stamp the first one recorded, holds nothing and saves its cursor past it; the advance then finds the row's observation later than its PATCH's answer while the row still holds the listed base — the forge held the base's content after the PATCH — and flags the mapping, with that observation as the flag's forge side (the listed base's fields and the observed stamp), so the revert stays visible and taking the remote version pulls it. Only an observation of the base's content counts: a flag a pull set inside the window raises the stamp as well, over other content it keeps in the snapshot, and that is a divergence the flag already shows (`TestResolveLocalKeepsAnEditFlaggedInsideThePushWindow`). The cost: a write transaction and one listing from that stamp for each such observation — a local edit not yet pushed whose forge issue changed outside the projection (a comment, a reaction) — and none for the same stamp again, which the row now records.

A flag goes once a pull finds block and forge in agreement (issue #509): a pull that finds them at one version on the rows it locks clears it (and its `conflict_at`) and records that version as the base — the convergence did so already, and now the noop cell does as well, where block, base and forge all hold that version (before, it wrote nothing, and the flag kept the mapping out of the push's listing for good). It takes a fetch the row's stamp does not show to be older: a flagged noop row whose `forge_updated_at` lies ahead of every listing of the entity — a push answer stamped ahead of the forge's later listings, a forge stamp that went back — skips every fetch as older, and its flag stays; the way out is the one for a stamp that went back, above. A push advance clears no flag: it knows what the forge held in the fields its PATCH sent when it answered, not what the forge holds since, and a flag another instance's run set while the PATCH was on the wire can stand for a remote edit that landed after it — the run that set it holds its cursor, and the next run pulls that edit where block and base hold the sent version. Cleared by the advance where its block held the sent version, the edit stayed behind a 304 or a `since` past it, and a later local edit was pushed over it without a flag. A flag over a real divergence of both sides stays until it is resolved (the resolve surface below) — a later local edit is not pushed meanwhile; a remote edit clears it only while the block has not moved. A known limit remains, pinned: the same stamp pulled by another instance between this pull's fetch and its read of the mapping reads like the next version of one second and is written — once that instance's cursor answers 304, the block stays on the older version and a later local edit is pushed as a field-diff over the newer one (two instances, two forge writes within one second, and a pull of the other instance inside a window of milliseconds). That orders two observations of the forge on the forge's clock; the direction stays a matter of content hashes (W16). The push records the forge's stamp of its own write as well (issue #509): GitHub answers a PATCH or POST with the entity it left, `updated_at` included, and the advance (or the create's finalize) writes that stamp with the base — never one older than the row records (`GREATEST`: a pull may have recorded a later observation of the same version meanwhile). An answer without a readable `updated_at` keeps the row's stamp and is no error of the push; the write landed. Before, the advance left the stamp of the version a pull last saw, and with the same stamp and an unmoved base the matrix decided about a fetch older than the push: a spurious conflict after a later local edit, a local revert to the older version lost without a trace, or a step back of the block that the next pull healed; now such a fetch is older than the row's observation and writes nothing. A remote edit that lands in the second of the PATCH carries the stamp the push recorded: the next pull reads the mapping after the advance, finds the base unmoved and pulls it; a pull that read the mapping before the advance and writes after it cannot order the two versions of that second and flags the mapping, its run saves the cursor no further than that stamp and without an ETag, and the run after it pulls the edit and clears the flag. A base write sets `synced_at` to the `updated_at` of the block version it records, or `-infinity` when a local edit moved the block past it before the lock. A convergence no longer stamps `now()`, which hid every local write whose transaction began before the convergence and wrote after it; a pull-update records its own write. A known limit remains for all three base writes (convergence, pull-update, push advance): `updated_at` is the writing transaction's start, so a local write whose transaction began before the writer of the recorded version began, and that takes the row only after the base write committed, stores an `updated_at` below `synced_at` — it is no push candidate and is not pushed until the block is written again, and nothing flags it (pinned by `TestPullConvergenceKnownLimitWriteBegunBeforeTheRecordedVersion`). No timestamp tells it apart; closing it needs a write counter that advances in the order writers take the row, which is a schema change. A local-only mapping (`forge_id=0`, an unpushed `issue-create`) is never a fetch id, so a pull leaves it untouched. Each issue applies in its **own transaction** (block + mapping + references atomic); the fetch cursor (`sync_cursor.issues.{etag,since}`) advances durably only **after** a page's apply succeeds, so an apply error mid-page leaves it un-advanced and the resume re-applies the committed rows as idempotent no-ops. The mapping lookup is one batch query per page (no N+1 at 10k+ issues/repo).

**Status apply + fallback (§4.5.4).** The forge `state` maps to `workflow_status` via the type's `forge_state_map` (open→backlog, closed→done). A pull-create writes the mapped status. A pull-update writes it only when the remote state differs from the state the locked block projects to (open ↔ closed) or the block carries no status of the resolved workflow (none yet, or one a change of the type's workflow dropped — no local verb can move a block out of such a status); otherwise the block keeps its status, so a local move between two statuses of one forge state (backlog → in-progress, done → wontfix) survives a remote edit of the title or the body — the projection carries the forge state only, so such a move is invisible to the 3-way decision. Up to issue #486 every pull-update wrote the mapped status and reset such a move without a conflict. When the registry is not resolvable, the pull writes **only `metadata.forge_state`** and leaves `workflow_status` NULL — a documented fail-safe, never a guessed status set (a pull-update sets a status a block carries from a registry that resolved before to NULL as well, whatever the forge state does: with no workflow there is no set to tell a kept status from a stale one, and a kept status would be read again once a workflow resolves); an idempotent backfill lifts the corpus once the registry ships. The push (create and update) and a convergence write `metadata.forge_state` as well — the state of the base they record: what the PATCH made the forge hold, what the pull read from it (issue #491). Before, only the pull wrote it: after a pushed or a converged close it still said open, and with the workflow lost any later local edit projected the issue as open against the closed base and the push reopened it. The value is written only when it changes and does not move `updated_at`. The ctx projection reads state from `workflow_status` (terminal ⇒ closed, else open) when the registry resolves, and from `metadata.forge_state` otherwise — so a freshly pulled issue projects to exactly its forge state (`ctxH == base` byte-identical, the golden gate) in both modes. A status the resolved workflow does not carry (a change of the type's workflow dropped it) decides nothing about the state: the block projects the state of the base it is compared with (the mapping's field snapshot, else `metadata.forge_state`), issue #491. Before, a dropped terminal status was no member of the new terminal set and projected to open against the closed base, so the next push of any local edit reopened the forge issue and a remote edit of it read as a conflict. Reopening an issue the forge holds closed takes a local status change against the base — a move to a status of the workflow that is not terminal — and that still pushes `state=open`; a local reopen not yet pushed whose status a workflow change then drops projects the closed base again and is not pushed, and in the other direction an unpushed local close into a terminal status that a workflow change then drops projects the open base again and is not pushed either — the forge issue stays open, no local verb moves the block out of the dropped status, and the next remote edit writes the status the forge state maps to (pinned by `TestDroppedStatusUnpushedLocalCloseIsNotPushed`). Over-cap bodies are truncated on a rune boundary + flagged `metadata.truncated` (§5.5), and the hash runs over the truncated bytes so a >50 KB issue does not drift.

**References edges (§4.5.7).** Issue/comment bodies are parsed for `#<nr>` tokens; each resolves via the mapping to a target block and gets a `references` edge in `context_structural_links` (class `references`, origin `forge-sync`, idempotent via the PK). An unknown number yields **no phantom edge**; a later pull-update of the source adds it (a pull of the target does not — the edge belongs to the source's body); self-references are dropped. Zero forge requests — pure local parsing. The targets are resolved before the issue's transaction begins and, where the issue's block exists already (a pull-update; a pull-create's new block is no other transaction's to wait for), locked in one order of ids with that block (issue #503): the targets whose id lies below the block's before it, in ascending order, those above it after it by the reference write itself. The lock is `FOR SHARE`, the lock the link's validation takes, which keeps a target's scope from moving under the link (a scope move takes the row `FOR NO KEY UPDATE` — a scope is no key column — which `FOR KEY SHARE` would let through). Two instances that pull two issues referencing each other no longer end in a deadlock (`40P01`): the later one waits before it holds a row the earlier one needs. Comments pull on their own leg (`sync_cursor.comments.{etag,since}`) after the issue leg (so the parent issue mapping exists); a comment whose parent is not yet pulled is skipped and picked up on a later run.

**I-H is the PUSH pass (`forge.Pusher`), the mirror of the pull.** It runs as a third sync leg AFTER both pull legs (§4.5.3: "on GitHub's return the next run drains ctx-ahead via push"), gated fail-closed by `push_enabled` (default **false**, §5.6 — a fresh repo is pull-only until an explicit tenant-admin toggle) AND a resolved token (a write needs auth). A mapping is a push candidate iff it is **not conflict-flagged** and either `forge_id=0` (a local draft) or the block's `updated_at` is newer than the mapping's `synced_at` — because the pull already set `base := forgeH` for anything the forge changed, a surviving `base != ctxH` is by construction **ctx-ahead** (`base == forgeH`), so the push needs no extra fetch to decide direction. Cases: **create** (`forge_id=0`) ⇒ POST the issue, then in ONE transaction write `forge_id`, rename `#L<seq>`→`#<nr>` (block title) + cascade the comment titles `#L<seq>.cL<n>`→`#<nr>.cL<n>` (one UPDATE, identity-neutral — the mapping is the identity) + `base := ctxH`; **update** (`forge_id>0`) ⇒ a **field-diff** PATCH carrying only the projected fields that diverge from the last-synced snapshot, so a local status flip pushes `state` and **never** the body; comments push AFTER their issue (CreateComment needs the forge number). Idempotent: after a create/update the mapping is in-sync (`updated_at==synced_at`, `base==ctxH`), so a re-run drops it — no double-rename, no base drift. The update's base advance locks the block (`FOR NO KEY UPDATE`) and projects it again (issue #452): `synced_at` becomes the `updated_at` of the version the PATCH wrote, or `-infinity` when a local edit changed the block while the PATCH was on the wire, so that edit is listed and pushed by the next run whatever `updated_at` its transaction carried (the known limit above aside: a write whose transaction began before the pushed version's writer began and that takes the row only after the advance). The push writes an entity — the PATCH and the advance that records it, or the advance alone — under the entity's push lock (a session-level advisory lock keyed on the block id, `pg_try_advisory_lock`, on one pool connection the section holds), once it finds the mapping still at the base its listing read and not conflict-flagged (issue #491). An entity another ctxd instance is writing now, wrote since the listing, or flagged since (its pull saw both sides move), is left to the next run and counted (`push_skipped` in the run state forge-sync-status serves and in the run row's stats; a DEBUG line names the block and the reason): the lock is only tried, so no push leg waits on another one's wire call, and a listing another push overtook sends no stale field-diff. Two instances therefore never have updates of one entity in flight at once (a push-create — POST and finalize — runs outside the section; no production path writes the `forge_id=0` mapping a create starts from yet) — before, B's PATCH and advance of a newer local version could run while A's PATCH of an older one was on the wire, A's landed last, and a pull in between found the block at B's base and the forge ahead of it and wrote the older version over the newer one on both sides. No transaction is open on that connection while the PATCH is on the wire, so the forge's answer time holds no snapshot back from the vacuum horizon and no relation lock that an `ALTER TABLE` on `context_project_sync_map` — and every access queued behind it — would wait for (the first form of the section kept a transaction open across the PATCH: idle in transaction with `backend_xmin` set and an `AccessShareLock` on the table, for up to the forge client's 30 s timeout); the advance runs afterwards in one short transaction on the same connection. The lock is given back on every way out, and a connection whose release is not proven is closed instead of pooled (the server ends a closed session's advisory locks), so no pooled connection keeps an entity locked. The connection stays out of the pool across the wire write — one per running push leg; a running sync holds one pool connection at a time (the pull's write transaction, which since issue #503 resolves its reference targets before it begins, or the push section's), V68 still reckons two per sync, and `project.sync.max_concurrent` is clamped at boot so that the syncs cannot hold the whole pool (V68: at most 9 syncs, 18 of the pool's 20 connections; a larger value is clamped with a warning). The advance writes the base only while the mapping still holds the base the listing read or the version the PATCH sent (issue #486; another instance's pull that ran after the PATCH landed converges on the sent version, and that is no conflict, issue #491): another instance's pull may still move it to a third version while the PATCH is on the wire — it converged on what the PATCH sent and then pulled a remote edit — and then the advance cannot tell what the forge holds. It records the base `unknown` (no projection hash can equal it), drops the field snapshot and flags the mapping as a conflict: the push leaves it alone, and the next pull's 3-way decision converges when block and forge agree (base := their hash, flag cleared) and keeps the conflict otherwise. Two older limits of the push stay (named, not built): (i) a flag set while a local edit was in flight stays while that edit stands: A's PATCH landed, a local edit followed, B's pull flagged the mapping (block at the edit, forge at the sent version), A's record set the base and kept the flag (the block does not hold what it sent) — the edit is not pushed until the flag is resolved (the resolve surface below; keeping the local version pushes the edit against the base the record wrote) or block and forge agree again (the edit undone, or the forge brought to it); (ii) a remote edit that lands before the PATCH is overwritten by it in the fields the PATCH sends (GitHub has no conditional PATCH), and the overwritten fields are gone in every order: a pull that fetched the remote edit before the PATCH landed flags the mapping when it applies before the advance, the advance records the sent version as the base and keeps the flag, and the run after the flagging one lists the entity again (the cursor hold above) and, where block and base hold the sent version, pulls the forge's state — the remote edit's other fields included — or clears the flag alone where block, base and forge agree; applied after the advance, the fetch is older than the push's recorded stamp and is skipped (WARN); and where no pull saw the edit it is gone without a trace. A listed mapping whose block projects to its base already (a tags write, or an edit undone before the run) gets no wire write and goes through the same advance, so it leaves the candidates instead of filling the batch for good. Such an advance without a wire write writes only while the mapping still holds the base the listing read (issue #509): it sent nothing, so a base a pull moved since the section's check is the forge's own, and it records, flags and stamps nothing — before, it recorded the base `unknown` and flagged the mapping as if a PATCH had been on the wire. Milestone is never pushed (it needs a forge milestone *number*, and there is no local milestone-edit surface, §4.5.7). The 3-way base snapshot is persisted per base write (`context_project_sync_map.metadata.base_fields`) — the field-diff compares VALUES, not just the opaque `base_hash`.

**Resolving a flag (issue #509).** Three tenant-admin manage actions, with the ownership check and the uniform 404 of the other forge actions, and the `ctx project issues` commands beside them, serve the flagged mappings ([API](api.md#forge-sync-manage-actions-workflow-i-f)). `forge-conflict-list` pages through a project's flagged mappings in block id order with both sides: the block's projection (as the pull and the push compare it), the base the mapping records, the time of the flag, and the forge side as far as the database knows it without a request to the forge — the newest forge stamp the row records and the version the flagging pull fetched. A flag the pull sets keeps that version in the mapping's metadata (`forge_seen`: projection, hash, stamp) and records its stamp as the row's `forge_updated_at` when it is the later one; every base write drops the snapshot, and so does a push advance (a pull that flagged while the PATCH was on the wire saw the forge before or after it landed) — unless the snapshot's stamp lies after the stamp of the PATCH's answer: then the pull saw a remote edit that landed after the PATCH, and the snapshot stays as the flag's forge side (issue #509, the follow-up list of 2026-11-23). Dropped, a local resolution kept the sent version as the base and the next fetch of that remote edit — at the stamp the row records, the base unmoved — pulled it over the block although the local version was chosen (`TestAPushAdvanceKeepsANewerForgeSnapshot`). An advance that records the base unknown keeps such a snapshot too, or, without one, takes the moved base as the flag's forge side when its stamp lies after the answer's — a pull applied or converged on that version after the PATCH landed (`TestAnUnknownBaseKeepsTheForgeVersionAPullAppliedAfterThePATCH`); an observation at or before the answer's stamp, or any without an answer stamp, is dropped as before. The list names the snapshot current only while its stamp is the row's, and it cannot know whether the forge changed after that observation. A page reads the project's flagged rows through the partial index `idx_sync_map_conflict` (`project_id WHERE conflict`) and sorts them; its cost grows with the flagged rows of the project, not with its mappings (a keyset index on `(project_id, block_id) WHERE conflict` would take a migration). `forge-conflict-resolve` resolves one mapping: **local** makes the forge version the flag recorded the base (or keeps the row's base where no current snapshot exists; an unknown base stays unknown, so the push sends every pushed field — a run that lists the entity before that push flags it again with a snapshot, and a second local resolution diffs against that; the advance that left the base unknown holds the entity's fetch leg at the later of the row's forge stamp and its PATCH's answer stamp, so the next run lists the entity whatever cursor another instance's run saved meanwhile — it converges where block and forge agree, and records a newer forge version as the flag's forge side; before, a run of another instance that listed the entity between the PATCH's landing and the advance found nothing to decide and saved its cursor past it, and a flag over a block and a forge that agreed stood for good, with every later local edit unpushed (`TestAnAdvanceThatLeavesTheBaseUnknownHoldsTheLeg`; the hold is written in a transaction of its own after the advance's, which takes the project row after nothing else; the advance marks it as pending on the mapping row in its own transaction (`metadata.hold_pending`), and where the hold write fails or the process ends before it, the next run of any instance sets every pending hold before it reads its cursor — a check over the partial index `idx_sync_map_conflict`, a mark only ever sits on a flagged row — and a local resolution sets it, a resolution now taking the project row first in both directions; `TestAHoldThePushCouldNotWriteIsSetByTheNextRun`) with `synced_at` `-infinity`, so the next push diffs the block against it and sends the block's version; a pull that lists that same forge version reads ctx-ahead, a newer remote edit is a new conflict. Refused (409) for an issue whose truncated body differs from that basis — the push never sends a truncated body. **remote** makes the block's own projection the base and holds the entity's fetch leg at the row's forge stamp (a full listing without one), so the next pull lists the entity — its forge stamp lies at or after the recorded one — and pulls the forge's version over the block. Until a pull decided over the entity, the push leaves the mapping alone (`synced_at` `infinity`: the candidate filter `b.updated_at > m.synced_at` is false for every local write, also for a release that does not know the gate): the base is a version the forge never held, so a push of a local edit made after the resolution would have diffed against it and sent the edit over the forge's version, the one the resolution chose, without a flag. The pull that lists the entity pulls the forge's version (no local edit since), flags the mapping (a local edit since: block and forge both moved off the base), or finds the forge at the base and opens the gate, and the push sends the block's edit (`TestAPushAfterARemoteResolutionWaitsForThePull`, `TestTheRemoteResolutionsPushGate`). An entity that left the forge — an issue deleted, or transferred to another repository — is never listed again and kept the gate for good, unseen: `forge-sync-status` counted flags only and the conflict list showed flagged rows only (issue #509). Both status surfaces now count the gated rows whose block is live (`gated`), `forge-conflict-list` with `gated: true` lists them in the conflict shape (`ctx project issues conflicts --gated`), and the way out for an entity that left the forge is archiving its block: the push lists no archived block, the count and the list leave it out, and the next issue's edit is pushed (`TestAGateOverAnIssueThatLeftTheForge`). A local resolution of a gated row opens the gate (`synced_at` `-infinity`, basis `gate`) under the locks and with the audit row of every resolution — for an entity the forge still has, when the operator keeps the local version after all: the next push diffs the block against the base the remote resolution wrote and sends the edits made since, over the forge's version in the fields they touch, without a flag (no pull has shown the forge side since the remote resolution dropped its snapshot). For an entity that left the forge it is no way out: the push gets the forge's answer for any mapping of such an entity — 404 for a deleted issue, a 301 the forge client refuses for a transferred one — and the push leg fails on every run before the candidates after it, the class of every mapping of a gone entity with a local edit, older than the gate. No index holds the gate: the count and a page of the gated list read the project's mappings through the primary key — 8–20 ms and 2 330 buffers at 100 000 mappings of one project, where the conflict count takes 0.2–0.5 ms over its partial index; a partial index on `(project_id, block_id) WHERE synced_at = 'infinity'` would bound both by the gated rows and takes a migration. Both clear the flag, its time and the snapshot, keep the row's forge stamp (it orders the next fetch), and write a `context_settings_audit` row (`entity_type` `forge_sync`, action `resolve-local` / `resolve-remote` / `stamp-reset`, the acting key, the mapping before and after, the owning tenant in `metadata.tenant_id`; `GET /api/audit?entity=forge_sync`). A resolution runs under the locks of the sync and in their order: the entity's push lock, tried and not waited for (a push whose PATCH is on the wire ⇒ 409, retry), then for remote the project row (the cursor; a project delete takes the project row before its mappings), then the block and the mapping row `FOR NO KEY UPDATE` — the order of the pull and of the push advance — so a pull or a push of the entity runs wholly before or after it (`TestResolveAgainstAConcurrentPull`, `TestResolveAgainstAConcurrentPush`, both orders over hold points). It is idempotent: a mapping that is not flagged (resolved already, or a pull cleared the flag) is answered `changed:false` and nothing is written; `expect` names the flag the caller listed (`flag` in the list), and a row flagged again or holding a newer forge observation since is refused with 409. Clearing the flag without moving a side is not offered: with block and forge apart from the base, the push sends the block's changed fields where it lists the row and a pull flags it again where it lists the entity — which happens first decides; where block and forge agree, local and remote both converge; where one side holds the base, it is the other direction. **The fetch-cursor hold.** A remote resolution and a stamp reset write a hold beside the legs (`sync_cursor.holds.<leg>`: a time and a nonce) and set the leg's `since` no later than that time and its ETag empty. A run lists the leg from the hold's time without an ETag whatever `since` and ETag the leg carries. A run that started before the hold — its project row, and so its cursor, predates it — saves its cursor no further than the hold's time and without an ETag, and keeps the hold; a run that read the hold lists from that time on, saves its own cursor, and drops the hold once it read the leg to its last page (`TestAHoldSurvivesARunThatStartedBeforeIt`). Before, a run under way that had passed the entity saved its newest stamp and its ETag after the change, and the entity was not listed again. The hold sits outside the leg objects because the release before it saves a leg's cursor by merging `{leg: {etag, since}}` into `sync_cursor`, which replaces the whole leg object: during a rolling deploy such an instance's cursor commit leaves the hold in place, and the next run of an upgraded instance honours it (`TestAHoldSurvivesAnOldInstancesCursorCommit`). The comment leg's orphan record (`sync_cursor.orphans_until`, below) sits beside the legs for the same reason. A stamp reset does not take the push lock: a push advance that commits after it records its PATCH's answer over the NULL — the forge's own stamp of that write, from the clock the forge runs on now, which a push after the reset records as well; the held listing returns the entity's current version with that stamp, decided on content, so a remote edit carried in that version or made later is pulled. Only a forge whose stamps go back again after the PATCH lists an older version, which is skipped as after any push that follows a reset — the reset recovers recorded stamps, it does not guard against a later regression, and another reset recovers that one (`TestAStampResetInsideAPushWindow`). **Named limits of the resolve surface.** A hold is dropped only by a run that read it and committed a cursor after the leg's last page; a leg that lists nothing from the hold's time on (the held entity left the forge, and nothing else changed) commits no cursor, so the hold stays and each run lists from its time without an ETag — one small listing per run instead of a 304 — until an entity changes again. A local resolution decides against the forge version the list showed: a remote edit that no pull has seen since (it lands after the flag, before or after the resolution) is overwritten by the push without a flag, because the push never reads the forge before it writes (the class of issue #452); a pull that lists it first flags the mapping again. **Rolling deploy.** An instance of the release before the resolve surface does not serve the three actions; its runs list a leg from the leg's own `since` and ETag (a hold set before such a run starts has moved those, one set while it runs it overwrites in the leg and leaves beside it, and the next upgraded run honours it); its pulls record no forge observation, so the two orders of issue #509 that lost a remote edit stay possible where the instance that reads the newer version runs the old release; its pull opens no push gate on a ctx-ahead or level read (the gate holds until an upgraded instance's pull, or its own pull of the forge version, convergence or flag, ends it — its push honours the gate, which is the candidate filter); its base writes keep a forge snapshot they do not know (listed, but not current once the stamp moved); and it holds no orphan comment. Upgrade every instance before relying on the resolve surface. Two more limits of the push gate: a stamp reset gives up the order of fetches for the entity, so after a remote resolution and a reset, a page another run fetched before the flag — when the forge held the block's own version — decides on content and opens the gate on that old version (pre-existing for every reset: it decides on content); and where the forge's stamp went back behind the one the gated row records while the forge holds the base, every pull skips the entity as older and the gate holds a local edit back without a WARN (the content equals the base, which the stale report leaves out) until a stamp reset. While an issue leg stops at its page bound, every orphan comment holds the comment leg at the earliest orphan's stamp, so a bounded catch-up re-reads those comments on each run until the issue leg completes. A comment whose parent issue has no mapping holds the comment leg's cursor at its stamp (so the next run lists it again): every such comment while the run's issue leg stopped at its page bound — the listing is ascending by `updated_at`, not by number, so the parent may be any issue the leg has not reached yet — and, after an issue leg that read its listing to the end, one whose parent number lies above every mapped issue and that the previous run did not list (an issue the forge created between the two legs). What the previous run listed is one timestamp beside the legs, `sync_cursor.orphans_until`: the newest comment stamp its comment leg listed, saved with each page's cursor; a comment at or before it was listed — and held, if it was an orphan — by that run (issue #474). Before, the record was the list of the held comment ids, written again after every comment page and carried in every later cursor commit: a page-bounded catch-up of 1000 pages of 100 orphans wrote 0.9 MB of JSON, about 240 MB of WAL and 20–28 s of database time per run; now 107 bytes, 0.1 MB and 0.4 s (`TestTheOrphanRecordOfABoundedCatchUpStaysSmall`). An edit of a held comment on a pull request moves its stamp past the record, so it holds the comment leg once more. A comment on a pull request (the issue listing drops those) so holds the cursor once after a complete issue leg and on each run of a bounded catch-up, never beyond it (`TestACommentOnAnIssueABoundedIssueLegHasNotReached`, `TestACommentOnAPullRequestHoldsTheCommentCursorAtMostOnce`).

**Push data-loss guard (§4.5.2).** An entity with `metadata.truncated=true` HARD-excludes `body` from the push: a status flip on a truncated issue PATCHes `state` **without** the body, and if the (truncated) body is what diverged the entity is flagged **conflict** and written NOWHERE — the 50 KB cap must never overwrite a 64 KB forge body (up to ~15 KB of foreign content). Conflict-flagged mappings and `push_enabled=false` both mean **zero wire writes**.

**Push throttle (token-scoped, §6.1).** GitHub's 80 content-POSTs/min secondary limit is per **credential**, not per repo, so the push throttle is an in-process token bucket (`forge.Throttle`) keyed on the credential — repos sharing one PAT draw from ONE bucket (2 repos on 1 PAT with per-repo buckets would sum to 2× and trip a 403 cascade). **Deviation from §6.1's literal "token_secret name" key:** under masterplan K14 each project seals its OWN secret (`forge.token.<project_id>`), so the *name* is per-repo; to realise the per-credential intent the key is `forge_kind + sha256(resolved PAT)` (in-memory, never logged). The bucket steady rate (30/min, burst 30) keeps any 60-second window under the 80/min limit. When the bucket runs dry the pass STOPS (batch-wise) and the rest drain on the next run; a push wire/rate-limit error backs off exactly like a pull (never a conflict).

## Principal identity (migration 094)

The identity layer on which the three auth paths converge — `api_key` bearer, OAuth token (Achse 03), external-login session (Achse 04/05). `context_principals` (`id`, `display_name`, `primary_email`, `is_active`) is the **person**; `context_api_keys.principal_id` is `NOT NULL FK ON DELETE RESTRICT` (one key belongs to exactly one principal — no rights-bearing orphans, a principal hard-delete requires prior key deactivation). `context_external_identities` (`UNIQUE(issuer, subject)`, `ON DELETE CASCADE`) holds the external-IdP link that Achse 04 fills under INV-C (allowlisted+validated issuer, never the raw `iss` claim). Decision **E1=B′** (Big-Bang with *additive* audit, DECISIONS.md): the 12 audit FKs keep `api_key_id` (key/client forensics) and gain `principal_id` additively (person attribution) — no information loss (that additive FK wave is migration 096).

The backfill is **green-field** — every existing key gets its own fresh principal (10 keys → 10 distinct principals, 1:1). It runs `WHERE principal_id IS NULL` and is guarded by `pg_advisory_xact_lock` at the migration body: when 094 was written the runner took no lock before a migration, so two ctxd instances starting in parallel could both pass the applied-check and double-backfill — the advisory lock serialises the body, the second instance blocks until commit and then finds nothing to backfill (since issue #398 the runner itself takes a lock per file and checks `_migrations` again under it, see [operations](operations.md#several-instances-booting-together)). Every step is idempotent (`CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`, `SET NOT NULL` no-op, FK behind a `duplicate_object` guard). Migration 094 ships the **schema only** (`ctx_auth()` untouched, existing auth byte-identical); **migration 095 (F2)** wires the convergence. `ctx_auth()` now RETURNs `principal_id` as its last column (append pattern — every named SELECT stays valid, old binaries read the first ten columns) and enforces a **third** fail-closed gate: the principal must be `is_active` — the revoke-all mechanism (`is_active=false` locks every key of a person key-agnostically, no key-by-key deactivation). The inner scope build is factored into **`ctx_auth_by_id(uuid)`**: `ctx_auth(plaintext)` resolves `key_hash→api_key_id` and delegates via `RETURN QUERY`, and Achse 03 (token at `/mcp`) + Achse 05 (browser session) resolve their `AuthResult` through the **same** function — no gate-drift twin, since the three gates (key `active`, tenant status, principal `is_active`) + the `last_used_at` write live in one place. The soft-revoke negative gate (`active=false` → no `AuthResult`) is pinned in the by-id UPDATE's WHERE, so a session/token path can never bypass the `active` clause. `AuthResult.PrincipalID` surfaces at `/api/whoami` (`principal_id`) and threads into `dispatch.Principal` as an identity dimension — carried like `TenantID`, **not** the fairness key (`fairKey` stays `HomeScope`), so scheduling is byte-unchanged. The invariants are binding on 03 and 05: **INV-A** (one `AuthResult` = one key, a multi-tenant principal never unions scopes across its keys), **INV-B** (`principal_id` is never an authorisation gate — tenant isolation + scope filter stay the sole decision), **INV-C** (issuer trust, above).

**Consumer branch of the dispatch principal (wave W01-7, design/01 §4.5).** External model consumers are their own credential class (`ctxm_` model keys, invariant **I-K0**): a model-key request carries an `auth.ConsumerAuth` instead of an `AuthResult`, and `handler.RequestPrincipal` maps it to `dispatch.Principal{TenantID, ConsumerID, ConsumerKind, FairWeight}` with `ApiKeyID`, `HomeScope` and `PrincipalID` **empty** — the B8 interactive authorization stays pinned on `ApiKeyID != ""`, so it remains the only interactive entrance for knowledge keys; a consumer has no corpus home and is no person, and `TenantID` is attribution only. Invariant **I-K10** is enforced at both admission doors (`Acquire`, `TryAcquire`) before B8: a consumer principal in a class whose `External()` is false — today every class — is refused with `ErrClassUnauthorized`, never downgraded. A request context with both credentials, or with an invalid `ConsumerAuth`, resolves to the poisoned principal `{Conflict: true}` (never the zero principal, which is ctx' own detached work) and is refused with `ErrPrincipalConflict`. The knowledge branch is byte-identical; the external queue's cap and fairness key (`_consumer:<id>`, weighted by `FairWeight`) arrive with the external class.

**Migration 096 (F3)** delivers the additive audit-FK wave: the 12 audit FKs on `context_api_keys` (11 tables; `context_secrets` carries two) keep their key anchor and gain a nullable person anchor (`api_key_id` → `principal_id`; `X_by` → `X_by_principal`), FK → `context_principals` with NO ACTION — mirrored on the existing key FKs. The write paths do **not** thread `PrincipalID` through Go signatures: each INSERT/UPSERT derives the person anchor in SQL from the acting key (`SELECT principal_id FROM context_api_keys WHERE id = <acting key>`) — key→principal is 1:1 `NOT NULL` since 094, so the two anchors can never drift apart (INV-A: the acting principal IS the key's principal). Existing rows are NOT backfilled (F3 gate "Bestand unverändert"): historical person attribution stays derivable at any time via the retained key anchor (the NO-ACTION FK blocks key deletes while audit rows reference them — no data-loss window). `context_write_log` gets the column schema-only: its two writers (guard, dream) are internal paths without an acting key.

**Migration 098 (OAuth S1)** makes the authorization-code store persistent: `context_oauth_codes` replaces the process-local in-memory map, so codes survive restarts and redeem across instances (HA). The row stores `code_hash` (SHA-256, never the plaintext code) plus the INV-A single-key selector `api_key_id` + `principal_id`; single use is an atomic `DELETE … RETURNING` (two racing `/token` calls get exactly one row), and a janitor-tick GC sweeps expired rows (correctness never depends on the sweep). The transitional `api_key_sealed` column (code-derived AES-256-GCM, S1→S3 bridge for the api-key passthrough) is dropped by migration 099 — S3 mints opaque tokens from `api_key_id` and never needs the plaintext key again.

**Migration 099 + S3 (OAuth W03-3)** land the **universal opaque-token store** `context_access_tokens` — per the E-03h reconcile the ONE credential store (Achse 05 builds no second one; its web overlay `context_web_sessions`, migration 102, only FKs onto these rows; a login mints `issued_via='login'` rows with `audiences=[ctx-mcp, ctx-web]` into this same table → a login token is structurally MCP-capable, E2). `/token` now answers with an **opaque, revocable `ctxt_` access token** (SHA-256 in DB, TTL 1h per E-03c; `expires_in` in the response; the refresh token + rotation follow in S4) — the raw api key no longer circulates through OAuth-client token storage. Resolution is the shared **`resolveCredential`** gate used by the Auth middleware AND both SSE in-stream re-auth ticks: prefix branching on the raw extracted value **before** `SanitizeKey`, header-agnostic (`X-Context-Key` or Bearer); a `ctxt_` miss never falls back to the raw-key path, `ctxr_` is rejected outright, and a pure-hex value takes the byte-identical pre-S3 raw-key path (raw keys stay valid as Bearer — deliberate E2 legacy behaviour, documented spec deviation). Both paths materialise through `ctx_auth_by_id` (095): a soft-revoked key or deactivated principal kills its tokens instantly, no token-side revocation bookkeeping. Rows carry `audiences` (RFC 8707 — the membership check at `/mcp` lands in S5) and the `refresh_family`/`parent_id` lineage columns; a janitor-tick GC sweeps rows 7 days past expiry (the long grace preserves reuse-detection evidence).

**S4 (OAuth W03-4, Go-only)** adds the **refresh grant with rotation and reuse detection**: the code exchange now mints an access+refresh pair (one fresh `refresh_family`; TTLs per E-TTL — access 1h, refresh 30d rolling, family absolute cap 90d; overridable via `CTX_OAUTH_ACCESS_TTL`/`CTX_OAUTH_REFRESH_TTL`/`CTX_OAUTH_FAMILY_CAP`, fail-safe to the defaults). A `refresh_token` grant atomically takes the presented refresh (the take predicate carries the client binding — a wrong-client presentation is a side-effect-free miss, so a value-sniffing third party cannot revoke the victim's session by spraying client_ids) and mints the successor pair chained via `parent_id` in the same family. Presenting an **already-rotated** refresh is the theft signal: the **whole family is revoked** (both directions of the race are indistinguishable, so the human re-authorizes); the wire answer stays the generic `invalid_grant` — detection is logged server-side, never oracled to the caller. A capped-out family (anchor older than the 90d cap) refuses rotation and is revoked as hygiene; a rolling refresh TTL never outlives the cap. `grant_types_supported` now advertises `refresh_token` — the C3 coupling rule applied in both directions (advertise exactly what is served).

**S5 (OAuth W03-5/6, Go-only)** hardens the endpoint parameters and completes discovery: `code_challenge_method` MUST be `S256` (plain AND absent → 400 — RFC 7636 defaults absent to plain); RFC 8707 `resource` is validated at `/authorize` and `/token` (ctx is a single-resource server — anything but the canonical `<issuer>/mcp` answers `invalid_target`, and only the validated value ever reaches the code row); `redirect_uri` rebind at `/token` (presented-but-different → `invalid_grant`; absent is accepted — OAuth 2.1 drops the token-side requirement in favour of the enforced PKCE). At `/mcp` the token path now enforces the RFC 8707 **audience membership check** (token `audiences` must contain the canonical MCP resource; requires `CTX_CANONICAL_ISSUER` — unset skips the gate, since no trustworthy expected value exists; raw api keys bypass it by design, the documented E2 deviation). The 401 carries `WWW-Authenticate: Bearer resource_metadata="…", scope="mcp"` (RFC 9728 §5.1 — MCP clients bootstrap their flow from this header), discovery advertises `scopes_supported: ["mcp"]` (E-03d: a requestable label, never an authorisation input — INV-B), and the protected-resource metadata answers under both the root and the RFC 9728 path-insertion form (`…/oauth-protected-resource/mcp`).

**S6 (OAuth W03-7, Go-only)** completes the server strand by wiring the 097 client model into enforcement: at `/authorize` a client with **registered `redirect_uris` is matched exclusively against them** (exact array membership via the C2 lookup — no loopback rule, no static fallback: the registration is the contract, and a fallback would let a narrowly registered client escape to the broader static list), while an empty registration (plain `ctx mcp add`, pre-097 rows) keeps the static S2 allowlist + RFC 8252 loopback rule. At `/token` the registered `token_endpoint_auth_method` is enforced for **both grants** before any code/refresh handling: confidential clients (`client_secret_basic`/`client_secret_post`, secret via either advertised channel) must authenticate — the stored SHA-256 hash is compared **constant-time in Go** (`subtle.ConstantTimeCompare`, never matched in SQL); public `none` clients presenting a secret fail closed, as does a Basic username contradicting the form `client_id`. Failures answer `invalid_client` **401** (with `WWW-Authenticate` on the Basic path, RFC 6749 §5.2) and never touch token state — a wrong-secret attempt cannot revoke a refresh family. An unregistered or deactivated `client_id` is `401 invalid_client` with or without a secret since the advisory §9c fix (it used to fall through to the S2/S4 binding checks as a secret-less public client). Since the advisory §6 fix `/token` also enforces the registered **`grant_types`** before any code or refresh row is touched: a DCR client gets a refresh token only when it registered `refresh_token` (otherwise the code exchange answers the access token alone, no family), and a grant outside its set is `400 unauthorized_client`; an empty `client_id` is `invalid_grant` for both grants (unregistered and deactivated ones are already `invalid_client`, see above — a deleted client no longer rotates its refresh family). Operator (`admin`) clients keep both grants: their column holds the 097 default `{authorization_code}` from before S4, never a declaration; `mcp-client-create` now writes both explicitly.

**S2 (Go-only, advisory core fix)** closes the GHSA-p3jf-x27v-4jg6 core (credential takeover via attacker-controlled `redirect_uri`, PKCE does not help — the attacker holds the challenge/verifier pair): `client_id` is **mandatory** at `/authorize` (the anonymous flow is gone) and always validated; `redirect_uri` must match a **static exact allowlist** of the known claude.ai/claude.com/ChatGPT callbacks (extendable per deployment via `CTX_OAUTH_REDIRECT_EXTRA`; loopback per RFC 8252 §7.3 stays allowed by rule; since S6/W03-7 the static list is the fallback for clients without registered `redirect_uris`); `/token` enforces the **`code.client_id == presented client_id` binding** (OAuth 2.1 §4.1.3 MUST — for public clients this equality is the only client binding there is). The RFC 9207 `iss` parameter and the discovery documents use the configured canonical issuer (`CTX_CANONICAL_ISSUER`, compose-derived from the proxy hostname) — never an `r.Host` derivation, which would be client-influencable and defeat the mix-up protection.

**Migration 097 (OAuth C1)** lands the OAuth 2.1 client model on `context_oauth_clients`: `redirect_uris` (exact allowlist, no wildcards), `scopes` (requestable **ceiling** — never authoritative, INV-B: the key authority stays the hard cap), `grant_types`, `response_types`, `token_endpoint_auth_method` (`none`/`client_secret_basic`/`client_secret_post`), `registration_source` (`admin`/`dcr`/`cimd`), `metadata` (RFC 7591 low-prio fields), `updated_at`, plus `client_secret_hash DEFAULT ''` so DCR public clients insert without a secret (an empty hash is never a valid secret — the 03 wiring checks `auth_method != 'none'` before any comparison). All defaults are behavior-neutral: existing clients keep `redirect_uris='{}'` and the static S2 allowlist stays the enforcing layer until 03 wires per-client matching (S6/W03-7). Data only — the store/CLI (C2), metadata advertisement (C3) and DCR `/register` (C4) consume it in later waves.

**Migrations 100+101 (OAuth L1)** open the consumer strand (external login, Achse 04) — schema only, zero consumer code active, existing auth byte-identical. `context_oauth_providers` is the **allowlist carrier** for INV-C: only registered IdPs are trusted, the expected issuer always comes from this config row and never from a raw `iss` claim; `slug` is CHECK-pinned to the sealbox name regex (the client secret lives AES-256-GCM-sealed in `context_secrets` as `oauth_provider.<slug>.client_secret`, never in the row), `single_tenant_issuer=false` requires an `allowed_claim` filter at runtime (Azure `common`/Google without `hd` — fail-closed, provider stays inactive without it). `context_sso_states` ports the battle-tested single-use login-state pattern: DB-backed (HA — login starts on instance A, callback lands on B), consumed via atomic `DELETE … RETURNING` keyed on the httpOnly-cookie row id (double-UUID: the URL `state` param is a second UUID inside `state_data`, so the consume key never appears in IdP logs/referrers), `purpose` (`login`/`link`) blocks cross-use. `context_external_identities` gains display-only `last_login_at`/`display_name` (never trust anchors) and a principal index.

**internal/oidc (OAuth L2, Go-only)** is the OIDC/OAuth consumer library for external login — a pure lib with zero active callers (the flow handler mounts in a later wave), ported from the hand-written serviceportal consumer and generalized to a provider abstraction: one `Provider` interface, two shapes of IdP. The discovery/JWKS cache carries TTL 5min/10min, singleflight (a login storm never thundering-herds the IdP), timeout + 1 MiB body cap + non-200 reject without negative caching. ID-token verification is parameterized instead of hardlocked: `alg ∈ id_token_algs` per provider (RSA + EC key material; alg:none and HS/RS key confusion rejected before key lookup), `iss` must equal the **configured** issuer, `aud` must contain the client_id — with multiple audiences `azp == client_id` is additionally enforced (OIDC Core §3.1.3.7) — `exp` required, `nonce` bound to the login round trip, email only surfaced when `email_verified=true`. The Entra `tid` check generalizes to the `ClaimFilter` hook (`allowed_claim` `{claim,values[]}`, enforced after the cryptographic verify). The generic OIDC provider enforces `doc.issuer == configured issuer` before any discovered endpoint is used (substitution guard); the GitHub provider is the deliberately divergent proof of genericity — fixed endpoints, no ID token, identity via `/user` + `/user/emails` (subject = stable numeric id, email only when `verified=true`, a failing emails call is a hard reject, not degraded data).

**C3 (Go-only, discovery metadata)** extends the RFC 8414 document under the §4c coupling rules: `token_endpoint_auth_methods_supported` advertises `none`/`client_secret_basic`/`client_secret_post` (no `private_key_jwt` — no jwks path in the MVP; constant-time secret enforcement at `/token` is 03/S6), `client_id_metadata_document_supported: false` (CIMD is post-MVP), and `registration_endpoint` appears only when `CTX_OAUTH_DCR_MODE` (`open`/`admin`, anything else fails closed to `off`) is switched on — the `/register` route lands in 02-W4. Deliberately absent: `scopes_supported` (no enforced catalog exists) and `refresh_token` in `grant_types_supported` (03/S4 issues it later) — the discovery document never advertises what the server does not do.

**C4a (Go-only, DCR /register)** serves RFC 7591 Dynamic Client Registration on an always-mounted `POST /register`; `CTX_OAUTH_DCR_MODE` gates per request (`off` → 404 and no advertisement — the fail-closed default; `admin` → server-admin bearer key in the handler itself; `open` → unauthenticated, announced by one boot-time `WARN` naming the env var; what stands between an anonymous registration and a user's key is the K7 consent screen at `/authorize`, see below). `redirect_uris` (required, ≥1) run through the same registration rule as the CLI path (`validateRegisteredRedirectURI`: https for real hosts, plain http only on loopback — the §4b core fix, since this list is what 03 matches exactly at `/authorize`); `response_types` ⊆ {`code`}, `grant_types` ⊆ {`authorization_code`,`refresh_token`} with default **both** (a deliberate deviation from the RFC 7591 default `authorization_code` alone: `/token` enforces the registered set, and a client that omits the field relied on refresh before that enforcement), `token_endpoint_auth_method` ∈ the advertised set with default `none` (a deliberate deviation from the RFC 7591 default `client_secret_basic` — the MCP client population is public-client-PKCE-dominated); anything else is a 400 per RFC 7591 §3.2.2. `client_name` loses Unicode format (Cf: bidi controls, zero-width runes) and control characters, then truncates to the label column (no 22001), `scope` lands as requestable ceiling (INV-B: never authoritative — open registration grants zero data access), the low-prio URIs ride in the 097 `metadata` jsonb. Confidential registrations get the `client_secret` echoed exactly once with `client_secret_expires_at: 0`; `registration_source='dcr'`, `created_by` = acting admin key or NULL (open).

**K7 (Go-only, consent screen; advisory §6)** turns `GET /authorize` from a bare key prompt into a consent screen. `client_id` (registered, active) and `redirect_uri` (the same exact-match rule the POST applies — registered list exclusive, else the static S2 allowlist + loopback) are validated **before** anything is rendered; an invalid pair gets an error page without a key field. The page (server-side `html/template`, script-free CSP `default-src 'none'; style-src 'unsafe-inline'; frame-ancestors 'none'; base-uri 'none'` — no `form-action`, because browsers apply it to the post-submit redirect to the client's callback) shows the client name (format and control characters dropped again at render time — covering operator-made and older rows — and bidi-isolated in `<bdi>`; `unnamed client` when empty), the `client_id` and the redirect origin (scheme + host in full, a non-ASCII host escaped and flagged, the path shortened), and warns when the client registered itself (`registration_source` ≠ `admin` and `created_by` NULL — open DCR) — unless the `redirect_uri` of this very request is an exact member of the static allowlist or `CTX_OAUTH_REDIRECT_EXTRA`: the code then lands at an operator-vetted callback the registrant cannot receive, and a warning on every genuine claude.ai/ChatGPT connector would only train users to click past it. The requested redirect decides, not the client's registration list, so a registration that mixes a vetted and a foreign callback still warns when the foreign one is requested; the loopback rule does not count (a local listener is not verifiable by the user). The POST requires the explicit consent checkbox (`consent=yes`), checked server-side before the key is looked at; missing consent or a bad key re-renders the screen (400/401) and issues no code.

**C4b (Go-only, DCR guardrails)** layers pure resource protection over `/register` — INV-B already makes registration authority-free, this is table-DoS defense only. Guard 1: a process-local fixed-window per-IP rate limit (`CTX_OAUTH_REGISTER_RATE`, default 10/min/IP) before any body work; the source IP is `RemoteAddr`, and only when `CTX_TRUSTED_PROXY` is set AND `RemoteAddr` matches that hop does the **last** `X-Forwarded-For` entry count (the hop's own appendix — every other XFF position is client-forgeable by rotation and never consulted). Guard 2: the hard row cap (`CTX_OAUTH_MAX_CLIENTS`, default 10000) → 403, checked after validation and before insert — the backstop that holds even when IP counting is evaded (and across instances, where the in-memory limiter divides). The rate-limit log line carries the IP: that is the forensic trail for open-mode registrations (`created_by` is NULL there). Inactivity GC is deliberately not built — the table has no honest usage signal (`context_oauth_codes` rows die on redeem/expiry), and a `created_at`-keyed GC would delete active clients; revisit once 03's token store leaves a last-used trace.

**SSO state store (OAuth L4, Go-only)** is the Go layer over `context_sso_states` (schema above, L1): `StoreSSOState` generates the opaque row id server-side — never the OAuth `state` param (double-UUID) — and `ConsumeSSOState` is the atomic single-use `DELETE … RETURNING` keyed on that cookie row id, filtered by `purpose` and `expires_at`. Every miss (replay, cross-use, expiry, malformed id) is the same silent `(nil, nil)` — no oracle for which check failed. A janitor-tick sweep evicts rows an hour past expiry; correctness never depends on it, consume checks expiry itself.

**Provider store + admin actions (OAuth L3, Go-only)** wire migration 100 to an operator surface: `internal/store/oauth_providers.go` (create / list / get-by-slug / delete) plus the manage actions `oauth-provider-create/list/delete` — all three `tierServerAdmin` (the provider table is the INV-C trust anchor: whoever writes it decides which issuers ctx trusts; pinned by the S9 enumeration gates). The `client_secret` travels only in the create payload, is sealed via the existing sealbox stack into `context_secrets` (`oauth_provider.<slug>.client_secret`, scope `_global` — the migration-100 slug CHECK keeps every legal slug `ValidSecretName`-compatible) in the **same transaction** as the row insert, and is never echoed; list/get expose secret existence only as a `has_secret` bool. Create validates fail-closed **before** any write: `token_auth='none'` (public client, PKCE-only) rejects a configured secret and every other method requires one; `single_tenant_issuer=false` without a well-formed `allowed_claim` (`{claim, values[]}`, strict decode — unknown fields rejected) is refused, since the schema deliberately carries no DB CHECK for that pair. Delete sweeps the sealed secret with the row (one transaction, no orphaned secrets). The login/callback flow handlers are a later wave — this surface is config only.

**External login flow (OAuth L5, Go-only)** mounts the consumer routes `GET /auth/login/{provider}` + `GET /auth/callback/{provider}` in the public route region (they ARE the auth flow) and wires L1–L4 into the actual round trip. Login: allowlist resolve fail-closed (unknown, inactive and `single_tenant_issuer=false`-without-`allowed_claim` rows are an indistinguishable 404), PKCE S256 + `nonce` for OIDC only (a classic GitHub OAuth app gets neither — its replay protection is state single-use + one-time code), server-side sealed state with the **double-UUID split** (the `context_sso_states` row id lives only in an httpOnly `Path=/auth` cookie; the OAuth `state` URL param is a second UUID), `return_to` filtered against open redirects (parsed, cleaned same-origin path without control bytes — else `/`), `redirect_uri` derived from `redirect_base`|`CTX_CANONICAL_ISSUER` — never `r.Host`. Callback: cookie cleared immediately, atomic single-use consume, URL-`state`-vs-sealed-state match, provider resolved **exclusively** from the sealed state (a diverging URL `{provider}` is a hard reject — mix-up defense, OAuth 2.1 §4.15; RFC 9207 `iss` checked when present), IdP `error` short-circuits before any exchange, `client_secret` unsealed only for `token_auth != 'none'`, token exchange with timeout + 1 MiB body cap over an **ssrfguard-hardened client** (dial-time deny-list, same guard as forge/camo), identity verified inside the L2 provider abstraction, then `(issuer,subject) → principal_id` with `verified_at`/`last_login_at`/`display_name` refresh and email refresh only when the provider marked it verified. An unknown verified identity is a neutral 403 (E4b admin-invite — no auto-create, no email-based auto-link), every other callback reject is ONE generic message (no oracle). Both routes sit behind a process-local per-IP fixed-window rate limit (X-Forwarded-For honored only behind `CTX_TRUSTED_PROXY`). The success response is a handover **stub** — `principal_id` carries no authority (INV-B); the session issuance replaces it in the Achse-05 wave.

**Migration 102 (OAuth R1)** lands the web overlay `context_web_sessions` (E-05-3 variant (a): own table — CSRF/UA/IP are web-only noise on the universal token table) — schema only, zero Go changes, existing auth byte-identical. The overlay holds **no token cleartext and no token hash**: cookie binding runs through `access_token_id` (FK onto the ONE 099 token store; INV-A — exactly one token row, exactly one `api_key_id`, which lives on the token row and is never duplicated here), `principal_id` is audit/whoami only (INV-B, never an authorization input), and `refresh_family` (NOT NULL here, nullable in 099 — a web session only exists with refresh lineage) lets the cookie rotation follow the 03 lineage while `csrf_secret` (per-session synchronizer token, server-side) stays stable across rotations. Instant revoke does NOT ride the FK-CASCADEs — key revoke is a soft-delete (`active=false`), the overlay row survives it and the per-request resolver (`ctx_auth_by_id` gates) answers 401; the CASCADEs are cleanup netting for hard deletes (tenant offboarding) only. Store functions and session issuance follow in R2+.

**R2 (OAuth 05-W2/W3, Go-only)** wires the cookie-session resolution: a request with NO header credential falls through to the httpOnly `ctx_session` cookie (header ALWAYS wins — the §4.2 precedence), whose value is the `context_web_sessions` row id (v7 UUID, ≥74 bits randomness). Resolution runs overlay→token→`ctx_auth_by_id`: `ResolveWebSession` re-applies the token gates exactly as `LookupAccessToken` (`token_type='access'`, not revoked, not expired; write-on-read `last_used_at` stamp), then materialises through the SAME `AuthenticateByID` as the token and raw-key paths — a soft-revoked key or revoked token family kills its cookie sessions instantly, and every session miss is one uniform silent 401 (malformed ids folded before 22P02, NO fallback to the key path). The discrimination is an explicit `isSession` flag, never value-shape sniffing (a dashed UUID would SanitizeKey-strip into a key-shaped hex string). Both SSE re-auth seams capture `(credential, isSession)` at connect time and re-resolve the pair each tick — a cookie-carried stream dies with its session like a token-carried stream dies with its token. Session ISSUANCE (login/logout/CSRF synchronizer) lands in R3 — until then no route mints an overlay row, so the ambient cookie path has no live surface without its CSRF gate.

**R3 (OAuth 05-W4, Go-only)** adds the web-session lifecycle: `POST /auth/login` (key entry) mints a login pair through the SAME 03 mint path as `/token` (`issued_via='login'`, audiences carry the MCP AND web resource — E2: a login token is structurally MCP-capable, `client_id` NULL ↔ the rotation binding ""), lays the overlay row (32-byte csrf secret, ua/ip forensics) and sets both httpOnly cookies: `ctx_session` (overlay row id, Path=/, SameSite=Lax) and `ctx_refresh` (the `ctxr_` plaintext, Path=/auth so it never rides data requests, SameSite=Strict); the Secure flag derives from the canonical-issuer scheme, never from spoofable proto headers. `POST /auth/refresh` rotates through 03's `RotateRefreshToken` — reuse detection and the family kill are inherited, so a replayed refresh cookie revokes the whole family and the session dies with it — and repoints the overlay **family-bound in the predicate** (a refresh of family A can never capture a session of family B). `POST /auth/logout` revokes the family and deletes the overlay in one tx (idempotent). The CSRF synchronizer gate lives in the Auth middleware: cookie-path mutations (POST/PUT/PATCH/DELETE) must echo the per-session secret as `X-CSRF-Token` (constant-time compare, 403 otherwise); the secret reaches the SPA via the login response and a new `whoami.csrf_token` field (omitempty — header-credential responses stay byte-identical, and header paths are never CSRF-gated: the MCP-Bearer regression gate). Login sits behind the shared per-IP fixed-window limiter (the key-guessing surface).

**R5 (OAuth 05-W6, Go-only)** completes the SSO onboarding under E4b admin-invite: the `/auth/callback` handover stub is replaced by real session issuance — a linked identity resolves to its principal, `PickPrincipalKey` chooses the most recently USED active key ("continue where the person last was"; the R6 selector switches afterwards), the full `AuthenticateByID` gate set runs BEFORE minting, and the browser lands on the filtered `return_to` with the same cookie pair as a key-entry login. A principal with NO active key answers a fail-closed 403 and no cookie — SSO establishes identity, never authorization (INV-B), and a session row structurally requires a key (INV-A); the inactive-key shape is double-gated (pick predicate AND `AuthenticateByID` — a tautologised predicate alone cannot open access, probed). Provisioning is the operator surface `oauth-identity-link/list/unlink` (tierServerAdmin, S9-pinned): link binds `(provider_slug, subject)` to an existing principal with the issuer resolved server-side from the provider row (github → the fixed constant — the stored value always matches what the login path looks up), re-binding to a DIFFERENT principal is a 409 (unlink explicitly first — the account-takeover shape), and the login flow itself never creates identity rows.

**R6 (OAuth 05-W7, Go-only)** adds the multi-tenant key selector for principals holding keys across tenants: `GET /api/session/keys` lists the session principal's ACTIVE keys (label, tenant slug/display name, role, home scope — never a hash or plaintext) with the current one marked `active_now`, and `POST /api/session/select-key` switches the session onto another OWN key — cookie-path only (a header-credential request has no session to switch, 400) and CSRF-gated like every cookie mutation. The switch **mints a fresh token/session family** on the target key (same login shape: `issued_via='login'`, MCP+web audiences, new csrf secret) and only then destroys the old one — it never mutates `api_key_id` of an existing token row in-place, because that row may run in parallel as an MCP bearer (universal credential, E2) and would silently change tenant underneath it. Ownership is one fail-closed predicate (`active=true AND principal_id = session principal`; foreign, revoked, unknown and malformed ids are ONE 403 — no oracle, no 22P02), negativ-geprobt: tautologising the predicate turns the foreign-key gate red. INV-A holds through the switch — one key replaces one key, the post-switch `AuthResult` carries no scope of the previous tenant.

**R4 (OAuth 05-W5, web-only)** moves the SPA off the stored-key Bearer model onto the cookie session: the login mask POSTs the entered key to `/auth/login` and the raw key never touches client storage anymore (the old `sessionStorage['ctx.api-key']` is gone). The per-session CSRF synchronizer from the login response / `whoami.csrf_token` is held **in-memory only** (a JS-readable copy would undo the httpOnly hardening) and rides every state-changing `/api/*` request as `X-CSRF-Token` — GETs and the SSE streams send nothing extra, the httpOnly cookie is ambient. Page reload restores via a whoami probe over the cookie with ONE silent `POST /auth/refresh` fallback; a 401 on any data request gets the same single-flight refresh + one replay (concurrent 401s share one rotation — a parallel second rotation would trip 03's reuse detection and kill the family) before the interceptor tears down to the login screen. Logout POSTs `/auth/logout` and drops the in-memory token. Header-credential paths (X-Context-Key / raw-key Bearer for MCP and scripts) stay byte-identical and are never CSRF-gated.

**F4 (Go-only)** closes the mint window that 094's `NOT NULL` opened: both production mint paths — `insertApiKeyTx` (the single INSERT path behind `CreateApiKey`/`MintOwnerKey`/self-service/provision) and `BootstrapAdminKey` — mint a **fresh principal per key** in the same atomic statement (data-modifying CTE), the exact 1-key-1-principal semantics of the 094 backfill. A failed key INSERT rolls the principal back with it (no rights-less orphan); the bootstrap guard CTE gates both inserts, so a populated table yields zero principals AND zero keys with unchanged single-statement TOCTOU semantics. Linking a new key to an EXISTING principal (a person's second key) is a later, explicit flow (Achse 05 key selector / Achse 04 SSO onboarding) — never an implicit default.

## Guard (deduplication)

Async deduplication via PG LISTEN/NOTIFY + HNSW similarity. Policy-parameterised since migration 074 (WF T7): `ctx_guard_check` takes the thresholds + the candidate-type **allowlist** as mandatory parameters (NULL candidates ⇒ 0 matches; a legacy 1-arg call ⇒ loud 42883, no silent default fallback), plus a `p_same_scope_only` switch for same-scope dedup with `hnsw.iterative_scan='relaxed_order'` against filtered-ANN false-cleans. The batch picks only `guard.check=true` types (per-type thresholds via `guard.threshold_duplicate`/`_review`, seed defaults 0.98/0.92 = former literals), and the pending pick/count queries ride partial indexes instead of full scans — since migration 182 the pick reads `idx_guard_pending_type` (`type_name`, then `created_at` as UTC wall time, with every pick condition a predicate can hold): one range per checked type, locked in a savepoint, the oldest over all types kept and locked again by row version, so the pick reads the blocks it takes and not the unchecked blocks the pick filters out (issue #360).

Two further per-type dimensions are resolved in Go and passed to every call **explicitly** — never relying on the SQL default (a forgotten parameter would silently re-open cross-scope matching): `guard.candidates` (`all` | `same-scope`) drives `p_same_scope_only`, and `guard.mode` (`archive` | `flag`) drives the persist branch. In `flag` mode a near-duplicate is recorded as a `possible_duplicate` flag (`guard_status` + `guard_matched_id`) and is **never** auto-archived — the issue axis (design/02 §4.7) surfaces duplicates instead of silently removing them, while the knowledge line keeps the `archive` + cross-scope bestand byte-for-byte. `hnsw.iterative_scan='relaxed_order'` is load-bearing only when the planner chooses the HNSW index; whether it does is not a property of the scope's size alone (see the next paragraph), so a small circle is checked exactly by the batch itself.

**Search window and exact check (issue #381).** At pgvector's default `hnsw.ef_search` of 40 the greedy graph search can end in a local minimum: for a block in a sparsely populated region it never reaches the neighbourhood, and the check answers `clean` with a real but distant block where an exact search finds the near-duplicate (measured on a production copy, index graphs grown in write order: 38 of 6 000 checks of a fresh near-duplicate, 0.63 %; 1.1–3.7 % per scope at 1.1 M derived rows). No `iterative_scan` mode helps — the search is not starved by the filter, it searches the wrong region. Two measures, both in the guard batch (`internal/guard/checkpath.go`), no migration:

- **Its own search window, on the index.** After the pick and before the first check the batch runs `set_config('hnsw.ef_search', guard.ef_search, true)` together with `set_config('jit', 'off', true)`: transaction-local, so every `ctx_guard_check` of the batch searches with it (the function sets nothing but `iterative_scan`), a `ROLLBACK TO SAVEPOINT` of a failed block keeps it, and the connection goes back to the pool with the session's values. The pick plans before the setting exists; no other statement of the batch orders by distance. Default 800 (V66: 40, pgvector's default, to 1000, its maximum). Each call of `ctx_guard_check` runs with `enable_seqscan`, `enable_bitmapscan` and `enable_sort` off for that one statement (the switches `recall_check`'s ANN leg uses), so its nearest-neighbour query takes the HNSW index and the function's cached plans are built that way: pgvector prices `ef_search` into the index cost, and at 800 the planner otherwise sorted every candidate of the table by distance up to about 55 000 vectors — the tenant disjunction leaves no scope index to narrow it — measured as 41 s for a batch of 100 at 20 000 vectors (2.1–2.6 s with the plan pinned) and 6.3 s on 11 000 blocks (1.0 s pinned). On the production copy ef 800 left 0 of 6 000 checks wrong at ≈ 3 100 HNSW buffers and ≈ 3 ms per check; at 224 000 and 1.12 M rows a check of a large circle reads ≈ 4 300–6 400 HNSW buffers in ≈ 5–10 ms. JIT is off because every check ends in one row and a large store's estimates pass `jit_above_cost` (1.12 M rows: 16 ms of compilation in an 18 ms exact check), as migration 180 found for the counter triggers.
- **An exact check for a small candidate circle.** Once per batch the guard reads, from the block counters (`context_block_counts` plus pending deltas — no count over `context_blocks`; ≈ 3–5 ms for 100 blocks), how many live blocks each picked block's candidate circle holds: its own scope for a same-scope type, every scope of its tenant otherwise. A block whose circle holds at most `guard.exact_max_candidates` blocks (default 400; at 0 the counters are not read and every block goes through the index) is checked by a statement of its own that computes `ctx_guard_check` exactly — the same candidate predicates (the scope disjunction as the array of the circle's scopes), the same similarity expression, thresholds compared with the same types, the same answer for a block without a vector or without candidates, the whole title of the match — with a distance ordering (`… + 0`) no index can serve, so it reads no HNSW block under any plan, the generic plan a prepared statement switches to included, and finds every duplicate (22 418 calls on a production copy with redistributed scopes and tenants answered like the function computed exactly — measured before migration 188, on a copy without zero-norm vectors and without titles over 197 characters, where the two cases below do not arise). A vector of zero norm in `halfvec(1024)` has no cosine distance (NaN, which passes every threshold): on both routes a nearest candidate at NaN counts as no candidate, and the check answers `clean`, similarity 0, no match — the exact check from the start, `ctx_guard_check` since migration 188, which also returns a match's title whole, where its `VARCHAR(255)` variable failed the check with `22001` on a title over 255 characters ([operations — Migration 188](operations.md#migration-188-zero-norm-vectors-and-long-titles-in-ctx_guard_check)). The embed quality gate keeps zero-norm vectors out of the write path. Without the exact check a small scope rode the HNSW index too: for every type but `issue` the tenant disjunction leaves no scope index usable, and for `issue` the function's plan cache switches to the generic HNSW plan after five calls. The exact check reads the circle's candidates (≈ 0.042 ms and ≈ 4.7 buffers each); the index check of a small circle walks foreign rows until it finds its own, the more the larger the store (50 candidates next to 1.12 M rows: 79 ms, 26 700 HNSW and 11 000 heap buffers; exact: 2.8 ms). Both cost the same at ≈ 230 candidates in a store of 224 000 rows and at ≈ 400 at 1.12 M rows; the default is the target line's. The limit is a declared resource limit like `cluster.centroid_ann_threshold`, hot and global-only; 0 sends every check through the index. A counter drift below the real circle (writes the triggers cannot see, until the reconcile corrects them) makes an exact check read the real circle.

**Concurrent guard runs (issue #359).** Several ctx instances on one database run their guard batches independently. Each batch picks its blocks `FOR NO KEY UPDATE SKIP LOCKED`, so no two runs check the same block, and no run waits for another: the audit row's foreign key on the matched neighbour takes a key-share lock, which a picked block's lock does not conflict with (under the former `FOR UPDATE` pick two runs that each held the other's neighbour waited for each other until PostgreSQL aborted one with `40P01`). Archive verdicts that share a block are mutually exclusive: before archiving block A against B the run takes, without waiting, a transaction-level advisory lock on A (exclusive) and on B (shared), the lower id first, and then re-reads that B still stands. When another run holds a conflicting lock (it is deciding an archive that involves A or B right now) or B has been archived since A's check, A gets no verdict in this run and stays pending; the next run checks it against what that decision left. Several blocks archived against the same standing block take only its shared lock and go through side by side. No two guard verdicts therefore archive two blocks against each other, nor three in a cycle (A against B, B against C, C against A — C meets A as its neighbour once B is gone), and every block still gets exactly one verdict and one `context_write_log` row; a client that archives the neighbour itself is outside this rule, as it is when it archives after the guard. `needs_review` and `flag`-mode verdicts archive nothing and take no lock.

**Review pipeline (guard W1–W4).** Flags are no longer pull-only. The grey zone (`needs_review`/`near_duplicate`/`possible_duplicate`) flows through a closed loop: **push** — `/api/status` carries a `guard_review` section on both auth paths (global vs. home-scope-filtered) and the daily report closes with a queue-stand section while flags are open (live reports only); **triage** — the SPA `/guard` page renders the pair view (flagged block vs. matched partner, similarity) with keep/archive and batch selection; **resolve** — `guard-resolve` accepts `data.ids[]` (one transaction, cap 500, every id accounted for as resolved or skipped+reason; the batch touches only flagged states — deliberately narrower than the single-id path, blast-radius line); **agents** — the MCP tools `guard_list`/`guard_resolve` are the third transport (REST parity; `archive` refused for `confirm_writes` keys, fail-closed). Flagged blocks keep ranking in retrieval until resolved — `ctx_rrf` reads no `guard_status`; changing that is a deliberate future eval-gated decision, not a side effect of this pipeline.

## Block-type registry (migration 072)

`context_block_types` is the declarative per-type behaviour registry of the workflow-engine line. The four M035 block-type classes (`knowledge`, `audit-trail`, `reference`, `system-meta`) ship as builtin seed rows (migration 072) whose JSONB configs reproduce today's hardcoded behaviour (retrieval damping, guard participation, dream linkability, digest/overview inclusion, classify rules); Welle I-C adds two more builtin rows (migration 084), the `issue`/`comment` workflow types, and migration 107 adds the `checkpoint` evidence type (see below). Migration 136 adds the two tool-evidence axes `tool-evidence` (damping 0.15, classify priority 19) and `tool-overview` (damping 0.35, priority 18) — like `checkpoint` they stay out of guard, dream, digest and overview, but unlike it they are `damped` rather than `excluded`, because they are answered by a QUESTION ("which command was that again?") instead of by an exact block ID; both priorities sit deliberately **below** `audit-trail`'s 20, since `Set.Classify` takes the first match ascending and the block title carries the root session name. Both also carry `retrieval.untrusted` (set by **migration 138**, a separate forward-only `jsonb_set` rather than an edit to the landed 136) — the presentation-side flag that marks a type as **foreign text** (tool output an attacker can shape, not knowledge somebody wrote): `Set.IsUntrusted` resolves it per source and the synthesis prompt then renders that source as `trust="untrusted"` and adds one framing sentence (see [Backend pool](#backend-pool-f3-migrations-053055)). Absent = `false`, so every other type is unaffected; on an `excluded` type the flag is inert but valid. **Migration 141** puts `checkpoint` in the same class, and being excluded is precisely why: transcript prose reproduces tool output, fetched web content and foreign agent prompts, so it is foreign text in exactly the sense the flag names — it simply never needed the framing while the type reached no prompt. It is set now because a **derived** type that distils checkpoints has to read the property AT ITS SOURCE, under a fail-closed rule (untrusted unless every source class is provably first-party); with `checkpoint` unflagged that rule would answer "first-party" and the derived layer would launder foreign text into knowledge. The migration touches `{retrieval,untrusted}` only — the policy stays `excluded`, so no ranking, no visibility and no rendered answer changes today. **Migration 143** adds the two **derived knowledge layers** in one step: `insight` (classify priority 17, `retrieval.untrusted=true`) for blocks distilled from a root session's transcript material, and `catalog` (priority 16, `untrusted=false`) for blocks distilled from the corpus blocks of one cluster topic. Both are blocks written *about* other blocks, so both stay out of every autonomous pipeline permanently — `guard.check=false` **and** `guard.candidate=false` (a derivative must archive neither its source nor itself), `dream.linkable=false` (dream links are the only input the topic clustering reads, so a linkable derivative would shape the partition it is derived from), `digest.include=false` and `overview.include=false`. Both ship `retrieval=excluded` **as a start position, not as a verdict**: the damping factor is meant to be measured, not guessed, so the types stay invisible until the pilot runs, after which the swept factor arrives as a registry data update without a deploy — which also means `p_types_visible` is byte-identical after 143 and `ctx_rrf` sees no change. Their `intent_patterns` are seeded anyway (inert while excluded) so that later switch is a one-field change over an already measured list. Note that the registry row alone does not make a type *safe*: `type` is a client field on both write surfaces and is validated only for registry membership, so the write lock that reserves derived types and their categories for internal writers is a separate, immediately following change — 143 stays undeployed until it lands. **Migration 146** is the first registry value set by a **paired** measurement against a declared noise floor: `audit-trail`'s damping factor moves from the Welle-41 value 0.3 to 0.6, scored on 1 000 paired gold cases (+0.036 nDCG@10 on the KI slice, 95-% CI excluding 0 at 11.2× the minimum detectable effect; across all five slices 22 cases gain their Hit@5 and none loses it). 0.3 was not unmeasured — Welle 40 benched it (M036/M037/M038) — but that was the uniform damping regime, unpaired and without a noise floor, and the combination of 0.3 *with* the query-aware intent lift was never scored afterwards. Like 138 and 141 the change is a forward-only `jsonb_set` on one path, not an edit to the landed seed — but its guard is a **value** guard (`damping_factor = 0.3` plus `policy = 'damped'`) rather than an existence guard, because the field is present: every row still carrying 0.3 is lifted, every other value stays, so a re-run touches nothing and a tuned instance keeps its factor. The guard compares a value, not a provenance — a row an operator deliberately set to 0.3 is indistinguishable from the seed and is lifted with it, and an `updated_by IS NULL` clause would make that worse rather than better, since the stamp is per row, not per field. Factors are meant to be tuned without a deploy, and this migration is the deploy-side counterpart of that rule, not an exception to it. The daemon starts on a compiled-in builtin set, overlays the DB rows at boot (merge — a deleted builtin row can never blank the default type) and hot-reloads on any table write via the same NOTIFY channel the settings use; edits via `psql` take effect without a restart.

A boot that finds the table but cannot load it (corrupt row) degrades **loudly**: `/health` carries `blocktype_registry: "builtin-fallback"`, the overall status drops to `degraded`, and a 30s retry loop self-heals once the row is fixed.

**Checkpoint evidence type (migration 107).** `checkpoint` structurally anchors ID-referenced evidence chains — compaction-checkpoint manifests plus their transcript source parts, written by external agent plugins before a lossy context compaction. Resolution runs **exclusively over exact block IDs** (the manifest carries `source_block_ids` and a `parent_manifest_id` chain), so the type is out of **every** autonomous pipeline: `retrieval=excluded` (token-dense transcript parts would flood retrieval candidate sets — hex-heavy prefixes tokenize at ~2 bytes/token and overflow reranker slot windows), `guard.check=false` **and** `guard.candidate=false`, dream/digest/overview all off. The guard exemption is the load-bearing part: consecutive checkpoints of one session are near-duplicates **by construction** (manifest = boilerplate + IDs, parts overlap in the transcript window), and the default knowledge lane (archive mode, 0.98) auto-archived manifests/parts — with every read path filtering `NOT is_archived`, active summaries were left pointing at dangling IDs while the data sat intact (2026-07-20 incident). Blocks classify via the two stable writer title prefixes (`compaction source` for transcript parts, M107; `compaction checkpoint` for the ID-anchoring head manifests, M120 — heads used to fall through to the default type and re-entered exactly the pipelines this type closes), priority 30; writers SHOULD still assert `type=checkpoint` explicitly on store (`type_source='manual'`). Migration 107 also repairs the existing corpus: retype plus un-archive of the guard-archived evidence rows (newest per `(category,title,scope)`, guarded against the partial unique index; guard metadata stays for auditability — re-archive is impossible on both axes, `guard_checked_at` stays set and the type left the guard allowlist). That repair only ever reached the rows M107's own title rule matched — **migration 121 repairs the head corpus** the same way, in the same order (retype first, un-archive second), with a third guard on top: only rows the retype actually turned into `checkpoint` are un-archived, so a head an operator typed by hand (`type_source='manual'`) stays `knowledge`, stays guard-checked and stays archived instead of being handed straight back to the archive lane. Unlike M107 the repaired rows land on `guard_status='active'`, not `needs_review` — their guard freedom is structural by then, so there is nothing left for a human to decide; `metadata.guard_repair='M121'` carries the audit trail instead.

**Transcript parts are stored once per identical write (hermes `ctx_checkpoint` 0.15.0, GottZ/ctx#344).** Measured on the reference instance, 44 % of all checkpoint characters were exact copies of a part the store already held (34 % across conversations, 10 % repeats of one transcript), because every part named its root, session, transcript digest and position. Since 0.15.0 a part's title is the first 32 hex characters (128 bits) of the SHA-256 of its whole write (`Compaction source part <32 hex>`: category, content after redaction, metadata, sensitivity, tags, type) and the part names no conversation. Reuse therefore needs the identical complete write, not only the same text: the same text after redaction from the same profile (tags), platform, agent context, host contract, writer redaction passes and sensitivity, in the same scope and category, meets the stored block through the existing identical-content check (`store.IdenticalContentMatch`) — the answer is "No change needed" with the stored id, no write is booked, and the new manifest lists that id; the same text with any of those values different gets another title and another block. No server logic is involved; scope (one tenant per scope, `context_tenant_scopes` primary key) and category are part of the upsert identity, so a part is never shared across a scope or tenant boundary. The consequence for every reader is that one part can be listed by several manifests, of one root or of several. The conversation, the active session, the transcript digest, the part's position and the role and ordinal a headerless part is read with are the manifest's: the distiller reads a part once per manifest and carries the attribution from the last message header before it in that manifest's order, and its ledger drops a repeated chunk within a root (`distill_seen` is keyed per source key, which carries the root), so a repeat is not delivered again and the attribution of the occurrence the ledger recorded first stands. **Archiving or deleting a part reaches every manifest that lists it**, and an in-place edit of a part's content (`manage update`) is undone by the next write of the same payload, which meets the part under its title with other content and restores the payload the title names; so any retention over checkpoint blocks must keep a part while a manifest that stays lists it — `metadata @> jsonb_build_object('source_block_ids', jsonb_build_array(<id>))` finds those manifests through `idx_context_metadata`. Parts written before 0.15.0 keep their old titles and headers; nothing rewrites them in bulk. A retry of the checkpoint a head names rewrites that manifest in place, as since plugin 0.10.0: after a 0.14.0 checkpoint, a 0.15.0 retry of the same transcript lists new-format parts in it, every one stored before the manifest is written, and the parts it listed before stay stored.

Since T10 the registry is **API-exposed** (no schema change) via the `type-*` manage family: `type-list`/`type-get` are open reads (scoped to `_global` ∪ the caller's own tenant namespace), `type-create`/`type-update`/`type-delete` are server-admin (tier 1: only the shipped `_global` namespace is writable). Configs are validated by the SAME decoder the reload path uses (422 with the offending key path); builtin rows are undeletable (their config IS editable), a delete is refused while ANY block references the type, and every mutation runs in one attributed transaction (`via='api'` + acting key) followed by a synchronous reload. Since T9 (migration 075) the legacy `is_meta` column + index dropped — the third type axis consolidated into the registry (`metadata.is_meta` survives as a JSONB classify-input key only).

**Tenant overlays (Stufe 2, WF T12 — no migration; the schema carries `UNIQUE(name, scope)` since M072).** On top of the `_global` base generation the registry keeps a lazy per-tenant cache — the exact `config.Store` overlay mechanism (immutable snapshot behind an atomic pointer, a monotone `baseGen` stamp per cached generation, single-flighted MISS builds, O(1) cache wipe on a base reload). `SnapshotForTenant(scope)` / `SnapshotForRequest(ctx)` resolve `_global ∪ tenant`, where a **tenant row WINS** on a name collision (**D6: "Overlay gewinnt" v1** — no monotonic narrowing; the alternative that would forbid a tenant lifting a `_global`-excluded type is a named open decision, pinned by a semantic-fixier test so a later flip is a visible break). A tenant with no own rows inherits the base pointer byte-for-byte, so the single-tenant / default-tenant server is functionally identical (zero per-tenant generation footprint). The request path derives the tenant scope from the auth context (never a caller argument, §5.4); a tenant-scope registry write drops **only** that tenant's cached generation via the NOTIFY dispatch (`InvalidateTenant`), while a `_global` write bumps `baseGen` and wipes the whole tenant cache. **Consumer reach:** request handlers (RRF/graph) resolve per caller tenant; the background **dream** and **digest** loops resolve per iterated tenant — the dream `PickBlock` is bound to the iterating tenant's scopes (`scope = ANY(owned)`) so tenant A's `dream.linkable`/allowlist never governs tenant B's blocks. The type policy is a **ranking/visibility** steering, **not** a confidentiality boundary (that stays scope + grants + sensitivity): a grantee's overlay steers the ranking of granted FOREIGN blocks too (Reader-Overlay wins). **Known Stufe-2 boundaries (documented, no leak):** the guard batch and the overview rebuild stay single global runs on the base allowlist (guard-state counts are global telemetry; overview visibility overrides need a per-tenant overview) — reads on both remain scope-filtered.

## Type & lifecycle axes

- **Lifecycle state machine** (`lifecycle_state`, migration 070) — every block carries an explicit, code-owned pipeline state: `knowledge` (default) → `canonical` (dream promotion at quality ≥ 0.8) → `snapshot` (superseded — entered at a weighted supersedes confidence ≥ 0.7; with exit hysteresis it stays a snapshot while ANY supersedes link from a non-archived source of its scope remains, whatever that link's confidence, `superseded_by` moving to another superseder when its own link goes; reverts to `knowledge` when the last one is dropped); `chunk` (ingest) and `synthesis` (daily report) are set by their pipelines. A `chunk` row belongs to the ingest and never leaves `chunk` (issue #191, migration 169 repairs older rows): the chunk-mode ingest finds its `(source_id, chunk_index)` slot only through a `chunk` row, so a `supersedes` link onto a chunk is written but marks nothing — the query path reads the link (`SupersedesMap` → `filterSuperseded`, `superseded_by` in the response), not the lifecycle — and a daily report whose title a chunk already holds leaves that row `chunk` (the report's text lands in that row, as before, until the next changed ingest of the slot replaces it). NOT NULL, mechanism-only — dream, ingest and the daily report are the sole writers; the one user-facing path is a writer-declared supersedes on store (issue #197), which runs the same reconcile. Archiving a block or moving it to another scope reconciles the targets of its supersedes links in the same transaction (`lockSupersedesSource` before the write, then `ReconcileSupersedesTargets`), so a target whose last live superseder leaves returns to `knowledge` at once rather than at the next daily link sweep. Since migration 103 `synthesis` blocks are dream-eligible (the lifecycle conjunct excluded them before — 66 reports sat edge-less in the ego graph); `snapshot` stays excluded, superseded content grows no new edges.
- **Policy-type axis** (`type_name` + `type_source`, migration 071 — renamed from `block_role`) — WHAT a block is: `knowledge` / `audit-trail` / `reference` / `system-meta` (+ future workflow types). The M035 CHECK enum fell with migration 073 — the registry is the type-name authority now (fail-closed lives in the READ path). `type_source` (`auto`|`manual`) records whether the auto-classifier set the type; `manual` overrides auto permanently. The classifier is policy-driven since T4 (rules live as data in `context_block_types`, `internal/rrf/pattern.go` is a pure match engine over passed patterns); it runs on store, MCP store, confirmed staged writes, block-mode ingest, digest (topic map and its stub), root map, dream daily report AND the update afterwork (REST manage update, MCP update, confirmed updates). It runs after the write committed, so its type is written only while the block still holds the title and the metadata its rules read (`source` and the classify flags): under the same type rules, the afterwork of an earlier write never overwrites the type of a later one, and a write of tags, content or other metadata keys in between leaves the verdict standing (issue #426).

## Backend pool (F3, migrations 053–055)

`context_backends` replaces the hardwired primary+fallback pair with a declarative, role-routed, priority-ordered pool. Each row is one backend: `base_url`, wire `protocol` (`openai`/`ollama`/`anthropic`/`rerank` — `anthropic` is the native Messages API wire, chat-class roles only, see [api — Anthropic](api.md#backend-pool)), `provider_class` (`generic`/`llamacpp`/`openrouter`/`ctx` — `ctx` is a peer ctx instance under its model key, Migration 166, see [api — peer ctx instance](api.md#backend-pool)), a **trust level**, an egress `locality`, a `roles` list (`synthesis`, `translate`, `embed`, `rerank`, `dream`, `digest`, `chat`, `classify`, free-form), a per-role `model_map`, per-role `timeouts`, `priority` and `enabled`. Order/priority are pure DATA — no code path references backend names or priority constants.

`context_disable_profiles` + `context_disable_profile_backends` (092) add named **disable profiles** — a profile takes its member backends out of every chain while active (maintenance / eject use-case). Membership is a real FK join (no name matching, rename/delete-safe by CASCADE), profiles carry a `scope` (`_global` for operator profiles) with `UNIQUE(scope, name)`, and the migration backfills the legacy gaming toggle as the reserved profile `eject` (label „Eject-Modus“) — value and member set copied losslessly from `gaming.active`/`gaming.disabled_backends`. The pool loads profiles + memberships into the same atomic snapshot as the backends (ORDER BY name — the status frame's diffKey needs a byte-stable order). The chain-time exclusion arm is live: an active profile takes its members out of every chain (`disabled by profile <names>`, effective state `profile-disabled`, precedence disabled > profile-disabled > cooldown > active). Since U01-W5 the eject profile is the **sole** chain-time exclusion mechanism — the legacy `gaming.active`/`gaming.disabled_backends` settings keys and the parallel gaming arm were retired (the `gaming-mode`→`eject` alias shim stays as a compat surface, and the status payload's `gaming.active` field is derived live from the eject profile).

The table is the **only** source of truth. Nothing seeds it at boot: until an operator fills it — `ctx init`, `ctx backends seed`, or the web UI — it stays empty, and an empty pool is the ordinary, announced state of a fresh install (boot advisory `backend_pool: empty`, `/health` `unhealthy`) rather than a silent fallback to some default topology. The env bridge that filled it on a first boot until v4.38 is gone with the tuple keys it read (v5.0.0, see [operations](operations.md#environment-variables)). Multi-tenant scope isolation of the pool is documented in [multi-tenancy](multi-tenancy.md#backend-pool-isolation-egress); the trust × sensitivity gating and the OpenRouter ZDR guarantees in [security](security.md). CRUD is in [api](api.md#backend-pool).

**Synthesis on the pool chain** (054) — query-path synthesis walks the role chain from `context_backends` (priority-ordered, cooldown-sorted; the chain is the ONLY way to a backend, so the trust gate sits structurally before prompt transmission). Transport-class failures advance to the next backend (e.g. the `llama-cpu` sidecar at priority 10: same GGUF, CPU speed, its own per-role timeout); HTTP-500 and attempt timeouts stop the chain — the server *ran* the request, slow-but-alive is not down. The OpenAI-compatible gateway passes through on the same pool chain with one walker for every gateway path (`llm.WalkChain`: a lease per attempt, the first acquire the request's only wait and every failover acquire non-blocking, no failover once a data frame went to the client, and a context-window rule for `bad_request` — a 404 or a refused redirect moves on, any other 4xx on a row of known `num_ctx` only to a row with a larger or unknown one); its two wire calls (`llm.ChatRaw`/`ChatRawStream`) pick the egress client internally by the one `EgressGuarded()` predicate and have no header parameter, so no inbound header reaches a backend — the body comes from `llm.BuildUpstreamBody`, where row sampling only fills defaults, row `model_map` params and `extra_body` win over the client (the thinking switch included), the OpenRouter ZDR force has the last word on `provider`, and `model`, `stream`, `max_tokens` (the minimum of the caller's ceiling and the row caps — `extra_body` cannot lift it) and the absence of `n` are ctx's. The response heartbeat starts whenever synthesis is on (`synthesize != false`), so a CPU-leg answer survives buffering proxies even with rerank off. Since 055 the WHOLE query path resolves through the chain (translate, temporal, query-embed, rerank dispatch, inline backfill) with a real requirement: `max(query sensitivity, sensitivity of the FINAL prompt set)` — measured after rank filtering, so a credentials block on rank 180 that never enters the prompt cannot lock the failover. **Untrusted source framing** (W02-4) — a source whose block type carries `retrieval.untrusted` renders as `<source … trust="untrusted">`, and the system prompt gains exactly one sentence, spliced into the same `<security>` element as the promptguard nonce rule, defining such sources as **observation data**: quotable, never followed as an instruction, and never a fact about anything beyond that output. It is a truth-value rule, which is what the two pre-existing rules do not cover — they forbid FOLLOWING foreign text, not BELIEVING it. The sentence is added only when at least one untrusted source is actually in the prompt (a prompt without one is byte-identical to the pre-W02-4 rendering, which is what leaves the eval baseline untouched on a corpus with no foreign-text block), the budget pass charges it before the source set is fitted, and the type name never reaches the model — only the trust class does. An empty dream chain (gaming/disabled/trust) skips the cycle BEFORE the block pick — no claim, no cooldown touch, so a gaming session never smears the back-off statistics.

**Rerank sidecar.** Post-RRF rerank (`rerank.enabled`, ships off, fail-open) via a local **bge-reranker-v2-m3** cross-encoder sidecar (`http://ctx-rerank:8082`, cohere-style `/v1/rerank`, all-local/$0) — a pool row of role `rerank` like any other backend — or LLM-as-judge on the chat model when the pool serves no such row. Voyage AI rerankers (`rerank-2.5`/`-lite`) work as a remote alternative: the client accepts their OpenAPI dialect — results under `data` instead of `results`, `usage.total_tokens` instead of `prompt_tokens` (the same total_tokens dialect is accepted by the OpenAI-protocol embed client) — and maps Voyage's calibrated [0,1] relevance through logit() at the wire boundary, so the raw-logit score contract (and the downstream sigmoid+blend) is backend-invariant. Container name and score domain are coupled backend properties — by default: the backend row's `metadata.score_domain` slot (`auto` | `logit` | `probability`, default `auto` = the container coupling) overrides the interpretation for dialect-mixing backends (a gateway speaking `results` but scoring probabilities, or vice versa). A probability-domain score outside [0,1] or an entry missing `relevance_score` errors → fail-open to the pre-rerank order. The surface-gold counter-probe showed the cross-encoder earns its keep (nDCG@10 +0.164, MRR +0.169) while blend 0.5 keeps it neutral on latent gold — `graph+ce-bw0.5` is the best arm on both gold sets; the ~80–90s query path stays proxy-safe via the body heartbeat.

**Embed wire.** Both embed wires (`/api/embed`, `/v1/embeddings` in `internal/embed`) take a list of texts and accept exactly one vector per input: the OpenAI wire re-aligns its answer by `data[].index` (every index in `[0, n)` once), `/api/embed` answers in input order and is checked by count. The internal path still sends its one text as a bare string — the body every deployed backend has seen, byte for byte — and keeps its 1024-d, prefixed, normalized space and its float64 normalization; `embed.EmbedRaw`, the gateway's path, sends the texts as a list without prefix and returns the raw vectors at their native length, decoded straight into float32. Both share the two wire sites and the egress client choice.

## Model aliases (migration 162)

The OpenAI-compatible model API never exposes a backend: the `model` a client names is an **alias**, a row of `context_model_aliases` — name, kind (`chat` / `embedding` / `rerank`), a **pool role**, a sensitivity floor, a policy of request caps, `enabled`, and a scope (`_global` or a tenant scope). An alias points at a role, not at backend rows, so a request on it walks `Pool.Chain(role, sensitivity, tenant)` like any internal call: trust, disable profiles, cooldown and tenant visibility apply without a second copy. Id, name, kind and scope are immutable (an identity trigger, `psql` included), so a model id keeps its meaning; releases to consumers bind the alias id, and renaming is delete + create. `internal/modelalias` holds the rows as one atomic snapshot (`Registry`, monotone `Generation()`), reloaded at boot, on every `ctx_settings_write` NOTIFY of the table and on every listener backlog — the listener only triggers it (`Registry.Trigger`: single flight with a pending bit, so a burst of N writes costs at most two table reads and never holds the listener loop that serves every other channel); a failed reload keeps the previous snapshot. `Offers(snapshot, tenantScope)` is the one rule of what a consumer may see — aliases visible to its scope (`_global` only for an empty scope), a tenant alias in place of the `_global` one of the same name (decided by presence: a disabled or broken tenant alias hides the name instead of handing it back to the operator's alias), and of those the enabled ones whose policy parses; `Lookup` resolves one name by the same rule. The policy is a flat object of dotted keys (`tools.max_count`, `embedding.sub_batch`, …) and its parse is fail-closed: an unknown key, a key of another kind, a wrong type or a value over its code ceiling makes the alias invisible, named by a `WARN` per reload. Nothing writes the table yet; the admin actions and the `/v1` endpoints build on it.

## Federation hop headers

When one ctx instance (B) carries another (A) as a backend, every model call between them carries a small header contract, defined in `internal/fedhop` — a leaf on the standard library alone, so the wire packages (`llm`, `embed`, `rerank`), `backends`, `httpx` and `handler` can all import it. The package holds the instance identity (migration 163, see [security](security.md#instance-identity)), the header grammar, the hop token, the monotony rules and the stamp of outgoing calls. Every model wire site stamps its calls and reads the answers with it ([outgoing side](#the-outgoing-side) below); every authenticated route group with model egress refuses loops and over-long chains at its entrance ([incoming side](#the-incoming-side) below); the federation context for ctx rows, the ingress policy of `/v1` and the learned peer state arrive with their own waves, so this section describes the contract they build on.

**Principle: restrictive headers hold for every caller, widening ones for nobody.** A hop header is unauthenticated metadata. Each one can only narrow a request — refuse it, raise its sensitivity, keep it local, lower its class, shorten its wait — and every right (class ceiling, sensitivity floor, model release, egress breadth) comes from data on the authenticated consumer or the backend row, never from a header. A forger can therefore only get its own request refused or narrowed, which is why the loop protection needs no signature over the chain. A missing inbound header means the sender's own value (its lease class, the sensitivity its chain was admitted under); the restrictive default applies only when that own value is missing.

| Header | Sent to | Grammar | Folds over hops | Unreadable value |
|---|---|---|---|---|
| `Ctx-Hop` | every target except `openrouter` | hop tokens, comma-separated with optional SP/HTAB; several header lines are one list; at most 16 | append a fresh token | **400** `federation_header_invalid`; a repeated entry is **508** |
| `Ctx-Path` | ctx rows | lower-case UUIDs, as above; at most 16 and never more entries than `Ctx-Hop` | append the own instance id | **400**; a repeated entry is **508** |
| `Ctx-Sensitivity` | ctx rows | `credentials` \| `personal` \| `internal` \| `public` | rank maximum (only raises) | `credentials` |
| `Ctx-Egress` | ctx rows | `local` \| `any` | sticky `local` | `local` |
| `Ctx-Class` | ctx rows | `interactive` \| `external` \| `background` \| `external_bulk` | the lower class (urgent above bulk, nothing finer) | `background` |
| `Ctx-Max-Wait-Ms` | ctx rows | decimal 0 … 120000, no sign, no leading zero | minimum, minus the time already waited | ignored: the receiver keeps its own budget |
| `Ctx-Pipeline` | ctx rows | `[a-z0-9][a-z0-9:_-]{0,63}` | replaced | dropped |
| `Ctx-Embed-Space-Require` | ctx rows, embed calls | 16 lower-case hex digits | replaced | **400** (an unreadable space condition is no "no condition") |
| `X-Request-ID` | ctx rows | `[0-9A-Fa-f-]{1,64}`, what the receiver's request-id middleware accepts | the sender's server-side id | not sent |

Values are matched exactly: lower case is the grammar, an upper-case spelling is an unknown value. A one-value header sent on several lines is unreadable. A federation header under a non-canonical key of a hand-built header map is refused (400) rather than skipped. Every value taken as its fail-closed default or dropped counts `federation_header_ignored`, which is where a peer of another version shows up. The response side carries `Ctx-Instance` (to peer consumers only), `Ctx-Reason` (`busy`, `draining`, `loop`, `depth`, `hop_required`, `peer_mismatch`, `embed_space`), `Ctx-Loop-Token` (on a 508 only) and `Ctx-Embed-Space` (embeddings only).

**The hop token** is `hex(nonce ‖ HMAC-SHA256(instance_secret, nonce)[:8])` with an 8-byte nonce from `crypto/rand`: 32 lower-case hex characters, minted fresh for every call. Only the minting instance recognises it again — it recomputes the MAC of the nonce and compares in constant time (`hmac.Equal`) — two calls of one instance carry tokens nobody else can link, and a token twice in one chain is two identical strings. A foreign nonce matching a 64-bit MAC by chance has probability 2⁻⁶⁴ per entry. A third party learns the length of the chain, nothing else. An instance recognises a loop when its own token is in `Ctx-Hop`, its own instance id is in `Ctx-Path`, or the chain repeats an entry; a 508 that echoes an own token in `Ctx-Loop-Token` marks the row as leading back to this instance, whatever kind of consumer this instance is on the other side.

**The stamp** of an outgoing call runs between the row's `extra_headers` and the core headers (`Content-Type`, `Authorization`): it first removes every `Ctx-…` and `X-Ctx-…` header of the row in any case, so a row edited by `psql` can neither set nor forge a marker; a target of tier None (`openrouter`) gets nothing more. Otherwise it appends a fresh own token to the inbound chain; a ctx row also gets the path plus the own id and the folded context of the table. Without an instance identity the stamp sends no marker at all and logs an `ERROR` (`federation_stamp_without_identity`): ctxd refuses to boot without an identity, so in ctxd this is unreachable, and a tool that links the wire packages without loading the identity shows it on every call. The zero value of a target's tier is the loop tier, so a site that forgets its tier still marks its calls. A Tier-F call's wire timeout is the attempt timeout plus the wait budget it sends plus 500 ms, because the peer's queue time must not eat the generation time.

**Why not RFC 8586 `CDN-Loop`.** Intermediaries in front of a ctx (reverse proxies, CDNs) append their own `CDN-Loop` entries, so a strict parser would refuse legitimate traffic and a tolerant one would lose the fail-closed property. ctx takes the semantics of RFC 8586 — append, refuse your own mark — in a header of its own, without an `X-` prefix (RFC 6648).

### The outgoing side

Every model wire site — the ten of the wire census: Ollama and OpenAI chat (`llm/client.go`), the OpenAI stream (`llm/stream.go`), the Messages API and its stream (`llm/anthropic.go`, `llm/anthropic_stream.go`), Ollama and OpenAI embeddings (`embed/embed.go`), rerank (`rerank/rerank.go`) and the gateway's `llm.ChatRaw`/`ChatRawStream` (`llm/passthrough.go`) — derives its target from the backend row alone (`backends.(*Backend).HopTarget`, never from request data), stamps the request between the row's `extra_headers` and the core headers (`setChatHeaders`, `setAnthropicWireHeaders`; the embed and rerank wires send no row headers, so there the stamp comes first), and hands the answer headers to `fedhop.Observe` before it looks at the status, on every tier. The tier hangs on the provider class, like the OpenRouter ZDR force:

| `provider_class` | Tier | Sent |
|---|---|---|
| `openrouter` | None | no hop header at all — the row's `Ctx-…`/`X-Ctx-…` headers are removed, the inbound chain is not forwarded |
| `generic`, `llamacpp`, any other or empty class, on every protocol (`openai`, `ollama`, `anthropic`, `rerank`) | Loop | `Ctx-Hop`: the inbound chain plus one fresh own token |
| `ctx` (rows since Migration 166; until the federation tier lands they are sent Loop like `generic`) | Federation | `Ctx-Hop` plus the federation context of the table above |

`provider_class` is a declaration nobody verifies, so a ctx instance registered as `generic` or `llamacpp` — for its `/health` probe, or behind llama-swap or LiteLLM — still sees the loop marker. A third party gets one opaque token per call that nobody else can link to another, and learns the length of the chain; no instance id, no stable value. **Live effect** from the release that carries this: every row except `openrouter` receives a `Ctx-Hop` token on every call — on the reference install today the seven rows `herbert-chat`, `herbert-rerank`, `llama-cpu`, `llama-embed`, `lonius-embed`, `spark-chat` and `spark-embed`. A backend ignores a request header it does not know (HTTP semantics), so none of them needs any configuration. The backend-test reachability probe and the OpenRouter endpoint discovery (`orwindow.go`) stay unstamped until their own waves — both still send a `psql`-written row's headers as they are, the discovery even after its own `Authorization`, so a row header overrides the key there.

`Observe` reports a valid `Ctx-Instance` in any answer to the backend pool: the row carries the status hint `answers_as_ctx_instance` (`hints` of the row in the backends section of `/api/status`, one `WARN` on the row's first such answer, the instance id in the log only) — a ctx instance registered under another class, whose calls carry the loop marker only. A `508` that echoes an own token in `Ctx-Loop-Token` reaches the pool as well; excluding such a row from the chains is a later wave's. The pool is installed as the observer at boot, right after it is built.

Two censuses keep every site stamped. `stampPin`, next to `wirePin` in `internal/chat/dispatch_invariant_test.go`, carries the same keys and counts as the wire census and counts the stamp and `Observe` calls per wire file in the source; the capture test (`internal/chat/wire_hop_capture_test.go`) needs a driver for every `wirePin` file, fires each site against a capturing server and checks the headers on the wire. A new wire file without a stamp entry or a driver is red, and so is a site that sends no token, lets a row's federation header through, or drops the answer unread.

**Tools without an identity.** Only `ctxd` loads the instance identity. The other binaries (`ctx`, `ctx-armcost`, `ctx-armsweep`, `ctx-distillreset`, `ctx-goldbench`, `ctx-llmlog-export`) link the wire packages through shared dependencies but reach no wire site of the census — the call graph of each of their `main`s has `fedhop.Stamp` unreachable (`deadcode -whylive`) — so they load none. The bench tools that call a model directly (`ctx-goldbench`, `ctx-goldset`) use their own HTTP clients and send no hop header: they originate requests, they never forward one, so the loop guard loses nothing. A tool that gains a direct model call stamps without identity: no marker, and an `ERROR` plus the counter `federation_stamp_without_identity` per call, visible rather than silent.

**Admission toward a peer.** The dispatcher (`internal/dispatch`) treats a ctx row as a local target, whatever its locality. Its `Enforcing()` coverage term exempts rows of an external locality — a cloud target scales on its own, so leaving it uncapped must not keep the legacy yield fallbacks on forever — but the projection of the pool onto the dispatcher's rows (`events.DispatchBackendRows`) never marks a `ctx` row exempt (wave F-W7). The reason is on the other side of the hop: the peer serves the calls of one row under one consumer — the one the row's key belongs to — with one concurrency limit, and only this instance knows which of them are interactive. Without a `slots` cap on the row, its background calls pass through and fill that limit, and its interactive calls meet the peer's `429` instead of its own queue order (interactive before background, the demand herald); with `slots` the order holds up to the peer's door. A ctx row with a background role and no `slots` therefore keeps `Enforcing()` off with a `WARN` naming the origin ([operations](operations.md)); the backend write refuses such a row (`422`), so only a row written past it (psql) gets there. The duty binds a ctx row whose `limits` count for its origin under the K2 authority rule: a tenant ctx row on an origin a `_global` row carries, or one of several tenants' rows on an origin without one, counts as exempt like a cloud row (`coverageRows`, wave F-W5) — its `slots` are ignored anyway, and a tenant row must not switch the instance-wide mode. The row's second predicate, self-admitting (class `ctx` or an external locality), is a different question — how the target offers the external class of this instance's own `/v1` consumers ([operations — external offer](operations.md#external-offer-per-target)) — so a ctx row is self-admitting and coverage-bound at once.

### The incoming side

`handler.LoopGuard` (wave F-W8) sits directly behind the authentication of every route group with model egress and before the body cap, in this order (masterplan K14):

| Group | Stack |
|---|---|
| `/mcp` | `Auth` → `LoopGuard` (house envelope) → strict body cap → MCP handler |
| `/api` (main group, ingest, blob store) | `Auth` → `LoopGuard` (house envelope) → body cap → handler (admin gates inside) |
| `/v1`, `/v2` (`mountModelGroup`, mounted with the gateway routes) | `EnabledGate` → `ModelAuth` → `LoopGuard` (OpenAI envelope) → `PeerIngress` → body cap / in-flight budget → handler |
| camo fetch `GET /api/img/{sig}`, webhook `POST /webhooks/github/{project_id}` | no guard: no authentication, no model egress |

The guard parses `Ctx-Hop`/`Ctx-Path` (`400` unreadable, `508` repeated), refuses the own token or the own instance id (`508 federation_loop`, the own token echoed in `Ctx-Loop-Token`) and a chain of `federation.max_depth` entries or more (`508 federation_depth`), and otherwise puts the chain — `Ctx-Hop` and `Ctx-Path` only — into the request context, where the stamps of the pipelines behind it ([outgoing side](#the-outgoing-side)) continue it. On `/api` and `/mcp` no stage reads a foreign request's class, sensitivity or wait budget. On `/v1` and `/v2` the ingress policy `federation.PeerIngress` (wave F-W9) follows the guard and replaces the reduced chain by the cleaned full inbound state (`fedhop.InboundFrom`): an app's `Ctx-Class`/`Ctx-Pipeline` and a pathless peer's are dropped; a peer with `Ctx-Path` is bound to its last entry on first contact and compared with that binding afterwards (wave F-W12, [peer binding](security.md#peer-binding)) — only a peer that proved its binding keeps class and pipeline (`federation.PeerHint`, `fedhop.PeerInstanceFrom`), and only it gets `Ctx-Instance` (or a pathless peer while `federation.require_peer_hop` is off); next to it goes the request's policy (`federation.PolicyFrom`: required sensitivity = consumer floor raised by `Ctx-Sensitivity`, egress local; without a PeerIngress the fail-closed default credentials + local). The chain build of a route handler then runs `Pool.Chain` → `federation.FilterChain` (rows learned on the path out; `local` ⇒ own engines only; transit ⇒ at most one instance hop) → export filter → `llm.WalkChain`, with `federation.ScanRaise` over the parsed body first ([security](security.md#federation-ingress-policy-peeringress)). Guard and PeerIngress are fixed in `mountModelGroup`, and mounting a group registers the router's federation ingress (`fedhop.Ingress`, one per router, both marks); `gateway.enabled` cannot be on without that registration — the settings write answers `409`, the boot refuses. `internal/federation` imports neither handler nor store (depguard `federation-layering`); its in-process mesh tests (`internal/federation/fedtest`) assemble the real stack per instance.

## Supporting mechanisms

- **Digest freshness state (retired, migration 129)** — `context_digest_state` plus `trg_digest_dirty`/`mark_digest_dirty()` from the initial schema are gone. The table was verified dead (no Go consumer; the scheduler keeps its dirty flag in memory), but the trigger still fired on **every** block write and updated a SINGLETON row — one shared row lock per writer, i.e. a pure serialisation point at target scale with nothing on the other side of it. Two historical timestamps were dropped with it, deliberately and by explicit decision. Drop order is load-bearing (trigger → function → table): the function resolves its table by name at execution time, so a table dropped first would break not the migration but every subsequent write.
- **Supersedes filtering** — temporal-gated removal of outdated blocks from query results.
- **Transport retry** — all inference HTTP calls (chat ollama/openai/anthropic, embed, rerank) retry exactly once on transient transport failures (connection reset / EOF before any response bytes) via `internal/httpx`. Covers the keep-alive race with llama.cpp's cpp-httplib servers (~5s idle close vs Go connection reuse); HTTP status errors and context deadlines are never retried. Inference POSTs are stateless, so a replay is safe.
- **Streaming tool-call wire** (`llm.ChatStream`) — streaming OpenAI-compatible chat with function calling: multi-turn message arrays, per-delta events, index-keyed tool-call assembly, arguments normalisation (llama.cpp JSON-string fragments and whole-object form yield identical calls), hardened against OpenRouter SSE comment frames and mid-stream error events inside HTTP-200 streams; usage falls back to llama.cpp `timings` incl. MTP draft-acceptance. Drives the web-chat harness (see [api](api.md#web-chat-sessions)). Since issue #26 the **non-streaming** chat path carries the provider stop reason too (`ChatResponse.FinishReason`, decoded from Ollama `done_reason` resp. OpenAI `choices[0].finish_reason`, raw and unnormalised, `""` when the provider reports none) — until then only the SSE path saw it, which left every background pipeline unable to tell a `length` truncation from malformed output.
- **Decide primitive** (`llm.DecideChoice`, `llm.DecideOptions`) — a classification read off the FIRST generated token's top-logprobs instead of decoded text (System-One style). The caller phrases its question so the answer is one short label token (`A`…`E`, `Yes`/`No`); the OpenAI wire is asked for `logprobs`/`top_logprobs` (`Options.TopLogprobs`, JSON-tagged off so the Ollama options block never carries it), and `ChatResponse.TopLogprobs` hands the alternatives back as a distribution over the labels — renormalised probabilities, the raw label **mass** (share of belief that landed in the requested vocabulary at all) and a TypeSafe-style **confidence** `(n·peak−1)/(n−1)`. Rationale: on the serving hardware one output token costs ~100× an input token (decode 18–30 tok/s vs prefill ≈2.5k tok/s) and a decision needs none; there is also no JSON to truncate or drift. A backend that reports no logprobs (Ollama, some relays) or an answer outside the label set (`ErrNoLogprobs` / `ErrNoLabelMass`, `IsDecideFallback`) is a fallback signal, never a fabricated distribution. Measured 2026-09-20 against the goldbench gold sets: rerank nDCG@15 0.841 vs 0.648 for the generating judge (equal on the judge's parsed cases, no parse failures), dream links 0.605 vs 0.599, recurrence 0.885 = 0.885, at 0 output tokens.
- **Embed cache** — content-hash-keyed embedding cache (`context_embed_cache`) to avoid re-embedding identical text across pipelines.
- **LLM log** — per-call request/response capture (`context_llm_log`) with input/output token counts (Ollama + OpenAI), dream-pipeline version tagging, and parse-format drift tagging (`metadata.parse_format`). The dream-eval rows additionally carry `metadata.links_parsed` (how many links the answer actually yielded — a legitimate zero-link "nothing relates" verdict is otherwise uncountable), `metadata.links_dropped_invalid` (how many of those parsed links the candidate filter rejected — non-UUID target, id outside the candidate set, unknown relationship type, out-of-range or below-floor confidence; written only when it dropped something. Paired with `links_parsed` it names a failure that is otherwise silent: a row reading *parsed n, dropped n* is a cycle in which the model did answer and nothing survived, yet it is booked **inert** onto the multi-day back-off exactly like an honest "nothing relates" verdict. Observability only — no cooldown or retry behaviour changes), `metadata.candidates_capped` (how many retrieved candidates the aggregate candidate cap — `MaxCandidatesPerKeyword * MaxKeywords`, the item count the prompt-budget gate models for this pipeline — dropped before the evaluation saw them; written only when the cap actually bound, and mirrored on the `dream: candidates found` log line as `candidate_cap_hit`/`candidates_capped`. Not pure cost: a dropped candidate is one the eval never judges, and a cycle left without links is booked *inert* onto the back-off curve, so a cap that fires has to be countable rather than inferable) and `metadata.cap_hit`, set when a parse failure coincides with `completion_tokens >= num_predict`: the non-streaming wire formats decode no `finish_reason`/`done_reason`, so an answer truncated at the output cap is otherwise indistinguishable from malformed output — both book the parse error and the transient cooldown, and a backend that deterministically overruns the cap silently re-burns one eval call per cooldown. Since issue #26 the flag is no longer heuristic-only and no longer observability-only. `metadata.finish_reason` carries the provider's raw stop reason whenever one arrives (on successful rows too — "which backends report one at all" is only answerable from the rows where nothing went wrong), and `metadata.cap_hit_source` says which signal produced the verdict: `finish_reason` when the provider stated `length`, `tokens` when it reported no stop reason and the completion count reached the cap. A cap hit now triggers **one bounded retry** at `dream.eval_cap_retry_factor` times the *resolved* cap — resolved meaning after a `model_map` `num_predict`/`max_tokens` override, because the scaling is applied where that override is (`llm.applyModelParams`); the retry sends the identical prompt and writes its own llmlog row, marked `metadata.cap_retry`, so token and cost accounting stays one row per wire call. A **second** cap hit is booked as a completed-but-inert eval (`dream_eval_count` + 1, `dream_last_inert`, `dream.backoff_inert_offset` on the curve) instead of the 5-minute transient cooldown: the transient path has no attempt counter, so a prompt that cannot fit would otherwise re-burn one eval call every five minutes forever.
